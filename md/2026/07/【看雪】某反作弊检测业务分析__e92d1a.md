## 1\. 总体结论

该体系不是单一 Hook，而是一套由入口采样、原生检测、后台环境取证和虚拟机策略共同组成的运行时完整性系统。它围绕输入真实性、游戏对象与控制链、调试与篡改、设备与包环境四类风险收集证据，并在策略层完成关联与结果聚合。

整体链路可归纳为五层：

1.  **UE 业务入口层** ：在输入、移动、控制、视角、对象访问、弹道等敏感调用点获得现场。
2.  **轻量原生检测层** ：执行指针范围校验、输入行为统计、设备身份检查、状态快照、函数表归属和反调试自检。
3.  **后台环境检测层** ：独立于 UE Hook，由内部调度器扫描目录、设备节点、进程映射、系统属性、基础库和应用包状态。
4.  **比较型策略引擎** ：负责入口路由、快照组合、条件表达式、模块与环境规则。
5.  **寄存器型策略引擎** ：由两个高敏感入口经全现场 trampoline 进入，执行共享的模块、设备、系统与 Hook 自完整性策略。

多数入口侧检测器的业务语义是“记录异常和快照，然后返回原流程”。在当前证据范围内，未发现它们直接修改游戏对象、丢弃输入事件或在本地检测函数内实施最终处置。是否上报、如何评分、是否处罚以及服务端如何消费结果，均不在本次分析覆盖范围内。

## 2\. 范围、版本变化与证据口径

### 2.1 覆盖范围

本轮材料覆盖数百个 UE 入口映射、多个匿名原生业务段、两个全现场 trampoline、一个比较型策略引擎和一个寄存器型策略引擎。已闭合的业务包括：

| 层级  | 已确认业务 |
| --- | --- |
| 输入与交互 | MotionEvent 行为连续性、InputDevice 静态身份、移动输入现场 |
| 控制与对象 | 视角/控制对象指针守卫、玩家状态采样、UObject 与加载器函数表、结构一致性 |
| 反调试与篡改 | ARM64 硬件断点/观察点、SIGTRAP 协同链、入口时延探针 |
| 后台环境 | 私有目录、设备节点、maps、系统属性、服务、libm、PackageManager |
| 策略引擎 | 入口路由、模块完整性、跨状态快照、综合环境规则、全现场策略分发 |

核心游戏数据处理与变换逻辑仅保留历史业务归类，不分析其内部实现，也不将其列为待闭合项。

### 2.2 本版本变化

本版本相较较早样本呈现以下明确变化：

-   增加了触控行为连续性入口，并把更多与位置、视角、骨骼和碰撞相关的 UE 调用纳入对象指针守卫。
-   比较型策略引擎新增入口路由，并新增核心模块完整性、跨状态快照和综合环境规则。
-   寄存器型策略程序经过整体重编排，不能解释为旧程序尾部追加少量逻辑。
-   环境策略新增或强化了对 `shadowhook-enter` 、 `anon:LMA` 、 `rwxp` 、 `---p` 等进程映射特征的关注。
-   过去容易被邻接 memcpy helper 干扰的断点、时延和函数表业务已重新定位到真实处理器。

### 2.3 证据使用原则

匿名 Hook 页附近常包含复制、缓存或跳转辅助函数。业务识别必须先沿入口的跳转链追踪到实际处理器，再结合数据写入点和运行时结果区命名。仅凭相邻字符串、辅助函数或一次性快照，不足以推断具体业务身份或最终风险结论。

## 4\. 输入、交互与包环境

### 4.1 输入链路分工

输入检测由两条相邻但独立的链路构成：

| 检测链 | 主要输入 | 业务目的 |
| --- | --- | --- |
| InputDevice 身份链 | virtual/external 属性、厂商与产品标识、name、descriptor | 确认输入设备静态身份是否符合内置基准 |
| MotionEvent 行为链 | action、时间、指针数量、history、X/Y、SIZE、TOUCH/TOOL 尺寸 | 确认事件序列和触控几何是否具有连续、自然的特征 |

两者不能相互替代：设备身份异常不必然表示注入，轨迹异常也不必然意味着设备身份被伪造。策略层才负责将两类结果与控制链、环境和模块证据关联。

### 4.2 InputDevice 静态身份

当前样本内置的触控设备基准包含如下字符串和字段：

| 字段  | 当前基准 |
| --- | --- |
| 输入来源 | 触屏来源 |
| 设备标识 | 负值虚拟设备标识 |
| name | `Virtual` |
| virtual/external 标志 | 预期的布尔组合 |
| vendor/product | 默认值组合 |
| descriptor | `a718a782d34bc767f4689c232d64d527998ea7fd` |

任一字段不一致时，函数会保存完整设备快照。该逻辑是静态身份比对，不负责分析手势动作、跨事件轨迹或历史样本。

```
function inspectInputDevice(device, report):
    expected = {
        name: "Virtual",
        descriptor: "a718a782d34bc767f4689c232d64d527998ea7fd",
        source: expectedTouchSource,
        virtualExternal: expectedFlags,
        vendorProduct: expectedIds
    }

    if anyIdentityFieldDiffers(device, expected):
        report.record("input_device_identity_mismatch", snapshot(device))

    return ForwardToOriginalFlow
```

**证据与边界** ：完整设备属性读取和快照写入均在该链路中闭合。两个布尔属性属于 virtual/external 属性族，但现有证据不足以可靠指定二者在底层分发中的绝对顺序。

### 4.3 MotionEvent 行为连续性

该检测器只处理预期触屏来源的 `MotionEvent` 。它读取当前事件的 action、device ID、event/down time、pointer count、pointer ID、tool type 和 history size，并读取以下几何字段：

```
X / Y / SIZE / TOUCH_MAJOR / TOUCH_MINOR / TOOL_MAJOR / TOOL_MINOR
```

当前主体没有看到 `PRESSURE` 与 `ORIENTATION` 的直接建模，也没有逐条遍历历史轴样本；history size 用于判断 action、数量和时间关系是否一致。系统会按字段组合匹配轨迹槽，维护 action 集合、命中次数、坐标极值、移动状态、比例模型和异常标记，而不是直接用 pointer ID 作为数组下标。

| 风险维度 | 已确认的观察方式 |
| --- | --- |
| 工具与尺寸关系 | tool type、TOUCH/TOOL 的长短轴关系和相互大小 |
| 几何有效性 | 关键轴是否出现负值、越界或不自然的比例组合 |
| 时间与动作连续性 | action、event/down time、pointer count、history size 的跨事件关系 |
| 轨迹形态 | X/Y 极值、MOVE 行为、固定值倾向和长期比例模型 |

```php
function inspectTouchEvent(context, event):
    if event.type is not MotionEvent or event.source is not expectedTouchSource:
        return ForwardToOriginalFlow

    context.updateEventSequence(
        event.action,
        event.deviceId,
        event.pointerCount,
        event.downTime,
        event.eventTime,
        event.historySize
    )

    for pointer in event.pointers within processingBudget:
        geometry = readCurrentAxes(pointer,
            X, Y, SIZE, TOUCH_MAJOR, TOUCH_MINOR, TOOL_MAJOR, TOOL_MINOR)
        anomalies = validateToolAndGeometry(geometry)
        track = context.findOrCreateTrack(event.deviceId, geometry)
        if track exists:
            track.mergeAction(event.action)
            track.mergePosition(geometry.X, geometry.Y)
            track.updateRatioModel(geometry)
            track.anomalyFlags |= anomalies

    context.saveLastEvent(event.action, event.eventTime)
    return ForwardToOriginalFlow
```

**业务结论** ：这是跨事件触控行为画像，而非简单的当前事件过滤器。当前证据显示它只记录统计和异常，不修改、过滤或重写原始输入事件。

### 4.4 指针守卫与输入关联

多个与角色位置、视角、骨骼、视线和碰撞相关的 UE 调用共享对象指针守卫。处理器从直接参数或嵌套对象链抽取候选指针，并与预期引擎区域比较；异常时记录实际指针，部分入口会额外保存调用现场。

```php
function observeSensitivePointer(guardContext, callFrame, selector):
    candidate = selector.extractPointer(callFrame)
    if guardContext.engineBase is available and
       candidate is outside expectedEngineRegions:
        guardContext.report.record(
            "unexpected_object_pointer",
            candidate,
            selector.captureOptionalContext(callFrame)
        )

    return ForwardToOriginalFlow
```

该守卫关注的是控制链使用的对象地址是否合理，不针对某一个原函数的返回值做修正。嵌套取值路径依赖上游调用保证对象可读；原始业务未显示为每级嵌套对象补充独立的空指针恢复逻辑。

### 4.5 PackageManager 包状态检测

包环境检测通过 Java 包管理链获取具有 `android.permission.SYSTEM_ALERT_WINDOW` 的候选包，再组合可启动性、UID、安装状态、隐藏状态、系统应用属性、加密感知属性和变更包记录进行分类。

| 输出标签 | 业务含义 |
| --- | --- |
| `[Startable]` | 候选包可按预期启动 |
| `[HideToMe]` | 包在当前用户或可见性路径中表现为隐藏 |
| `[Uninstalled_App]` / `[Not_Installed_For_User]` | 安装或用户可见性不一致 |
| `[Not_System_App]` | 包属性不符合系统应用预期 |
| `[Frozen]` / `[Not_Startable]` | 包不可用或启动失败 |
| `[Not_Encryption_Aware]` | 应用加密感知属性不满足条件 |
| `[ChangedPackage]` | 来自变更包队列的记录 |

错误初始化还会产生 `[INTERNAL_ERROR_01]` 、 `[INTERNAL_ERROR_02]` 与 `[INTERNAL_ERROR_03]` 。两个实现变体属于同一业务族，但 SDK 范围和版本字段不同，不能当作字节级完全相同的副本。

```php
function inspectPackageState(state, packageManager, report):
    if state.finished:
        return report.commitCompletion(state.counts)

    overlayCandidates = packageManager.getAppOpPermissionPackages(
        "android.permission.SYSTEM_ALERT_WINDOW")
    changedPackages = packageManager.getChangedPackages()

    while report.hasCapacity() and hasMore(overlayCandidates, changedPackages):
        item = nextCandidateOrChangedPackage(overlayCandidates, changedPackages)
        result = classifyInstallVisibilityStartabilityAndPermission(item)
        report.append(result)

    releaseLocalReferences()
    report.commitPage()
```

有效应用记录只保留非系统且声明目标权限的条目。包状态结果是环境证据，不宜单独解释为作弊或恶意软件结论。

## 5\. 控制链、玩家快照、函数表与引擎状态

### 5.1 控制链的业务定位

该业务段覆盖控制输入、投影、视角旋转和状态续体等敏感调用。多个入口复用同一对象范围守卫，另有独立处理器执行玩家快照、函数表扫描和结构一致性校验。

| 子能力 | 作用  | 输出  |
| --- | --- | --- |
| 控制链 pointer guard | 检查控制、视角、位置相关对象是否落在预期区域 | 异常对象指针和现场摘要 |
| 玩家状态采样 | 限频采集玩家与输入相关字段 | 低成本状态快照 |
| UObject/加载器函数表 | 检查函数指针是否来自允许模块区域 | 函数表槽位和模块归属 |
| 引擎状态一致性 | 校验对象链、现场目标和关键状态组 | 实际状态值与现场片段 |

### 5.2 限频玩家状态快照

采样入口属于移动输入/玩家状态处理族。它先经过计数门控，触发时清空上一轮结果槽，然后沿全局根对象、状态节点和玩家对象的链路采集少量整数、浮点和连续状态字段。

```php
function sampleEngineState(sampleContext, frame):
    if not sampleContext.rateGate.shouldSample():
        return ForwardToOriginalFlow

    sampleContext.clearPreviousResultSlots()
    root = resolveEngineRoot(sampleContext)
    state = followExpectedObjectChain(root)
    player = resolvePlayerState(state)

    if root, state, and player are valid:
        sampleContext.report.write(selectLowCostFields(root, state, player))

    return ForwardToOriginalFlow
```

**业务含义** ：该采样用于建立低开销完整性快照，不是逐帧输入回放，也不替代原有移动逻辑。当前入口可稳定闭合到移动输入处理族，但正式方法名缺少完整符号证据。

### 5.3 UObject 与加载器函数表扫描

扫描器先检查对象存储的数量和容量关系是否合理，再遍历活动对象的虚函数表以及全局加载器函数表。若函数指针不在预期代码区域，处理器会先确认目标页已映射，随后解析其模块归属并记录结果。

```kotlin
function inspectFunctionTables(scanContext):
    objects = getObjectStoreIfStructurallyPlausible(scanContext)
    if objects is unavailable:
        return

    for object in objects within scanBudget:
        if object is empty or excluded:
            continue
        table = object.virtualFunctionTable
        if table is outside expectedTableRegion:
            inspectTable(scanContext, table, object.identity)

    inspectTable(scanContext, getGlobalLoaderTable(), "GPackageLoader")

function inspectTable(scanContext, table, owner):
    for entry in table until termination or scanBudget:
        if entry is inside expectedCodeRegions:
            continue
        if pageFor(entry) is accessible:
            scanContext.report.record(
                "unexpected_function_owner",
                owner,
                entry.index,
                resolveModuleFor(entry.address)
            )
```

**证据与边界** ：扫描器检查的是“函数指针来自哪里”，并不直接回答该函数是否存在作弊语义。页面可访问性检查位于模块归属解析之前，可避免把无效地址误判为外部模块。

### 5.4 关键结构状态一致性

另一条链从全局对象链获取状态节点，只在该节点与当前 HookFrame 的现场目标一致时，才读取并比对一组关键状态字段。出现不一致时，会同时记录实际状态和现场摘要。

```php
function checkEngineStateConsistency(stateContext, frame):
    node = followExpectedObjectChain(resolveEngineRoot(stateContext))
    if node is unavailable:
        return ForwardToOriginalFlow

    if node does not match frame.currentTarget:
        stateContext.report.record("unexpected_state_pointer", node)
        return ForwardToOriginalFlow

    observed = readExpectedStateTuple(node)
    if observed differs from expectedStateTuple:
        stateContext.report.record("engine_state_mismatch", observed)
        stateContext.report.record("call_frame_summary", frame.summary)

    return ForwardToOriginalFlow
```

函数表扫描回答“函数指针来自哪里”，状态检查回答“关键对象链是否保持内部一致”。二者共同覆盖函数表替换、对象代理、异常上下文和部分内存篡改风险。

## 6\. 断点、信号与执行环境完整性

### 6.1 硬件断点与观察点自检

反调试处理器会枚举当前线程和若干关键工作线程，读取 ARM64 的硬件执行断点与观察点状态，检查槽位数量、非空状态、地址、控制状态和容量异常。它还使用短时自有探针验证资源是否能够正确注册、回读和恢复，并按线程写入阶段状态与异常计数。

```cpp
function assessHardwareDebugIntegrity(context):
    threads = collectCurrentAndCriticalThreads(context)
    for thread in threads:
        snapshot = readHardwareDebugResources(thread)
        result = evaluateSlotCountAddressAndControl(snapshot)
        selfCheck = readShortLivedSelfCheckResult(thread)
        context.report.merge(thread, result, selfCheck)

    return context.report
```

运行时快照显示，受控线程集合、执行探针、观察点和结果区的数量关系能够相互印证。这证明当前采样时刻的硬件调试资源状态符合检测器预期，但不能外推为整个进程生命周期内始终不变。

### 6.2 SIGTRAP 协同链

该模块不是简单判断 SIGTRAP handler 是否等于自身。它会保存已有 handler，安装自有的 `SA_SIGINFO` 处理器，并将未知 SIGTRAP 转交给旧链路；对于自有执行探针和观察点访问，则更新命中状态并跳过已触发的指令。

```php
function verifyTrapSignalChain(trapContext):
    if not trapContext.frequencyGate.shouldRun():
        return

    if currentThread is not tracked:
        return

    ensureOwnHandlerPreservesPreviousHandler(trapContext)
    trapContext.clearCurrentProbeFlags()
    runNextExecutionProbe(trapContext)
    accessNextWatchProbe(trapContext)

    if probeFlagsAreMissing(trapContext):
        trapContext.report.record("trap_probe_failure")

    trapContext.rotateProbeIndexes()
```

**真实业务** ：硬件调试自检与 SIGTRAP 处理器形成链式协同，而非互相覆盖。该机制通过低频门控和轮转探针降低高频入口的额外开销，并保留未知信号的原有处理语义。

### 6.3 入口时延探针

时延检测会对少量候选安全入口和基准路径做受控短路后计时，滤除离群样本并输出比较结果。它用于发现额外跳板、代理层或 inline hook 可能带来的执行特征差异。

时延结果只能作为辅助证据。设备性能、调度、负载和编译差异均可能导致波动，必须与函数表、模块归属、内存映射和入口完整性结果联合解释。当前反编译证据确认入口指令会恢复；页面权限是否在所有路径上对称恢复，尚未完全闭合。

## 7\. 后台环境检测与调度

该段不依赖 UE 直接 Hook，由内部初始化和调度逻辑分批运行。它的共同特点是先生成记录，再分页提交，并使用完成态或缓存避免每个周期重复全量扫描。

### 7.1 业务清单

| 子任务 | 关键字符串或目标 | 业务目的 |
| --- | --- | --- |
| 私有目录解析 | `/data/data/com.proxima.dfm` 、 `/proc/self/fd/%d` | 发现容器、虚拟化、路径替换或目录重定向 |
| 设备节点/sysfs | `/sys/dev/char/*` 、 `/dev/<leaf>` | 收集异常设备节点、驱动暴露和命名形态 |
| maps/stack | `/proc/self/maps` 、 `[stack]` 、 `MAGISKTMP` 、 `app_process` | 识别特定栈尾和映射布局特征 |
| 系统属性与服务 | `ro.crypto.state` 、 `encrypted` 、 `init.svc.*` | 补充设备加密和异常服务线索 |
| libm 完整性 | `sin` 、 `cos` 、 `tan` 、 `atan` 、 `fabs` 等 | 识别基础数学库替换、符号重定向或浮点环境异常 |
| 包状态 | `android.permission.SYSTEM_ALERT_WINDOW` 、变更包记录 | 建立候选包的安装、权限和可启动性状态 |

### 7.2 私有目录重定向

处理器打开应用私有目录，通过 `/proc/self/fd/%d` 和 `readlinkat` 获得实际规范路径，然后把解析状态与路径提交给上层。它不在本地直接做 expected/actual 字符串比较；是否异常由上层策略决定。

```php
function inspectPrivateDirectory(report):
    fd = open("/data/data/com.proxima.dfm")
    if fd is unavailable:
        return report.record("private_dir_resolution", "open_failed")

    resolved = readlinkat("/proc/self/fd/" + fd)
    report.record("private_dir_resolution", resolved)
    close(fd)
```

因此，该能力的业务本质是“获取实际规范路径”，而不是“本地直接宣判路径一定异常”。

### 7.3 设备节点与 sysfs 扫描

扫描器分组遍历 selected `/sys/dev/char/*` 条目，并将解析出的 parent、leaf、major/minor 与若干命名形态标志写入命中表。每轮记录数量有限，未完成记录会在后续 tick 中按页输出。

相关命名特征包括：小写 parent/leaf 组合、包含单个 `!` 的短名称，以及类似 `xx_........._xxx` 的固定形态。某个 access 标志仅代表原始探测结果非零，不能反推为设备节点一定存在或一定恶意。

```css
function runDeviceNodeJob(jobState, report):
    if jobState.hasPendingRecords():
        return report.submitNextPage(jobState.takeNextPage())

    if not jobState.scheduler.isDue():
        return jobState.scheduler.advance()

    findings = []
    for item in selectedSystemDeviceEntries():
        target = resolveSymlink(item)
        if target matches expectedVirtualDeviceLayout:
            findings.append(classifyParentLeafAndAccess(target))

    jobState.loadPagedFindings(findings)
    report.submitNextPage(jobState.takeNextPage())
    jobState.scheduler.advance()
```

### 7.4 maps、MAGISKTMP 与栈尾分类

该逻辑打开 `/proc/self/maps` ，读取最后一条映射记录，要求其名称为 `[stack]` ，然后只读取栈映射末端的一小段数据。它检查 `MAGISKTMP` 、全零内容以及 `app_process` 形态，并输出打开状态、字符串命中和分类结果。

这不是对所有 maps 路径逐行搜索 `MAGISKTMP` 的实现。该修正非常重要：它限定了证据的实际覆盖面，不能将其夸大为“全进程映射的广泛特征扫描”。

```css
function inspectStackTailFromMaps(report):
    lastMapping = readLastMapping("/proc/self/maps")
    if lastMapping.name is not "[stack]":
        return report.record("stack_layout", "unexpected_last_mapping")

    bytes = readTail(lastMapping)
    category = classify(bytes,
        contains = "MAGISKTMP",
        zeroCase = allZero,
        expectedProcessMarker = "app_process")
    report.record("stack_layout", category)
```

### 7.5 系统属性、服务与 libm 完整性

系统属性检查以 `ro.crypto.state=encrypted` 为基准，并枚举 `init.svc.*` 。服务过滤器会排除大量常见词和包含复杂分隔符的名称，只把剩余短名称/状态放入候选表。进入候选表不等于仅凭服务名完成 Root 或作弊定性。

libm 检测会动态解析 `sin/sinf` 、 `asin/asinf` 、 `cos/cosf` 、 `acos/acosf` 、 `tan/tanf` 、 `atan/atanf` 、 `atan2f` 、 `fabs/fabsf` ，对固定三角函数向量进行容差比较，并按 API 组输出错误位。异常可能来自 inline hook、PLT/GOT 或符号替换，也可能来自浮点环境差异。

```php
function verifyBaseMathLibrary(report):
    api = resolveMathFunctions(
        "sin", "sinf", "asin", "asinf", "cos", "cosf",
        "acos", "acosf", "tan", "tanf", "atan", "atanf",
        "atan2f", "fabs", "fabsf")
    failures = runExpectedNumericVectors(api)
    report.record("libm_integrity", failures)
```

### 7.6 调度语义

后台任务不是一次性完成。设备节点任务在稳定状态下按周期推进，扫描结果较多时会先持续分页，输出完成后才进入下一阶段；maps 和包状态等重任务有各自的完成标记或缓存路径，不能把某一个任务的周期套用到所有任务上。

```php
function runBackgroundEnvironmentJob(jobState, report):
    if jobState.hasPendingRecords():
        report.submitNextPage(jobState.takeNextPage())
        return

    if not jobState.scheduler.isDue():
        jobState.scheduler.advance()
        return

    findings = collectDueEnvironmentFindings()
    jobState.loadPagedFindings(findings)
    report.submitNextPage(jobState.takeNextPage())
    jobState.scheduler.advance()
```

“未看到新结果”可能表示任务尚未到期、正处于分页输出，或已进入缓存完成态，不能直接解释为功能未运行或环境正常。

## 8\. 两个全现场 trampoline

两个全现场 trampoline 分别位于弹道命中和移动输入两个高敏感业务入口。它们完整保存通用寄存器、向量寄存器和状态标志，将栈现场交给共享 dispatcher，随后恢复现场并继续原始 UE 调用。

```
function dispatchHighSensitivityEntry(dispatchContext, originalCall):
    savedContext = saveFullCallContext(originalCall)
    try:
        dispatchContext.strategyRunner.run(
            dispatchContext.entry,
            dispatchContext.descriptor,
            dispatchContext.reports
        )
    finally:
        restoreFullCallContext(savedContext)

    return ContinueOriginalCall
```

trampoline 本身不直接包含反自瞄、反瞬移、Root、设备指纹、maps 或 Hook 完整性规则；它只承担“无损转发”的职责。真正的规则位于 dispatcher 后端和共享寄存器型策略程序中。

## 9\. 比较型策略引擎

### 9.1 路由与动态规则的区别

比较型策略引擎包含两种不同的对象：

| 对象  | 实际职责 | 不应误解为 |
| --- | --- | --- |
| 静态路由项 | 将敏感 UE 入口匹配到检测组 | 一条独立、可执行的检测规则 |
| 动态规则程序 | 基于快照、条件与环境执行组合判断 | 每个入口各自独占一套程序 |

新增入口的静态路由项本身没有可执行内容；实际业务位于三类动态程序：核心引擎完整性、跨状态快照和综合环境规则。

### 9.2 核心引擎完整性与跨状态快照

核心完整性规则关注 `libUE4.so` 的模块状态、关键相对位置和原生 pointer guard 的允许区域是否一致。跨状态规则不携带明确业务字符串，主要负责把多个状态源采样到共同结果槽，供后续表达式使用。

这意味着跨状态快照不能仅凭某个状态句柄就强行归到 MotionEvent 或某一个 UE Hook；当前最稳妥的命名是“多来源快照初始化与组合”。

### 9.3 综合环境规则与特征字符串

综合环境规则组合基础库入口、目录与文件、Android/JNI 上下文、设备、包和网络能力。已确认的相关字符串包括：

| 类别  | 字符串或目标 |
| --- | --- |
| 基础库入口 | `malloc` 、 `syscall` 、 `free` |
| 应用/临时目录 | `/data/data/com.tencent.tmgp.dfm/` 、 `/data/data/com.tencent.tmgp.dfm/files` 、 `ano_tmp` |
| 配置/落地文件 | `dfm_auth.json` 、 `/data/system/data_hook_address.txt` 、 `/data/local/tmp/Mac_File` |
| 系统/模块路径 | `/sys/module/example` |
| Android 上下文 | `Build$VERSION.SDK_INT` 、 `AndroidThunkJava_PushSensorEvents` |
| 设备与网络 | `MediaDrm` 、 `getPropertyByteArray` 、 `WifiInfo.getMacAddress` 、 `NetworkCapabilities.isValidTransport` |
| 包环境 | `ApplicationPackageManager.getInstalledPackages` |

这些字符串说明规则会搜索或调用相应目标，不代表当前进程必然已经命中所有目标。

## 10\. 寄存器型策略引擎

### 10.1 共享程序与独立上下文

弹道命中和移动输入两个入口分别拥有独立 descriptor、strategy、VM context 和当前执行位置，但指向同一份逻辑字节码和常量池。应理解为“同一套策略程序在不同高敏感业务入口下运行”，而不是两份互不相关的虚拟机实现。

### 10.2 规则覆盖与字符串证据

| 规则类别 | 已确认的字符串或目标 |
| --- | --- |
| Hook 自完整性 | 弹道/输入入口附近 patch 的移除或篡改特征 |
| 模块完整性 | `libUE4.so` 、 `libanogs.so` 、 `libanort.so` |
| 特权环境 | `/data/adb` 、 `/data/adb/ksud` 、 `/data/lost+found/` 、 `getuid` |
| 设备身份 | `MediaDrm` 、 `deviceUniqueId` 、 `UUID` |
| Android 上下文 | `ActivityThread` 、 `Application` 、 `JNI Context` |
| 渠道与应用信息 | `AnoStamp` 、 `INTL_STORE_CHANNEL` 、 `ApplicationInfo/metaData` |
| 存档与配置 | `.Save` 、 `key` 、 `serial` |
| 映射与模块 | `/proc/self/maps` 、 `dl_iterate_phdr` 、 `bsigchain` 、 `HttpDns` 、 `libc++_shared` |
| 渲染与追踪 | `EGL` 、 `hwui` 、 `atrace_get_enabled_tags` |
| 链接与异常段 | `linker` 、 `vdso` 、 `shadowhook-enter` 、 `anon:LMA` 、 `rwxp` 、 `---p` |

这些字符串构成规则的目标集合，不等同于当前运行时一定加载了对应模块、存在对应文件或已判定风险。

### 10.3 策略执行语义

```php
function evaluateRuntimeEvidence(policyContext, entry, reports):
    route = policyContext.findRouteFor(entry)
    if route is absent:
        return policyContext.currentResult

    snapshot = collectRelevantSnapshots(reports, route)
    policyContext.storeSnapshot(route, snapshot)

    for rule in route.executableRules:
        result = rule.evaluate(snapshot, policyContext.environment)
        policyContext.merge(route, result)

    return policyContext.currentResult
```

短时运行时采样未命中解释器只能说明该观察窗口内两个高敏感策略未被触发，不能否定驻留程序、常量池和两个上下文的存在。具体由哪些游戏态触发该解释器，仍需围绕弹道和输入场景做针对性采样。

## 11\. 跨模块业务关系

| 业务风险 | 入口/原生采样 | 比较型策略引擎 | 寄存器型策略引擎 |
| --- | --- | --- | --- |
| 合成输入与自动化操作 | MotionEvent 轨迹、InputDevice 身份、对象指针 | 入口路由、快照与环境条件 | 输入现场和设备环境策略 |
| 控制链或瞄准相关篡改 | 视角/位置对象守卫、状态快照、函数表 | 核心引擎区域与状态规则 | 弹道/输入入口自完整性 |
| 代码、函数表或入口代理 | 函数指针归属、libm、时延 | 基础库与核心模块规则 | 模块、linker、匿名映射与代理特征 |
| 调试与断点 | 硬件槽位、SIGTRAP 链、轮转探针 | 快照条件与基础状态 | 系统与环境策略 |
| 特权、容器与异常环境 | 目录、设备节点、maps、属性和服务 | 文件、设备、包和网络上下文 | 特权路径、设备指纹和运行时布局 |
| 包与安装状态 | PackageManager 分页结果 | 安装包与网络能力条件 | 渠道、ApplicationInfo 与上下文策略 |

整体上，系统采用“多点取证、延迟组合”的模式：前端模块不急于单点定性，而是将局部观察交由后端策略结合场景、时间和环境共同判断。

## 12\. 运行节奏、结果语义与性能策略

### 12.1 运行节奏

-   输入、指针守卫和状态校验随敏感 UE 入口触发，优先保持低开销。
-   玩家快照经过计数限频，不替代逐帧业务逻辑。
-   SIGTRAP 与硬件探针经过低概率门控和轮转，避免持续使用调试资源。
-   后台扫描分阶段、分批、分页执行；不同任务拥有各自的完成态和缓存语义。
-   两个全现场入口只在对应的高敏感游戏场景将完整现场交给后端策略。

### 12.2 结果语义

前端模块主要输出：

-   异常标志、命中计数和阶段状态；
-   输入、设备、对象、函数表和环境快照；
-   模块或函数指针归属；
-   后台任务完成态、分页游标与缓存结果；
-   供比较型或寄存器型策略引擎消费的中间结果槽。

这些输出是检测证据，不等同于最终风险等级、账号处罚或用户提示。当前材料没有建立本地结果与外部网络传输、服务端处置之间的直接因果关系。

| 项目  | 状态  | 当前结论 |
| --- | --- | --- |
| 匿名原生业务段与 trampoline | 已闭合 | 入口、实际处理器、主要输出和业务关系均已确认 |
| 输入设备与触控轨迹 | 已闭合 | 静态身份与跨事件行为是相邻但独立的检测链 |

## 14\. 脱敏与使用说明

为避免样本实例定位、内存布局复刻或探针重建，以下内容仍已移除或改写：
