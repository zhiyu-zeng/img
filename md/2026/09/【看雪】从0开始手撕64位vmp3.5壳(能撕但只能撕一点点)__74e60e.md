> 64位 VMP 3.5 壳虽能“手撕”，但作者只初步实现从加壳入口去混淆并解析出若干 handle，尚不能完整还原全部指令。
> 
> - **工具定位：** 作者开发了开源辅助工具 DisassembleVmp，配合 x64dbg、Unicorn 和 Lua，以自动化方式辅助分析 VMP 虚拟化代码，降低手撕门槛。
> - **加壳与入口定位：** 仅选择“虚拟化”并关闭其他保护；加壳后原函数 call 位置不变，跟进就是虚拟机入口，特征是连续的 push/call/jmp，再往里是虚拟化初始化的保存现场。
> - **去混淆主流程：** 先用 Unicorn 模拟执行记录动态 Trace（寄存器与栈快照），再将 x86 指令译成 Ghidra Sleigh PCode，最后做反向活跃性分析，标记并删除不被后续使用的死代码（混淆指令）。
> - **关键混淆处理细节：** 反向扫描时，STORE/BRANCH/CALL 等副作用指令的输入视为活跃；写寄存器若输出不在 live 集合则标记 dead；CBRANCH 在已确定 Unicorn 执行路径时按无条件跳转处理，不传播 flag 活跃性，从而避免大量 flag 混淆指令被误判。
> - **阶段成果与局限：** 去混淆后可见 9 号、10 号 handle 汇编几乎一致，差异多为未清除的混淆；VMP 为同一语义准备了多个不同 handle 以增加分析难度，因此先除混淆才能更好找规律。当前文章仅到“保存现场”部分，完整还原尚未完成。

### 4.去混淆

虽然加壳的时候我们选择的是仅虚拟化，但实际上还是有混淆的，而且还有很多jmp之类的，分析起来十分麻烦。

如果不去混淆对于初学者来说十分折磨。因此先放下对于虚拟化的好奇心，开始老老实实去混淆。

去混淆大致方案:

汇编转换成为PCode 语义 也就是读取了什么寄存器，写入了什么寄存器

从上往下进行判断，举个最简单的例子 mov rax,0x123； mov rax,0x456。 如果两行汇编之间没有任何读取rax的指令那么 mov rax,0x123就是没用的，就是混淆。

将会遇到的问题：

对于去混淆来说，实际静态就可以，接下来我们讨论下将要遇到的几个问题

1.去混淆要写一些匹配逻辑，逻辑写的规则太严谨会导致去混淆不彻底，写的太松散，导致去混淆可能把真实代码也删掉。这就需要不断地测试，用眼睛看是不是把正常代码当混淆了，这工作量太大了。

2.去混淆应该怎么去除。代码里有各种跳转，是跟着跳转进去去混淆还是按汇编地址逐行去混淆？遇到jz 是跳转还是不跳转? 因此不判断出执行顺序就不会清楚下一行汇编会执行什么，就不容易高效去混淆。

解决方案：

先模拟执行，确定汇编执行流程并且记录下来所有寄存器还有常用的堆栈（比如RSP±0x100，记录太多了实在是存不下）这样去混淆就有正确的路径并且去混淆后再次模拟执行对比寄存器就能知道去混淆是否正确。当然这也有一些问题，我们后面讨论

#### 具体方案：

##### 第一阶段：动态 Trace

核心：Unicorn 模拟执行，按需内存映射。

1.  通过 IPC 从 x64dbg 读取目标进程的寄存器快照和内存页
    
2.  初始化 Unicorn 引擎，写入寄存器和已有内存页
    
3.  注册两个 hook：
    

-   cb_code：每条指令执行前记录地址、寄存器快照（16 个 GPR + RFLAGS）、栈快照（RSP 上下各若干 slot）
    
-   cb_unmapped：遇到未映射页时，通过 IPC 从 x64dbg 实时读取并映射（按需加载）
    

5.  模拟执行直到达到步数上限，产出一条 TraceEntry\[\] 序列
    

##### 第二阶段：PCode 语义翻译（Sleigh）

核心：将 x86 指令翻译为 Ghidra Sleigh PCode 原子操作。

每条 x86 指令被翻译为若干 PCode 操作（RawOp），每个操作有：

-   opc：操作码（COPY, INT_ADD, LOAD, STORE, BRANCH, CBRANCH 等）
    
-   out：输出 varnode（space + offset + size）
    
-   ins\[\]：输入 varnode 列表
    
-   dead：是否被死代码消除标记
    

Varnode 地址空间：

-   register：CPU 寄存器（offset 对应 Ghidra 寄存器编号，如 rax=0x00, rcx=0x08, rsp=0x20）
    
-   const：立即数常量
    
-   unique：Sleigh 临时变量（指令内部中间结果）
    
-   ram：内存地址空间
    

示例：mov r11, \[rsp+0x90\] 翻译为：

```
INT_ADD  unique:tmp = register:rsp + const:0x90
LOAD     unique:tmp2 = [ram: unique:tmp]
COPY     register:r11 = unique:tmp2
```

##### 第三阶段：死代码消除（vmp_dead.cpp）

核心：反向活跃性分析 + RuleVmpEarlyRemoval。

这是去混淆最关键的一步，直接对应 VmpHelper 的 ActionVmpHandlerDeadCode。

##### 反向活跃性分析

这是一种优于正向分析的方式，经过测试比正向好使。

从 handler 段末尾反向扫描，维护一个 live 集合（当前活跃的 varnode）。

初始状态：所有 16 个 GPR 视为 live（handler 出口处必须保证寄存器一致）。EFLAGS 各位不预设。

扫描规则：

-   有副作用的操作（STORE, BRANCH, CBRANCH, CALL, RET）：所有输入加入 live
    
-   写 ram 的操作：所有输入加入 live
    
-   写 register/unique 的操作
    

-   如果输出 ∈ live → 从 live 移除输出，将所有输入加入 live（活跃传播）
    
-   如果输出 ∉ live → 标记为 dead（此操作无人使用，是垃圾指令）
    

CBRANCH 特殊处理：在 Unicorn trace 已确定路径的前提下，CBRANCH 退化为无条件跳转。此时不传播 flag 输入的活跃性，避免大量 flag 计算指令（VMP 混淆的主要手段之一）被误判为活跃。

问题也随之出现了：

当真的出现有效的jz jnz 由于我们忽略的flag 就会导致本次Unicorn 模拟可能走的A分支，去混淆正确，下次B分支就会出问题。这个解决就要靠打磨去混淆细节。

### VMP入口：

```
mov rax,1 可以翻译为
```
