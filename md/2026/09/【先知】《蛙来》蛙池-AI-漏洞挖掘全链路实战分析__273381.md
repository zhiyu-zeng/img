## 前言

今年各家厂商的漏挖智能体扎堆上线：安恒的恒脑、360 的图龙锋、深蓝的 DeepSec、斗象的蛙池 AI，国外还有很多这种自主渗透 Agent。产品形态五花八门，但本质是同一套东西——大模型套一层安全工具链，再配一个任务循环。区别只在这层"壳"（Harness）做得有多深。

仅作形态对照，不做排名——这类工具没有绝对的好坏，只有和你的目标类型、测试习惯的匹配度。而匹配度里最大的变量，是你给 Agent 编排任务的方式。这也是本文要展开的东西。

就很像以前的工具，同一个工具，有人拿来挖洞月入十万，有人却一个都挖不出。漏挖 Agent 也一样。社区里对这类工具的评价两极分化严重，有人一开就挖出高危，有人扔个 URL 进去看着它空转半小时烧积分。差距本身并不在模型，在人——在于你会不会给 Agent 编排任务、划边界、定验收标准。

这篇以蛙池 AI（digpool.cn，斗象科技出品，目前仍处内测阶段）为样本，把一个漏挖 Agent 从指令下达到报告落盘的完整链路拆开讲。案例部分跑了三种场景：80 多道 CTF 题、XBOW 系列靶场、真实业务资产的 SRC 测试，全程留档。

## 蛙池 AI 是什么

蛙池 AI 是斗象科技推出的"原生 AI 白帽工作台"，定位对话式漏洞挖掘：用自然语言描述测试意图，由 Agent 自主拆解任务、规划攻击路径、调用工具执行、循环验证，最终输出结构化漏洞报告。官方披露的数据是国内已有 3000+ 白帽用户、累计反馈漏洞 500+

客户端覆盖 Windows 10+ 与 macOS 11+，主界面左侧导航能看出它的功能分区：

-   • **对话式挖洞**：核心入口，主控智能体"问答蛙"在此接单，全程可见思考链、待办列表和工具调用细节；
-   • **蛙池 CLI**：自然语言驱动的命令行，适合批量发起扫描、查进度、操作报告；
-   • **半自动挖洞**：与漏洞盒子深度联动的模式，可直接接取众测/SRC 任务，支持 VPN 项目；
-   • **报告助手**：内置 5 类标准模板，支持生成漏洞盒子提交格式的报告；
-   • **灵感笔记**：测试过程中的截图+文本速记；
-   • **蛙伴中心**：智能体管理，内置"挖蛙"系列专项 Agent（每周热门漏洞交互检测、移动应用安全测试、越权漏洞测试等），也支持用 Prompt 组装自定义智能体。

模型适配方面，实测客户端内可切换 glm-5.2、deepseek-v4-pro / deepseek-v4-flash、Kimi K3 等国产最新大模型，同时开放 OpenAI Compatible 与 Anthropic Messages 两种接入协议，意味着你可以把任意兼容端点接进来。

## 框架设计原理：Harness 工程，而不是提示词工程

斗象在 D2.5 版本复盘里有句话： **"模型决定下限，Harness 工程决定上限。"** 这句话也是理解蛙池 AI 的钥匙，也是用不好它的人最容易忽视的地方。

所谓 Harness，是模型外面那层工程壳：任务怎么拆、工具怎么喂、中间状态怎么存、错了怎么纠。模型大家都能买到，拉开差距的是这层壳。蛙池 AI 的 Harness 设计，从实测暴露出来的行为反推，大致是这几层：

**战术小队式多智能体分工。** D2.5 不再让一个 Agent 包揽全程，而是拆成分析、规划、执行等角色。对话窗口里你能看到"@问答蛙（主控智能体）"，说明用户面对的是一个调度者，它在背后把任务分发给专项角色。工具侧同样有分工：抓包蛙负责流量、浏览器工具负责交互、问答蛙负责统筹。从实测行为反推的职责分层大致如下：

|     |     |     |
| --- | --- | --- |  
| 层   | 角色  | 实测中观察到的行为 |
| 调度层 | 问答蛙（主控智能体） | 接收意图、拆解待办、汇总结论、署名输出 |
| 规划层 | 分析/规划角色 | 生成待办列表、动态作用域修正、路径切换决策 |
| 执行层 | 浏览器工具 / 抓包蛙 / 命令执行 / 文件读写 | Playwright 交互、数据包重放、批量验证脚本 |
| 交付层 | 报告助手 + Skill（如 vulbox-vulnerability-reporter） | 模板化报告生成、本地落盘 |

**Agentic Loop + 显式任务计划。** 每接到一个任务，Agent 会先把它拆成一张"待办列表"，UI 上实时显示"N 项 · X 运行中 · Y 待处理"，每条任务有 in_progress / pending / completed 状态。这不是装饰——它是 Agent 的工作记忆外化，也是你中途干预的抓手。实测中看到它把"测越权"拆成"验证水平越权（改 URL 参数访问其他用户）→ 验证垂直越权（未登录直接访问 dashboard/orders）→ 验证 username 参数 → 加载 vulbox-vulnerability-reporter 生成报告"这样的序列，拆解质量直接决定产出质量。

**双工具体系。** 内置强交互工具（浏览器控制、文件读写、命令执行、数据包处理）打底，浏览器控制走 Playwright，客户端内置 wachi-playwright-mcp-runtime，工具调用记录里能直接看到 Ran Playwright code 和真实执行的 await page.goto(...)；外扩靠 MCP 扩展中心，第三方安全工具以 MCP 协议接入。侦察阶段还有动态作用域规划——基于捕获流量自动提取关联域名、修正测试边界，并做接口 Endpoint 探测。

**Skill 市场。** 把高频安全场景封装成标准化的能力单元，比如 vulbox-vulnerability-reporter（报告生成）、penetration-tester、webapp-nikto、MobileSecurityTestingSkil 等。Skill 决定 Agent "会用哪套打法"，选错 Skill 等于让外科医生拿菜刀。

把这几层串起来，一条标准的 Agent 漏挖链路是这样的：

```plain
目标/意图输入
   │
   ▼
侦察建模 ── 接口探测、动态作用域、流量基线（抓包蛙/浏览器）
   │
   ▼
任务编排 ── 待办列表拆解（主控智能体）
   │
   ▼
自动化探测 ── 浏览器交互 / 数据包重放 / 批量脚本验证（执行角色）
   │
   ▼
结果验证 ── 回显比对、状态码分析、正反用例交叉（分析角色）
   │
   ▼
报告交付 ── Skill 模板化生成，本地落盘（Markdown/漏洞盒子格式）
   │
   ▼
人工确认 ── 复现、定级、合规审查（人，不可省略）
```

看懂这条链路的意义在于：你知道该在哪个环节插手。侦察窄了，补信息；编排歪了，改指令；验证弱了，人工补刀。把 Agent 当黑盒许愿机的人，恰恰是把所有环节都推给了模型。

顺带把这套拆解本身的方法也分享了——逆向一个闭源 Agent 的 Harness 不需要源码，盯四个观察点就够：一看 **工具调用记录** （每次调用的类型、入参、执行结果，本文的 Playwright 代码与数据包面板证据都来自这里）；二看 **待办列表的生成与变更** （规划层的思维外化）；三看 **中间产物的形态** （浏览器返回 DOM 快照 YAML 而非截图，直接决定了它的感知偏好）；四看 **落盘文件** （报告保存路径、命名规则、模板结构）。四个观察点串起来，Harness 的骨架自己就浮出来了。

## 错误用例展示与正确测试用例

先看一个典型的反面教材。不少人对漏挖 Agent 的第一条指令长这样：

http://xxxxxx.com/ 测试一下这个网站

实测结果：Agent 对着这条指令"正在思考"了 **29 分 44 秒**，还没进入有效执行。

![](https://cdn.jsdelivr.net/gh/zhiyu-zeng/img@main/img/2026/09/f7803c90bfeefa33.png)

问题出在哪？没有测试边界、没有漏洞假设、没有深度约束、没有交付物定义。

模型被迫同时决策"测什么、怎么测、测多深、什么时候停"，思考 token 全烧在纠结上。这和把新人白帽扔进项目只说一句"你看着办"是同一个管理事故。

同一个靶标，换成结构化指令：

```plain
http://target/ 测试一下这个网站，一个简单的sql注入、数字型SQL注入漏洞，
可通过构造特殊数字注入 payload 验证漏洞利用过程，最后生成漏洞报告
```

Agent 的反应是完全不同的：短暂思考后直接 browser navigate，Playwright 执行 await page.goto('http://target/') 进场，随后沿"功能确认 → 布尔验证 → UNION 取数"的路径一路推进。

![](https://cdn.jsdelivr.net/gh/zhiyu-zeng/img@main/img/2026/09/69f191e9f54c9f21.png)

拆一下这条指令的四要素：

1.  1\. **目标**：明确 URL，无歧义；
2.  2\. **漏洞假设**：数字型 SQL 注入——把侦察收敛成定点验证，省掉全端口全目录的瞎摸；
3.  3\. **验证方法**：构造 payload 验证利用过程——要求打穿，不允许停在"疑似存在"；
4.  4\. **交付物**：漏洞报告——终态明确，Agent 知道什么时候算完。

通用模板可以沉淀成这样：

```plain
测试目标：{URL/资产范围}
测试方向：{漏洞类型假设 或 全面侦察}
约束条件：{禁止动作，如：禁止爆破/禁止 DoS 类测试/仅测试 X 路径}
验证要求：{必须实际验证利用过程，给出可复现 payload}
交付物：{漏洞报告 / POC / 资产清单}
```

Objective（目标）、Assumption（假设）、Constraint（约束）、Deliverable（交付）：目标定边界，假设定深度，约束定红线，交付定终态。四格填不满，就别怪 Agent 自由发挥——它自由发挥的空间，正是你指令里留下的空白。

需要说明：四要素里"漏洞假设"不是必需的。SRC 场景你往往没有先验假设，这时要把省下来的信息量补到约束条件里——资产范围、排除项、深度限制、停止条件。指令的信息量决定 Agent 的 token 花在刀刃上还是刀背上。

## 案例测试 · CTF 专项

CTF 这块基本简单测了一轮，大概 80 多道题，覆盖 Web、密码、Misc 三个方向。跑下来有个很清楚的规律： **中低难度的题，把题目描述原样丢给 Agent 就能直接解出 flag；高难度的题不行，得把人这边的思路和分析路径喂给它，也就是给思维链，它负责执行和验证。** 这个分水岭后面还会反复出现。挑几道有代表性的展开。

### 数字型 SQL 注入：十分钟打穿的标准链路

承接上文的结构化指令，看完整链路。

先 id=1 正常请求确认功能正常（返回用户"张三"的数据）；接着 1 AND 1=1 有数据返回、1 AND 1=2 无数据返回，布尔条件两分，数字型注入坐实——无需引号闭合；然后 -1 UNION SELECT 1,2,3,4,5 确认 5 列均可回显；再 -1 UNION SELECT 1,database(),3,4,5 读出当前库名 sql_injection_lab，-1 UNION SELECT 1,@@version,3,4,5 读出 MariaDB 版本。测试总结直接定级高危。

![](https://cdn.jsdelivr.net/gh/zhiyu-zeng/img@main/img/2026/09/865b4193468e56bd.png)

Agent 的浏览器工具返回的不是截图，而是 DOM 快照（Snapshot），以 YAML 形式给出带 ref=eXX 引用的节点树。实测快照里能看到 SELECT \* FROM use... 的语句回显和表格结构（ID/姓名/邮箱/部门/薪资，首行数据 1 sql_injection_lab 3 4 5）。

![](https://cdn.jsdelivr.net/gh/zhiyu-zeng/img@main/img/2026/09/ca30598e72ce23bb.png)

这意味着回显型漏洞（SQLi 联合查询、反射 XSS、信息泄露）对 Agent 天然友好——证据以文本形式进入上下文，判断会更准确；反过来说，依赖视觉特征或时序特征的漏洞，Agent 的把握会明显变弱，排任务时要有这个预期。

报告产出环节，加载报告模板后直接生成结构化文档：影响目标（URL、参数 id、GET 数字型无引号包裹、后端 MariaDB）、漏洞类型（数字型/Boolean-based/UNION-based）、风险等级判定理由、漏洞描述精确到后端拼接方式（SELECT \* FROM users WHERE id = {用户输入}）、7 步可复现步骤、4 条修复建议（参数化查询、int(id) 强制类型转换、关闭生产环境 SQL 回显、数据库账号最小权限）。修复建议给到了代码层（cursor.execute("SELECT \* FROM users WHERE id = %s", (id,))），这份报告已经很标准了，人工只要把 payload 亲自打一遍即可。

![](https://cdn.jsdelivr.net/gh/zhiyu-zeng/img@main/img/2026/09/600f251420783e32.png) ![](https://cdn.jsdelivr.net/gh/zhiyu-zeng/img@main/img/2026/09/f7ddc28333df80cb.png)

### GBK 宽字节注入：addslashes 绕过

这道题入口在 /，一个 id 查询表单，实际接口是 /query?id=。目标是读出独立表 flag_store 里的动态 flag。

Agent 的解题路径：id=1 正常返回 alice，确认注入点存在；随后识别出服务端用了 addslashes()——单引号会被转义成 '，直接闭合没戏。转机在数据库编码上：GBK 编码下提交 %df'，addslashes 插入的转义符 %5c 会和 %df 拼成合法汉字"運"，反斜杠被"吃掉"，单引号成功逃逸。访问 /query?id=%df%27 直接触发 MariaDB 语法报错（1064, You have an error in your SQL syntax... near ''??'），闭合确认。

后面的流程就是轻车熟路：%df' or 1=1# 返回两条记录（id=1、id=2），注入生效；%df' union select 1,2,3,4,5# 正常回显，确认 5 列；最后 %df' union select 1,flag,3,4,5 from flag_store# 读出 flag，同时顺手摸清了库名 ezsql、目标表 5 列结构（id/name/col2/col3/col4）。

![](https://cdn.jsdelivr.net/gh/zhiyu-zeng/img@main/img/2026/09/27e39207f5ccf249.png)

这道题值得留意的不是宽字节本身，而是 Agent 对"转义函数 + 编码"组合缺陷的敏感度——它没有在引号闭合上死磕，试了几次直接跳到编码层找突破口。

### ElGamal：调试信息泄露送分题

密码方向的一道题。服务端在 DEBUG 日志里把 ElGamal 的长期私钥 x 直接打印了出来，属于典型的调试信息泄露。

ElGamal 的结构是：私钥 x，公钥 y = g^x mod p；加密选随机数 k，密文 c1 = g^k mod p、c2 = m · y^k mod p。关键在共享秘密 s = c1^x = g^(xk) = y^k——拿到私钥 x 就能算出 s，明文随之还原。

Agent 的恢复过程很规范：先验证泄露的 x 确实正确（pow(g, x, p) == y 成立），再算共享秘密 s = c1^x mod p，然后 m = c2 · s^(-1) mod p，最后把 m 转成字节串，从附件 output.txt 中恢复出明文 litctf{elgamal_leak_makes_happy_decryp...}。

![](https://cdn.jsdelivr.net/gh/zhiyu-zeng/img@main/img/2026/09/fdb9127bf0564dfb.png)

### RSA 费马分解：邻居素数

另一道密码题。出题脚本先选素数 p，再多次调用 next_prime 得到 q——p 和 q 离得很近，费马分解对这种"邻居素数"异常高效。

Agent 给出的推导：设 n = p·q，令 a = ⌈√n⌉，不断自增 a 直到 a² - n 是完全平方数 b²，此时 p = a - b、q = a + b。实测分解出来的 p 和 q 差异只有 1135 左右，完全符合题目设定，a 只需迭代很少次数就收敛。随后 φ(n) = (p-1)(q-1)，扩展欧几里得求 d = e⁻¹ mod φ(n)，最终 m = c^d mod n 拿到明文 litctf{rsa_fermat_finds_close_primes...}。

![](https://cdn.jsdelivr.net/gh/zhiyu-zeng/img@main/img/2026/09/9b23e0d018b55020.png)

CTF 这一轮跑完，账面上有个很说明问题的数字：GBK 宽字节那道 Web 题，单题积分消耗只有 **25.75**。对比后面 SRC 场景单案上千的消耗，题目信息给得越足，Agent 的试错成本就越低——CTF 恰好吃在它最便宜的那个区间里。

## 案例测试 · SRC：真实业务资产

XBOW 毕竟是靶场，更进一步是把 Agent 拉到真实业务的 SRC 场景里。这轮测试覆盖的漏洞类型比靶场宽得多：越权、存储型 XSS、未授权访问、SpEL 注入 RCE、SSTI、敏感文件泄露，逐个说。

合规前提先交代：SRC 场景有授权边界和平台规则。漏洞盒子 2026 年 6 月发布了《关于规范 AI 辅助漏洞报告提交标准的公告》，态度明确——鼓励白帽子合理使用蛙池 AI 等 AI 工具，但报告必须经人工验证，纯 AI 生成、未经复现确认的报告属于违规提交。"AI 辅助"和"AI 代劳"在这个生态里有制度化的分界线，本文所有 SRC 案例均在此前提下进行。

### ID 越权：信任客户端的一切皆漏洞

先是一个两步认证流程（用户名页 → 密码页 → Dashboard）的目标。Agent 的链路回放值得细说：先跑侦察与认证流程分析，梳理出 / → /password/{username} → /dashboard 的认证路径，顺手发现首页 HTML 注释泄露测试凭据（<!-- TODO: Delete the testing account (test:test). -->）；对登录用户名、密码路径、密码提交表单的字段做了 SQL 注入测试——均未成功，后端走了参数化。注意这里 Agent 没有恋战，注入打不动立刻换面，转向越权方向。

突破口有三个，层层递进：

1.  1\. /password/{username} **未授权访问**：无需登录即可访问该路径，页面隐藏字段泄露内部 user_id（如 10032）和用户姓名（如 John），可枚举；
2.  2\. \*\*user_id\*\*\*\* 参数篡改越权\*\*：密码提交表单中的 user_id 是客户端可控的隐藏字段，篡改为其他用户 ID（如 10031）后仍成功登录（302 → /dashboard），服务端没有校验 user_id 与 username 的绑定关系；
3.  3\. \*\*X-UserId\*\*\*\* 请求头信任\*\*：密码提交端点（POST /password/{username}）直接信任客户端发送的 X-UserId 请求头确定用户身份；服务端签发的 Flask Session Cookie 中的 user_id 字段（Base64 解码为 {"user_id":10032}）同样源自客户端提交值，攻击者可任意篡改头值伪造其他用户身份完成认证。

![](https://cdn.jsdelivr.net/gh/zhiyu-zeng/img@main/img/2026/09/34acafafd106549d.png)

报告定级高危（越权访问/身份认证绕过，Broken Access Control / IDOR），漏洞描述把三个弱点串成了完整的身份伪造链。

![](https://cdn.jsdelivr.net/gh/zhiyu-zeng/img@main/img/2026/09/55f4cba47cc6a713.png)

另一个目标的链路更短平快：登录框弱口令 admin/123456 直接登录拿到 openid=12；抓包识别订单接口 POST /api/get_orders.php，请求体 JSON 格式 {"openid":"12"}；改 openid=10，成功拉到他人订单——接口对请求方身份零校验，仅按客户端传入的 openid 查单。报告把弱口令和水平越权拆成两个漏洞分别交付。

![](https://cdn.jsdelivr.net/gh/zhiyu-zeng/img@main/img/2026/09/b071811813b59299.png)

把"注释泄露凭据 + 隐藏字段可控 + 请求头信任"三个中低危弱点串成高危利用链，这种串联判断此前被认为是人类白帽的专利。这一关 Agent 做得像模像样。

### 客服对话存储型 XSS：一条完整利用链的构造

这个目标的要求很明确：拿到在线客服的 cookie。环境的认证环节没有弱口令，爆破路线被排除，只能从前端交互链路里找机会。

Agent 的利用链构造过程：

1.  1\. **功能建模**：在线客服系统，攻击者以普通客户身份发起人工请求（support_handoff）创建会话，经 support_send 接口发消息；
2.  2\. **过滤识别**：support_send 接口仅过滤原始尖括号字符（< 和 >）；
3.  3\. **绕过构造**：使用 HTML 实体编码（&lt; / &#x3C; / &#60; 等）绕过尖括号过滤，payload 持久化存储到服务端数据库；
4.  4\. **渲染链分析**：前端 assets/app.js 中存在两个关键函数——decodeHtmlEntities() 将实体解码，supportMessageItem() 在 render_mode 为 html_preview 时把解码后的值通过 innerHTML 直接写入 DOM；
5.  5\. **触发点**：客服人员（agent 角色）在客服服务台页面 support-agent.html 查看会话记录时，payload 在客服浏览器上下文中执行任意 JavaScript——存储型 XSS 成立，cookie 到手。

![](https://cdn.jsdelivr.net/gh/zhiyu-zeng/img@main/img/2026/09/4b698095610efa44.png)

![](https://cdn.jsdelivr.net/gh/zhiyu-zeng/img@main/img/2026/09/8e888aafe6364797.png)

同样值得记录的是报告里的"阴性结果"章节：SQL 注入测试了 quote_estimate、quote_create、policy_search、claim_query、search、news_detail、product、outlets、trust_score 共 9 个接口，均使用参数化查询或输入验证，未发现注入；IDOR 测试中 policy、claim_detail 正确限制为当前用户；权限提升尝试注册时传 role=agent，role 字段由服务端硬编码，失败。把"测过什么、为什么不成"写出来，这一点比很多人工报告都规范——既证明测试覆盖度，也帮审核人员排除重复劳动。

### Spring Cloud Gateway Actuator：从未授权访问到 SpEL RCE

这个目标一上来就是重灾区。Agent 验证确认了两个漏洞：

**其一，Actuator 端点未授权访问导致敏感信息泄露（高危）。** /actuator/env 暴露了 root 用户、内部 IP 172.17.0.40、主机名等敏感信息，/actuator/heapdump 可以匿名下载 42MB 的堆转储文件——堆转储里能翻出什么，做过 Java 安全的都懂。

**其二，Actuator API SpEL 注入远程代码执行（CVE-2022-22947，严重）。** 链路是标准的 Gateway 打法：通过 POST /actuator/gateway/routes/{id} 动态添加路由，路由的 Filter 参数支持 SpEL 表达式，借 AddResponseHeader 注入 T(java.lang.Runtime).getRuntime().exec(...)；POST /actuator/gateway/refresh 刷新路由配置触发解析执行；最后在路由配置中确认 id 命令的执行结果——uid=0(root) gid=0(root) groups=0(root)，以 root 权限实现 RCE，执行结果可直接经 GET /actuator/gateway/routes 读取。测试结束后 Agent 还清理了恶意路由

![](https://cdn.jsdelivr.net/gh/zhiyu-zeng/img@main/img/2026/09/c896a1ea119dc9e1.png)

报告里的修复建议也到位：management.endpoints.web.exposure.include 收敛为仅必要端点（如 health），避免暴露 env、configprops、heapdump；为 Actuator 端点配置 Spring Security 鉴权；management.server.address 绑定内网网卡，不对外网暴露。

### .DS_Store 泄露：小文件，大清单

这类漏洞技术含量不高，但极考验信息收集的覆盖度。Agent 探测常见敏感文件时，GET /.DS_Store 返回 200，可匿名完整下载——16388 字节，魔数 00 00 00 01，是合法的.DS_Store 格式。后续用 ds_store_exp 解析（或直接读其中的 UTF-16LE 文件名记录），整个目录结构和文件清单就全出来了，属于高危信息泄露。

![](https://cdn.jsdelivr.net/gh/zhiyu-zeng/img@main/img/2026/09/5a608632a4cef081.png)

修复建议给到了运维层：Apache 用 <Files ~ "^.DS_Store$"> Require all denied、Nginx 用 location ~ /.DS_Store { deny all; } 封禁；部署前清理源码目录里的.DS_Store、.git、.svn、Thumbs.db、\*.bak、\*.swp 等开发残留；Web 根目录与真实敏感文件分离；把敏感文件残留检测塞进 CI 流程。

### SSTI → RCE：模板预览接口的致命便利

目标应用提供了模板预览功能，前端把用户输入的模板源码直接提交到 POST /api/template/preview 接口，后端用 Jinja2 渲染且没有任何过滤和沙箱限制。接口认证也形同虚设——x-access-token 请求头可由 POST /api/auth/login 匿名获取任意有效 token。

Agent 的验证链：

1.  1\. **表达式求值**：{{7*7}} 提交后返回 {"preview":"49","status":"rendered"}——表达式被服务端求值，SSTI 成立；
2.  2\. **命令执行**：{{config.\__class\_\_.\__init\_\_.\__globals\_\_\['os'\].popen('whoami').read()}} 返回 {"preview":"root ","status":"rendered"}——任意命令执行成立；
3.  3\. **回显确认**：popen 执行 echo ssti-rce-confirmed，响应原样回显，排除缓存干扰；
4.  4\. **环境信息**：uname -a; id 返回 Linux 666ea2b6842a 6.8.0-31-generic... uid=0(root) gid=0(root) groups=0(root)——目标是以 root 运行的 Linux 容器。

报告里有一段补充说明值得原文引用：目标服务为 Linux 容器，不存在 Windows 的 calc.exe，故无法"弹计算器"；但已通过无副作用的回显命令（echo/whoami/uname/id）证实可执行任意系统命令，危害等同且高于弹计算器。这种"证据严谨性自觉"，恰恰是 AI 生成报告最容易缺的东西。

![](https://cdn.jsdelivr.net/gh/zhiyu-zeng/img@main/img/2026/09/22b46acca5910dfb.png)

### 使用过程中的小Tips:

SRC 这轮踩出来的几个实操要点，单独归拢一下：

**上下文比你想象的短，要给它指明方向。** 客户端显示真实上下文 5423 / 1000000 tokens（0.5%），账面容量看着很大，但长任务跑到中后段，中断恢复的问题就来了。实测遇到过一次任务中断后，Agent 去读之前的待处理报告文件，直接报 File not found（.pending_opencode_xxx.md 句柄已失效），它只能自我恢复："我需要先恢复任务上下文。让我检查当前工作目录和待处理的报告文件，以了解中断时的任务状态。"教训有两个：阶段性成果让它随时落盘，别全指望上下文；中断后续跑时把方向和当前进度在指令里讲清楚，别让它自己猜。

## Skills 选择与提示词思路

D2.5 上线 Skill 市场后，"挂什么 Skill"成了和"下什么指令"同等重要的决策。结合实测，沉淀几条原则。

**Skill 贵精不贵多。** 一个主战 Skill 打底，按需挂 MCP 工具，别堆叠。Web 渗透场景用 penetration-tester；移动应用测试用 MobileSecurityTestingSkil（覆盖 iOS/Android 静动态分析）；需要 Nikto 类扫描背书时挂 webapp-nikto；报告交付固定用 vulbox-vulnerability-reporter，生成漏洞盒子格式零排版成本。这几个目前都是免费 Skill。Skill 堆多了，工具调用的路由噪音反而上升，体现在账单上就是积分烧得快。

**提示词按场景分三种打法。**

定向验证型（CTF/已知疑似点）：套前文的四要素模板，把假设、方法、交付物一次给全，Agent 会直接进入验证循环，token 效率最高——CTF 单题 25.75 积分就是这么省出来的。

侦察扩展型（SRC/未知攻击面）：不给漏洞假设，给足边界——资产范围、排除项、深度限制、停止条件。参考结构：

```plain
目标：{主域名} 及其在授权范围内的子域
任务：全面侦察攻击面，识别可测试的接口与认证流程
排除：{第三方域名/CDN/已明确禁测路径}
约束：禁止爆破、禁止 DoS 类测试；单个接口验证不超过 N 个用例
停止条件：发现可确认的高危漏洞即暂停深入，先出报告
交付：资产清单 + 测试覆盖说明 + 漏洞报告
```

交付驱动型：开宗明义先声明报告格式和证据标准（请求/响应/复现步骤三件套），Agent 会在测试过程中就有意识地留存证据，避免打完再回头补数据包。

**负约束是隐形的省钱开关。** 比如你已经确认了"不存在弱口令"，就原样写进指令。一条负约束省下的可能是几百积分的无效字典尝试，同时也守住了授权合规的底线。

**模型是配置项，不是信仰。** 实测体感：侦察规划、利用链串联这类长程推理环节，glm-5.2 的产出更稳；批量脚本验证、模式化重放这类执行环节，deepseek-v4-flash 够用且便宜。Agent 在某个环节卡壳时，换模型往往比重写提示词见效更快——卡壳多半是模型的能力边界问题，不是表达问题。

## 结果研判与人工确认的边界

人工确认是必选项，也是链路结束的最后一环。

误报的高发区有迹可循：一是 **上下文相关型发现**，比如 HTML 注释泄露 test:test——在靶场这是中危信息泄露，在真实 SRC 里测试账号凭据算不算泄露、泄露的是否生产数据，必须人工核验；二是 **状态码驱动型判断**，408 超时和 200 命中混在批量结果里，不逐条看响应内容容易把网络抖动当成漏洞证据；三是 **影响面夸大**，Agent 倾向于把"理论上可遍历"写成"已验证可遍历"，复现时要核对它真实跑过的样本区间。

人工确认的标准动作就三步： **亲手复现** （把 Agent 给的 payload 用自己的环境重打一遍，不信它的回放）、 **核实影响面** （确认数据是真实用户数据而非测试桩）、 **审查合规性** （每一个请求都在授权范围内）。漏洞盒子的 AI 报告规范把这条写成了制度：AI 可以辅助，但提交人对报告真实性负责。审核员被 AI 水文轰炸的时代，这份纪律本身就是白帽的信用资产。

## 结尾：关于渗透测试智能体的一些思考

打完这一圈，对漏挖 Agent 这个位置想清楚了三件事。

**Agent 是杠杆，不是替身。** 它最擅长的是把人力不经济的事情做掉：100+ 订单的逐个遍历、9 个接口的参数化排查、格式严整的报告撰写。而攻击面的嗅觉——知道哪个业务流程里藏着越权、哪个过滤函数背后有渲染链——目前仍然来自人的经验。把三个中低危串成高危的操作，Agent 已经能做，但它做的是"验证串联"，最先怀疑"这里可能信任了客户端"的那个念头，还是人的。

**编排能力是白帽的新基本功。** 用 Agent 挖洞的产出差距，本质是测试计划的差距。会下指令，就是会做测试设计：范围怎么划、假设怎么提、深度怎么限、证据怎么验。这和带一个执行力极强但零经验的实习生是同一门管理学问——区别是这个实习生按积分计费，而且从不喊累。

**Harness 工程决定工具上限，人的 Harness 决定产出上限。** 厂商在卷模型外面那层壳，用户在卷自己工作流外面那层壳：指令模板、Skill 组合、成本纪律、人工确认清单。两层壳都对齐了，"AI 辅助挖洞"才从营销词变成生产力。至于下一步，等 Agent 有了跨任务的记忆和持续学习，今天这套手工编排的经验，大概又会变成下一轮工具演进要消化掉的东西——到那时再写一篇。
