>
> 手搓封包工具需先区分同步/异步发包模型，定位send、buffer与加密call，过滤心跳包，再InlineHook注入发包流程。
> 
> - **发包模型：** 单线程同步链路为控件call→功能call→组包→send；双线程由主线程组包加密后写全局队列，网络线程循环读取并send，需加锁防竞态。
> - **send定位：** WinSock send 原型为 `int send(SOCKET s,const char*buf,int len,int flags)`，stdcall；断点后send1长度常为1，send2才是真正发包函数。
> - **buffer回溯：** 从send的buffer参数入手，多级dump如 `[[[[0x1D6F0D4]+4]+0x14]+4]` 可定位封包缓冲区；memmove处用 `&edi==68750008` 条件断回溯写入源。
> - **心跳过滤：** 心跳包小、定时、独立消息ID；静置时定时断send可识别，用硬件写入断或偏移条件断过滤心跳，避免干扰业务包定位。
> - **加密与Hook：** 实测顺序为 send1→加密call→send2；手搓工具可InlineHook，覆盖目标函数头5字节为 `E9 相对跳转`，保存寄存器并读取栈上返回地址/参数，恢复原指令后跳回。

## 单线程发包（同步发包）

整条业务逻辑、组包、网络发送 **全部在同一个线程一次性跑完**，调用完发包 call 就立刻走网络。

### ① 无加密版本

**流程：控件 call → 功能 call1 → 功能 call2 → 组包 → 发包**

1.  **控件 call**：入口，触发发包事件（比如人物移动、技能、聊天这类动作入口函数）

2.  **功能 call1**：业务逻辑，填充对象、校验状态、读取角色数据

3.  **功能 call2**：业务处理，计算要发送的数据内容

4.  **组包**：把数据按游戏协议格式拼接成二进制数据包（包头 + 消息 ID + 包体）

5.  **发包 call**：直接调用底层 send 函数，把拼好的包发给服务器， **没有加密步骤**

✅ 优点：

-   链路简单，逆向最简单， **就是现在找到的 push 参数 + call send**

-   没有队列、没有多线程锁，不容易出现包乱序问题 ❌ 缺点：

-   网络阻塞会卡住游戏主线程，网络卡顿的时候游戏会掉帧、卡顿

-   大部分网游不会把核心业务放在这个链路，一般用于次要、轻量消息

### ② 单线程加密版本

**流程：控件 call → 功能 call1 → 功能 call2 → 组包 → 加密 call → 发包** 和上面几乎一样， **多一步加密 call**： 组包完成之后，调用加密函数对整个二进制包做加密 / 异或 / 压缩，加密完成后再调用 send 发包。

很多老游戏单线程加密包，加密逻辑直接嵌在主线程里。

## 双线程异步队列发包（主流网游标准方案）

```plain
线程1（生产者：构造数据包）：控件call → 功能call1 → 功能call2 → 组包 → 加密call → 写入【全局结构（包队列）】

线程2（消费者：网络发送）：循环读取全局结构的封包信息 → 拷贝缓冲区 → 调用底层send发包
```

1.  **线程 1（游戏主线程 / 逻辑线程）**  
    只负责 **生产数据包**：执行业务逻辑、组包、加密。  
    包做好之后 **不直接调用 send**，而是把包指针 / 包数据写入 **全局结构体（环形队列）**，写完就返回，继续跑游戏逻辑， **不会等待网络 IO**。

2.  **全局结构（共享包队列）**  
    一块全局内存，作为缓冲区，存放待发送的封包。  
    ⚠️ 重点：多线程读写，游戏内部会加互斥锁，防止两个线程同时读写导致内存错乱、崩溃。

3.  **线程 2（网络发送线程，独立后台线程）**  
    死循环不断扫描全局队列：

-   队列有包 → 取出封包信息，拷贝包缓冲区

-   调用底层 send 发包

-   发送完成，清理队列里这条包

✅ 优点：

-   网络 IO 阻塞完全隔离，就算网络卡，游戏主线程不会卡顿（网游最核心需求）

-   可以做包合并、限流、重发、丢包检测  
    ❌ 逆向难点：

-   组包和 send 发包 **不在同一段汇编**，断点断 send 很难定位上层业务 call

-   存在全局队列、锁，写模拟调用很容易因为多线程竞争导致崩溃

## 快速区分两种模型（逆向调试判断方法）

1.  **单线程（你当前找到的）**  
    断点断在 send 发包 call，往上回溯， **组包、业务逻辑都在同一个调用栈**，组包完直接 push 参数 call send，没有写入全局队列的操作。

2.  **双线程队列发包**  
    断 send 的时候，调用栈只有网络线程代码；上层控件 call 执行完，只是写全局内存，根本不会走到 send。

## Windows send 函数（WS2_32.dll）

send 是 **WinSock 标准 API**，位于 ws2_32.dll，TCP 连接建立之后，用来把内存里的二进制数据包交给操作系统内核缓冲区，最终发给游戏服务器。

就是你逆向里 call <JMP.&send> 这个 API。

## 1、函数原型（C 语言）

```plain
int send(
    SOCKET s,        // 参数1：套接字句柄（游戏和服务器的连接句柄）
    const char *buf, // 参数2：封包缓冲区指针（存放组包好的二进制数据）
    int len,         // 参数3：封包长度，多少字节
    int flags        // 参数4：标志位，游戏里几乎永远传 0
);
```

**调用约定：stdcall**，32 位程序， **从右往左 push 参数**，函数内部自己平衡堆栈。

所以汇编顺序：先 push 最右边的 flags，依次往左。

### 对应你之前那段汇编

```plain
mov eax,dword ptr ds:[0x1D6A368]  ; eax = 套接字s（第一个参数）
push ebx                           ; flags 第4参数
push 0x1                           ; len   第3参数
push 0x1326B7E                     ; buf   第2参数
push eax                           ; s     第1参数
call <JMP.&send>
```

注意：这里是 **游戏封装后的 send 包装 call**，不是原生 ws2_32!send，它重新包装了参数顺序，所以参数顺序和原生 send 反过来了，这是游戏自己封装的发包壳函数。

## 2、参数详解

1.  **SOCKET s** 游戏客户端和服务器 TCP 连接的句柄，全局唯一，登录成功后就固定。 游戏一般放在全局结构体，保存 socket、加密密钥、会话信息。

2.  **buf** **封包缓冲区指针**，就是组包完的二进制数据，包头 + 消息 ID + 包体。 你下断点断在这里，就能直接看到明文包内容（无加密发包）。

3.  **len** 数据包字节长度，告诉操作系统，缓冲区有多少字节要发。

4.  **flags** 控制选项，网游绝大多数情况填 **0**。

-   MSG_OOB：发送带外紧急数据（游戏极少用）

-   MSG_DONTROUTE：不走路由，内网直连

## 3、返回值

-   0：成功，返回 **本次拷贝到系统内核缓冲区的字节数** （不一定等于 len，TCP 分片）

-   \=0：连接正常关闭

-   SOCKET_ERROR (-1)：发送失败，网络断 / 服务器断开，可以用WSAGetLastError拿错误码

⚠️重点：send **不是直接把数据包立刻发到服务器**！ send 只是 **把数据拷贝到操作系统内核的 TCP 发送缓冲区**，send 返回只代表数据进了系统缓冲区， **不代表服务器已经收到**。真正的网络

## 心跳包（Heartbeat / KeepAlive）

## 一、是什么

心跳包是 **客户端定时发给服务器的极小数据包**，作用：告诉服务器「我这个客户端还在线，连接存活」。  
TCP 本身有系统层的 KeepAlive，但游戏几乎都会 **自己实现应用层心跳**，因为系统 TCP 保活粒度太粗、延迟高，容易被防火墙、中间代理误断连接。

> 一句话： **客户端每隔固定时间，发一个很小的包，告诉服务器：我还活着，别踢我下线。**

## 二、核心作用

1.  **保活，防止连接被断开**  
    运营商、防火墙、NAT 网关，长时间没有流量就会自动掐断空闲 TCP 连接。心跳包持续产生流量，维持通道。

2.  **服务器检测客户端是否掉线**  
    服务器设定超时阈值（例如： **5 秒没收到心跳 → 判断客户端离线**，踢下线、释放角色资源）。

3.  **部分游戏附带同步时间、延迟探测**  
    心跳包里附带时间戳，服务器用来计算客户端网络延迟 RTT。

## 三、心跳包特征（逆向一眼识别）

-   **包体极小**：很多只有包头 + 消息 ID，没有额外数据，几十字节以内。

-   **固定周期发送**：最常见 2s / 3s / 5s 定时发送，不是玩家操作触发（走路、放技能才发包属于业务包）。

-   **独立消息 ID**：单独一个协议号，和移动、聊天、战斗包分开。

-   **触发方式**： **定时器触发**，不是玩家按键触发。

> 重点区分：
> 
> -   业务包：玩家操作（移动、对话）才发包， **按需触发**
> 
> -   心跳包： **不管玩家动不动，定时自动发包**

## 四、两种实现方式，对应你前面的发包模型

### 1\. 单线程同步心跳（对应单线程发包模型）

游戏主线程定时器触发 → 控件 call → 组心跳小包 → 直接调用 send 发送

-   优点：简单，逆向容易找到心跳 call

-   缺点：主线程阻塞会影响心跳发送，网络卡顿会导致心跳延迟、被服务器踢下线

### 2\. 线程异步心跳（双线程队列发包）

定时器触发主线程组包 → 写入全局包队列 → 网络线程读取队列，执行 send  
心跳包和普通业务包走同一套队列，统一网络线程发送。

## 五、交互逻辑（标准流程）

1.  客户端登录成功，连接建立

2.  客户端启动定时器，每 N 秒构造心跳包

3.  调用发包链路，发送心跳包给服务器

4.  服务器收到心跳，更新该玩家的 **最后收到数据包时间戳**

5.  服务器持续轮询：

-   在超时时间内收到心跳 → 保持在线

-   超过超时时间仍未收到心跳 → 判定掉线，踢下线

> 可选： **双向心跳**：客户端发心跳给服务器，服务器回复心跳应答包。客户端也通过服务器应答判断连接是否断开。

## 六、逆向排查心跳包的方法

1.  在 send 下断点， **不操作游戏，静置不动**，看会不会每隔固定时间自动断下；自动断下的小包大概率就是心跳。

2.  抓包看流量：静止状态下，周期性出现的短小数据包就是心跳。

3.  向上回溯调用栈：找到定时器函数，就是心跳的入口 call。

## 0x00 InlineHook 简单示例（x86）

> 32位程序，对自定义Add函数实现Inline Hook，原理：修改目标函数头部5字节为 `E9 相对跳转` ，跳转到自定义Hook函数，执行完逻辑再跳回原函数。

```cpp
#include <iostream>
#include <Windows.h>

CHAR opCode[9] = { 0 };
DWORD dwRetData = 0;
CHAR szBuff[0x256] = { 0 };

DWORD dwRetAddr = 0;
DWORD dwParam1 = 0;
DWORD dwParam2 = 0;

using namespace std;

int Add(int a, int b) {
    return a + b;
}

_declspec(naked) void HookFun() {
    //保存寄存器环境
    __asm {
        PUSHAD
        PUSHFD
    }

    //功能代码实现
    __asm
    {
        //获取返回地址
        MOV EAX,[ESP+0x24]
        MOV [dwRetAddr],EAX

        //获取参数1
        MOV EAX,[ESP+0x28]
        MOV [dwParam1],EAX

        //获取参数2
        MOV EAX, [ESP + 0x2c]
        MOV[dwParam2], EAX
    }

    printf("%x \n", dwRetAddr);
    printf("%x \n", dwParam1);
    printf("%x \n", dwParam2);

    //恢复寄存器环境
    __asm {
        POPFD
        POPAD
    }

    //恢复原函数开头被覆盖的指令（这里写的是Add默认开头 prolog）
    __asm {
        PUSH EBP
        MOV EBP,ESP
        SUB ESP, 0xC0
    }

    //跳转回原函数剩余代码
    __asm {
        jmp [dwRetData]
    }
}

/// <summary>
/// 设置Inline Hook
/// </summary>
/// <param name="dwHOOKAddr">目标函数地址</param>
/// <param name="dwTargetAddr">自定义Hook函数地址</param>
VOID SetInlineHook(DWORD dwHOOKAddr, DWORD dwTargetAddr) {
    DWORD dwOldPro = 0;
    DWORD dwOldPr1 = 0;
    BOOL bRet = 0;
    DWORD dwJmpData = 0;

    //修改内存页属性为可读写执行
    bRet=VirtualProtect((LPVOID)dwHOOKAddr, 9, PAGE_EXECUTE_READWRITE, &dwOldPro);
    if (!bRet)
    {
        return;
    }
    //备份目标函数前9字节原始机器码
    memcpy(opCode, (LPVOID)dwHOOKAddr, 9);

    //填充NOP
    memset((LPVOID)dwHOOKAddr, 0x90,9);

    //构造E9相对跳转指令 E9 + 4字节偏移
    char szCode[5] = { 0 };
    szCode[0] = 0xE9;
    dwJmpData = dwTargetAddr-dwHOOKAddr - 5;
    *(PDWORD)(szCode+1) = dwJmpData;
    memcpy((LPVOID)dwHOOKAddr, szCode, 5);

    //记录跳转返回地址：原地址+5（跳过E9 jmp指令）
    dwRetData = dwHOOKAddr + 5;

    //还原内存页权限
    VirtualProtect((LPVOID)dwHOOKAddr, 9, dwOldPro, &dwOldPr1);
}

/// <summary>
/// 解除Inline Hook，恢复原始机器码
/// </summary>
/// <param name="dwHookAddr">目标函数地址</param>
VOID UnInlineHook(DWORD dwHookAddr) {
    DWORD dwOldPro = 0;
    DWORD dwOldPr1 = 0;
    BOOL bRet = 0;
    //修改内存属性
    bRet = VirtualProtect((LPVOID)dwHookAddr, 9, PAGE_EXECUTE_READWRITE, &dwOldPro);
    if (!bRet)
    {
        return;
    }
    //写回原始备份机器码
    memcpy((LPVOID)dwHookAddr, opCode, 9);

    //恢复内存页权限
    VirtualProtect((LPVOID)dwHookAddr, 9, dwOldPro, &dwOldPr1);
}

int main() {
    //Hook Add函数
    SetInlineHook((DWORD)Add,(DWORD)HookFun);

    Add(1, 2);
    //卸载Hook
    UnInlineHook((DWORD)Add);

    return 0;
}
```

## 0x01 代码说明

1.  编译环境：VS， **必须32位项目**， `_declspec(naked)` 取消编译器自动生成函数序言。
2.  Hook原理：覆盖 `Add` 函数头部5字节为 `E9 偏移` ，执行Add时直接跳转到 `HookFun` 。
3.  Hook函数内 `PUSHAD/PUSHFD` 保存全部寄存器，读取栈上返回地址与函数参数。
4.  执行完自定义逻辑后，手动执行原函数被覆盖的汇编指令，再 `jmp` 回到原函数继续执行。

## 0x02 注意缺陷

-   ⚠️ 硬编码写死 `PUSH EBP;MOV EBP,ESP;SUB ESP,0xC0` ， **只适配当前Add函数序言**。如果目标函数头部机器码不是这几条，直接崩溃，真实项目需要 **先备份原指令，在hook函数里执行备份指令，而不是硬写汇编**。
-   ⚠️ 没有多线程保护，多线程场景下会出现竞态，触发崩溃。
-   ⚠️ 只支持x86，x64地址大于4字节，E9跳转范围有限，实现方式完全不同。
-   ⚠️ 测试仅用于学习研究，不可用于商业/恶意用途。
