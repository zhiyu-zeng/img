## 02｜逆向手法

本次目标为 **Unity IL2CPP 架构**、接入旧版 **TapTap TDS SDK** 的《鬼谷八荒》移动端。

整体策略一句话：

> **不侵入 `libil2cpp.so` 原生层，仅修改 Java 侧 Smali 字节码。**

整套流程分为七个阶段：

```
侦察 APK 体检
  → 入口架构分析
  → IL2CPP 逆向解析
  → 验证链路全景测绘
  → Patch 实施
  → 打包签名
  → 动态验证
```

### ① 侦察 APK

![图片](https://cdn.jsdelivr.net/gh/zhiyu-zeng/img@main/img/2026/10/5f1b46bb3e725529.png)

使用 `apktool` 反编译样本，确认：

-   **无加固壳**
    
-   引擎版本： **Unity 2020.3.49f1c1**
    
-   启动顺序：隐私协议页 `PrivacyActivity` → `UnityPlayerActivity`
    
-   提取游戏服务、DLC 缓存服务器 IP
    
-   初步定位 SDK 相关包： `com.tds`
    

### ② 入口架构分析

通过 Jadx 反编译 Java 源码，理清通信桥接链路：

```
C# 游戏代码
  → JNI Bridge
  → TapTap Java SDK
```

关键结论：

> **游戏业务本身不发起鉴权网络请求，只接收 SDK 向上抛出的回调结果。**

这决定了后续 Patch 的落点：改 Java 侧，而不是硬啃原生层。

### ③ IL2CPP 逆向解析

样本元数据为 `global-metadata.dat v27` ，通用 `Il2CppDumper` 无法正常解析。

于是自研 Python 脚本读取元数据表、类型定义、方法符号，定位核心管理类：

```
TapTapManager
```

核验回调接收函数：

```
OnTapLogin
StartAntiAddiction
```

关键结论：

> **C# 侧不存在 token、授权状态的二次校验。**  
> 这是整套方案成立的核心前提。

### ④ 验证链路全景测绘

梳理出三道强耦合校验卡点，三道全部返回成功才可进入游戏：

| 卡点  | 校验内容 |
| --- | --- |
| ①   | Tap 账号登录校验 |
| ②   | 防沉迷实名校验 |
| ③   | 游戏本体 DLC 的 License 付费校验 |

同时额外发现： **防沉迷附带游玩时长管控逻辑，超时会被强制踢出。**

### ⑤ Patch 实施：四处 Smali 短路

针对 4 处 Smali 目标函数做短路改造。

**不删除原有联网代码**，而是把原版逻辑放在不可达分支作为死代码留存，方便审计对比。

| 目标函数 | 改造方式 |
| --- | --- |
| `TDSLoginServiceImpl#startTapLogin` | 不再唤起 Tap 客户端，在 Smali 内构造合法 AccessToken、用户资料 Bean，直接触发登录成功回调；同步修补资料查询接口，避免游戏读取到空对象判定登录失效 |
| `AntiAddictionUIImpl#startup` | 跳过实名联网请求，直接向回调返回放行 `code=500` |
| `TapAntiAddictionServiceImpl#getCurrentUserRemainTime` | 返回常量 `0x7FFFFFFF` ，消除限时踢下线 |
| `TapTapLicense#check` | 跳过 Tap 购买记录查询，调用授权成功回调，伪造已购买凭证 |

修改时严格对齐原方法 `.locals` 寄存器数量，规避 `apktool` 编译寄存器非法报错。

### ⑥ 打包签名

调用 `apktool` 重编译 Smali 得到未签名 APK。

沙箱环境缺少官方 `apksigner` 、 `jarsigner` ，于是自研 Python 脚本实现完整 **V1+V2 签名**：

-   遵守 `doNotCompress` 规则
    
-   `lib` 下 so 资源保持 `STORED` 不压缩
    
-   修正 ZIP 头部、EOCD 偏移、APK 签名块
    
-   生成可在 Android 34 模拟器识别的安装包
    
-   补丁完成后检索 dex 内特征标记，确认补丁写入
    

### ⑦ 动态验证闭环

```
adb 推送 APK
  → 静默安装
  → 拉起游戏
  → dumpsys window 读取当前焦点 Activity
  → logcat 抓取运行日志做状态判定
```

不依赖截图图像识别。

若命中验证页面、程序崩溃，则回退调整补丁，循环迭代，直到进入游戏主界面。

## 03｜方案亮点

### 亮点一：避重就轻

本次抓住一个特点：

> **鉴权职责完全交给第三方 SDK。**  
> 只伪造 SDK 放行回调，相当于伪造门卫放行条，不触碰游戏核心原生逻辑，大幅降低逆向难度。

### 亮点二：最小改动

保留原始代码作为死代码，而不是直接删除。

版本比对、bug 排查时可以快速对照原版 Smali；支持单点开关补丁，可单独绕过付费，或者只绕过防沉迷，灵活性高。

* * *

## 04｜客观局限

-   该补丁 **仅绕过 SDK 本地校验**；设备联网后，TapTap 服务端依旧会校验账号实名、购买状态， **联网后校验会失效**。
    
-   方案绑定 **旧版 TDS v1 SDK**，TDS v2 类名、接口全部重构， **补丁直接失效**。
    
-   仅适用于 **“C# 仅消费 SDK 回调”** 的游戏架构。如果游戏在 IL2CPP 层增加 token 二次校验，这套思路不再生效， **必须转向原生 SO 逆向**。

## 05｜AI 逆向架构

接下来讲： **我是如何开发这个 AI 逆向架构的。**

整体流程：一条流水线。

```
上传 APK
  → 加固检测
  → 反编译
  → AI 定位
  → 改包
  → 装模拟器验证
  → 没过就回喂修订（循环）
```

### 四层分工

#### 1\. 静态分析层（宿主）

-   `app-scanner` 一键跑：APKiD / 52 厂商特征查壳
    
-   `jadx` 出 Java 伪码，读逻辑用
    
-   `apktool` 出 smali 树，改包用
    
-   规则审计：密钥 / 端点 / 本地校验点
    
-   结果落 SQLite 台账，UI 和 AI 共用同一份数据
    

#### 2\. AI 定位层（容器里的 solver）

-   你说个目标，比如“破解 VIP”，起一个 pentest solver
    
-   双挂载：伪码只读 `/root/source` + smali 可写 `/root/work`
    
-   AI 读代码找目标方法，产出结构化 patch 计划
    
-   四个原语： `set_return` / `remove_call` / `replace_const` / `nop_lines`
    
-   **每条必须带 `file:line` 证据**
    

#### 3\. 改包层（宿主）

宿主把 patch 应用到 smali 树 → `apktool b` 重打包 → debug 签名 → 出成品 APK。

#### 4\. 验证层（核心：设备全在宿主，AI 只是远程遥控）

-   宿主侧：emulator / redroid / 外部模拟器（MuMu / 雷电 / 夜神）三种设备后端，adb 全走宿主
    
-   AI 容器里跑一个 `app-debug` MCP server
    
-   把“装机 / 启动 / 点按 / 截图 / logcat / frida hook”这些工具调用转成 HTTP 请求
    
-   经 `host.docker.internal` 回环打宿主的 `/api/sandbox/*` 接口
    
-   **所以 AI 能操作真设备，但模拟器、adb、frida-server 都不进容器**：镜像不膨胀、无暴露面

## 07｜AI 操纵模拟器

核心设计： **设备不进容器，AI 远程遥控。**

```
┌─ Docker 容器（AI solver）─────┐
│  app-debug MCP server        │
│  （薄代理，无 adb / 无模拟器） │
└──────────┬───────────────────┘
           │ HTTP 回环 + token
           │ host.docker.internal:<port>
           ▼
┌─ 宿主（WSL）──────────────────┐
│  /api/sandbox/* 路由          │
│  ├─ 设备操作：adb 命令         │
│  ├─ frida：宿主起 python 客户端│
│  └─ 事件：每个操作 emit 进流   │
└──────────┬───────────────────┘
           │ adb
           ▼
   模拟器（MuMu / 雷电 / 夜神 / 内置 AVD）
```

### 一、关键工具——adb

Android 模拟器出厂就带一个万能遥控器： **adb（Android Debug Bridge）**。 了解移动安全的人已经很熟悉adb，无论是root，还是安装证书，调试真机都要用到这个工具。

它暴露在容器本地端口上，所有操作都是：

> **发一条文本命令 → 收一段文本回显。**

```
adb devices                    → 列出可用模拟器（发现阶段）
adb install game.apk           → 装包
adb shell am start -n com.xxx/.MainActivity   → 拉起应用
adb shell input tap 540 960    → 模拟点击
adb shell am start -a android.intent.action.VIEW ...
```

AI 发现模拟器的方式就是第一条命令：

```
adb devices
```

回显设备列表，有输出 = 有活的模拟器。

模拟器在它眼里就是一个能听懂文本指令的终端设备—— **这恰好是 LLM Agent 最强的交互模态。**

### 二、监测运行状态：三个文本传感器

| 传感器 | 命令  | 回答的问题 |
| --- | --- | --- |
| `logcat` | `adb logcat --pid=$(adb shell pidof com.xxx)` | 应用在说什么？崩溃栈？验证日志？ |
| `dumpsys` | `adb shell dumpsys window \| grep mCurrentFocus` | 现在屏幕上停在哪？焦点是主菜单还是验证页？ |
| `uiautomator` | `adb shell uiautomator dump`<br><br>→ 拉回 XML | 屏幕上有哪些控件、验证弹窗文案是什么 |

关键洞察：

> **验证弹窗还在不在不需要看图。**  
> `mCurrentFocus` 回显当前 Activity 的类名。如果焦点还停在 `VerifyActivity` 而不是主菜单 `MainActivity` ，验证没绕过去，一锤定音。

配合：

```
adb shell ps -A | grep 包名
```

还能测进程生死：进程没了 = 被 `System.exit()` 杀了，或者崩了。

> 补充： `adb exec-out screencap -p > screen.png` 可以截屏，多模态模型能直接读图。但 Agent 优先用上面三个，因为 **XML / 文本是确定性的，比像素可靠**。并且，这个方案比多模态的读图更加便宜。
