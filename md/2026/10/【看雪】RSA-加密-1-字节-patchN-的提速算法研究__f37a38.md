> 💡 **AI 总结（key-points）**
>
> 解决单字节 patch RSA 模数后，快速找到可直接分解的 n′：关键在于利用同一字节位置候选之间只差一个小整数的等差结构，把“候选数 × 小素数”的试除规模降低为“只扫一遍小素数”，并把开销很大的 Miller-Rabin 判素减少到约 1/4。
> 
> - **问题与约束：** 4096 bit 模数有 512 个字节，每个字节 255 种取值，约 13 万个候选；每个候选都要满足 `n′ = p×q`（p 为小素数、q 为素数）且 `gcd(e, φ)=1`，才能反解出私钥指数 d。逐个候选跑完整分解流水线时，成本会随候选数线性增长，估计需 10¹¹ 次大整数整除。
> - **同余反推：** 固定字节位置 m 时，`n′(d)=n+d·256^m`；对奇素数 r，仅凭 `n·256^(−m) mod r` 一个余数就能定出 256 个 d 中哪些被 r 整除（r>255 至多一个），于是扫描一遍素数表即可得到全部候选的 `cnt` 与最小素因子，计算量从“候选数×素数数”降到“素数数”，相差约四个数量级。
> - **位置切换常数：** 下一位置所需余数等于上一余数乘 `256⁻¹`；借助预先算好的 `r⁻¹ mod 256`，用 `t+k·r` 右移 8 位实现该逆乘，每个（位置，素数）只需两次 32 位乘法，与模数有几千位无关。
> - **三级预筛：** `cnt≥2` 必为合数，`cnt==0` 在搜索空间内找不到小因子 p，只保留 `cnt==1` 做判定；判定前再剔除 `gcd(e, φ)≠1` 的候选（e=3 时约删掉 3/4），每位置 256 个候选平均仅剩 57~66 个进入 Miller-Rabin。
> - **上界取舍与实测：** 筛表上界从 3×10⁴ 升到 3×10⁵ 时素数多 8 倍而候选只少 12%，因此代码按模数大小选择 3×10⁴（≤2048 bit）或 3×10⁵；生产者按位置递增分配任务，消费者并行，从而保证结果确定。实测 4096 bit 需 84.4 ms，对比 rpatch 26.4 s，开源同类工具差距上千倍。另外，由于 GMP 的 mpn 快速路径依赖 `__int128`，实现须用 GCC。

> 一句话总结：快的关键不是"算得更快"，而是别对每个候选单独试除——利用候选之间的等差结构，把「候选 × 2.6 万个小素数」压成「2.6 万个小素数」，再把真正昂贵的 Miller-Rabin 压到 1/4。

## 背景

软件破解场景，试图只 patch 一个字节就能生成 RSA 私钥、过 RSA 公钥验证。没啥实际意义，但是比较好玩。  
具体是这样的：手里有一个 RSA 模数 `n` ，要找出一个 `n'` ，它和 `n` 恰好只差一个字节，并且满足

```python
n' = p × q            p 是小素数，q 是素数
gcd(e, φ(n')) = 1     φ(n') = (p − 1)(q − 1)
```

找到之后就能算出私钥指数 `d = e⁻¹ mod φ(n')` ，得到配套的私钥。

穷举空间不算大：4096 bit 的模数是 512 个字节，每个位置 255 种取值，一共约 13 万个候选。问题在于—— **怎么快速判断这 13 万个候选里哪些可以分解、商又是不是素数**。

## 朴素做法慢在哪

一种很自然的实现路线是"逐个候选"：每生成一个 `n'` ，就把它当成一个独立的因子分解问题，跑一遍完整的分解流水线——判素、试除、Brent、P-1/ECM，找到因子再看商是不是素数。

复杂度是 `O(候选数 × 单个候选的分解成本)` 。分解本身既贵又带随机性，这条路的开销基本随候选数线性增长。

拿 4096 bit 粗估一下：13 万个候选，如果每个候选只做一遍千万级以内的试除，

```python
130,560 × 1,077,871 ≈ 1.4 × 10^11 次大整数整除
```

单线程按每次 30 ~ 50 ns 也要一两个小时，后面的 Brent/ECM 还没算。

本文的做法是

```python
512 个位置 × 2.6 万个素数 ≈ 1.33 × 10^7 次 32 位乘加
```

差四个数量级，而且只和「位置数 × 素数数」有关、与候选数无关。

关键在于这些候选不是互相独立的：固定字节位置 `m` 时，

```python
n'(d) = n + d · 256^m        d = 新字节 − 旧字节
```

同一个位置的 256 个候选， **只差一个小整数 `d`**。这种等差结构可以一起算。

## 优化一：一次扫描算完 256 个候选

对任意奇素数 `r` ：

```python
n'(d) ≡ 0 (mod r)   ⟺   d ≡ −n · 256^(−m) (mod r)
```

也就是说：只要知道 `n · 256^(−m) mod r` 这一个余数，就能反推出这个位置上 256 个 `d` 里哪些会被 `r` 整除——对 `r > 255` 至多一个，对 `r ≤ 255` 则是等间隔的几个。

于是扫一遍素数表，就能把该位置 256 个候选的整除情况全部算出来：

-   `cnt[b]` ：改成 `b` 之后被几个小素数整除（饱和到 2，够用了）
-   `killer[b]` ：其中最小的那个素因子

成本从「候选数 × 素数个数」降到「素数个数」——一次性降了一个维度。

## 优化二：换位置只要两次 32 位乘法

下一个位置需要的是 `n · 256^(−(m+1)) mod r` ，而它正好等于上一个余数乘以 `256^(−1)` ：

```python
n · 256^(−(m+1)) ≡ (n · 256^(−m)) · 256^(−1)  (mod r)
```

直接对大整数重新取模是 O(位数) 的；这里换一种做法：预先算好 `r^(−1) mod 256` ，让 `t + k·r` 能被 256 整除，然后右移 8 位，就等于"乘 256 的逆"：

```cpp
const std::uint32_t k = std::uint8_t(0u - t * inv);   // inv = r^-1 mod 256
const std::uint32_t d = t ? r - t : 0;                // 当前需要的位移
if (d <= hi)                 mark(old_b + d, r);     // 命中一个候选
else if (r - d <= old_b)     mark(old_b - (r - d), r);
t = std::uint32_t((std::uint64_t(t) + std::uint64_t(k) * r) >> 8);
```

每个（位置, 素数）就是两次 32 位乘法加一次移位， **和模数有几千位无关**。这一步是整条算法里最重要的常数因子。

## 优化三：两道近乎免费的预筛

扫完之后，只有 `cnt == 1` 的候选值得判素：

-   `cnt ≥ 2` ：被两个以上小素数整除，必是合数；
-   `cnt == 0` ：没有不超过上界的小素因子，按这个搜索空间的定义找不到 `p` ；
-   `cnt == 1` ：恰好有一个小素因子 `p` ，此时商 `q = n'/p` 与所有小素数互素，判素命中率高。

判素之前再筛一道： `gcd(e, φ(n')) ≠ 1` 的候选算不出 `d` ，连 Miller-Rabin 都不用做（ `e = 3` 时能扔掉约 3/4）。

实测每个位置 256 个候选里，平均只剩下 **57 ~ 66 个** 要真正判素。

## 优化四：筛表上界不是越大越好

预筛的收益，来自"用便宜的小素数除法换掉昂贵的 Miller-Rabin"。那第一个问题就是：筛表上界 `B` 取多大？

`B` 越大， `cnt == 1` 的候选越少；但每个位置要扫的素数按 `O(π(B))` 涨，建表和求 `n mod p` 也要时间。两条曲线的斜率差得很远——4096 bit 实测（同一个模数）：

| 上界 B | 素数个数 | 平均候选/位置 | 建表 + 求余 | 扫完 512 个位置 |
| --- | --- | --- | --- | --- |
| 3×10⁴ | 3,244 | 65.8 | 0.8 ms | 3.8 ms |
| 3×10⁵ | 25,996 | 57.8 | 6.1 ms | 14.3 ms |

素数多了 8 倍，候选只少 12%。所以上界不是越大越好：模数小的时候，多扫的素数根本省不回来；只有单次 Miller-Rabin 变得足够贵（模数大），加大上界才划算。

代码里的规则就是按这个权衡定的： `n ≤ 2048 bit` 用 `3×10⁴` ，更大用 `3×10⁵` 。顺带 `B` 也是正确性边界——能找到的 `p` 不会超过它。

## 并行

生产者线程按字节位置从低到高扫描，把候选按批投递到队列；消费者线程（ `hardware_concurrency()` 个）并行做整除、gcd、Miller-Rabin。

位置从低到高、同一位置取最小的新字节值，保证结果 **完全确定**——同样的输入永远得到同样的输出。

## 为什么必须用 GCC

MSVC 没有 GCC 风格的 `__int128` 。GMP 在 x86_64 上的 `mpn` 快路（64×64→128 位的单指令乘法）在 MSVC 下拿不到，只能回落到"把 64 位操作数拆成两个 32 位再拼高位"的 C 代码。

而 MinGW 这份 GMP 是 **fat 构建**： `libgmp.a` 里有 680 条 `mulq` / `mulx` ，运行时按 CPUID 选 `k8` / `bd1` 变体。整个程序 99.9% 的时间都在 Miller-Rabin，也就都在这条汇编路径上。

```bash
objdump -d libgmp.a | grep -cE 'mulq|mulx'   # 680
```

所以同一个算法用 MSVC 编，理论上是能跑的，但最热的那部分会被换掉。

## 实测

机器：AMD Ryzen 5 5600（6 核 12 线程，3.5 GHz）、16 GB、Windows 11、GCC 16.2.0（MSYS2 UCRT64）、GMP 6.3.0（静态 `libgmp.a` ，fat 构建）。编译选项 `-O3 -DNDEBUG -static -s --gc-sections` 。

每个尺寸一个用例，各跑 15 次取中位数，对比闭源实现 rpatch(https://github.com/nszy007/rpatch) ：

| 模数  | 本库  | rpatch |
| --- | --- | --- |
| 1024 bit | 4.5 ms | 19.2 ms |
| 2048 bit | 14.7 ms | 823 ms |
| 3072 bit | 43.6 ms | 4.85 s |
| 4096 bit | 84.4 ms | 26.4 s |

至于飘X阁的 RSA 一字节替换工具 v1.3 以及开源实现 RSA-PATCH-TOOLKIT(https://github.com/FTSTT/RSA-PATCH-TOOLKIT) ，速度差距更大，4096 bit 上千倍起步。
