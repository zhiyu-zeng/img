10 月 17 日，一篇复现文把 ARTEX 的利用链整个摊开了：不用账号，800 个并发，管理员密码被改掉，最后拿到 root。

ARTEX 是套 AI 自主渗透平台，Go 后端加 Next.js 前端，PostgreSQL 存任务和资产，默认管理端口 8787，抓流量的代理在 8788。用的人不少，部署方式也简单，一个二进制或者一条 docker compose 就起来了。

我把 v0.3.15 的源码拉下来对了一遍。修复确实做了，但有几处原文没提到，还有三处根本没动。先说结论： **这不是一个漏洞，是三个默认值串成的一条链。**

## 01链条不长，三环扣死

整条利用链只有三段。

第一段，登录初始化接口把“读不到”当成了“没设置”。第二段，数据库连接被打满，让这个错误稳定复现。第三段，拿到管理员身份之后，通过 MCP 的 stdio 传输起一个子进程，命令就执行了。

三段单看都不算致命。第一段是个异常处理疏忽，第二段是连接池没设上限，第三段是协议本来的设计。

串起来，就是未认证到 root。

这类漏洞比单个内存破坏难防得多，因为每一段的作者都会觉得“这不是我的问题”。异常处理是小事，连接池是性能参数，协议执行命令是天经地义。三个“不是我的问题”拼在一起，就是别人的 shell。

## 02那个被丢掉的下划线

出问题的接口是 `POST /api/auth/init` ，用来做首次设置管理员密码。原文贴了那几行代码，核心就一句：

⏰ server/auth.go · 出问题的判断（v0.3.14 语义）

existing, \_, \_:= pg.GetSetting(authPassKey) // error 被丢掉

if existing!= "" {

writeErr(w, 403, "密码已设置")

return

}

`GetSetting` 有两个返回值是空串：一种是键不存在，一种是查询出错。这两种情况唯一的区别，是第三个返回值 error。

代码把 error 丢了。

于是数据库抖一下，系统就认为“这台机器还没设过密码”，继续往下走，把攻击者传进来的密码 bcrypt 一下，写进去。写用的是 upsert， `ON CONFLICT DO UPDATE` ，已有的密码哈希直接被覆盖。

在 Go 里，多返回值加 `_` 太顺手了，顺手到没人觉得这是个安全边界。

CWE 给这类问题留了两个编号：CWE-636 失败时不安全（fail open），CWE-754 异常条件检查不当。前者说的是“出错时退化到更弱的状态”，后者说的是“没检查或者检查错了异常”。

那个下划线，是整条链的起点。

## 03把“偶发故障”变成“随时可造”

数据库为什么会出错？因为连接被占满了。

Go 的 `database/sql` 有个默认值很多人不知道：不调用 `SetMaxOpenConns` 时，上限是 0，也就是不限。官方文档的原话是 “The default is 0 (unlimited)”。

PostgreSQL 那边， `max_connections` 默认 100。

应用侧不限，数据库侧 100，中间没有任何缓冲。并发一上来，连接池里的请求全部打到数据库，第 101 个开始被拒，日志里出现 `FATAL: sorry, too many clients already` 。

到这里，第一环需要的那个 error 就出现了。

原文的复现是 800 并发跑两轮，统计下来 44 个 200、245 个 403、3 个 500、508 个连接异常。这组数字很说明问题：大部分请求被正常挡回 403，一小部分撞进了窗口，拿到 200。

这就是“抢窗口”。每个请求只做一次 SELECT，持连接的时间很短，所以要靠并发量去堆概率。800 不是魔法数字，理论上稍微超过数据库上限，再配合足够密的请求节奏，就能把错误率顶上去，800 只是让命中率变得可靠。

修复版把这里改成了 32。作者在注释里写得很清楚：封顶之后，超额查询从“报错”变成“排队等空闲连接”，同样的负载下变成变慢，而不是失败。调用方不用再去区分“读不到”和“没有”。

▲ 从连接打满到窗口打开：故障不是意外，是被造出来的

连接池上限从来不只是性能参数，它是故障注入的门槛。

## 04stdio 天生就是命令执行

拿到管理员 JWT 之后， `POST /api/mcp` 就成了执行入口。

平台支持三种 MCP 传输：stdio、http、sse。stdio 那一条，会把配置里的 `command` 和 `args` 直接交给子进程去起。ARTEX 的 `connectMCP` 函数里，这个分支只有两句判断：命令不能为空，然后就交给 MCP 客户端去启动。

这不是 ARTEX 写错了。MCP 协议就是这么设计的。

Anthropic 的 SECURITY.md 里有一段写得很直接：stdio 传输通过执行命令来启动服务器，这是 intended feature，不是漏洞；客户端以配置里的命令启动进程，进程以客户端的权限运行；关于“通过 stdio 配置实现任意命令执行”的报告，不被视为漏洞。

也就是说，在这个架构里， **“给管理员权限”和“给 shell”是同一件事。**

今年 4 月 15 日，OX Security 把这条设计级的问题整个摊开过一次：7000 多个公网可达的 MCP 服务器、1.5 亿次下载、最多 20 万个受影响实例，下游十几个 CVE，他们实测打穿了六个生产平台。

我在 NVD 上核了其中四个：LiteLLM 那个 9.8 分，LangChain-ChatChat 8.6 分，Agent Zero 和 Windsurf 同批，Windsurf 是零点击，处理一个攻击者控制的 HTML 就会改本地 MCP 配置。

所以第三环修不了。上游明确不修，你只能管住“谁能写 MCP 配置”这件事。

## 05护栏的坐标是客户不是自己

ARTEX 是有护栏的，而且设计得挺认真：工具调用可以配 allow、deny、ask 三类规则，还有模型兜底审批，资产层面有黑白名单，默认拦.gov、.edu。

听起来很稳。但我把内置规则翻出来看，默认只有一条：

匹配工具输入里形如 `/delete` 、 `/remove` 、 `/unlink` 的接口路径，直接 deny。

这条规则防的是“AI 把客户的数据删了”。它不防“别人把平台拿了”。

看表结构就更清楚：拦截规则的匹配目标只有两种， `tool_name` 和 `tool_input` 。也就是说，这套护栏长在 agent 的工具调用循环里，看的是“模型要调哪个工具、传什么参数”，它压根不看平台自己的 HTTP 接口。

护栏的坐标系，画在客户系统那一侧。

更要紧的是第二条路。平台给 AI 自己的工具清单里有个 `create_custom_tool` ，能创建 shell、command、script、http 四类工具。其中 command 和 script 最终都走同一个 bash 执行器。

也就是说，就算你把 `/api/mcp` 整个封掉，一个有管理员会话的人，仍然可以造一个 bash 工具出来，然后让 AI 去调用它。

## 06修了什么，还留着什么

v0.3.15 的 `auth.go` 我逐行看过，改动比原文列的三处多。

除了读失败回 503、写改成 `INSERT ... ON CONFLICT DO NOTHING` 、连接池封到 32，还有两处。

**一处是 JWT 签名密钥的位置。** 旧版本把 `jwt.key` 放在 dataDir 里，而 dataDir 是平台文件管理器能浏览的工作区根目录。新版把它挪到程序目录，还写了迁移逻辑：老位置的密钥搬过去、旧文件删掉，会话不失效。

一个能被文件管理器读到的签名密钥，等于谁都能伪造管理员 token。这一处原文没提，但它和前面三处是同一个性质的问题：信任边界画错了位置。

**另一处是两个回归测试。** 测试注释直接把事故写进去了：authInit 会放行未认证请求去覆盖已有密码，authStatus 会把前端送到 /setup 照着做一遍。这种把 bug 写进测试注释的做法，比漏洞通告更有信息量。

还留着的，有三处。

`/api/auth/` 整个前缀仍然在免认证白名单里。修复只是让“读失败”不再等于“没设置”，白名单没动。下一次任何一处 fail-open，还会以同样的方式生效。

stdio 的 `command` 和 `args` 仍然不设限。

JWT 只签了 subject、exp、iat 三个声明，没有密码版本。改密码之后，旧 token 还能用满 7 天。

顺手说一句， `/api/health` 不需要认证就回版本号， `{"ok":true,"service":"artex","version":"..."}` 。扫描器连猜都不用猜。

这次修的是这个洞，不是这类洞。

## 07十分钟自查清单

按顺序来，做到哪条算哪条。

**一、看版本。** 浏览器或者 curl 直接打 `/api/health` ，返回里的 version 小于等于 0.3.14，先停服务再处理。这个洞目前 NVD 上查不到 CVE，只能靠版本号判断。

**二、看监听地址。** 默认参数是 `-addr :8787` ，冒号前面没写地址就是全网卡。docker compose 里也是 `"8787:8787"` ，一样。

⏰ 三条可以直接抄的检查命令

\# 健康接口会回版本号，不需要认证

curl -s http://127.0.0.1:8787/api/health

\# 看本地地址是 0.0.0.0 还是 127.0.0.1

ss -lntp | grep 8787

\# 容器映射会写成 0.0.0.0:8787->8787/tcp

docker ps --format "{.Ports}"

**三、看前置。** 公网访问有没有过 VPN、SSH 隧道，或者带认证的反向代理。管理口直接对公网，前面所有讨论都失去意义。

**四、看 MCP 清单。** 不认识的 stdio 条目就是后门。

⏰ 查 mcp_servers 表（字段名按 v0.3.15 schema 核过）

SELECT id, name, transport, command, args, created_at

FROM mcp_servers

ORDER BY created_at DESC;

**五、看自定义工具。** system 为 false 的是人建的，exec 里能看到实际执行的命令。

⏰ 查 tools 表里的自定义工具

SELECT key, kind, exec, updated_at

FROM tools

WHERE system = false;

**六、看运行身份。** 容器里是不是 root，进程权限有多大。平台的正常功能就要跑 bash，root 跑等于把这个能力放大到最大。

## 08失陷之后看四处

如果前面查出来有问题，往下走。

**第一处，认证日志。** `/api/auth/init` 返回 200 的记录，正常情况下这辈子只应该有一次，就是初始化那次。之后再来 200，就是被覆盖了。

**第二处，数据库日志。** `too many clients already` 集中出现的时间点，和上面那个 200 对得上，基本可以定性。

**第三处，MCP 表。** 新增的 stdio 条目，command 是 `/bin/sh` 或者 bash，args 里带 -c，创建时间紧挨着那次 200。

**第四处，进程树。** ARTEX 派生的子进程，参数里出现 base64、curl、nc、 `python -c` 这种组合。

⏰ 两条看进程树的命令

\# 树状看 artex 派生了什么

ps -ef --forest | grep -A3 artex

\# 直接按进程号展开子树

pstree -ap $(pgrep -f artex | head -1)

这里有个坑：平台正常干活也在跑 bash，因为它的 worker 要用真实工具打目标。所以“有 bash 子进程”不能当告警条件，只能看参数特征。

处置顺序也要改一下。断网、隔离、取证这些照旧，但 **不要只改密码**。改密码不吊销已有 token，攻击者手里那个还能用 7 天。要换 `jwt.key` ，或者直接重启服务让它重新加载，再清 mcp_servers 和 tools 里来路不明的条目。

顺带看一眼出网。一个渗透平台如果连内网办公段和数据库都能直连，那它在别人手里就是最好的跳板。

## 09给写平台的人五条铁律

五条，都是能直接写进代码的。

**第一，初始化接口三条铁律。** 读失败必须拒绝，不能当“没设置”；写用 `INSERT ... ON CONFLICT DO NOTHING` ，让主键约束兜底，别靠先读后写；初始化完成后接口永久关闭，不是靠一个 if 判断。

**第二，连接池必须封顶。** 取值低于 PostgreSQL 的 max_connections，还要留出余量给 psql 和运维脚本。超额排队比报错好，因为报错会被上层当成业务状态。

**第三，管理面默认回环。** `-addr 127.0.0.1:8787` ，公网访问自己加反代。默认全网卡是最省事的选择，也是最容易被忘掉的一步。

**第四，stdio 三选一。** 要么禁用，要么白名单，要么沙箱加低权限跑。三样都不做，等于把“配置 MCP”这个功能直接做成 webshell。

**第五，密钥不进可浏览目录。** 前端能点到的文件管理器，和程序运行目录，必须是两个地方。token 绑密码版本，改密即失效。版本号别给未认证接口，那是最省事的指纹。

如果你不是写平台，是要买或者要验收一套，把上面五条翻译成五个问题去问：管理口默认监听哪里、初始化接口怎么防止重放、MCP 的 stdio 能不能关、签名密钥存在哪、改密码之后旧会话多久失效。

五个问题里有两个答不上来，这套东西就不该进生产网。

## 10安全工具为什么总在自己身上翻车

安全工具在自己身上翻车，不是第一次，也不会是最后一次。

原因就三个：这类工具默认跑在“可信内网”的假设下，为了能用，默认监听全网卡、默认少鉴权；它的核心功能本身就接近“执行任意命令”，功能即攻击面；用它的人是安全人员，反而更容易觉得“我知道我在干什么”。

三件事叠起来，就是现在这个样子。

一个工具的能力越接近“执行任意命令”，它的管理面就越等于 root。这句话对 AI 渗透平台成立，对 MCP 网关成立，对所有“让模型帮你动手”的东西都成立。

对甲方来说，最实际的一条建议是：把这类平台当生产系统管，别当工具管。工具可以随手装，生产系统要走变更、要最小权限、要审计、要有人负责。

它替你打别人，别人也会来打它。

// 老宋说：这件事的技术本质不是认证绕过，是异常处理里的一个语义错误：读失败和不存在，被合并成了同一个答案。这类错误在任何语言里都常见，只是平时没人拿 800 个并发去压它。  
  
行业里的观察是，AI 工具正在把“执行命令”这件事包装成配置项。MCP 的 stdio 是最典型的一个，官方明确说这是设计不是漏洞，那安全责任就整个落到写配置和管配置的人身上。上游不修，下游就得自己长脑子。  
  
你今天能做的一件事：去看一眼你那套平台的管理口是不是还在 0.0.0.0 上，版本是不是 0.3.14 以下。这两条查完，比读十篇分析都管用。
