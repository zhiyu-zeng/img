**ITPAPA** *2026年11月4日 12:15*

ARTEX、ConnectWise 供应链事件与 Microsoft 365 应用身份检测

![图片](https://cdn.jsdelivr.net/gh/zhiyu-zeng/img@main/img/2026/11/3f25d87293eb7200.png)

受信任应用凭据一旦失陷，攻击者可以绕开交互式用户登录，以机器速率使用既有授权。检测必须沿着“应用存在—应用认证—Graph 行为—实际影响”逐层推进。

## 一条容易被“用户登录中心主义”漏掉的攻击链

2026 年 10 月 21 日，微软披露 Storm-0940 使用开源 Agent 渗透测试框架 ARTEX，加速侦察、密码喷洒和 OAuth 应用滥用。微软将 ConnectWise Cloud Backup 多租户应用的供应链失陷归因于该组织，并称攻击者在取得相关应用身份后，使用被窃取的应用凭据登录下游 Microsoft 365 租户。

这里没有必要把 ARTEX 描述成一种全新的攻击原语。扫描、喷洒、有效账户、受信任关系、OAuth 应用滥用、Graph 枚举和应用凭据持久化早已存在。变化在于 Agent 把目标发现、尝试、结果解释和下一步动作连接成循环，使相同战术可以在更多租户、更短时间内重复执行。

判断  
AI 改变的是攻击速度、并行度和响应窗口；应用身份、授权、凭据和 API 请求仍会留下可观测证据。防守方不需要先识别“这是 AI”，而要先识别“哪个应用身份在什么时间、从哪里、用什么凭据访问了什么资源，并造成了什么变化”。

## 事件中的已知事实与证据边界

| 时间  | 公开事实 | 证据边界 |
| --- | --- | --- |

| 10 月 21 日 | 微软披露攻击者控制多个 ConnectWise 云应用身份，并尝试登录 2,250 多个租户。 | 尝试登录或成功认证本身不能证明数据被访问或外传。 |

微软报告还给出一组更能体现速度的数据：一部分行动使用 4 个应用凭据，在不到 4 分钟内完成 200 多次登录。微软同时称，若干 ARTEX 驱动的行动从最初选定目标到获得云端高权限不足 3 小时。两项数据均来自微软遥测与威胁情报，应写成“微软观察/评估”，不能扩写成所有受影响租户都经历了同样路径。

## 为什么应用凭据会绕开常见的登录防线

图 1 受信任多租户应用的凭据被控制后，攻击者可继承租户已经授予的应用权限。

Microsoft Entra 中的应用对象代表软件的全局定义；租户内的服务主体则是该应用在本租户中的实例。多租户 SaaS 获得管理员同意后，会在客户租户中拥有一个本地服务主体，以及被授予的应用角色或委托权限。

当应用使用 OAuth 2.0 client credentials 流程时，认证主体是应用，而不是某个正在操作浏览器的用户。凭据可以是客户端密钥或证书。只要凭据有效、服务主体启用且授权仍在，应用就能获取访问令牌并调用 Microsoft Graph。用户的 MFA、设备合规和交互式登录行为基线并不是这条链路的主要控制点。

| 对象  | 应记录的标识 | 为什么不能只看名称 |
| --- | --- | --- |
| 应用注册 | AppId / Application Object ID | 显示名称可改，AppId 才适合跨租户查找。 |
| 租户服务主体 | ServicePrincipalId / Object ID | 同一 AppId 在不同租户有不同本地对象。 |
| 凭据  | KeyId / 证书指纹 / 有效期 | 同一应用可同时存在多个密钥或证书。 |
| 授权  | AppRoleAssignment / OAuth2PermissionGrant | 应用存在不等于拥有相同权限。 |
| 实际请求 | SignInActivityId / RequestId / OperationId | 需要把令牌签发和 Graph 行为关联起来。 |

这也是为什么“删除一个企业应用”不应成为第一反应。立即删除会破坏服务，也可能丢失对象配置、授权关系、凭据元数据和调查上下文。更稳妥的顺序是先冻结或禁用连接、导出证据、确认影响，再按供应商指导和本地调查结果移除未授权凭据、角色与授权。

## ARTEX 真正改变了什么

微软将 ARTEX 描述为用 Go 编写、配有 Next.js 前端的多 Agent LLM 系统。Agent 在渗透过程中积累资产与漏洞图，并能从侦察推进到后续操作。公开资料没有给出本次行动中的完整提示词、模型版本、任务图或每一步人工干预，因此不能把所有动作都归因于完全自治。

| 能力变化 | 对攻击者的收益 | 对防守方的直接后果 |
| --- | --- | --- |
| 并行尝试 | 同时测试多个租户、身份和路径 | 同一时间窗内日志量骤增，人工逐条分析来不及。 |
| 结果反馈 | 根据认证、权限和 API 响应调整下一步 | 告警之间存在因果关系，单条规则容易低估。 |
| 图式记忆 | 保存已发现资产、身份与权限关系 | 攻击路径可快速转向另一个高价值对象。 |
| 重复执行 | 把同一工作流扩展到大量目标 | IOC 有效期短，行为基线和身份图更重要。 |
| 持续运行 | 跨时区、节假日和非工作时间活动 | 值守和自动遏制策略必须覆盖全天。 |

因此，“AI 检测器”并不是这里的首要建设项。即使无法判断某次 Graph 调用是不是由 Agent 决定的，防守方仍可以判断：应用是否从非预期网络登录、是否出现新凭据、是否自授高权限角色、是否突然跨多个 Key Vault 读取秘密，或者是否在修改后立即大量枚举 SharePoint。

## 四层证据链：不要把“存在”写成“失陷”

![图片](https://cdn.jsdelivr.net/gh/zhiyu-zeng/img@main/img/2026/11/ccbe411e7b7df0b1.png)

图 2 调查结论需要逐层升级；每一层都不能替代下一层证据。

## 第一层：暴露

确认受影响 AppId 是否在租户内存在、是否启用、服务主体 Object ID 是什么、持有哪些应用角色和同意授权。该层只能说明潜在暴露面。应用存在或曾安装，不等于凭据已被滥用。

## 第二层：认证

检查服务主体成功与失败登录，关注 AppId、ServicePrincipalId、源 IP、目标资源、认证结果、CredentialKeyId、证书指纹和时间。成功认证说明凭据被接受，但仍不能单独证明访问了邮件、文件或秘密。

## 第三层：行为

把登录事件与 Microsoft Graph 活动、Entra AuditLogs、Microsoft 365 Audit、Key Vault 和 Azure 控制面事件放在一条时间线上。重点关注应用凭据新增、服务主体所有者变化、AppRoleAssignment、同意授权、Global Administrator 等目录角色、自我赋权，以及异常的邮件、SharePoint、Teams 或 Key Vault 操作。

## 第四层：影响

确认请求是否成功、返回数据量、目标资源、后续传输、创建的持久化对象和仍然有效的访问路径。Graph 日志缺失不能自动推出“没有访问”，因为日志可能未启用、保留期不足，或相关活动发生在其他工作负载。相反，一条成功 API 请求也不能自动推出大规模外传。

## 三类日志如何拼成同一条时间线

![图片](https://cdn.jsdelivr.net/gh/zhiyu-zeng/img@main/img/2026/11/3593579f77cd197c.png)

图 3 AppId 适合跨租户定位，ServicePrincipalId 适合锁定本地对象，时间与请求标识用于关联行为。

| 日志  | 关键字段 | 回答的问题 | 常见缺口 |
| --- | --- | --- | --- |
| 服务主体登录 | AppId、ServicePrincipalId、IPAddress、Resource、Result、CredentialKeyId | 应用是否认证、从哪里、访问哪个资源？ | 门户会聚合同条件事件；保留期与导出配置不同。 |
| Entra AuditLogs | Activity、TargetResources、InitiatedBy、ModifiedProperties、CorrelationId | 谁新增凭据、授权、所有者或目录角色？ | 应用与服务主体更新可能记录为两个事件。 |
| Graph 活动 | RequestUri、Method、Status、Scopes、Roles、RequestId、SignInActivityId | 认证后调用了哪个 API，结果如何？ | 需 Entra P1/P2、Azure 订阅和预先配置诊断设置。 |
| Microsoft 365 审计 | Operation、Workload、UserId/AppId、对象、客户端 IP | 是否访问邮箱、文件、Teams 或创建规则？ | 不同工作负载字段与保留策略不同。 |
| Key Vault / Azure | 操作、资源 ID、身份、IP、结果 | 是否枚举或读取秘密、操作存储或 ARM？ | 资源诊断设置和平台覆盖可能不一致。 |

## 可直接落地的狩猎顺序

## 第一步：用 AppId 建清单

不要按显示名称搜索。显示名称可能变化、重复，也可能被攻击者用来混淆。用供应商或威胁情报提供的 AppId 找出本地 ServicePrincipalId，记录启用状态、授权、凭据和所有者。微软在本次报告中列出三个 ConnectWise 相关 AppId；实际调查应以微软和 ConnectWise 的最新清单为准。

基于微软公开查询精简 结果表示应用存在及其权限，不表示已经遭到滥用

## 第二步：把成功与失败认证分开看

失败洪峰可以说明扫描或喷洒速度，但影响判断更依赖成功登录。查询时不要只过滤已知 IOC IP；已知 IP 适合快速定位，移除 IP 条件后才能发现同一 AppId 从其他基础设施发起的活动。还应建立供应商正常网络、常用资源、调用周期、凭据 Key ID 和地域基线。

微软 Sentinel 示例的精简版 实际表名与字段应按本租户连接器验证

## 第三步：关联 Graph 请求与目录变更

行为查询 重点是资源、方法、状态和权限，不只看 User-Agent

MicrosoftGraphActivityLogs

| where TimeGenerated >= datetime(2026-10-13)

| where AppId in (Apps)

| project TimeGenerated, AppId, ServicePrincipalId, IPAddress,

RequestMethod, RequestUri, ResponseStatusCode,

Scopes, Roles, SignInActivityId, RequestId

| order by TimeGenerated asc

User-Agent 可以提供线索。微软在相关活动中观察到 Python urllib、python-requests、curl 和 azure-toolkit 等标识，但这些字符串都可伪造，也可能出现在合法自动化中。它们适合作为上下文，不适合单独作为高危结论。

## 第四步：检测“新增凭据后立即访问”

比“来自某个 IP”更稳健的检测，是把高风险状态变化和后续使用串起来。例如：服务主体新增证书或密钥，随后从新网络成功认证，并在短时间内修改角色或访问高价值资源。

防御性伪查询 2 小时为初始验证窗口，不是事件实测阈值

// 伪 KQL：字段需按本地 AuditLogs 解析结果调整

let CredentialChanges = AuditLogs

| where Category == "ApplicationManagement"

| where ActivityDisplayName has_any

("Update application", "Update service principal")

| where tostring(TargetResources) has_any

("keyCredentials", "passwordCredentials")

| project ChangeTime=TimeGenerated,

TargetObjectId=tostring(TargetResources\[0\].id),

Initiator=tostring(InitiatedBy);

| join kind=inner (AADServicePrincipalSignInLogs

| where ResultType == 0

| project SignInTime=TimeGenerated, ServicePrincipalId,

IPAddress, ResourceDisplayName)

on $left.TargetObjectId == $right.ServicePrincipalId

| where SignInTime between (ChangeTime.. ChangeTime + 2h)

| project ChangeTime, SignInTime, ServicePrincipalId,

IPAddress, ResourceDisplayName, Initiator

## 无害实验：用合成日志验证关联逻辑

不需要在真实租户中创建高权限应用或模拟攻击。可以在隔离的 Log Analytics 测试工作区，使用 datatable 构造完全合成的审计、登录和 Graph 事件，验证查询是否能把同一服务主体的状态变化串起来。所有 GUID、IP 和 URI 都是演示值。

合成数据实验 只验证时间线关联，不会访问真实 Microsoft 365 资源

let AuditDemo = datatable(TimeGenerated:datetime,

ServicePrincipalId:string, Event:string)

\[

datetime(2026-11-04 01:00:00), "sp-demo-001", "CredentialAdded"

\];

let SignInDemo = datatable(TimeGenerated:datetime,

ServicePrincipalId:string, IPAddress:string, Result:string)

\[

datetime(2026-11-04 01:07:00), "sp-demo-001", "192.0.2.44", "Success"

\];

let GraphDemo = datatable(TimeGenerated:datetime,

ServicePrincipalId:string, Method:string, Uri:string, Status:int)

\[

datetime(2026-11-04 01:09:00), "sp-demo-001", "PATCH",

"https://graph.microsoft.com/v1.0/demo", 204

\];

AuditDemo

| join kind=inner SignInDemo on ServicePrincipalId

| where TimeGenerated1 between (TimeGenerated.. TimeGenerated + 30m)

| join kind=inner GraphDemo on ServicePrincipalId

| where TimeGenerated2 between (TimeGenerated1.. TimeGenerated1 + 30m)

## 预期结果与复核方式

| 检查项 | 通过标准 | 失败时先查什么 |
| --- | --- | --- |
| 事件关联 | 同一 sp-demo-001 输出凭据变更、成功登录、PATCH 请求。 | join 键、字段类型与时间字段后缀。 |
| 时间窗口 | 把 Graph 事件改到 2 小时后，30 分钟规则不再命中。 | 时区、窗口边界、数据延迟。 |
| 身份隔离 | 把 Graph ServicePrincipalId 改为 sp-demo-002 后不命中。 | 是否误用 AppId 与 Object ID。 |
| 结果解释 | 查询只输出“需调查链路”，不标记数据已外传。 | 告警文本是否把认证或请求等同于影响。 |

完成合成验证后，再用已知正常应用做只读基线测试：确认服务主体登录能进入 SIEM、Graph 请求能按 AppId 检索、AuditLogs 能解析凭据和角色变化。若日志没有采集，先修复可见性，而不是先调阈值。

## 事件响应：先保全证据，再切断信任

1.按 AppId 盘点所有当前或曾经授权的租户，记录本地 ServicePrincipalId、权限、凭据、所有者和启用状态。

2.保全 Entra 登录与审计、Microsoft 365 Audit、Graph 活动、Key Vault、SIEM 和供应商平台证据；记录导出时间、时区和查询条件。

3.按照供应商当前指导禁用或保持相关连接关闭。需要紧急遏制时不要为了等待完整导出而延误，但要记录每项改变。

4.分别调查失败认证、成功认证、Graph 行为、目录变化和资源访问。确认是否新增了凭据、应用、所有者、同意授权、AppRoleAssignment 或目录角色。

5.对确认未授权的凭据、授权、角色和身份执行撤销；轮换供应商应用及受影响下游凭据，并验证旧令牌和后门路径失效。

6.检查邮件、SharePoint、Teams、Key Vault、存储和 ARM 操作，确定具体数据与资源范围。把“无日志”“未发现”和“确认无访问”写成三个不同结论。

7.按 ConnectWise 当前流程重新授权或恢复服务，并验证新备份快照确实成功。重新授权成功不等于备份任务已经恢复。

| 结论等级 | 可写结论 | 仍不能声称 |
| --- | --- | --- |
| 潜在暴露 | 受影响 AppId 存在并持有某权限。 | 凭据已被攻击者使用。 |
| 可疑认证 | 服务主体从异常来源成功登录。 | 已读取客户数据。 |
| 确认行为 | 观察到具体 Graph、目录或资源操作。 | 所有请求均成功或数据已外传。 |
| 确认影响 | 有成功访问、返回、下载、转发或持久化证据。 | 未调查资源也没有影响。 |

## 长期治理：把供应商应用当作非人身份管理

| 控制面 | 具体做法 | 代价与边界 |
| --- | --- | --- |
| 资产与责任人 | 为每个 AppId 建立业务所有者、供应商、权限、数据域、到期复审和紧急联系人。 | 需要持续维护；名称和供应商合并会造成漂移。 |
| 最小权限 | 拆分备份、监控、管理能力，避免一个多租户应用同时拥有不必要的高权限。 | 可能增加应用数量和运维复杂度。 |
| 凭据治理 | 优先受管身份或证书；限制生命周期；对新增凭据建立变更单与告警。 | 第三方 SaaS 未必支持受管身份；证书也需要保护私钥。 |
| 应用身份条件访问 | 为工作负载身份使用风险策略和受控网络条件。 | 取决于许可、产品支持和供应商固定出口能力。 |
| Graph 可观测性 | 启用 Graph 活动日志，进入 Log Analytics、Storage 或 Event Hubs。 | 需要 P1/P2、Azure 资源和额外采集成本。 |
| 自动遏制 | 对自授高权、异常凭据新增和高价值资源批量访问设计审批或自动禁用。 | 误报可能中断备份等关键业务，需分级动作。 |

应用身份治理的目标不是消灭第三方 SaaS，而是让每一条受信任关系都可枚举、可解释、可撤销。供应链事件发生后，组织应能在分钟级回答：哪些租户安装过这个 AppId、它们各自的本地 Object ID 是什么、授予了什么权限、最近用哪个凭据从哪里访问过哪些资源。

## 适用边界与容易误判的地方

·微软关于 Storm-0940、ARTEX 和攻击链的结论属于厂商威胁情报与遥测判断。公开材料没有提供所有客户的原始日志，也没有公开完整的 Agent 任务轨迹。

·ConnectWise 对备份档案保持加密隔离、未发现其失陷的表述，只针对存储档案；不能替代对每个 Microsoft 365 租户的独立调查。

·应用存在、认证成功、Graph 调用和数据外传是不同证据层级。文章中的查询不能自动完成影响定级。

·IOC IP 与 User-Agent 会变化。它们适合快速定位，长期检测应结合 AppId、ServicePrincipalId、凭据变化、权限状态和资源访问基线。

·Graph 活动日志需要事先启用并产生存储费用。微软给出的成本估算随租户规模和 API 调用量显著变化，应先做采样和数据计划。

·示例 KQL 是防御性起点。表名、连接器、字段和数据延迟在不同租户中可能不同，必须用本地正常事件复核。

最后的判断  
Agent 化攻击把“发现目标—测试路径—解释结果—继续行动”压缩到机器节奏。真正决定防守能力的，是应用身份是否可见、权限是否最小、关键变化能否自动关联，以及组织能否在服务中断和证据保全之间做出预先设计的响应。
