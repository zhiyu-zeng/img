## 0.3 一个必须先立的规矩

AI 在 OSINT 中的正确定位是 **放大器**，不是 **替代品**。放大器意味着：输入垃圾，输出更多垃圾；输入没有验证的线索，输出看起来更可信的谣言。所以本指南把 “验证”放在与“采集”同等重要的位置，而不是当成最后一章。

## 1.2 可以复用的五个骨架

以下五点是原文真正的干货，本指南后续所有流程都建立在这五点之上。

**骨架一：情报周期五阶段** （原文 2.1）

准备 → 收集 → 处理 → 分析 → 分发。关键不在五个词，而在于它是 **闭环**：分发之后要回到准备，用反馈修正下一次的收集计划。多数团队失败在把周期做成直线。

**骨架二：深搜的三条腿** （原文 5.1）

专用搜索运算符、定制化爬虫、档案与专业数据库 API。原文指出深搜的目标是“标准搜索引擎进不去的隐藏、档案、未索引数据”。这句话在 2026 年依然准确，只是“爬虫”这一条要换成“合规的采集基础设施 + 反封锁”。

**骨架三： AI 的三类能力** （原文 6.1）

自动化采集、 NLP 抽取（实体、情绪、主题）、计算机视觉。这三类能力今天依然成立，但原文低估了第四类： **生成与编排** （写查询、写代码、写报告、驱动多步流程）。这一类恰恰是 2025—2026 年变化最大的部分。

**骨架四：伦理三原则** （原文 3.3、14.2）

合规（ GDPR 等）、伦理（不侵权、必要时匿名化）、透明（记录来源与方法）。原文补充了三条可执行准则：同意、最小化、可问责。这三条在本指南第 12 章会被翻译成具体的操作动作。

**骨架五：工作流四模块** （原文 15.1）

自动化采集、数据处理管道、 AI/ML 分析模块、报告工具。这是最小可用的系统架构，第 9 章会把它实现成可运行的代码。

## 1.3 三个必须补上的缺口

**缺口一：从 “能力描述”到“操作步骤”。**

原文说 “AI 可以自动抓取并聚合数百个来源的数据”，但没有说用哪个库、怎么去重、怎么处理反爬、怎么留证。本指南用第 4 章的五阶段 SOP 和第 9 章的代码补上。

**缺口二：从 “AI 很强”到“AI 具体在哪里骗你”。**

原文对局限性的描述只有三行：偏见、误报、需要人工监督。而 2025—2026 年的实证研究给出了更精确的失败图谱：大模型在地理定位上会自信地指错国家 \[S6\]，在命名实体识别上低于可接受水平 \[S7\]，而且在只有一项 OSINT 专用系统真正测量过端到端幻觉 \[S3\]。这些结论直接改变了工作流设计。

**缺口三：模型坐标系已经换了三茬。**

2025 年 2 月的“先进模型”到 2026 年 11 月已被迭代多轮，且性能并非单调上升——Bellingcat 的对比测试显示新一代模型在地理定位上反而退步 \[S6\]。任何把“某个模型最强”写死的流程都会过期，正确做法是把模型当成可替换件（第 3.2 节）。

## 第 2 章 能力地图：AI 在 OSINT 里能干与不能干

这一章解决最常见的一个错误：把 AI 当成“更快的搜索引擎”。它不是。它是一个 **语言与模式的处理器**，强在压缩、转换、生成、比对，弱在事实、精确、责任。

## 2.1 八个应该交给 AI 的活

**（ 1）需求拆解：把模糊委托变成可检索的问题**

客户说 “查一下这家公司有没有问题”，这句话无法执行。让模型把它拆成 5—8 个关键情报问题（KIQ），每个 KIQ 再拆成 2—4 个可观测指标（EEI），这是 AI 目前最稳定、收益最高的用途之一。原因很简单：这一步不需要事实，只需要结构。

**（ 2）查询构造：把自然语言变成检索语法**

包括 Google 运算符、平台内搜索语法、SQL、正则、API 查询参数。模型对语法的掌握远好于对事实的掌握，而且语法错误是 **可立即验证** 的 ——搜一下就知道对不对。这是“低风险高回报”的典型场景。

**（ 3）多语言采集与转译**

原文 10.3 节强调语言壁垒。实操中 AI 的价值不只是翻译，而是 **保留原词**：同时输出直译、意译、原文关键词表。因为搜索时必须用原文词，机器翻译过的词搜不到东西。

**（ 4）大批量文本的主题与叙事抽取**

给定 500 条帖子，让模型归纳出 6—10 条叙事主线，并为每条主线附 3 条原帖引用。这一步是“降维”，人做需要一天，模型做需要十分钟，而且引用可核查。

**（ 5）线索扩展：从实体到下一跳**

拿到一个域名、一个邮箱、一个 Git 提交者名字，让模型列出“下一步可以查什么、在哪个平台查、用什么语法”。它给出的往往是通用套路而非新情报，但能有效防止遗漏。

**（ 6）时间线重建与矛盾检测**

把散落在多条来源里的时间点汇总成表，标注每个时间点的来源与精度（精确到日 /月/年），再让它列出彼此冲突的条目。这是纯逻辑工作，模型表现良好，而且冲突清单本身就是分析产出。

**（ 7）报告起草与结构改写**

把要点草稿改写成 BLUF 结构、把技术细节改写成管理层语言、把长报告压缩成一页摘要。注意： **只让它改结构，不让它补事实**。

**（ 8）代码与自动化脚本**

写 Python 采集脚本、写 SQL、写正则、解释报错。这是当前性价比最高的一类用途，因为代码的正确性可以被运行验证。

## 2.2 五个不能托付的判断

**（ 1）事实核实。**

Bellingcat 用 25 张自有照片、对 24 个模型做了 500 次地理定位测试，结论很直接：多数模型在某个时点给出过幻觉，即使最好的模型也会自信地指向错误地点；GPT-5 系列相比上一代在定位任务上明显退步 \[S6\]。这不是“再等等就好了”的问题，而是概率生成机制的固有属性。

**（ 2）精确实体抽取。**

一项针对 8 个开源与付费聊天机器人的评估发现：在“这条推文是否与网络安全相关”的二元分类上，聊天机器人可以接近专用模型；但在命名实体识别（NER）任务上，表现“低于可接受水平”，即使加大训练数据也无法与专用模型相比 \[S7\]。含义很明确： **批量抽取实体要用专用 NER 或规则 + 人工抽检，不要让通用模型直接产出实体表**。

**（ 3）信源可信度的终判。**

自动化偏见是真实存在的风险：人倾向于相信机器给出的结论，尤其是当模型输出看起来 “有条理”时；面对高风险目标研判，分析员会不自觉地放松审查标准 \[S8\]。所以信源评级必须由人签字，且评级理由要写下。

**（ 4）法律与伦理判断。**

某个查询是否越界、某张人脸是否该搜、某份数据能否跨境，这些判断依赖辖区法律、组织政策与公共利益权衡，模型既不掌握你的授权范围，也无法承担责任。

**（ 5）高风险决策。**

目标锁定、威胁优先级排序、战略预警这类决策，业界共识是保留人类最终决定权， AI 只提供建议 \[S8\]。这不是保守，而是因为错误的代价不可逆。

## 2.3 一条总原则

**AI 负责广度与初筛，人负责深度与判责。**

2026 年 7 月发表的一篇系统综述（覆盖 74 项研究）给出了同样的结论：现有研究在“采集”和“分析”环节支持充分，在“验证、报告、分发、决策支持”环节覆盖有限；作者认为最稳妥的近期架构是 **人机协同（ human-AI co-pilot）**——模型协助采集与初筛，分析员对验证与决策负责 \[S3\]。这与中文军事情报界对“数据过载”的反思完全一致：AI 应负责筛选与关联，重大决策的判断权必须留在人手里 \[S8\]。

## 2.4 人机分工决策矩阵

把任务按 “AI 自主度”分三档，团队照此执行，可以大幅减少争议。

|     |     |     |     |
| --- | --- | --- | --- |
| 任务类型 | AI 自主度 | 具体做法 | 人工必做 |
| 查询构造、脚本编写、格式转换、翻译初稿 | 可执行 | 直接采用，出错再改 | 抽查语法与常识 |
| 摘要、聚类、时间线整理、矛盾清单 | 建议  | 采纳为主 | 逐条核对引用 |
| 实体抽取、账号关联、地理定位假设 | 建议  | 作为线索 | 必须一手复核 |
| 信源评级、事实认定、结论措辞 | 禁止  | 不采纳 | 人独立完成 |
| 目标锁定、威胁定级、对外发布 | 禁止  | 不采纳 | 人独立完成并留痕 |

这张表的用法：在项目启动会上把它贴出来，明确 “哪些环节可以省人、哪些环节省不得”。多数事故不是因为用了 AI，而是因为在禁止档用了 AI 却没人发现。

## 第 3 章 开工前的 60 分钟：环境与纪律

## 3.1 身份与浏览器隔离

OSINT 的第一原则是“不要让目标知道你在看他”。AI 工具会显著增加暴露面：你输入的每一个查询都可能被平台记录，你打开的每一个链接都可能回传你的真实身份。

|     |     |     |
| --- | --- | --- |
| 层次  | 最低要求 | 推荐做法 |
| 浏览器 | 调查行为与日常浏览分开 | 单独浏览器配置文件 + 独立容器；高敏感项目使用托管归因浏览器 \[S9\] |
| 网络  | 不用家庭 /公司出口 IP 查敏感目标 | 住宅代理或受管出口，按国家 /城市选点 |
| 账号  | 不与真实身份关联 | 项目专用 “马甲”账号；只在必要时注册，注册即记录 |
| 文件  | 项目文件独立目录 | 按 “案例ID/日期/来源/哈希”命名，见 3.4 |

**马甲账号的伦理边界**：可以用于观察公开内容、降低被识别概率；不可以用于伪装身份套取信息、添加好友套话、诱导发布。这条线一旦跨过，就从 OSINT 变成了社会工程，法律与平台规则风险完全不同。

## 3.2 模型选型：把模型当可替换件

不要绑定单一模型，按任务类型路由。以下是一个实用的路由表。

|     |     |     |
| --- | --- | --- |
| 任务  | 更适合的模型特征 | 原因  |
| 需求拆解、查询构造、脚本 | 推理型（长思维链） | 需要结构化推理而非记忆 |
| 长文档 /多文档比对 | 长上下文 + 引用能力 | 一次性喂完整材料，减少切分损失 |
| 图像 /视频初筛 | 多模态 | 只能靠视觉输入 |
| 敏感数据摘要 | 本地部署开源模型 | 数据不出内网 |
| 多语言资料 | 非英语语料强的模型 | 小语种质量差异极大 |

三条 “红线”在选型时必须确认：

**1\. 数据条款**：输入是否用于训练、保留多久、可否关闭。企业数据进消费级对话框是常见事故。

**2\. 可复现性**：能否固定模型版本与参数（温度、 top_p）。不能固定的模型不适合做需要复核的分析。

**3\. 降级风险**：厂商可能下线旧模型。 Bellingcat 就遇到过最擅长地理定位的模型被下架、替换后性能反而下降的情况 \[S6\]。所以关键任务要保留“当前基线模型 + 备选模型”两套，并每季度复测一次。

## 3.3 数据分级：什么东西可以贴进对话框

这是实操中最容易出事的一环。用一棵决策树解决。

|     |     |     |
| --- | --- | --- |
| 数据类型 | 能否进公有云模型 | 处理方式 |
| 完全公开的信息（新闻、官网、公开帖子） | 可以  | 直接使用 |
| 半公开（需登录才能看的内容、论坛内部版块） | 谨慎  | 去标识化后使用，或改用本地模型 |
| 客户提供的商业机密 | 不可以 | 本地模型 / 私有部署 / 合同覆盖的专有实例 |
| 个人敏感信息（身份证号、住址、生物特征） | 不可以 | 脱敏后再处理；原始数据留在受控库 |
| 未公开的调查结论、内部报告 | 不可以 | 仅本地模型，且关闭日志 |

一个简单判据： **如果这段内容出现在明天的新闻里会让你难堪，就不要粘贴到公有云对话框。**

## 3.4 工作区与命名规范

可复现性的基础是文件管理。推荐结构：

case-2026-0142/  
00-brief/ 委托书、 KIQ 、法律预检记录  
01-raw/ 原始抓取（只读，永不修改）  
02-normalized/ 清洗后的结构化数据（ CSV/JSON ）  
03-analysis/ 图谱、时间线、假设表  
04-verify/ 验证记录、截图、哈希  
05-report/ 交付物与附件  
log.md 操作日志：时间 (UTC) 、动作、工具、结果

命名规则： YYYYMMDDTHHMMZ\_ 来源 \_ 简述 \_ 哈希前 8 位 。例如 20261118T0320Z_weibo_post-a1b2c3d4.png 。截图必须同时保存页面 URL、抓取时间（UTC）与文件哈希，否则在需要举证时价值归零。

## 3.5 一条最小可用的工具栈

不追求大而全，先跑通闭环。

|     |     |     |     |
| --- | --- | --- | --- |
| 层   | 免费 /低成本方案 | 付费 /企业方案 | 说明  |
| 采集  | 浏览器 + RSS + 官方 API | 托管归因浏览、代理池 \[S9\] | 先解决 “能不能稳定拿到” |
| 存储  | SQLite / 本地文件夹 | PostgreSQL、对象存储 | 结构化才可分析 |
| 分析  | 通用大模型 + 表格工具 | Maltego、Fivecast、Recorded Future | 图谱类工具的价值在关系而非数据 |
| 监测  | RSS + n8n + 模型分级 | Dataminr、Zignal、Blackbird.AI | 实时性是核心指标 |
| 验证  | Google Lens / Yandex / SunCalc / Overpass | 商业取证套件 | 免费工具足够完成 80% 的核验 |
| 留证  | 截图 + 哈希 + 时间戳 | Hunchly、Maltego Evidence | 证据链比工具品牌重要 |

工具选型的正确顺序是： **先确定要回答的问题，再选工具**。反过来的结果通常是买了一堆账号，却说不清哪个工具解决了哪个问题。

## 第 4 章 主流程：五阶段 SOP

本章把情报周期落成可执行的六个阶段（原文五阶段 + 前置的立项）。每个阶段给出：输入、动作、AI 介入点、产出物、质检门。 **质检门不通过不得进入下一阶段**，这是防止返工的唯一有效机制。

## 4.1 阶段 0：立项与需求

**输入**：委托方的模糊需求。

**动作**：

**1.** 写清 “决策”，而不是“话题”。不是“了解一下这家公司”，而是“是否建议以 2 亿元估值投资，需在 10 个工作日内给出风险清单”。

**2.** 用 AI 把需求拆成 KIQ（关键情报问题）5—8 条，再拆 EEI（可观测指标）。

**3.** 做法律预检：涉及个人信息吗？涉及特殊类别数据吗？是否需要授权？留存多久？

**4.** 定义 “成功标准”与“停止条件”。

**AI 介入点**：需求拆解、 KIQ 生成、检查清单补全。

**产出物**：一页纸《情报需求书》，含 KIQ 表、范围边界、法律预检结论、交付格式。

**质检门**：委托方书面确认 KIQ；法律预检有结论（哪怕结论是“不涉及”）。

## 4.2 阶段 1：采集

**输入**：《情报需求书》。

**动作**：

**1.** 建 “源清单”：按表面网/深网/社交/公开记录/专业库五类，每类列 3—10 个具体源，标明访问方式与可信度先验。

**2.** 为每个 KIQ 建“查询矩阵”：语言 × 平台 × 时间窗 × 语法，形成可执行的查询清单（第 6 章）。

**3.** 执行采集， **边采边留证**： URL、UTC 时间、截图、哈希、摘要一句话。

**4.** 记录 “未获取”：哪些源打不开、哪些数据要付费、哪些被删除。负面结果同样重要。

**AI 介入点**：查询矩阵生成、多语言关键词扩展、页面正文抽取、批量摘要。

**产出物**： 01-raw/ 原始材料 + 采集日志 （含失败记录）。

**质检门**：每个 KIQ 至少有一个独立来源覆盖；所有材料可回溯到 URL 与时间；无来源不明的文件。

## 4.3 阶段 2：处理

**输入**：原始材料。

**动作**：

**1.** 去重（按内容哈希 + 相似度）、去噪（广告、导航、重复转载）。

**2.** 统一结构：时间统一 UTC、地点统一到“国家/一级行政区/城市”、人名保留原文与译名两列。

**3.** 翻译：只翻 “理解所需”的部分，保留原文关键词列。

**4.** 入库：一张主表（证据表） + 若干关系表（人物、组织、账号、事件、地点）。

**AI 介入点**：批量摘要、字段抽取（受 JSON Schema 约束）、翻译、实体归一。

**产出物**： 02-normalized/ 结构化数据集（ CSV/JSON）+ 数据字典。

**质检门**：随机抽 20 条，人工核对字段准确率；低于 90% 则退回调整提示词或改用专用工具。 **不要用通用模型直接产出实体表**，见 2.2 节的实证结论 \[S7\]。

## 4.4 阶段 3：分析

**输入**：结构化数据集。

**动作**：

**1.** 建实体关系图：节点 =人/组织/账号/域名/地址/事件，边=关系 + 证据编号 + 时间。

**2.** 建时间线：单一时间轴，冲突处并列呈现。

**3.** 提出假设：至少 3 个互斥假设（含“无异常”这个假设）。

**4.** 用 ACH（竞争性假设分析）逐条评估证据对每个假设的支持/削弱。

**5.** 标出 “信息缺口”：哪些关键问题目前无证据。

**AI 介入点**：关系抽取建议、时间线整理、矛盾检测、 ACH 表格初稿、缺口清单。

**产出物**：关系图、时间线、假设评估表、缺口清单。

**质检门**：每条结论边都挂着证据编号；至少有一个假设被证据削弱（如果一个假设 “完美解释一切”，通常是分析者被锚定了）。

## 4.5 阶段 4：验证

**输入**：分析结论。

**动作**：

**1.** 三源规则：关键结论至少 3 个 **相互独立** 的来源。转载同一通讯社不算独立。

**2.** Admiralty 评级：给每个来源与每条信息打分（第 10.3 节）。

**3.** 反向检索：图片 /引文/数字逐个反查，确认最早出处。

**4.** 红队：让另一个模型（或另一位同事）专门找漏洞，提示词见第 5.2 节 P6。

**5.** 引用回溯：每条断言必须能点开一手链接并看到原文摘句。

**AI 介入点**：红队攻击、矛盾清单、引用完整性检查。

**产出物**： 04-verify/ 验证记录表（断言 → 来源 → 评级 → 复核人）。

**质检门**： 0 条无源断言；0 条“C 级来源支撑的核心结论”；红队意见已逐条回应。

## 4.6 阶段 5：报告与分发

**输入**：验证后的结论。

**动作**：

**1.** 写 BLUF：第一段给出结论、置信度、建议动作（第 11.2 节）。

**2.** 正文按 “结论—依据—不确定性—建议”组织，不按“我查了什么”组织。

**3.** 附《来源与方法说明》：模型名称与版本、提示词版本、数据截止时间、已知局限。

**4.** 分发后收集反馈，回到阶段 0 修正 KIQ。

**AI 介入点**：结构改写、语言压缩、管理层摘要、多语言版本。

**产出物**：情报产品 + 方法附录 + 可复现包。

**质检门**：非专业人员能在 60 秒内说出结论；所有数字可追溯；敏感性审查通过。

## 4.7 一张流程图式的检查表

|     |     |     |
| --- | --- | --- |
| 阶段  | 一句话目标 | 最常翻车的地方 |
| 0 立项 | 把话题变成决策问题 | KIQ 写成关键词，导致后面全在漫游 |
| 1 采集 | 拿得到、留得住 | 只存截图不存 URL 和时间 |
| 2 处理 | 变得可分析 | 让模型直接产实体表，错误静默传播 |
| 3 分析 | 形成可证伪的假设 | 只有一个假设，证据只找支持它的 |
| 4 验证 | 把 “看起来对”变成“经得起问” | 三个来源其实是同一篇通稿 |
| 5 报告 | 让决策者 60 秒内能用 | 按调查过程写，而不是按决策需要写 |

## 第 5 章 提示词工程：把分析经验编码进提示词

## 5.1 六段式结构

OSINT 场景的提示词不要写“请帮我分析”，要用固定六段结构。这个结构的作用是 **把不确定性显式化**。

【角色】你是一名有十年经验的开源情报分析师，专长是 < 领域 \> 。  
【任务】 < 一句话，动词开头，可验收 \>  
【上下文】 < 已知事实，逐条编号；明确区分 " 已核实 " 与 " 待核实 ">  
【约束】  
1\. 只使用我提供的材料，不得引入外部事实；  
2\. 每条结论必须附原文摘句与来源编号；  
3\. 无法判断时输出 UNKNOWN ，不要猜测；  
4\. 区分 " 事实 " 与 " 推断 " ，推断需标注置信度（高 / 中 / 低）。  
【输出格式】 <JSON Schema 或固定表格列名 \>  
【自检】输出前检查：是否有无源断言？是否混淆了时间？是否把相关当成因果？

四个关键设计：

· **材料边界**： 只使用我提供的材料 这一句能砍掉大部分幻觉。配合 “材料不足时明确说不足”。

· **强制引用**：要求 “原文摘句”，让引用可以被肉眼比对，而不是只给一个链接。

· **UNKNOWN 通道**：给模型一个合法的 “不知道”出口，否则它只能用编造来填满格式。

· **事实 /推断分离**：这是情报产品的基本要求，也正好是模型最容易混淆的地方。

## 5.2 六个可直接复制的模板

### P1 需求拆解器

【角色】你是情报需求官（ Collection Requirements Manager ）。  
【任务】把下面的委托拆解为可执行的情报需求。  
【委托】 < 粘贴原始需求 \>  
【约束】  
\- 生成 5—8 个 KIQ ，每个 KIQ 必须能用 " 是 / 否 / 数值 / 清单 " 回答；  
\- 每个 KIQ 拆 2—4 个 EEI ， EEI 必须是可观测的公开信息；  
\- 标注每个 EEI 的可能来源类型（官网 / 监管 / 媒体 / 社交 / 专业库）；  
\- 指出 3 个最可能的信息缺口与对应的替代验证路径。  
【输出】表格： KIQ 编号 | 问题 | EEI | 来源类型 | 优先级 (高 / 中 / 低) | 备注

### P2 查询矩阵生成器

【角色】你是检索专家，精通 Google 高级运算符与各平台站内语法。  
【任务】为下列 KIQ 生成查询矩阵。  
【 KIQ 】 < 粘贴 \>  
【已知实体】公司名 / 品牌别名 / 域名 / 关键人名 / 产品名  
【约束】  
\- 语言覆盖：中文、英文、 < 目标国语言原文 \> ；  
\- 每条查询注明：平台、语法字符串、预期返回什么、为什么这样写；  
\- 只使用真实存在的运算符（ site: filetype: intitle: inurl: intext: before: after: AROUND() ）；  
\- 对每条查询给出 " 可能的误报类型 " ，方便人工快速筛除。  
【输出】表格：编号 | 平台 | 查询语句 | 语言 | 目标 | 误报预警  
【自检】逐条确认运算符拼写正确；不要发明运算符。

实操提示：模型偶尔会编造运算符（例如 related:keyword ）。 **生成后必须自己搜一次**，把不工作的删掉。这个动作只需两分钟，能避免后面几小时的无效采集。

### P3 结构化实体抽取（防幻觉版）

【角色】你是信息抽取引擎。  
【任务】从下面每条文本中抽取实体与事件，严格按 JSON 输出。  
【输入】 < 编号文本，逐条 \>  
【约束】  
\- 只抽取文本中明确出现的实体，不得推断、不得补全；  
\- 每个字段附 \`evidence\` （原文摘句， ≤30 字）与 \`confidence\` （ 0-1 ）；  
\- 文本未提及的字段填 null ，不要编造；  
\- 人名保留原文写法，另给 \`name\_zh\` （音译），无法音译填 null 。  
【输出 JSON Schema 】  
{"items":\[{"id":"","persons":\[{"name":"","name_zh":"","role":"","evidence":"","confidence":0}\],  
"orgs":\[\],"locations":\[{"name":"","country":"","evidence":"","confidence":0}\],  
"event":{"date":"","type":"","summary":""},"lang":"","flags":\[\]}\]}  
【自检】抽查 3 条： evidence 是否真的在原文中出现？ confidence 是否虚高？

这段提示词的关键是 evidence 字段：它把 “模型说了什么”变成“模型引用了什么”，审校成本从“重新读全文”降到“扫一眼摘句”。

### P4 时间线重建与矛盾检测

【角色】你是情报时间线分析师。  
【任务】把下列带日期的材料整理成单一时间线，并列出冲突。  
【材料】 < 逐条粘贴，含来源编号与原文日期 \>  
【约束】  
\- 统一为 UTC ，并在括号内保留原文时间表述；  
\- 标注时间精度：日 / 月 / 年 / 区间 / 推测；  
\- 同一事件多条来源时并列，不合并、不取舍；  
\- 单独列出 " 相互矛盾 " 的条目对，并说明矛盾类型（时间 / 地点 / 主体 / 因果）。  
【输出】 1) 时间线表 2) 矛盾清单 3) 时间线上的空白区间（值得继续查的时段）

### P5 竞争性假设分析（ACH）

【角色】你是情报分析方法论专家，熟悉竞争性假设分析（ ACH ）。  
【任务】针对问题 "< 核心判断 \>" ，构建并评估竞争性假设。  
【已知证据】 < 编号列表，含来源评级 \>  
【约束】  
\- 至少 3 个假设，必须包含 " 无异常 / 无关联 " 这一假设；  
\- 对每个 假设 × 证据 组合打分： +2 强支持 / +1 弱支持 / 0 无关 / -1 弱矛盾 / -2 强矛盾；  
\- 只允许使用所列证据，不得新增；  
\- 指出哪个证据对区分假设最关键（诊断性证据），以及哪个证据其实没有区分力。  
【输出】 1) 矩阵表 2) 各假设得分与简要理由 3) 关键诊断证据 4) 仍无法排除的假设

### P6 红队审查（专门用来打自己）

【角色】你是对抗性审稿人，任务是找出这份草稿的漏洞，而不是称赞它。  
【任务】审查下面的分析草稿。  
【草稿】 < 粘贴 \>  
【审查清单】  
1\. 哪些断言没有一手来源？逐条列出；  
2\. 哪些 " 事实 " 其实是推断或转述？  
3\. 是否存在时间错位（用旧信息描述新状态）？  
4\. 是否存在把相关当因果？  
5\. 是否存在来源不独立（同一稿件的多处转载被当成多源）？  
6\. 如果结论是错的，最可能错在哪一步？  
7\. 有哪些反证被忽略？  
【输出】按严重度排序的问题清单（严重 / 中等 / 轻微），每条给出修改建议。  
【约束】不要提出无法验证的质疑；每条质疑必须指向草稿中的具体句子。

红队提示词是整份指南里单位收益最高的一个。它的作用不是让 AI 更聪明，而是 **强制它站在反方**——这正是模型默认不会做的事。

## 5.3 五个让输出可核查的技巧

**1\. 强制引用原文摘句**：不接受只给链接或只给 “据报道”。

**2\. 要求列出“我不知道”**：在输出末尾加一节 UNKNOWN / 信息缺口 。

**3\. 固定参数并记录**：温度、模型版本、提示词版本写进项目日志，否则无法复现。

**4\. 双模型交叉**：同一材料让两个不同厂商的模型各做一次，差异处就是重点复核处。

**5\. 分步而非一次到底**：抽取、归并、评级分三次调用，比一次 “全都要”准确得多。

## 5.4 十个反模式

|     |     |     |
| --- | --- | --- |  
| 反模式 | 后果  | 替代做法 |
| “帮我全面调查这个人” | 得到看似全面的编造 | 拆成 KIQ 逐个查 |
| 一次粘贴 200 页让它“总结一切” | 丢失关键细节且不可核查 | 分块 + 逐块引用 |
| 不设输出格式 | 每次结构不同，无法入库 | 固定 JSON/表格 |
| 允许它 “补充背景知识” | 引入过时或错误事实 | 明确 “只用我给的材料” |
| 用模型判断真假 | 幻觉被当成结论 | 模型只做线索，人做认定 |
| 只看最终答案不看推理 | 无法发现中间跳步 | 要求给出证据链 |
| 用同一个模型既生成又审核 | 自我确认偏误 | 换模型 /换人做红队 |
| 把模型输出直接贴进报告 | 责任无法追溯 | 每条断言回到一手源 |
| 忽略模型版本变化 | 结论不可复现 | 记录版本并季度复测 |
| 让 Agent 自主无限扩线 | 成本失控、暴露风险 | 白名单 + 预算 + 人工确认 |

## 第 6 章 深度检索：让 AI 帮你“问对问题”

原文第 5 章把深搜定义为“专用运算符 + 定制爬虫 + 档案/API”。这一章把它拆成可执行的四个层次。

## 6.1 深搜的四个层次

|     |     |     |     |
| --- | --- | --- | --- |   
| 层次  | 找什么 | 典型手段 | AI 的作用 |
| L1 索引层 | 表面网页 | Google/Bing/Yandex、站内搜索 | 生成与优化查询语法 |
| L2 档案层 | 已删除、已改版、历史快照 | Wayback、缓存、GDELT、新闻库 | 生成时间窗检索、比对版本差异 |
| L3 数据层 | 结构化公开数据 | 政府开放数据、专利、招标、船讯、航班、卫星 | 解释字段、生成 API 调用、清洗 |
| L4 关系层 | 人与人、组织与组织的连接 | 公司注册、股权、诉讼、捐赠、域名 WHOIS | 设计关系假设与验证路径 |

多数人只做 L1，然后抱怨“搜不到”。真正的信息差在 L2 和 L3。

## 6.2 Google 运算符速查 + 让 AI 生成 dork

|     |     |     |
| --- | --- | --- |  
| 运算符 | 作用  | 例子  |
| site: | 限定站点 | site:gov.cn 采购 中标 |
| filetype: | 限定文件类型 | filetype:xlsx 员工 名单 |
| intitle: | 标题包含 | intitle:"index of" backup |
| inurl: | URL 包含 | inurl:admin login |
| intext: | 正文包含 | intext:" 内部资料 " |
| "..." | 精确匹配 | " 某某科技有限公司 " |
| OR / - | 或 / 排除 | (起诉 OR 判决) - 招聘 |
| before: after: | 时间窗 | after:2025-01-01 before:2025-06-30 |
| AROUND(n) | 邻近共现 | " 项目 " AROUND(5) " 回扣 " |
| \*  | 通配  | "\* 有限公司 法定代表人 \*" |

用第 5.2 节的 P2 模板生成查询矩阵后，必须做三件事：

**1\. 实测每一条**：运算符不存在或语法错误会静默返回零结果，看起来像 “没有信息”。

**2\. 记录命中数**：命中数异常大（ >10 万）说明查询太宽，异常小（0）说明语法错。

**3\. 保存查询**：查询语句本身是方法资产，下次同类项目可直接复用。

一个真实感的例子：查某公司海外子公司，与其搜公司名，不如搜「注册地址 + 董事姓名 + 成立年份」的组合，因为子公司往往不挂母品牌。让模型列出“子公司可能使用的命名模式”（地名+行业词、创始人姓名缩写、当地语言译名），命中率会明显提升。

## 6.3 多语言检索的四个并行通道

原文 10.3 节指出语言是全球化调查的主要障碍。实操中要四路并行，缺一路就会漏。

|     |     |     |
| --- | --- | --- |  
| 通道  | 做法  | 常见错误 |
| 原文关键词 | 让模型给目标语言的 **原生词** （不是直译） | 用中文直译词去搜外语内容 |
| 音译变体 | 人名 /地名的多种罗马化拼写 | 只试一种拼写 |
| 地名别名 | 历史名称、殖民时期名称、当地俗称 | 只用现行官方名 |
| 本地平台 | 目标国的本土社媒、论坛、招聘站 | 只用 Google + 英文平台 |

提示词片段：

【任务】为目标实体生成多语言检索词表。  
【实体】 < 名称 \>  
【约束】  
\- 对每种语言给出：原生写法、拉丁转写、常见误拼、缩写；  
\- 给出 3 个该语言中最可能讨论该实体的本地平台；  
\- 标注哪些词是中性词、哪些词带有立场（避免用带立场的词导致样本偏差）。  
【输出】表格：语言 | 原生词 | 转写 | 误拼 | 平台 | 立场标注

**样本偏差提醒**：如果只用带贬义的词去搜，你当然只能搜到负面信息。这是 OSINT 中最隐蔽的分析错误之一，且会被 AI 放大——因为它会顺着你的用词继续生成同类查询。

## 6.4 时间维度：最被低估的一维

同一个主体在不同时间点可能是完全不同的样子。三个动作：

**1\. 时间窗切分**：把长周期切成季度，逐窗检索，观察变化点而不是看总量。

**2\. 快照比对**： Wayback 取同一 URL 的多个版本，让模型比对差异（删除的段落往往比新增的更有信息量）。

**3\. 事件对齐**：把检索结果与公开事件日历（财报、监管处罚、人事变动）对齐，寻找 “事件前后言论变化”。

## 第 7 章 图像、视频与地理定位

原文第 9 章把计算机视觉概括为“识别人脸、物体、环境，提取元数据，检测异常活动”。这一章给出可操作的验证链，因为 **图像是最容易被伪造、也最容易被 AI 自信误判的领域**。

## 7.1 三层验证链

|     |     |     |
| --- | --- | --- |  
| 层   | 要回答的问题 | 手段  |
| 来源链 | 谁最早发的？原始文件是什么？ | 反向图搜、平台时间戳、转发路径、账号历史 |
| 内容链 | 画面里有什么矛盾？ | 阴影方向、天气、植被、车牌制式、文字语言、建筑风格 |
| 地理链 | 具体在哪？ | 地形匹配、街景、 OSM、卫星影像、地标三角定位 |

三层必须都过。只做地理定位是最常见的错误 ——你能证明“这个地点存在”，但不能证明“这张照片拍于该地该时”。

## 7.2 AI 能做与不能做

**能做**：生成候选地点清单并排序、识别画面文字（ OCR）、判断大致气候带与建筑风格、比对两张图是否同一地点、把视频关键帧批量转文字描述。

**不能做**：给出可信的精确坐标、判断图片是否 AI 生成（检测器只是概率信号）、确认拍摄时间。

Bellingcat 的测试给出了一个值得记住的量级：在 500 次定位测试中，多数模型在某个时点给出过幻觉，最好的模型也会自信地指错；而且新一代模型未必更强 \[S6\]。所以正确用法是 **把模型当地点假设生成器**，把验证交给地图与街景。

## 7.3 八步工作流

**1\. 取原图**：不要用截图，找原始上传（平台压缩会破坏元数据）。

**2\. 读元数据**： EXIF、GPS、设备型号、软件痕迹。注意：社交平台通常已剥离。

**3\. 反向图搜三件套**： Google Lens（含 AI Mode）、Yandex（人脸与场景强）、Bing Visual。三者结果常不重叠。

**4\. 找最早出处**：按时间排序，找第一个发布者，而不是转发量最大的。

**5\. 文字与标识**：路牌、店招、车牌、制服、广告语言 → 缩小到国家/地区。

**6\. 地形与建筑**：山脉轮廓、海岸线、屋顶样式、电线杆形制 → 缩小到城市。

**7\. 精确匹配**： Google Earth / Mapillary / OSM Overpass 查询特定地物组合；用 SunCalc 校验阴影与日期是否自洽 \[S19\]。

**8\. 写验证记录**：每个判断附截图与理由，标注 “已确认/可能/排除”。

工具清单可参考 Bellingcat 维护的在线调查工具包 \[S18\]，它按卫星影像、地图、图像验证等场景分组，更新频率高，比任何“十大工具”榜单更可靠。

## 7.4 三个高频失败模式

|     |     |     |
| --- | --- | --- |  
| 失败模式 | 表现  | 对策  |
| 相似地标陷阱 | 两个城市有同款摩天轮 /同款海滩 | 找 “独一无二”的组合特征，而非单一地标 |
| 旧图新用 | 三年前的照片被当作今日现场 | 比对天气、施工进度、植被、车辆型号 |
| AI 自信错误 | 模型给出精确到街道的错误答案 | 只采信 “可被地图验证”的部分 |

## 7.5 合成内容与深伪

检测工具（专用检测器、平台标注、 C2PA 内容凭证）只能提供 **信号**，不能提供 **结论**。可靠的判断顺序是：

**1.** 有没有内容凭证（ C2PA）？没有不等于假，有也要看签名主体。

**2.** 原始上传者是谁？账号历史是否可信？

**3.** 是否有第二视角、第三视角的独立影像？

**4.** 物理一致性：光照、阴影、反射、声音与口型。

**5.** 动机分析：谁受益于这条内容被相信？

**结论表述纪律**：在没有技术取证的情况下，只能说 “未能验证其真实性”，不能说“这是假的”。这两句话在法律责任上完全不同。

## 第 8 章 社交网络、叙事与协同行为

原文 10.2 节把社交媒体称为“数据金矿”，并提到 AI 可识别协同虚假信息活动。这一章给出可操作的账号画像与协同识别方法。

## 8.1 账号画像三张表

|     |     |     |
| --- | --- | --- |  
| 表   | 字段  | 用途  |
| 资料表 | 昵称、 ID、简介、注册时间、所在地自述、外链、头像哈希 | 身份线索 |
| 行为表 | 发帖频率、时段分布（换算时区）、语言、设备标识、互动对象 Top20 | 行为指纹 |
| 网络表 | 关注 /被关注、转发来源、共同出现、群组 | 关系结构 |

三张表交叉，才能从 “这个账号说了什么”走到“这个账号是谁、属于哪个群体”。

**时区推断** 是个便宜且有效的技巧：把发帖时间按 UTC 画出 24 小时分布，活跃峰值通常对应作息时间，可反推大致时区，与自述所在地比对即可发现矛盾。

## 8.2 协同行为的六个信号

|     |     |     |
| --- | --- | --- |  
| 信号  | 观测方法 | 强度  |
| 时间同步 | 多条内容在分钟级窗口内集中发布 | 中   |
| 文案高度相似 | 文本相似度聚类，含相同错别字 | 强   |
| 账号同龄 | 注册时间集中在同一周 | 强   |
| 转发结构异常 | 少数账号贡献大部分放大 | 中   |
| 跨平台同步 | 同一内容在多个平台同时出现 | 中   |
| 叙事模板一致 | 相同的框架、相同的替罪羊、相同的行动号召 | 弱（需结合其他） |

任何单一信号都不足以判定 “协同”。正确表述是“存在协同行为的迹象（3 项信号）”，并列出信号清单。

## 8.3 工具与分工

|     |     |     |
| --- | --- | --- |  
| 任务  | 工具  | 说明  |
| 账号自动化评分 | Botometer、BotSlayer 类工具 | 概率评分，仅作筛选 \[S10\] |
| 关系图谱 | Maltego、ShadowDragon、Social Links | 图谱工具的价值在关系可视化与留证 |
| 叙事监测 | Blackbird.AI、Zignal、Fivecast | 商业平台，适合持续监测 \[S9\] |

Maltego 在 2025 年 5 月收购了网页证据采集工具 Hunchly，这类整合说明行业趋势是“采集—分析—留证”一体化 \[S9\]。对小团队而言，未必要买全套，但 **留证环节不能省**。

## 8.4 叙事解构提示词

【角色】你是叙事分析员，熟悉信息操作与框架理论。  
【任务】分析下列 200 条帖子（已去重）的主导叙事。  
【材料】 < 逐条：时间 | 账号 | 文本 \>  
【约束】  
\- 归纳 5—8 条叙事主线，每条给：核心主张、情绪基调、归因对象、行动号召、出现频次；  
\- 每条主线附 2—3 条代表性原帖（含账号与时间）；  
\- 标出叙事之间的演化关系（哪条先出现、哪条由哪条衍生）；  
\- 单独列出 " 反叙事 " （反驳这些主张的内容）及其规模；  
\- 不做真伪判断，只做结构描述。  
【输出】表格 + 演化说明 + 反叙事规模估计

注意最后一条约束： **叙事分析不判断真假**。真假是事实核查的活，混在一起会让整份分析失去可信度。

## 8.5 伦理红线

**1.** 不针对普通公民做画像，除非与公共议题直接相关且符合比例原则。

**2.** 不公开可识别个人的敏感信息（住址、医疗、性取向、家庭成员）。

**3.** 不参与、不诱导、不挑衅；观察者不变成参与者。

**4.** 马甲账号不用于套取信任。

**5.** 未成年人一律特殊处理，默认不采集。

## 第 9 章 自动化：把重复劳动交给机器

## 9.1 自动化分级

|     |     |     |     |
| --- | --- | --- | --- |   
| 级别  | 描述  | 人的角色 | 适用场景 |
| L0  | 全手工 | 全部  | 高敏感、一次性调查 |
| L1  | 脚本采集 + 人工分析 | 分析  | 定期监测、批量抓取 |

## 9.3 n8n 编排：不写代码的版本

如果团队没有开发资源，用 n8n 搭同样的流程，节点顺序如下：

**1\. Schedule Trigger**：每小时或每天。

**2\. RSS Read**：多个源，合并。

**3\. Remove Duplicates**：按 link 去重。

**4\. IF**：关键词匹配，过滤明显无关项。

**5\. Basic LLM Chain / HTTP Request**：调用模型做分级与摘要，要求 JSON 输出。

**6\. Item Lists + Sort**：按分数排序。

**7\. Google Sheets / 飞书多维表格 / Slack / 邮件**：落地与推送。

**8\. Error Trigger**：失败告警，避免 “以为在跑其实挂了”。

n8n 官方社区有现成的“RSS + AI 摘要 + 通知”模板可直接改 \[S11\]。要点是把提示词与输出格式写在节点里并版本化，而不是每次手改。

## 9.4 自建：Taranis AI

如果需要一个 **完全可控、开箱带 RAG 问答** 的开源 OSINT 平台，Taranis AI 是当前较成熟的选择：它把新闻采集、NLP 增强（实体识别、摘要、故事聚类）、RAG 问答、任务队列整合在一起，采用 EUPL 许可证，且对 CVE、APT、IoC 等网络安全术语有专门识别 \[S12\]。适合做威胁情报日报与舆情监测的中台。

部署要点： Docker Compose 起服务，Redis 做队列，先小规模接 10—20 个源跑通，再扩源。 **不要一上来接 500 个源**——噪声会把分析员淹没，这正是“数据过载”的典型症状 \[S8\]。

## 9.5 扩线自动化：SpiderFoot 与 Maltego

|     |     |     |
| --- | --- | --- |  
| 工具  | 适合  | 注意  |
| SpiderFoot | 域名 / IP / 邮箱的自动扩线，200+ 模块 | 结果噪声大，需人工剪枝；扫描行为可能暴露 |
| Maltego | 实体关系图谱 + 120+ 数据伙伴 | 付费数据源价值高；图谱好看 ≠结论正确 |
| theHarvester / Amass | 子域与邮箱枚举 | 仅用于自有或已授权资产 |

自动化扩线的最大风险不是技术，而是 **暴露**：大规模扫描会触发目标告警，也可能违反平台条款。授权范围内、低速、分批，是三条底线。

## 9.6 Agent 化的四条护栏

如果要走到 L3（让 Agent 自主多步执行），必须同时具备以下四条，缺一不可：

**1\. 工具白名单**：只允许调用预定义的工具与域名，禁止任意 URL 抓取。

**2\. 预算与步数上限**：单次任务最多 N 步、M 次模型调用、K 分钟。

**3\. 关键动作人工确认**：发送、注册、上传、付款、对外互动一律中断等人确认。

**4\. 完整审计日志**：每步的输入、输出、工具、耗时全部落盘。

依据是 OWASP 的智能体应用风险清单（2026 版）与 LLM 应用风险清单中的“提示词注入”条目：当 Agent 会读取外部网页时，网页里藏的指令可能改变它的行为，这叫间接提示词注入 \[S4\]\[S5\]。防御手段不是“让模型更聪明”，而是 **架构上不信任外部内容**：把抓取到的网页内容当作数据而非指令，用结构化解析剥离指令性文本，并对工具调用做硬性白名单。

## 第 10 章 验证与防幻觉：给 AI 输出上三道锁

这一章是全篇最重要的部分。前面所有效率提升，都会被一次 “引用了一个不存在的来源”摧毁。

## 10.1 幻觉的四种形态

|     |     |     |
| --- | --- | --- |  
| 形态  | 表现  | 识别方法 |
| 编造来源 | 给出不存在的报道、论文、链接 | 逐条点开；链接 404 或内容不符 |
| 张冠李戴 | 真实来源，但内容不属于该来源 | 在原文中搜关键句 |
| 时间错位 | 用旧信息描述新状态 | 核对发布日期与事件时间 |
| 过度概括 | “多方证实”“业内人士称” | 追问 “哪几方？原话是什么？” |

四种形态里， **张冠李戴** 最难发现，因为它看起来最可信。唯一的对策是强制摘句比对。

## 10.2 三源规则与“独立性”判定

关键结论至少三个来源，且必须 **相互独立**。独立性判定：

|     |     |
| --- | --- | 
| 情况  | 是否独立 |
| 三家媒体各自采访了不同当事人 | 是   |
| 三家媒体转载同一通讯社 | 否   |
| 官方通报 + 媒体转述官方 | 否（实为一个来源） |
| 官方通报 + 独立媒体调查 + 第三方数据 | 是（ 3 个） |
| 同一人在多个平台发同样内容 | 否   |

实操技巧：让模型画 “来源血缘图”——谁引用了谁。它做这件事比人快得多，而且这是纯文本比对任务，幻觉风险低。

## 10.3 Admiralty 评级落地

北约 Admiralty 体系用两个字符描述一条信息：来源可靠性（A—F）+ 信息可信度（1—6）。中文环境常用“甲/乙/丙”或“A/B/C”简化版。完整表如下 \[S20\]：

|     |     |     |     |
| --- | --- | --- | --- |   
| 来源可靠性 | 含义  | 信息可信度 | 含义  |
| A   | 完全可靠 | 1   | 已被其他来源确认 |
| B   | 通常可靠 | 2   | 很可能是真的 |
| C   | 相当可靠 | 3   | 可能是真的 |
| D   | 通常不可靠 | 4   | 存疑  |
| E   | 不可靠 | 5   | 不大可能 |
| F   | 无法判断 | 6   | 无法判断 |

**写法示例**： B2 = 通常可靠的来源提供、很可能是真的信息。报告中对每条关键信息标注两字符，并注明理由，例如“B2（该公司官网公告，与两家独立媒体报道一致）”。

**常见错误**：只标信息可信度、不标来源可靠性；或者把所有官方来源一律标 A——官方来源在自身利益相关议题上未必可靠。

## 10.4 引用回溯：一条断言一条链

每条进入报告的断言，必须有四件套：

**1\. 可点击的一手链接** （不是搜索结果页、不是转载）。

**2\. 原文摘句** （不超过 30 字，能直接比对）。

**3\. 抓取时间（UTC）与文件哈希** （防删除、防篡改）。

**4\. 评级（A—F / 1—6）与复核人**。

一个可执行的检查动作：把所有断言的摘句复制到一个文本文件，用查找功能在原始材料里逐个搜。搜不到的，就是可疑的。

## 10.5 红队机制

红队不是 “再看一遍”，而是 **有明确攻击目标的结构化审查**。三种做法，按成本从低到高：

|     |     |     |
| --- | --- | --- |  
| 做法  | 成本  | 效果  |
| 用 P6 提示词让另一个模型攻击草稿 | 10 分钟 | 能抓出 80% 的无源断言与逻辑跳跃 |
| 同事交叉审阅（不看你的结论，只看证据） | 1 小时 | 能抓出锚定与确认偏误 |
| 正式 ACH 复盘（把所有假设重跑一遍） | 半天  | 用于高价值 /高争议结论 |

**关键纪律**：红队意见必须逐条书面回应（接受 /部分接受/不接受 + 理由），否则红队会退化成形式主义。

## 10.6 置信度语言对照表

情报产品的措辞必须与证据强度匹配。建议统一使用下表，避免 “可能”“或许”“疑似”混用。

|     |     |     |
| --- | --- | --- |  
| 措辞  | 概率区间 | 适用条件 |
| 几乎确定 | 95%—99% | 多源独立 + 一手文件 |
| 很可能 | 80%—95% | 2—3 个独立来源，无矛盾 |
| 可能  | 55%—80% | 单一可靠来源或间接证据链 |
| 不大可能 | 20%—45% | 证据倾向于否定，但存在缺口 |
| 几乎不可能 | 5%—20% | 强反证 |
| 无法判断 | —   | 信息不足，明确写出缺口 |

**禁用词**： 据悉 、 有消息称 、 业内人士表示 、 疑似 （除非明确说明疑点）。这些词在情报产品里等于 “我没有来源”。

## 第 11 章 报告：从“资料堆”到“情报产品”

## 11.1 三类产品与结构

|     |     |     |     |
| --- | --- | --- | --- |   
| 类型  | 长度  | 结构  | 使用场景 |
| 预警  | 1 页 | 事件 —影响—时间窗—建议动作 | 突发、威胁情报 |
| 画像  | 3—8 页 | 身份 —关系—行为—风险点—证据附录 | 尽职调查、人员核查 |
| 评估  | 5—20 页 | BLUF—依据—竞争假设—不确定性—建议 | 投资、合规、政策 |

三类产品的共同点： **第一段必须是结论**，而不是背景。

## 11.2 BLUF 写法与样板

BLUF（Bottom Line Up Front）的意思是“结论先行”。中文情报产品常见毛病是按调查顺序写，读者要读到第 8 页才知道结论。

样板（供应商风险为例）：

**结论**：目标公司 E 的实控人很可能（80%—95%）通过两层离岸架构与已被列入制裁名单的实体存在关联，建议在签约前要求补充最终受益人声明，并将付款路径改为经第三方监管账户。

**依据**： ① 2025 年 11 月注册文件显示其唯一股东为 BVI 公司 X（A1）；② X 的董事与 Y 公司董事为同一人（B2，两名独立来源）；③ Y 于 2024 年被列入某国制裁清单（A1，官方公告）。

**不确定性**：未取得 X 的完整股东名册，无法排除代持；关联强度依赖董事同一人这一单一环节。

**建议**：暂缓签约；补充尽调项见附录 2。

这个样板体现了四个要点：结论带置信度、依据带评级、不确定性单独成段、建议可执行。

## 11.3 图谱与图表的表达规范

· 节点不超过 40 个，超过就分图；否则读者什么也看不出来。

· 每条边标注 **关系类型 + 证据编号**，没有证据的边用虚线并注明 “待验证”。

· 时间线用统一时区（ UTC），并在图注注明。

· 地图必须带比例尺与日期；卫星图注明传感器与获取时间。

· 图表标题写 “结论”，不写“数据”——例如“关联集中于三家离岸实体”优于“实体关系图”。

## 11.4 可复现性附件

一份专业报告应附带《来源与方法说明》，包含：

**1.** 数据截止时间与抓取时间。

**2.** 使用的模型名称、版本、关键参数。

**3.** 提示词版本（可附在附录，方便他人复跑）。

**4.** 来源清单与评级。

**5.** 已知局限与未覆盖范围。

**6.** 数据处理脚本（如适用）。

这份附件的作用不只是合规，它也是 **最好的质量证明**：能复现的分析，才谈得上可信。

## 11.5 八条常见退稿原因

|     |     |     |
| --- | --- | --- |  
| 原因  | 表现  | 修正  |
| 无结论 | 通篇是资料汇编 | 补 BLUF |
| 结论超出证据 | “必将”“一定” | 改置信度语言 |
| 来源不独立 | 三篇通稿当三源 | 做血缘图 |
| 时间错位 | 用 2023 年数据说 2026 年 | 标注数据日期 |
| 不可执行 | 建议是 “加强关注” | 改为具体动作与责任方 |
| 术语堆砌 | 读者看不懂 | 换管理层语言 |
| 缺不确定性 | 看起来什么都知道 | 单列缺口 |
| 无法复现 | 给不出原始链接 | 补证据附录 |

## 第 12 章 安全、合规与伦理

## 12.1 OPSEC：先保护自己

|     |     |     |
| --- | --- | --- |  
| 风险  | 后果  | 措施  |
| IP 暴露 | 目标识别调查者、反向施压 | 住宅代理 /受管出口；不用公司出口查敏感目标 |
| 浏览器指纹 | 跨项目关联 | 独立容器 /虚拟机；禁用同步 |
| 账号关联 | 马甲被识破 | 独立邮箱、独立设备环境、行为节奏拟人 |
| 文件元数据 | 泄露内部信息 | 对外文件清除作者、路径、修订记录 |
| 模型侧泄露 | 查询内容被平台记录 | 敏感查询用本地模型；关闭 “改进服务”选项 |

## 12.2 提示词注入与数据投毒

这是 AI 时代新增的攻击面，且直接命中 OSINT 的核心动作—— **阅读陌生人写的内容**。

|     |     |     |
| --- | --- | --- |  
| 攻击  | 机制  | 防御  |
| 直接注入 | 用户在对话中诱导模型越权 | 系统提示与用户输入分离；输出过滤 |
| 间接注入 | 网页 /PDF/邮件中藏指令，被模型读取后执行 | 抓取内容按 “数据”处理，剥离指令性文本；工具白名单 \[S4\] |
| 数据投毒 | 污染训练或检索语料，植入错误结论 | 多源交叉；对检索库做来源审计 |
| 过度代理 | Agent 拥有过大权限，被利用执行危险动作 | 最小权限；关键动作人工确认 \[S5\] |

实操建议： **任何让模型 “读网页然后行动”的流程，都必须假设网页是恶意的**。至少做到三点 ——只读白名单域名、抓取结果先做纯文本化、Agent 不持有写权限与支付权限。

## 12.3 数据合规要点

|     |     |     |
| --- | --- | --- |  
| 议题  | 要点  | 落地动作 |
| 合法性基础 | 公开信息 ≠可任意处理；仍需合法利益评估 | 项目立项时写 “处理目的与必要性” |
| 最小化 | 只采集与 KIQ 相关的字段 | 采集清单里逐字段写 “为什么需要” |
| 留存期限 | 设定到期删除 | 项目结束 N 天后归档或销毁 |
| 跨境传输 | 数据出境需评估 | 优先本地模型；跨境前做合规判断 |
| 特殊类别数据 | 生物特征、健康、政治观点等 | 原则上不采集；确需时走单独评估 |
| 第三方数据 | 采购的数据源可能本身违规 | 审查供应商合规声明 |

中国《个人信息保护法》与欧盟 GDPR 在“最小必要”“目的限定”“单独同意”上高度一致。跨辖区项目应按 **最严标准** 执行，避免 “在 A 国合法、在 B 国违法”。

## 12.4 人脸识别：一条不能靠“技术可行”决定的线

英国信息专员办公室（ ICO）的立场很明确：根据英国 GDPR，为 **唯一识别个人** 而处理生物特征数据，除 Article 6 的合法性基础外，还需满足 Article 9 的特定条件 \[S13\]。换言之，人脸搜索不是“搜一下而已”，而是高风险处理活动。

判断顺序：

**1.** 目的是否涉及唯一识别个人？是 → 进入高风险路径。

**2.** 是否有法律授权或明确同意？没有 → 原则上不做。

**3.** 是否符合比例原则（更轻的手段能否达成）？不能 → 不做。

**4.** 是否有留存与销毁机制？没有 → 不做。

**实用替代**：多数调查并不需要人脸识别。用 “账号行为 + 公开声明 + 文件记录”往往能得到更可采信的结论，且法律风险低一个数量级。

## 12.5 伦理四问

在每个项目启动时问四句话，写进立项文档：

**1\. 公共利益**：这项调查服务的是什么公共利益？能否说清楚？

**2\. 比例原则**：侵入性最小的手段是什么？我是否用了更重的？

**3\. 最小伤害**：如果出错，谁会被伤害？如何降低？

**4\. 可解释**：如果被调查者要求解释，我能说清方法与依据吗？

四问里任何一问答不上来，就应该暂停，而不是 “先查了再说”。

## 12.6 供应链与模型风险

· **数据出境**：使用境外模型 API 意味着输入内容出境，需按组织政策判断。

· **训练数据污染**：模型可能带有偏见或过时认知，尤其在地区冲突、民族、宗教议题上。

· **供应商锁定**：模型下线、价格调整、条款变更都可能让流程失效（第 3.2 节）。

· **日志留存**：部分平台保留输入输出用于风控，敏感项目需确认。

|     |     |     |

## 13.4 四个可量化指标

|     |     |     |
| --- | --- | --- |  
| 指标  | 定义  | 目标  |
| 时效  | 从事件发生到预警发出 | 按业务定，舆情类 < 2 小时 |
| 命中率 | 预警中被确认为真的比例 | \> 60%，低于则调整阈值 |
| 返工率 | 因证据不足被退回的比例 | < 15% |
| 幻觉拦截率 | 红队发现的无源断言 / 总断言 | 应逐季下降，说明流程在改善 |

## 13.5 六种失败模式与对策

|     |     |     |
| --- | --- | --- |  
| 失败模式 | 症状  | 对策  |
| 工具收藏家 | 买了 20 个账号，没跑通一个流程 | 先定 KIQ，再选工具 |
| 自动化幻觉 | 日报天天出，没人看 | 加 “高信号阈值 + 人工抽检” |
| 只做 L1 检索 | 搜不到就说 “没有信息” | 补 L2/L3 源 |
| 单假设锚定 | 所有证据都支持一个结论 | 强制 ACH，含“无异常”假设 |
| 模型依赖 | 模型一升级，结论全变 | 记录版本 + 季度复测 |
| 合规后置 | 上线后才发现不能采 | 立项即做法律预检 |

## 13.6 结语

原始文档结尾写道： OSINT 站在传统与创新的十字路口，AI 加速了调查过程，但伦理与人工监督不可放弃。一年半过去，这句话被实证研究反复确认：AI 在采集与初筛上确实有效，在验证与判断上仍然不可托付 \[S3\]\[S8\]。

所以这份指南的最终建议只有一句： **把 AI 用在它能被验证的地方，把不可验证的地方留给人，并把“如何验证”写进流程，而不是写进口号。**
