Alpine于11月5日公开密码认证绕过问题，特定musl、非PAM及账号配置组合下，攻击者可能无需知道密码就能登录。各分支修复包已发布，管理员应核实实际暴露条件，更新并重启sshd，同时排查异常登录。

一、这次预警是什么：先划清影响边界

SSHole不是“所有安装OpenSSH的服务器都能被直接登录”。OpenSSH 10.6p2发布说明明确将问题指向使用musl且未启用PAM的特定Linux环境，并说明在sshd中提供了规避措施；项目认为根因位于sshd之外。\[1\]

Alpine的默认openssh-server构建不带PAM，因此需要优先检查。装了openssh-server-pam但实际配置为UsePAM no的机器，也不能仅凭包名排除。\[2\]

| --- | --- |
| 问题名称 | SSHole，研究者写作“\*sshole” |
| 风险类型 | 密码认证绕过 |
| 上游处置 | OpenSSH 10.6p2，11月5日发布 |
| 利用前提 | 认证方式、账号状态和网络可达性等条件同时满足 |

研究者公开复现，不等于已观察到真实入侵；未见公告确认在野攻击，也不能作为推迟修复的理由。\[3\]

Alpine初始公告写明发布时尚未分配CVE。本次未完成后续编号及评分的权威核对，正文不引用尚未核实的CVE编号或CVSS分数。\[2\]

## 触发条件核查

二、哪些条件需要同时核查

先看服务器是否使用musl、是否运行受影响的sshd认证路径，再检查有效配置与账号状态。依据Alpine公告，需要重点核对以下组合：\[2\]

**未使用PAM，且服务端仍允许密码认证。** 也就是默认openssh-server，或PAM版配合UsePAM no，并且有效PasswordAuthentication为yes。

**存在密码字段为单个星号的目标账号，同时存在相关密码哈希账号。** 公告列出的另一条件是本机至少一个账号保存了以 `$5$` 或 `$6$` 标识的密码哈希。具体账号是否可以登录，还需结合访问限制和认证规则判断。

攻击者还需要能够访问SSH服务并知道目标账号名。排查对象应包括自定义SSH端口，而不只检查22端口。

这里容易误判的是：“我们都用密钥，没人在SSH里输密码。”这描述的是人的习惯，不是服务端拒绝密码认证的证据。 **使用密钥登录，不等于已关闭密码认证。**

root也不是无条件可被直接登录。官方说明，默认PermitRootLogin prohibit-password对root提供保护；放开为yes时，才需要结合其他条件评估该账号路径。普通账号的登录风险则仍需单独处理。\[2\]

不运行sshd的Alpine容器，不属于这条SSH登录路径的受影响对象。容器、云主机和其他musl环境都应以实际服务和配置为准，不能仅凭镜像名称判定受影响。

## 漏洞原理

三、问题为什么会出现在“没有密码”的账号上

研究者的分析指出，在相关非PAM路径中，sshd调用crypt()计算密码结果并进行比较；某些错误处理会返回星号，而账号保存的字段也可能恰好是星号，导致错误结果被当作匹配结果。\[3\]

这是多个组件和账号约定组合产生的问题。不能据此把所有禁用密码的账号都看作同一状态，也不建议为消除扫描提示，直接批量改写账号字段。

尤其是依赖密钥登录的运维账号，账号状态变更可能影响管理通道。更稳妥的处理是采用已发布修复，或在验证密钥可用后关闭密码认证入口，并保留恢复手段。

## 修复包升级

四、修复包已发布：按Alpine分支核对

Alpine于11月5日发布3.21.10、3.22.8、3.23.8和3.24.4等更新，明确要求运行sshd的用户更新并重启；各分支openssh修复包如下。\[2\]\[4\]

| Alpine分支 | 公告列出的修复包版本 |
| --- | --- |
| edge | 10.6_p2-r0 |
| 3.24 | 10.3_p1-r2 |
| 3.23 | 10.2_p1-r1 |
| 3.22 | 10.0_p1-r11 |
| 3.21 | 9.9_p2-r1 |
| 3.20 | 9.7_p1-r6 |
| 3.19 | 9.6_p1-r3 |
| 3.18 | 9.3_p2-r4 |
| 3.17 | 9.1_p1-r7 |
| 3.16 | 9.0_p1-r6 |

**按所属分支核对修复包，不必强行跨分支升级到10.6p2。** 上表是本次修复基线，后续同分支更新应以官方仓库和公告为准；有旧分支补丁，不代表该分支重新获得完整常规维护。

实施时先确认系统分支和仓库配置，查询实际安装的服务端及关联包，按本单位变更流程升级。不要通过修改仓库混装不同分支的软件包来追求某个版本号。

## 政企处置流程

五、政企单位按这个顺序处置

**第一，列出资产，并落实到系统及维护负责人。** 建议把公网云主机、边缘节点、运维镜像和容器内sshd一起盘点，记录操作系统分支、服务端包版本、认证路径、SSH访问来源和业务责任人。

要求原厂及第三方维护单位提供实际运行证据，而不是只回复“已处理”。建议至少回传包版本、有效认证配置、重启时间、新连接结果和日志核查情况；身份与账号信息按必要范围脱敏。

**第二，更新前确认备份、控制台及有效登录通道。** 保留当前会话，先验证另一条密钥登录连接可用，再安排变更。保存配置和恢复办法，确认云控制台或带外管理可以接管，避免修复时把管理员锁在外面。

**第三，无法立即更新时，关闭密码认证并核验生效。** Alpine给出的临时措施是PasswordAuthentication no。\[2\] 同时可按业务需要收紧SSH来源地址，但仅改端口或限制来源不等同完成修复。

配置检查不能只搜索某个文件里的一个配置行。Include、Match及启动参数可能影响实际结果。OpenSSH手册说明， `sshd -T` 可以输出有效配置， `-C` 可以代入连接条件检查相应Match规则， `sshd -t` 用于配置和密钥健全性检查。\[5\]

对于具体账号与来源，应按本机版本的手册核对有效结果，再执行服务变更。不要只新增一份配置文件就认定已生效，也不要在未部署相应认证组件时简单切换UsePAM。

**第四，升级后重启sshd，再测试新建连接。** 仅替换磁盘上的软件包，不能证明监听服务已经换成修复版本。Alpine的OpenRC服务命令为 `rc-service sshd restart` ，执行前仍需完成配置检查及恢复准备。\[2\]\[4\]

重启后检查服务状态、实际运行程序和有效配置；新建合法密钥连接，验证运维作业和文件传输。若实施了禁用密码认证，还应确认对应账号与来源不再获得该认证方式。运行sshd的容器需更新镜像并重建部署，不能只更新宿主机包。

若变更失败，恢复必要业务和管理通道后继续采取临时控制，并明确下一次窗口。不要把“恢复旧包、继续暴露原入口”作为整改完成的结论。

## 异常登录排查

六、排查异常登录，不能只盯着失败记录

官方建议检查无密码账号出现的 `Accepted password for` 成功日志，并复核doas使用及异常新增账号、文件和授权密钥。\[2\] 这些是核查线索，不是无需关联分析就能成立的入侵结论。

**保留成功登录、提权及账号变更记录，核对异常来源。** 除默认日志位置外，还应检查本单位实际配置的集中日志、容器日志和审计记录，关联账号、时间、来源地址、权限及后续操作。

发现不符合该账号用途的成功密码登录，应及时保全证据并按事件流程隔离、研判；确认或无法排除入侵时，由应急人员评估凭据轮换、环境恢复及后续排查。升级可以阻止继续利用，不能自动清除此前可能留下的访问权限。

七、一张可发给维护单位的核查便签

请核查运行sshd的Alpine及相关musl资产：确认系统分支、实际服务端包、PAM路径、有效密码认证配置及账号条件。按分支安装修复包并重启sshd；暂不能升级的，先验证密钥和控制台可用，再关闭密码认证。请回传负责人、资产、版本、配置、重启及新连接验证、异常登录核查结果；未完成项说明临时措施和期限。

本次处置最重要的证据，是修复包已经安装、服务已经使用修复后的程序，以及实际连接按预期认证。把这三步核实，比一句“服务器已升级”更能说明问题。
