**句芒安全实验室** *2026年11月22日 11:03*

上周，一个做 SRC 的朋友把一份「AI 渗透报告」转给我。十二个漏洞，四个 critical，复测命令、请求响应、截图一应俱全。我挑了两条最像的跟着跑了一遍：一条没复现，另一条复现出来的影响比报告小两档。

他说了一句话挺典型：「模型说它验证过了。」

这句话是当下 AI 渗透工具最大的问题。模型不是不会扫，而是它「验证」的标准和你「验收」的标准不是一回事。你说服它相信一个 200 响应代表越权，它就敢写 critical；你让它证明拿到了别人的数据，它才知道还差得远。

GitHub 上的 `chu0119/Pojun` （破军）就是把这套「验收标准」往代码里写的尝试。434 星、275 个 fork、11 个未关 issue，Go 写的，AGPL-3.0，2026 年 10 月 9 日建仓，最新版本 v0.4.91 发布于 11 月 21 日。

先交代来源，这一点它自己写在 README 里：项目 fork 自已删除的 `Autumn-27/ARTEX` ，也就是百度「Agent+」攻防挑战赛冠军项目的最终定版 v0.3.15。原作者代码留在 git 历史里作为起点，v0.3.16 之后的 700 多个提交、约 5 万行新增由现维护者完成。它不是从零写的，但也不是简单改个名——这个区别在选型时值得分清。

## 它到底是什么

一句话：给一个目标和范围，它自己拆解、侦察、挖洞、利用、后渗透、出报告，人随时可以插手纠偏。

它不是一个包着 API 的扫描器。README 里反复强调的一件事是「让 AI 像一个守纪律的渗透测试工程师一样干活」。这句话听着像宣传，但往下翻代码，确实能看到对应的硬约束：

-   每个目标必须带可核验的验收标准，比如「未授权接口不带凭据返回 200 且含业务数据」；
    
-   critical / high 必须附可机械复现的证据，纯版本匹配进不了交付报告；
    
-   确认漏洞不等于完成意图，高危漏洞会自动派下一跳利用链；
    
-   所有 HTTP/S 流量过 MITM 代理逐请求留存，发现绑定流量证据。
    

作者给的基线是：12 个任务、56,000 多次工具调用、295 个确认漏洞（严重 28、高危 140）、2,752 个资产节点，全程无人值守。这组数字是作者自报，我没有复现，下面只把它当参考，不当结论。

## 两张图，三个角色

破军的状态拆成两张图，这个设计比「一个 Agent 一个上下文」清楚得多。

**资产图** 是全局共享的真值库，节点分六类：根域名、子域、IP、服务、应用、接口。公司归属和授权边界挂在这里，跨任务复用。

**探索图** 是每个任务一份的推进链：目标 → 意图 → 事实 / 漏洞。五种边构成血缘——谁派生了谁、谁证明了谁。一个漏洞是从哪条线索推出来的，在这张图里能一路回溯。

三个角色分工也明确：

-   **planner** 是唯一的意图生成者，持有一份跨唤醒共享的待办清单。串行利用链只记一次，按依赖逐步派发，不重复不错序；
    
-   **worker** 领一条意图做完就停，结果写回双图后自动唤醒 planner；
    
-   **mainagent** 接管对话、补写报告、处理工具触发的即时任务，比如复测提醒。
    

代码里图变更做了 800 毫秒防抖，worker 用 CAS 领取意图，避免两个 worker 抢同一条。这些是实现细节，但它决定了这套东西能不能跑长任务，而不是跑十分钟就乱套。

## 亮点一：目标闸门，不让模型自己说「完成了」

这是我觉得最值得看的一段。

很多 AI 渗透工具的任务结束条件是「模型认为完成了」。模型说完成，任务就 done，报告就开始写。问题是模型很容易把「发现了一个入口」当成「拿到了权限」。

破军的 `set_goals` 允许每条目标带 `criteria` ，也就是可核验的验收标准。更关键的是 `goal_met` 这个工具：还有目标没达成时，调它会被直接拒绝。

代码里的报错模板是这样的（ `%d` 和 `%s` 会替换成实际数量和目标 id，下面三个 id 只是示意）：

```
还有 3 个目标未达成（g1、g2、g4），禁止整体收官：goal_met 只能在全目标已用
prove_goal 证明后调用。请继续派深挖/利用链意图；若确认客观不可推进，把阻塞
证据写成 fact（含已尝试手段与失败输出），任务会按超时/轮数上限以「未完成」收尾，
而不是显示达成。
```

这句话把「假装跑完」这条路堵死了。任务终态只有两种：全部目标达成才落 `done` ；有目标没达成，无论超时、自动空转还是覆盖度收尾，一律落 `timeout` ，列表、详情、报告三处都标 x/y 目标。

还有一层更细的：如果目标文本里出现「RCE」「命令执行」「getshell」「控制权」「管理员权限」「敏感数据」「越权访问」这类词， `prove_goal` 不接受普通 fact 作为证据，必须关联一个 high 或 critical 的漏洞节点。代码里把这类词列成了一张表：

```typescript
var capabilityGoalTerms = []string{
    "rce", "远程代码执行", "命令执行", "代码执行",
    "getshell", "webshell", "反弹shell", "反弹 shell", "reverse shell",
    "控制权", "管理员权限", "管理员控制权", "管理员凭据", "domain admin",
    "root权限", "root 权限", "提权", "privilege escalation",
    "立足点", "foothold", "敏感数据", "数据泄露", "高危数据", "越权访问", "越权泄露", "敏感信息泄露",
}
```

同时它又留了一个例外：目标是「是否存在」「确认是否」「排查」「探测」这类否定式表述时，不套用能力型门槛，否定性结论是合法证据。这个细节说明作者想过误杀问题，不是一刀切。

从 AI 安全的角度看，这段代码解决的是「模型自评不可信」。它没有让模型更聪明，而是让模型的结论必须落到一个可检查的对象上。这个思路比换更强的模型有用。

## 亮点二：证据阶梯，L1 不够就不许报高危

第二段是证据分级。这里有一个必须先说清楚的细节：平台里其实有两套 L 阶梯，名字一样，口径不完全一样。

第一套在 `agent/verification_depth.go` ，是给 worker 的验证深度指引：

-   **L1 可控性**：输入确实到达后端，比如时间差、报错变化、响应变化——还不够上报；
    
-   **L2 读取影响**：真实读到数据，给出条数、字段、样本；
    
-   **L3 权限影响**：匿名、普通用户、管理员对同一接口的权限差异，水平或垂直越权；
    
-   **L4 写入/控制影响**：自建测试对象写入并回读、命令执行回显、上传文件可访问、订单状态篡改可回读。
    

第二套在 `agent/finding_workflow.go` ，是上报门槛：

-   **L1 接口有响应**、参数被后端处理；
    
-   **L2 证明输入真实影响了后端逻辑**，比如引号闭合、条件差异、报错差异；
    
-   **L3 真实影响达成**，比如数据外带、越权读到他人数据、命令执行回显、登录绕过；
    
-   **L4 关键影响**，比如全量数据、系统接管。
    

两套阶梯不冲突，但也不是同一张表：一套讲「验证走到哪一层」，一套讲「上报能报到哪一级」。上报门槛写死在工具指引里： **只有达到第二套的 L3 才允许报 critical / high；L2 最多报 medium；L1 不报漏洞，只记进待办。** 这条规则比「让模型谨慎一点」有用得多，因为它是可检查的：报告里的证据到不了 L3，severity 就上不去。

还有三个判定问句，我觉得是这套东西里最有价值的几句话：

第一句， **挡住你的是「安全机制」还是「外部运维约束」？** 输入校验、权限判定、ORM 防护、参数化查询属于安全机制，挡住了不算漏洞，顶多写加固建议；网关、WAF、IP 白名单、组件未部署属于外部约束，挡住了可以上报，但证据必须写明这个前置条件，severity 按绕过约束后实际能拿到什么来评。

第二句， **观察不等于推断。** 证据里只写亲眼看到的请求、响应原文和命令输出；从响应里推断出来的结论写进分析，不能当证据。这一条直接对着大模型的毛病：它太擅长把「看起来像」写成「已经证明」。

第三句， **severity 自查。** 给 critical / high 之前先问「最终谁受损、攻击者拿到了什么本不该拿的东西」。如果理由里出现「需要管理员配合」「影响有限」「本来就能看到」，那就不该评高危。理由不能反驳定级。

这三句话不是技术突破，是工程纪律。但 AI 渗透工具最缺的往往就是纪律。

## 亮点三：流量留痕，报告能回放到请求级

第三段是证据链。

破军内置一个 MITM 记录代理，worker 的所有 HTTP/S 流量逐请求留存，CA 证书路径由 `traffic.CACertPath()` 给出。请求和响应体按内容寻址存进 `_blobs/sha256/` 目录，同一份响应只存一次。

一条 finding 可以绑定四类流量证据：baseline、proof、verification、supporting。证据有版本号，改动会留痕。报告里引用的请求，能回到原始流量。

上图是仓库里的真实运行截图，目标域名和企业名称已由作者脱敏。左边是多 Agent 会话，右边是 planner 的态势研判。这个界面本身不稀奇，稀奇的是它下面挂着「这条意图为什么被派发、执行了什么、写回了什么」的活动流。

![破军漏洞详情：摘要、复测命令与证据 PoC](https://cdn.jsdelivr.net/gh/zhiyu-zeng/img@main/img/2026/11/e329bdb27bf7ae42.png "破军漏洞详情：摘要、复测命令与证据 PoC")

漏洞详情页把摘要、复测命令、证据 PoC 和状态卡放在一起。这个结构比「一段 Markdown 说发现了 SQL 注入」要难做，因为它要求每条 finding 都能被另一个工程师按图重放。

![破军流量代理：所有 HTTP/S 往来逐请求留存](https://cdn.jsdelivr.net/gh/zhiyu-zeng/img@main/img/2026/11/669a002639cc1d3b.png "破军流量代理：所有 HTTP/S 往来逐请求留存")

第三张是全局流量代理。所有 HTTP/S 往来逐请求留存，这是「报告可信度」的物理基础。没有这层，前面所有证据分级都只是话术。

但这里有一个必须说清楚的边界： **MITM 失败就透传，透传就不记录。** 代码里写得很清楚，某个 host 的 MITM 出错后，改为直连目标，请求照常发，但不再记录。也就是说，流量证据的覆盖范围是「能成功 MITM 的 host」，不是「所有流量」。你在报告里写「全程留痕」之前，得先确认目标有没有把某些域名排除在这层之外。

## 亮点四：去重，一份漏洞一份真相

第四段是去重。这件事听起来不性感，但它决定了报告能不能看。

AI 模型有一个坏习惯：同一个漏洞换个接口、换个参数、换个标题，它能给你报十遍。人工渗透工程师也会重复，但模型重复得更快、更自信。

破军的做法是多键去重：

-   强键： `cve` 、 `root` （根因）、 `endpoint` （归一化到 host + path）、 `param` ；
    
-   弱键： `asset_class` 、 `name` ；
    
-   新上报自动命中合并目标， `merge_count` 计数，来源 finding 收进 `finding_updates` 时间线，证据与资产锚点取并集；
    
-   跨任务去重默认开：同资产同漏洞在别的任务报过，默认不再重复打扰。
    

根因键的归一化写得很克制：转小写、只留字母数字和 `. : _ -` 、截断 96 字符；短于 4 个字符、或者落在通用词表里的，一律视为没传。通用词表里有 `xss` 、 `sqli` 、 `ssrf` 、 `idor` 、 `rce` 、 `injection` 、 `auth` 、 `generic` 、 `unknown` 、 `test` 这些词。

这个设计背后的判断是对的：把「xss」当根因键，等于断言「所有 XSS 是同一个漏洞」，不同漏洞会被物理合并进同一行，报告随后互相覆盖。宁缺毋滥，比强行合并好。

接口归一化也有一个 fail-closed 的细节：URL 解析失败时不回退成原文小写，而是返回空。代码注释写得很清楚，此前的回退会把「http://host（说明文字」这种带标点的片段变成垃圾键，让分组结果随文案措辞漂移。

## 亮点五：确认漏洞之后继续走

第五段是攻击链续跳。 `report_finding` 的回执带一个 `chain_intent_id` ，平台按漏洞类别自动派发继任意图：

-   SQL 注入 → 数据外带验证 → 登录态获取 → 后台横向；
    
-   文件上传 → 落地验证 → webshell 能力边界确认；
    
-   未授权接口 → 越权对照 → 数据面影响评估。
    

worker 的纪律写在代码注入的提示里，不受前端词表编辑影响：确认漏洞不等于完成意图；按 L1 信息、L2 认证/越权、L3 控制、L4 数据/资金推进；判「不可利用」之前必须换过至少两种本质不同的手段，并留下失败输出。

这条规则解决的是 AI 渗透的另一个常见问题： **找到一个洞就收工。** 真实红队不会因为拿到一个 SQL 注入就结束，它会继续问「这个注入能不能读数据、能不能拿登录态、能不能横向」。破军把这条「继续问」写成了平台的默认动作。

## 上手：三条命令和一笔真实的账

硬件要求不低：最低 2 核 4G、20G 磁盘，推荐 4 核 8G、60G，含 SecLists 约 2.5G、nuclei 模板、Playwright 浏览器和 LibreOffice。它不是那种 `pip install` 就能跑的轻工具。

Linux 一条命令全自动安装：

```
curl -fsSL https://github.com/chu0119/Pojun/releases/latest/download/install.sh | sudo bash
```

脚本会问部署形态（二进制或 Docker）和出网代理，然后装 PostgreSQL、建库、装 systemd 服务、首次启动。macOS 走 Homebrew + launchd，不需要 sudo。已经会用 Docker 的，直接：

```bash
git clone --depth 1 https://github.com/chu0119/Pojun.git pojun && cd pojun
cp .env.example .env    # 至少改 POSTGRES_PASSWORD
docker compose up -d     # → http://localhost:8787
```

装完打开 8787，初始化管理员密码，配 LLM 通道，然后新建任务给一句话目标。LLM 这块它内置了 32 家厂商预设，分官方、聚合、中转、本地四类，三步向导：选厂商、粘 Key、选模型。模型列表在线拉取失败会回退到预置清单，并标注「回退」。选完模型会自动推断上下文窗口，也能手动覆盖。

## 避坑：六件它不替你兜底的事

下面这些是我翻代码和 issue 之后觉得必须先说清楚的。它们不影响这套设计值得看，但直接影响你敢不敢把它放到真实项目里。

### 一、默认是 fail-open，不是 fail-closed

拦截引擎的第一条不变量写得很直白：未命中规则的调用默认放行。这是授权测试的产品决策，不是 bug。想收紧，得自己改 `fail_action` 。

模型兜底裁判的默认值也有一个口径差：设计文档写「失败兜底动作默认 allow」，代码里是 `defaultJudgeFailAction = "ask"` ，也就是模型裁决失败先转人工，等 180 秒没人处理，再按 `defaultJudgeAskTimeoutAction = "allow"` 放行。

这两个默认值放在一起看：无人值守跑长任务时，模型裁决失败不会立刻放行，但三分钟后会。你要是以为「它默认会拦住」，就会高估这层防护。

### 二、授权范围机制被移除了

`guard/guard.go` 开头的注释写得很直接：RoE 授权范围机制已被移除，后续可能再加。破坏性/外发拦截也不再硬编码在这个包里，而是落在数据库的拦截规则里，作为普通的内置规则 seed 进去，用户可以禁用或删除。

这意味着两件事：

第一，「授权优先」是流程约束，不是技术强制。你不在任务里声明范围，平台不会替你判断这个目标能不能打。

第二，内置的 10 条硬禁规则、13 条研判规则、1 条人工确认规则，都是数据库里的行。有权限的人可以改、可以关、可以删。它是默认配置，不是不可绕过的边界。

### 三、MITM 失败就透传，证据会缺口

前面说过，MITM 出错的 host 会改为直连，请求照发但不记录。这不是缺陷，是可用性取舍：目标把 TLS 握手搞坏，你还坚持 MITM，任务就卡死。但它意味着「全程流量证据」这句话有前提。

报告里写「所有请求已留存」之前，先看一眼 `traffic` 里有没有 passthrough 的 host。有，就得在证据范围里如实写缺口。

### 四、平台自己也是一个 Agent 攻击面

这是我觉得最值得写的一段。

破军本身是一个由模型驱动的系统：模型决定调哪个工具、传什么参数。工具参数是模型可控的，而平台把这些参数拼进 shell 命令。11 月 21 日，仓库里有一个还没关的安全 issue（#52），标题是「安全：diff_responses.header_a/header_b 与 auth_request.header 的 CRLF 注入与 -H @file 本地文件读取」。

它说的两件事都很具体：

第一， `diff_responses` 的 `header_a` / `header_b` （ `agent/tools_diff.go` ）和 `auth_request` 的 `header` （ `agent/tools_auth.go` ）没有做字符校验，直接进 `curl -H` 。header 值里带 `\r\n` 时，curl 会把后面的内容当成新的请求头发给目标，这是 CWE-113 头注入。

第二， `curl -H '@/path/to/file'` 会把本地文件的行当成请求头发给目标。也就是说，模型只要能控制 header 值，就能让平台读本地文件，并把内容带到目标侧。

`quoteShell` 做的是 POSIX 单引号转义，它挡住的是 shell 注入，挡不住 curl 自己的 `-H` 语义。这个区分很关键：很多工具作者以为「我转义了 shell，就安全了」，但 curl 的参数解析是另一层。

同一个 issue 里还提到，相邻的 `user_agent` 已经加了拒绝式校验，复用 `normalizeToolUserAgent` 的字符集和长度规则，拒绝 CR、LF、NUL、其它 C0、DEL 和非 ASCII；但 header 值这条路径还没跟上。

把这件事和前面的架构放在一起看，结论很清楚： **一个 AI 渗透平台，自己就是一个高价值目标。** 它手里有目标凭据、有内网可达性、有 LLM key、有流量证据。模型被提示注入之后，能控制的就是工具参数；参数进了 shell 和 curl，平台本地的文件就可能被读走。

这不是破军独有的问题，所有「模型决定工具参数」的平台都有。区别在于有没有人把它当安全问题修。这个 issue 现在是 open 状态，说明还没修。

### 五、公网部署的四条硬要求

README 和 docs/公网部署安全加固-2026-10-29.md 写得很清楚，我挑四条最重要的：

1.  **必须 HTTPS，反向代理必须覆写 `X-Forwarded-For` 。** 登录限流按这个头计数，不覆写的话，客户端可以伪造这个头绕过按 IP 锁定。全局阈值仍在兜底，但按 IP 维度会失效。
    
2.  **限流是进程内存态，服务重启清零。** 全局阈值能兜住 XFF 伪造，但分布式低速爆破（大量 IP 各打四次）在原理上无法被单机限流根治。公网实例建议额外套一层 WAF 或 CDN 限速。
    
3.  **不建议在公网实例上配置真实目标的授权凭据。** 拿到平台访问权的人能通过 `auth_request` 读到它们。这句话是作者自己写的，很实在。
    
4.  **密码是公网部署唯一的认证边界。** 这个系统能在服务器上执行命令，最少 8 位是下限，不是建议值。
    

还有一条它没写在文档里、但代码里能看到的：登录失败按 IP 十分钟五次锁十五分钟，全局一分钟三十次锁五分钟，失败响应固定延迟 300 毫秒。这些数字说明作者认真做过防爆破，但内存态和单机阈值的边界仍然在。

### 六、文档和代码有口径差

我至少看到三处：

-   README 写内置规则是 10 条硬禁、12 条研判、1 条人工确认；代码里实际是 10、13、1，多出来的一条是「goal_met 收官研判」；
    
-   设计文档写模型兜底裁判的失败动作默认 `allow` ；代码里是 `ask` ；
    
-   文档写默认进入规则系统的工具是 8 个；代码里是 11 个，多了 `listener_start` 、 `listener_stop` 、 `goal_met` 。
    

这三处都不致命，但它们说明一件事： **安全默认值要以代码为准，不要以 README 为准。** 选型时把这三处对一遍，比看 star 数有用。

另外， `http_request` 不在默认规则集合里。也就是说，默认配置下，HTTP 请求工具的参数根本不进规则引擎。你要靠规则拦它，得自己去「工具」页把它加进去。这一点和 issue #52 是同一个攻击面的两面。

## 适合谁，不适合谁

**适合：**

-   做授权 SRC、红队交付，需要一份能复现、能回溯的报告的小团队；
    
-   想把 AI Agent 的输出变成可审计证据的安全工程师；
    

**不适合：**

-   想一键打穿、不想配 LLM、不想看证据的人。它的价值在证据链，不在自动化程度；
    
-   没有任何授权就想扫线上系统的人。它的 README 写得很清楚，只允许本地隔离环境验证，禁止对线上系统发起测试；
    
-   想把它直接暴露在公网、又不想做 HTTPS、XFF、WAF 的人。它的默认安全边界不够厚，公网部署要自己补。
    

## 最后

AI 渗透工具这两年最大的进步，不是模型变强了，而是有人开始把「什么算证据」写成代码。破军的目标闸门、L1-L4 证据阶梯、流量留痕、多键去重，都是这条路上的工程活。它们不酷，但决定了报告能不能被另一个工程师重放。

它也有另一面：默认 fail-open、授权范围机制被移除、MITM 失败就透传、平台自己还有一个未修的 header 注入 issue。这两面放在一起看，才是 AI 安全现在的真实水平：能力跑得比约束快，而约束正在一点点补。

选不选它，取决于你要的是「一个能报洞的 Agent」，还是「一个能交付证据的系统」。这两个目标，不是一回事。
