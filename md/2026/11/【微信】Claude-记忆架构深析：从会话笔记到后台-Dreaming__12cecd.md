## Claude 记忆架构深析：从会话笔记到后台 Dreaming

11 月 6 日，Anthropic 公开了智能体（Agent）记忆系统的设计与实验。Claude 可以在工作中写笔记，后台再读取会话记录和已有记忆，纠正错误、组织 Wiki、调整下一次会话开场加载的内容。研究者把这类后台处理称为 Dreaming。

这里的记忆，是跨会话保留、以后可以重新读取的材料。模型参数没有因此改变。一次长对话中的历史消息，以及为继续当前任务而生成的压缩摘要，也不属于本文讨论的跨会话记忆。

这次公开的资料包含研究观察、开发者示例和接口定义，尚不足以还原所有 Claude 产品的后台。不过，沿着一次经验的保存、整理和复用过程，已经可以看到它怎样影响后续决策，以及开发者需要在哪些地方承担维护工作。

## 四层记忆结构

官方将记忆分成原始记录、记忆笔记、Wiki 等知识表示，以及会话开场注入的上下文。四者允许系统保留不同程度的细节，也决定了模型读取信息时要经过多少步骤。

![四层记忆结构](https://cdn.jsdelivr.net/gh/zhiyu-zeng/img@main/img/2026/11/f494dff466f6cf87.png)

原始记录保存用户消息、工具输入输出和模型当时的判断。它适合回查一次操作到底发生了什么。例如，模型说修复完成，记录里是否真的有测试结果；某条规则究竟来自用户确认，还是模型自己的推测，都需要回到这里核对。

笔记提取模型认为以后有用的内容。记录一条经过测试的操作方法，可以省去下次探索；保存当前计划，可以让新会话继续任务。但写笔记已经涉及选择和概括，条件可能被删掉，暂时成立的观察也可能被写成普遍规则。

Wiki 将这些内容按主题组织成页面，再用链接连接相关主题。它可以汇集多份材料中的信息，让模型先看到整理过的关系，而不是每次只拿到若干互不关联的搜索片段。这里的链接是一种导航结构，不能仅凭存在 Wiki，就推断系统底层用了图数据库或某种向量检索算法。

开场注入层的使用频率最高。运行框架不等模型先提出搜索请求，就把少量内容放进新会话。Claude Code 的自动记忆索引采用了明确的预算限制，只加载前 200 行或前 25 KB，以先达到的限制为准，详细主题文件等需要时再读取。

索引解决的是知识发现问题。模型不知道以前记录过什么，就可能想不到应该搜索哪个主题。索引可以先告诉它有一份相关笔记，以及应该到哪里读取。不过，索引里的描述仍然需要准确，否则模型可能根本不会打开那个文件。

从应用实现看，可以把笔记和 Wiki 理解为从原始材料中整理出的派生视图，类似数据库提前计算好的查询结果。这个类比有一个限制：模型改写自然语言会引入新的推断，无法像确定性查询那样保证每个结果都严格由固定运算得到。因此，派生内容需要保留返回来源的路径，不能只剩一句没有依据的结论。

常驻索引直接进入上下文，成本相对固定，也会在每次会话中重复支付。

主题笔记和 Wiki 按需读取，模型要先发现入口，再调用工具取回内容；少量链接可以减少搜索范围，过深的链接也会增加读取次数。

原始记录用于搜索和核验，保留信息最多，但筛选开销通常也最大。

![三种读取入口](https://cdn.jsdelivr.net/gh/zhiyu-zeng/img@main/img/2026/11/15a9ced654560866.png)

把更多内容放进常驻层，可以减少发现和读取步骤，却增加上下文占用，也提高错误内容被反复使用的机会。把内容全部移到外部，开场会更轻，但模型可能找不到、想不到查，或者在工具预算耗尽前没能读到。四层结构给了开发者调节这些成本的位置，并没有自动给出最优分配。

Dreaming 可以改变这种分配。它能把记录提炼成笔记，也能直接生成 Wiki，或把索引中的细节移到主题页，只留下入口。信息不必按四层顺序逐级上移。

## 经验提取与整理

CL-Bench 1.0 的一个数据库任务，让模型连续回答问题，每道题都启动新会话。系统在作答后提供正确答案，模型可以把经验写入跨会话保留的目录。研究者观察到不同模型读取、验证和复用记忆的行为差异。

Sonnet 4.6 会留下关于错误原因的猜测，但经常没有测试这些解释，有时也不读之前的笔记。提供记忆目录后，它的平均得分只从 0.330 提高到 0.364。研究者增加先读记忆、再测试假设的指引后，得分达到 0.641。

从失败中归纳规则时，模型可以先对错误提出解释，再寻找能区分解释的证据，最后决定是否把它写成后续可以采用的规则。只记录“刚才失败了”，后续会话仍不知道失败的条件；直接记成“这种方法不可用”，则可能把一次失败扩大成永久禁令。

![从反馈到可用规则](https://cdn.jsdelivr.net/gh/zhiyu-zeng/img@main/img/2026/11/fec3d447c09058ad.png)

较强模型会进一步组织验证结果。Opus 4.7 开始区分已检查事实和未确认内容，Opus 5 及后续较强模型会记录规则及其依据。Opus 5.5 在同一任务中，无状态基线为 0.655，使用记忆后达到 0.838。以上都是官方报告的数据库子任务结果。

![CL-Bench数据库任务记忆前后比较](https://cdn.jsdelivr.net/gh/zhiyu-zeng/img@main/img/2026/11/da3a550a00744644.png)

CL-Bench数据库任务记忆前后比较

写入指令也会改变模型选择。要求只记录失败，会削弱 Opus 5 和 Opus 4.7 的记忆收益。成功操作及其适用条件，同样可以帮助后续任务。对较强模型，过细的固定记录清单可能删掉有用信息；对较弱模型，明确要求读记忆和验证假设又能带来帮助。提示词应当按模型实际行为调整。

在线记录还面临时间限制。执行任务时，模型不知道哪个细节以后会再次使用，也未必已经看到推翻早期判断的证据。Dreaming 在后台读取更多记录，可以重新检查当时留下的结论。

《宝可梦红》的实验提供了一个具体例子。Claude 错记了月见山附近地标的位置，以为自己已经穿过山洞，后续三次走回原来的区域。研究者让 Dreaming 回查会话记录，模型修正了位置笔记。使用修正后记忆的运行重新进入山洞，随后抵达下一座城市。

核验需要比原笔记更完整的输入。如果后台只拿到一份摘要，就无法恢复摘要已经删掉的细节；如果它读到的只是模型自述，也不能据此确认操作真的完成。原始工具结果与结论之间的对应关系，应当保留到整理阶段。

官方 Wiki 示例中的维护提示词把这件事写得很具体。分析 Agent 先完整读取分配的输入，搜索相关记忆，再完整读回有关页面，检查已有说法是否得到来源支持。

某份输入没有提到一条旧知识时，Agent 不应直接删除它，因为其他输入可能提供依据。新输入明确反驳旧知识时，才修正或标记冲突。模型自己的推断，也不能随意覆盖项目成员已经作出的决定。

这比“采用最新信息”更严格。新的记录可能讨论不同版本，也可能只是一个未经确认的猜测。整理者需要判断两条说法是否针对同一个对象、同一个条件，再决定哪条过期；无法判断时，保留冲突和双方来源，比静默合并成单一答案更便于后续核查。

后台还要维护文件间关系。示例用稳定的主题标识连接页面，用根目录索引登记主题。分析 Agent 可以补充事实和链接，但合并文件、重命名、留下迁移指向等操作，交给所有分析任务结束后独占运行的整理 Agent。这样安排可以减少其他 Agent 仍在写旧文件时，文件被整体改写或迁走的机会。

![分析与整理的写入分工](https://cdn.jsdelivr.net/gh/zhiyu-zeng/img@main/img/2026/11/37e1351ba24a1270.png)

分析与整理的写入分工

合同实验说明了写入分工为什么会影响答案。多个 Agent 同时把条款概括进共享表格，发生了覆盖和遗漏，基于 Wiki 生成的简报只覆盖 57 项评分事实中的 41 项。调整后，每份合同交给单个 Agent 写独立页面，重要条款逐字保留，改进后的 Wiki 可以支持全部 57 项评分要求。

这个改动同时降低了共享写入冲突和概括损失。对法律条款这类细节不能随意压缩的材料，整理目标需要包含准确保留，而不只是缩短文本。

## 适用范围与局限

在 Stainless 的测试中，研究者使用约 35 万份文件、合计约 4.2 亿 tokens，让 Opus 5 经最多 128 次会话逐步构建 Wiki，再用 25 道问题评估。Tokens 是模型处理文本的计量单位。

仅搜索原始资料，回答满足约 53% 的评分要求。

Wiki 加搜索，随着 Wiki 扩展，成绩达到 61%，比搜索基线高八个百分点。

仅依赖 Wiki，最好达到 48%。

![Stainless：Wiki与搜索的表现](https://cdn.jsdelivr.net/gh/zhiyu-zeng/img@main/img/2026/11/3153484aaba2ad7a.png)

Stainless：Wiki与搜索的表现

组合方案每题还约少用两万个 tokens。Wiki 可以提前组织跨文件关系，原文搜索则让模型补查未覆盖的细节。仅用 Wiki 没有达到搜索基线，至少说明这组测试中仍需保留原文检索，不能把整理后的页面当成全部知识。

但 Wiki 不是所有检索任务的必要前置步骤。另一组并购问题需要跨文档综合、判断或计算，使用 Wiki 的相关项目得分为 87%，仅搜索为 73%；部分法律任务的大多数答案位于单份文件，Wiki 没有明确优势。还有一个任务，用 115 KB 原文生成了 203 KB Wiki，体积反而扩大到 1.77 倍。

![一个法律任务的原文与Wiki体积](https://cdn.jsdelivr.net/gh/zhiyu-zeng/img@main/img/2026/11/e54951ac22032fe5.png)

一个法律任务的原文与Wiki体积

它的经济性取决于复用次数。可以先用一个简化条件估算：

```
⁠⁠⁠重复查询次数 × 每次节省成本 > 首次构建成本 + 持续更新成本
```

这里的成本需要统一换算，不能拿不同模型的 token 数直接相减。这个式子也只估算开销，准确性仍要单独检查。资料持续变化、每轮都要重建时，维护开销可能超过查询节省；只回答一次的问题，也很难摊薄预处理成本。

官方动态工作流示例处理约 12 MB 的五十份长会话记录，默认配置下约花费八美元、耗时十分钟。这只能作为特定示例的运行数据，不能当作 Dreams 接口报价。资料规模和模型配置变化后，需要重新测量。

除了计算成本，派生知识还会带来一致性问题。原文更新了，笔记、Wiki 和常驻索引可能仍保留旧内容。只修改一处不能保证所有会话都使用新结论。若要让来源更新触发局部重验，应用至少需要知道哪些派生页面引用了这个来源。

同一条链路也可能长期保留错误或不可信指令，这是架构风险分析，并非已发现的 Claude 漏洞。外部文档要求关闭检查，模型将其写入笔记，后台又汇入项目 Wiki，内容逐渐脱离原始场景，但并没有因此得到用户授权。

官方维护提示词已经要求把输入和旧记忆当作数据，不执行其中夹带的指令。这是必要的模型指引，工具权限仍须由运行环境约束。无论记忆里写了什么，是否允许外发文件、修改系统，都不能只由这段文字决定。

纠错和删除也需要覆盖派生内容。原始消息删除后，笔记里的概括仍可能存在。项目之间共享主题页时，还要保留来源访问限制，不能把只能由部分成员读取的事实整理到公共页面，再仅凭页面权限放行。

这要求应用维护来源、版本和派生关系，也要求整理过程允许明确的待确认与冲突状态。没有这些信息，后续 Agent 即使命中了正确主题，也难以判断其中的规则是否仍适用于当前任务。

## 工程实现与取舍

官方 Python SDK，也就是供程序调用的开发包，已经提供 Dreams 接口。创建请求发送到 `POST /v1/dreams` ，输入包括一项记忆存储和一项会话集合。当前类型定义允许一次提供 1～100 个不重复的会话 ID，且这些会话必须属于同一工作空间。接口仍处于研究预览阶段。

创建后，应用拿到后台任务，而不是立即拿到一份完成的记忆。初始状态为 `pending` ，输出列表为空。应用需要查询任务，等待进入 `completed` 、 `failed` 或 `canceled` 等终态，再按结果处理。不能把请求被接收当成整理完成。

![Dream后台任务状态](https://cdn.jsdelivr.net/gh/zhiyu-zeng/img@main/img/2026/11/a6066f2c09c8c59f.png)

Dream后台任务状态

默认输出策略是 `create_new` ，将结果写到新存储，保留输入存储。这个选择让应用有机会比较新旧版本，执行检查，通过后再切换后续会话使用的记忆。但 SDK 没有因此替应用完成审核和发布。

如果采用这条路径，我会让一次工作会话固定读取同一版记忆，新版本只供之后启动的会话使用。这是避免任务中途混读新旧索引、主题页的工程建议，不是接口已经承诺的一致性保证。紧急撤回则需要另设机制，不能只等旧会话自然结束。

![候选记忆与版本切换](https://cdn.jsdelivr.net/gh/zhiyu-zeng/img@main/img/2026/11/312a1aec11111b3c.png)

接口也支持 `update_existing` ，直接改写输入存储。调用凭据没有写权限时返回 403；同一存储还有另一个未完全停止的原地更新 Dream 时，新请求返回 409。这能阻止相应 Dream 任务重叠运行，却不代表模型同时编辑共享文件就不会覆盖。

官方 Wiki 示例仍承认，最繁忙的共享页面会因覆盖丢失约 5% 的行。其维护提示词要求使用定点编辑，每次写入后读回，确认内容确实存在；若多次合并仍未成功，就另建文件保存事实，再建立链接。

读回检查可以发现部分覆盖，却不能等同于写入原子性。一个 Agent 确认成功之后，另一个持有旧内容的 Agent 仍可能覆盖它。对不能接受丢失的知识，应用需要更强的控制，例如按主题分配单一写入者，或在保存前检查版本是否已经变化，发现变化就拒绝旧版写入。这些需要存储或调度层实现，不能只靠提示词约定。

![读回确认后的覆盖风险](https://cdn.jsdelivr.net/gh/zhiyu-zeng/img@main/img/2026/11/8c1ce74be936927f.png)

读回确认后的覆盖风险

另一条公开路径，是用动态工作流自行组织 Dreaming。官方 cookbook 先导出已结束的会话，由分析 Agent 逐份处理，再由整理 Agent 统一维护索引与页面关系。后续工作 Agent 只读使用记忆。开发者可以自行选择模型、整理指令和触发时间。

自建流程会更新原存储，应用需要另行保存版本。输入导出时也应保留消息角色、工具输入输出和会话标识。若只导出模型回答，整理者就缺少检查它是否真正执行过操作的依据。

运行频率不必一开始就设成全量定时重建。一次成功整理后，应用可以记录已处理的会话集合，下一轮只提交新增记录；失败时保留重试范围，不提前把记录标为已处理。来源更新、发现矛盾或高频使用的规则变更，可以另行触发相关主题的核验。这是增量调度建议，具体策略仍需按任务测试。

发布前，应用可以检查索引能否找到主题、链接是否有效，以及关键规则能否回到依据；再让固定测试题在新旧记忆上各运行一次，比较答案和开销。文件数量和 Wiki 体积可以记录，但不适合替代质量验证。

Claude Code 自动记忆、Claude 聊天记忆和 Managed Agents 的 Dreams，也不能据此视为同一个后台。实际接入时，应以所用产品的读取、写入和保留规则为准。

应用需要决定哪些经验可以写入，怎样检查后台改动，以及何时切换新版本。先在小范围任务里测出可重复的收益，再增加 Wiki、并行整理和自动调度，才能知道每增加一个环节，究竟省掉了多少重复探索，又增加了多少维护成本。
