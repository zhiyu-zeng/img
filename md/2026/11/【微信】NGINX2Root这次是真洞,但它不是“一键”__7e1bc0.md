**MessFreeSecurity** *2026年11月19日 10:32*

这两天 2Shell、2Root 满天飞。刷到 NGINX2Root,我本来想照昨天写 Java4Shell 的路子再泼一盆冷水,查完发现泼不了。

这次是真洞,RCE 的 PoC 也公开了。只是它没传的那么“一键”:打一次,要往一条 HTTP/2 连接里灌大约 128 GB 流量。

所以短期内没人能拿它大面积批量打,但平时限并发、限请求数的那套规则,也拦不住它。

## 名字底下是六个洞,最要紧的只有一个

NGINX2Root 是 Xint 起的统称:五个 nginx CVE,加一个 Linux 内核 SCTP 的本地提权。五个 nginx 的洞,触发条件差得很远:

|     |     |     |     |
| --- | --- | --- | --- |
| CVE | 什么配置下受影响 | 最早受影响版本 | 关 HTTP/2 能挡住吗 |
| CVE-2026-123007 | 开了 HTTP/2 | 1.9.5 | 能   |
| CVE-2026-123633 | 开了 HTTP/2,并且请求转发给后端 | 1.19.7 | 能   |
| CVE-2026-123634 | 配了 resolver,proxy_pass 的目标取自请求,并且用了 mirror 且 mirror_request_body off | 1.13.4 | 不能  |
| CVE-2026-121810 | 开了 HTTP/3,并且请求转发给后端 | 1.25.0 | 不能  |
| CVE-2026-113425 | 邮件代理,用了 proxy on 和 auth_http | 0.5.15 | 不能  |

表里的条件和版本按 Xint 的披露原文。

**最要紧的是 123007。** 开了 HTTP/2 就能打,不需要登录,也不需要配合别的洞,打下来是 nginx worker 进程的代码执行。Wiz 说只挂静态文件的 nginx 也在范围里,这一点目前只有它一家这么讲。受影响版本从 1.9.5 到 1.31.8,也就是说这个洞在代码里待了十年。

名字里的 Root 要另算。worker 一般不以 root 运行,Xint 的做法是打完 123007 再接那个 SCTP 提权,拿到宿主机 root,顺带演示了从 Docker 里逃出来。这一段只有 Xint 自己的测试,内核洞的 CVE 号没公布,也没有别人复现过,我先打个问号。

123633 也能未授权 RCE,但除了反向代理,还要赶上 worker 的连接槽快用完的时候才触发,目前没有公开 PoC。剩下三个各有各的配置前提,多数站点对不上。

下面主要说 123007,因为它门槛最低,也是现在唯一有公开 PoC 的。

## 它不是“一键”,是把流控计数器算到下溢

123007 出在 HTTP/2 的流控上,是个整数下溢。服务端每次往外发多少数据,是按流控窗口算出来的。这个洞能让它算出一个错的长度,接下来拷贝内存就照着这个错的长度拷,写出了缓冲区,落在堆上。

要触发它,客户端得故意不按常理来:把 SETTINGS_INITIAL_WINDOW_SIZE 设成 0,收到的数据不读,同时不停地发 WINDOW_UPDATE 去拨窗口。按 Rapid7 公开的 PoC,这样要在一条连接上灌大约 128 GB 流量才能凑齐条件。128 GB 这个数来自媒体对 PoC 的报道。至于为什么要这么多,我猜是流控计数和堆布局都得推到一个很精确的位置,这是我自己的理解,不是来源的说法。

量确实很大,但都压在一条连接上,不是靠并发。

别把它想成开几千条连接一起冲。它只有一条连接,只是这条连接流量特别大、挂的时间特别长。后面讲怎么防,靠的就是这个区别。

和 Java4Shell 比,它强在写进去之后还有后手。它能先读出内存地址,再去改堆,最后把一个 cleanup 函数指针换掉,让 nginx 执行命令。地址是它自己读出来的,所以 ASLR 开着也挡不住。Java4Shell 写进去的是固定值,只能赌砸中什么;这个洞能读,写什么也是攻击者自己定。

## 为什么它“打得通,但打不快”

先承认它打得通。Rapid7 的 Stephen Fewer 已经放出完整的 RCE PoC,在官方 nginx 1.31.8 的 Docker 容器上做出了未授权代码执行,不是只能崩的那种。所以“能不能武器化”这关已经过了,公开的。

但把它变成对真实目标的规模化攻击,门槛还很高:

-   **打一次要往一条连接里灌大约 128 GB。**
    
    按 Precursor 的估算,万兆链路上大约两分钟,千兆要十七分钟,带宽低于 300M 基本打不成。时间不算长,但很吃带宽,在网络层动静也大,想拿它做蠕虫、做大面积扫描,成本太高。
    

-   **挑 libc,还挑 CPU。**
    
    公开 PoC 依赖 glibc 里的一个内存拷贝例程,这个例程只在带 AVX-512 的 CPU 上才会被选中。用 musl 的目标(比如很多 Alpine 容器)和不带 AVX-512 的机器,大概率都不在这套 PoC 的覆盖里。
    

-   **要按版本、构建、配置适配。**
    
    Wiz 自己的原话是 difficult to exploit remotely,没有通杀;连 CVSS 3.1 向量都标了 AC:H,攻击复杂度高。
    

所以现在的真实档位是:定点打一台你已经确认版本和架构匹配的目标,可行;大规模、隐蔽、自动化地打,短期不现实。但方向是单向收窄的,公开 PoC 把最难的“行不行”证明了,剩下的是有人去压流量、适配更多环境的时间问题。

## 怎么发现:统计单条连接的收发字节

这个打法在访问日志里几乎不留东西。要发现它,得去数每条 TCP 连接收了多少、发了多少。

正常的 HTTP/2 连接,nginx 是发得多、收得少:客户端发几个请求头,服务端回一堆页面和资源。这个打法反过来,nginx 在一条连接上收进来几十上百 GB,自己几乎没往外发什么。

Xint 给的办法是在 nginx 机器上直接用 `ss` 看:

```
ss -tinH state established '( sport = :443 )'
```

每条连接看三样:

-   `bytes_received`
    
    ,这条连接累计收了多少。到了 GB 级就该看一眼,正常浏览很难到这个量。
    

-   `bytes_sent`
    
    (老版本 iproute2 看 `bytes_acked`),累计发了多少。收的比发的高出几个数量级,就是倒挂。
    

-   隔几分钟再采一次,同一条连接还在,`bytes_received` 还在涨。
    

三样同时出现,就值得马上去查这条连接。

有上传业务的站点,本来就有入向流量很大的正常连接,把上传接口单独拎出去,剩下的再按这个规则报。

机器上不方便跑 `ss` 的,在前面的负载均衡或者流量采集(NetFlow 一类)上做同样的统计也行:按连接算入向和出向字节,找入向特别大、收发倒挂、挂的时间又特别长的那几条。

“GB 级”这个线是我按 128 GB 的总量倒推的,不是来源给的数字。具体卡在多少,要拿你自己的流量基线来定。

## 先查自己中没中

在 nginx 机器上跑四条命令。

看版本。1.9.5 到 1.31.8 之间的,都在 123007 的范围里:

```
nginx -v
```

看二进制里有没有编进 HTTP/2 模块。没有任何输出,就不受 123007 影响:

```
nginx -V 2>&1 | grep -o with-http_v2_module
```

看配置里有没有打开 HTTP/2。出现 `listen 443 ssl http2;` 或 `http2 on;` 这样的行,就是开着:

```
sudo nginx -T 2>/dev/null | grep -nE 'listen.*http2|http2 +on'
```

再从外面确认一次,把域名换成自己的。看到 `ALPN protocol: h2`,说明 HTTP/2 对外是通的:

```
openssl s_client -connect 你的域名:443 -servername 你的域名 -alpn h2 </dev/null 2>/dev/null | grep ALPN
```

版本在范围内、模块编进去了、配置里开着、外面连得上,四条都中,就按下面的办法处理。

## 有没有人在打,怎么修

到 11 月 19 日为止,还没有确认的在野利用,CISA KEV 里也没有它,watchTowr、CERT-EU、Cycode 三家说法一致。有一家写它 11 月 13 日就进了 KEV,那个日期比漏洞披露还早,应该是写错了。

不过 RCE 的 PoC 已经公开,Wiz 和 Xint 手里也各有一份没放出来的利用。排期的时候别拿“还没人打”当理由往后拖。

怎么修:

-   升到 nginx 1.31.9(mainline)或 1.30.7(stable),升完要重启,reload 换不掉正在跑的旧二进制。NGINX Plus 的 R34 到 R36 没有单独补丁,要升到 37.x 的修复版。
    
-   一时升不了的,先把 HTTP/2 关掉,1.25.1 之后的写法是 `http2 off;`。这只能挡住 123007 和 123633,表里另外三个挡不住。改完同样建议重启,只 reload 的话,已经建好的 HTTP/2 连接还留在旧 worker 上。
    
-   用发行版自带包的,以发行版的安全公告为准。发行版会把补丁 backport 到旧版本上,光看版本号判断不了修没修。
    
-   配置对得上表里另外三行的(HTTP/3 加反向代理、resolver 加 mirror、邮件代理),只有升级这一条路。
    

## 起这种名字,就是在卖货

说句难听的。今年这一串 2Shell、2Root,我现在看到名字就烦。

先看名字是谁起的。NGINX2Root 是 Xint 起的,Xint 是卖 AI 挖洞平台的,官网页脚上写的就是 AI-powered vulnerability discovery。它自己的披露文章里说,123007 是研究员备赛时找到的,另外四个是全自动扫描跑出来的,还特意强调“没有人工引导”。这句话是写给谁看的?写给准备掏钱买扫描器的人看的,页面顶上就挂着 Talk to an Expert。昨天那个 Java4Shell 也一样,名字、分数、对标 Log4Shell 的说法,全出自披露方自己。

我不是说洞是假的。123007 是真洞,该修。我烦的是他们把一份漏洞通告做成了产品发布会。

五个 CVE 打包成一个带 Root 的名字。可要到 root,得再接一个没有编号、没人复现过的内核洞,名字里却先把 Root 写上了。9.2 分摆在最前面,AC:H、128 GB、挑 libc 挑 CPU 这些放在后面没人看的地方。媒体只抄前一半,老板只看媒体标题,然后全行业的运维半夜爬起来升 nginx。

吃亏的全是下游。修的人要连夜排期;复现的人发现公开 PoC 只认特定环境,还得先灌一百多 G;打攻防的人拿到手基本用不上。可你还不能不看,十个里总有一个是真能打的,不从头看完你分不出来是哪个。最恶心的就在这:他们发一篇博客就完事了,我们要搭进去一个团队两天时间来甄别。

AI 能把这些躺了十年的内存洞翻出来,是好事,早该有人翻了。但翻出来第一件事是起名字、约媒体,这我接受不了。别跟我说这叫负责任披露,大家陪着加班,最后是给他家产品打了一轮广告。

年底之前肯定还有,我估计三四个起步。还是 AI 扫出来的内存洞,还是一堆前置条件,通稿里还是会提 Log4Shell。

## 写在最后

我现在看这类通告,名字和分数基本不看了,直接去翻披露原文,找攻击者能控制什么那一段,然后看有没有别人复现出来。顺便查一下起名字的是哪家公司、卖什么的,一般查完心里就有数了。

123007 这个洞该修还是得修。它能读能写,PoC 是公开的,现在只是卡在 128 GB 上没法批量用,哪天有人把这个量压下来就麻烦了。

nginx 开着 HTTP/2 的,这两天把版本升了。升不了就先关 HTTP/2。
