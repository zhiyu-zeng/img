## 游戏加固分析（msa / FairGuard）

-   加固一： `libmsaoaidsec.so`
    
-   加固二： `libZzprotect.so`
    
-   环境：Pixel 5 / Android 11 / root + frida-server
    
    > 包名：WTI5dExuaDBkR011YzNrPQ==
    

## 摘要

该APP的反调试和自毁分三层。第一层 `libmsaoaidsec.so` 用自己的监控线程和 shellcode 退出发生器；第二层 FairGuard（以 `libZzprotect.so` 为入口）把 `exit_group` 桩注入每个受保护业务库；第三层 FairGuard 在运行期循环改写 `libcocos2djs.so` 的代码页，把合法指令异或成非法指令。

前两层用 15 个 `Interceptor.replace` 拆掉退出路径，600s 实战稳定。第三层不经过库里的退出桩，Hook 拦不住，改为把目标代码页锁成只读：写者的 store 变成可恢复的 SIGSEGV，漏网的坏字用 dump 下来的干净镜像恢复。

全文分四部分：第一部分分析 `libmsaoaidsec.so` 的线程、检测点、退出路径和 10 个 Hook；第二部分分析 FairGuard 的 dump / 修复、 `svc` 桩和 5 个 Hook；第三部分分析代码页加固的范围、算法和页级写陷阱的实现；第四部分总结三层的组合、验证和方法。附录 A 是 OLLVM 控制流还原，附录 B 是全部运行时脚本。

## 1\. 从 pthread_create 入手

### 1.1 观察脚本

```javascript
'use strict';

const TARGET_SO = 'libmsaoaidsec.so';

function hook_pthread_create() {
    const pthread_create = Module.findExportByName('libc.so', 'pthread_create');
    if (pthread_create === null) {
        console.log('[-] pthread_create not found');
        return;
    }

    console.log('[+] pthread_create @ ' + pthread_create);

    Interceptor.attach(pthread_create, {
        onEnter(args) {
            const fn = args[2];
            if (fn.isNull()) return;

            const mod = Process.findModuleByAddress(fn);
            if (mod === null || !mod.name.includes(TARGET_SO)) return;

            console.log('\n[pthread_create]');
            console.log('  module : ' + mod.name);
            console.log('  base   : ' + mod.base);
            console.log('  entry  : ' + fn);
            console.log('  offset : 0x' + fn.sub(mod.base).toString(16));
            console.log('  arg    : ' + args[3]);
        }
    });
}

setImmediate(hook_pthread_create);
```

## 2\. maps 监控线程（0x1AAA4）

> pthread_create 传入的入口是 `0x1AAA4` ，跟进后发现 IDA 没有在这里切函数，它被并进了 `sub_0_1A7C0` 的函数视图。所以从 `0x1A7C0` 往下读，依次看到 maps 扫描（ `0x1A7C0` ～ `0x1AA94` ）、 `0x1AAA4` 处的字符串解密、以及尾部的 4 秒循环。

### 2.1 maps 扫描段（0x1A7C0 正常入口）

> `0x1AA94` 的 `ret` 是未命中返回， `0x1AA98` 是命中后的 `_exit(0)` ；4 秒循环里 `0x1B440 bl 0x1A7C0` 每次重新回到这个入口。

![图片描述](https://cdn.jsdelivr.net/gh/zhiyu-zeng/img@main/img/2026/11/a811973d5ec11696.webp)

  
`sub_0_1A7C0` 流程：

1.  `fopen("/proc/self/maps", "r")` ；
2.  逐行 `sscanf` 解析；
3.  `strstr(path, "/data/local/tmp")` 过滤 + 权限同时含 `r` 、 `x` ；
4.  唯一路径插入 `std::set` ；
5.  对每个路径调用 `sub_0_173B8` / `sub_0_16EB8` 解析 ELF；
6.  调用 `sub_0_16CE4` ，用 `_AGENT_1.0` 、 `frida-agent` 做 `strstr` 匹配；
7.  命中 → **函数体内直接 `_exit(0)`** （见第 5 节）。

`strstr(s, needle_)` 里的 `needle_` 是 `/data/local/tmp` ，只用于路径过滤；真正的 Frida 特征在 `sub_0_16CE4` 。

### 2.2 0x1AAA4：字符串解密

  
密钥在 `0x2AA1C` ，按 4 字节步长取前 3 字节：

```python
KEY = 0x99, 0xA7, 0xA9
算法：plain[i] = enc[i] ^ KEY[i % 3]
```

```python
import ida_bytes, idaapi

B = idaapi.get_imagebase()
K = [ida_bytes.get_byte(B + 0x2AA1C + i * 4) for i in range(3)]

def dec(a, n):
    r = (ida_bytes.get_bytes(B + a, n) or b'').split(b'\x00', 1)[0]
    return bytes(x ^ K[i % 3] for i, x in enumerate(r))

for a, n in [(0x3901C,16),(0x3902C,26),(0x39046,12),(0x39052,6),
             (0x39066,10),(0x39070,16),(0x39080,16),(0x39090,11),(0x3909B,12)]:
    print(hex(a), dec(a, n))
```

## 3\. task 监控线程（0x191B0）

> pthread_create 传入的入口是 `0x191B0` ，跟进后发现 IDA 没有在这里切函数，它被并进了 `sub_0_1900C` 的函数视图。所以从 `0x1900C` 往下读，依次看到 task 状态扫描（ `0x1900C` ～ `0x191A0` ）、命中后置返回值 `0x309` （ `0x191A4` ）、以及 `0x191B0` 起的线程轮询循环。

### 3.1 task 状态扫描段（0x1900C 正常入口）

> `0x191A0` 的 `ret` 是未命中返回， `0x191A4` 是命中后置 `w0 = 0x309` （777）； `0x191B0` 线程入口在 `0x191CC` 轮询这个返回值。  

![图片描述](https://cdn.jsdelivr.net/gh/zhiyu-zeng/img@main/img/2026/11/1a009ed4890b8709.webp)

1.  拼出 `/proc/<pid>/task` ，遍历每个线程目录；
2.  打开对应 task 的 `stat` ，读入后找 `)` 后面的状态字符；
3.  状态为 `'t'` / `'T'` （stopped）即命中；
4.  命中时在 `0x191A4` 置 `w0 = 0x309` （777），再走 `0x1917C` 的公共返回路径（ `0x191A0 ret` ）。

线程入口在 `0x191CC` 处循环：

```python
0x191CC  mov w0, w19
0x191D0  bl 0x7790        ; usleep(2 秒)
0x191D4  bl 0x18B78       ; tracerpid
0x191D8  cmn w0, #1
0x191DC  b.eq 0x191F8
0x191E0  cbz w0, 0x191EC
0x191E4  bl 0x18884       ; 二次检查
0x191E8  tbz w0, #0, 0x191F8
0x191EC  bl 0x1900C       ; task_scan
0x191F0  cmp w0, #0x309   ; 777
0x191F4  b.ne 0x191CC     ; 未命中 → 继续轮询
0x191F8  bl 0x133D8       ; 退出
```

-   `0x18B78` 读 TracerPid（调试器检测）：返回 `-1` 直接跳到 `0x191F8` ；非 0 时再走 `0x18884` 二次检查，检查不过也跳到 `0x191F8` ；
-   `0x1900C` 返回 `777` 表示命中；
-   命中后 `0x133D8` → `0x21B44` → `exit_group(0)` ，退出码固定为 0。

## 4\. 0x1B458：启动器与 PrettyMethod 检查

这一段被 OLLVM 控制流平坦化处理过，状态变量在 **W24**，立即数由 **W8** 装入。还原分三步：

1.  在分发器里找 `CMP W24, W8` 和它后面的条件跳转。 `B.LE` / `B.GT` 是二分查找树的分叉导航， `B.NE 0x1B4E0` 是未命中时回到根节点，只有 `B.EQ target` 且 `target != 0x1B4E0` 才是状态到业务块的映射。
2.  汇总 `MOV` / `MOVZ` / `MOVK W24, #imm` ，建立状态值和目标块的对应关系。按这个规则从 `0x1B458` 里提取到 18 组映射。
3.  找到装入状态值的指令后，把后面跳回分发器的 `B 0x1B4E0` 改写成 `B target` 。实际 patch 到 11 条；再遍历所有写 W24 的指令，另外 7 条是 `CSEL` 条件选择，属于分发器内部逻辑，不是业务块。

完整的提取脚本、18 组映射表和 patch 脚本放在附录 A。还原后的主流程如下：

```python
sub_0_1B458()                    ← 启动器（主函数）
  │
  ├─ ① 按 off_0_37FC0（n20）分支：
  │   ├─ 20 < n20 < 23 → dlopen("libart.so") + dlsym
  │   ├─ 22 < n20 < 26 → sub_0_17998 + sub_0_17AAC（自定义，绕过 hook）
  │   └─ n20 > 25      → sub_0_17998 + sub_0_17AAC（另一组密文）
  │   └─ 三处都 XOR 解密 ART 符号名（密钥 [0x99,0xA7,0xA9]）
  │
  ├─ ② sub_0_21D98(0)          ← PrettyMethod 同步检查
  │     ├─ dlsym 找 PrettyMethod
  │     ├─ 比对函数开头机器码（检测 Frida Hook）
  │     └─ 返回 bit0：1=命中(Frida)，0=未命中
  │
  ├─ ③ if (bit0 == 1) sub_0_21B44(0)   ← 反调试总入口（仅命中时调）
  │     ├─ 解密 28B ARM64 syscall 桩（MOV X8,#0; SVC #0; RET）并执行
  │     ├─ sub_0_18B78()       ← TracerPid 检测
  │     └─ sub_0_1A7C0()       ← Frida 线程名扫描
  │
  └─ ④ pthread_create(start_routine__0, name)   ← 看门狗线程
```

本节分析启动器 `0x1B458` 与 PrettyMethod 检查；fork + ptrace 和延迟环境检查分别见 5.1 节、5.2 节。

### 4.1 PrettyMethod 同步检查 0x21D98

`PrettyMethod` 是 Android 运行时（ART）里的一个内部函数，全称是 `art::ArtMethod::PrettyMethod` 。它的作用是把一个代表 Java 方法的 `ArtMethod` 对象，转换成人类可读的字符串（比如 `java.lang.String.toString` ）。Frida 的 Java 层 Hook 会顺带 Hook PrettyMethod，用来绕过 ART 的一个 Bug（避免 Native 线程抛异常时崩溃），这个行为正好可以用来判断 Frida 是否在运行。

![图片描述](https://cdn.jsdelivr.net/gh/zhiyu-zeng/img@main/img/2026/11/0e85505ac5aac0e8.webp)

`sub_0_21D98` 通过比对 PrettyMethod 函数开头 4 字节是否为 `LDR X16/X17, #...`（Frida Hook 的标准桩）来检测 Frida。 `0x58005010` / `0x58005011` 就是 Frida Hook 后留下的机器码。

```python
0x18EF4  bl 0x7CD0              ; pthread_create(0x1885C)
```

### 5.2 延迟环境检查线程 0x19200

线程创建于 `0x1A358` ， `x3 = sp + 0x24` ，传入的是父线程栈上的地址；线程入口先 `sleep(6)` ，6 秒后再做检查。该函数的控制流同样被平坦化，状态变量为 W9，常量由 W8 装入，分发器位于 `0x19294` 。

还原规则与第一部分第 4 节相同：收集 W8 常量，匹配 `CMP W9, W8` 及其后的 `B.EQ` ，排除跳回 `0x19294` 的边，共提取 31 条映射（脚本见附录 A.2.1）。对应字符串使用同一套 key `[0x99, 0xA7, 0xA9]` 做 XOR，解密脚本见附录 A.2.2。

解密结果：

| 变量  | 明文  | 用途  |
| --- | --- | --- |
| `filename` | `/proc/self/maps` | `fopen` 扫描内存映射 |
| `format` | `%lx-%lx %s %lx %s %ld %s` | `sscanf` 解析 maps 行（start-end perms offset dev inode pathname） |
| `v104` | `MAGISKTMP` | **Magisk 挂载点特征** （检测 Magisk 环境） |
| `s2` | `u:r:zygote:s0` | **SELinux 上下文特征** （与 `attr/prev` 比对） |
| `v55` | `/proc/%d/attr/prev` | 读取进程 **前一个 SELinux 上下文** （ `/proc/<tid>/attr/prev` ） |

第二个立即数应只取低 5 字节；多取会把上一段的 `FE C8` 拼入，解出 `u:r:zygoWQzU` 这类错误结果。

检查流程：

1.  `fopen("/proc/<pid>/cmdline")` ，读入后 `strchr(cmdline, ':')` ，区分主进程 / `:service` 子进程；
2.  `fopen("/proc/self/maps")` ，用 `sscanf` 解析，找到包含 `a1` （即父线程栈地址）的那条映射——也就是 `[stack]` ；
3.  从该映射的 `end - 512` 开始，按 `strlen + 1` 步进扫到 `end - 6` ，用 `strstr` 找 `MAGISKTMP` （栈顶的 argv/env 区）；命中 → 退出；
4.  未命中则 `sprintf("/proc/<pid>/attr/prev")` ，读取内容与 `u:r:zygote:s0` 做 `strcmp` ；相等 → 退出；
5.  退出统一在 `0x197CC` ： `mov w0, wzr; bl 0x21B44` → `exit_group(0)` 。

`/proc/%d/attr/prev` 是 Linux 内核提供的伪文件接口，用来读取进程在上一次 `execve()` 之前使用的安全上下文。

在 Pixel 5 上，普通进程的 `attr/prev` 并不是 zygote：

```python
com.android.systemui   prev=u:r:init:s0  cur=u:r:platform_app:s0
com.google.android.gm  prev=u:r:init:s0  cur=u:r:untrusted_app:s0
com.android.settings   prev=u:r:init:s0  cur=u:r:system_app:s0
```

## 6\. 检测命中后的退出路径

### 6.1 maps 分支的 \_exit(0)

`sub_0_1A7C0` 里命中后不返回，直接：

```python
0x1A9FC  bl 0x16CE4
0x1AA00  tbnz w0, #0, 0x1AA98   ; bit0 = 命中
...
0x1AA98  mov w0, wzr
0x1AA9C  bl 0x80C0               ; _exit@plt
```

-   `0x80C0` 是 `_exit@plt` ，也就是 maps 分支的最终退出调用；这个桩本身不需要单独处理，因为替换 `0x1A7C0` 入口后函数体不执行，走不到 `0x1AA9C` ；
-   IDA 伪代码里的 `exit(0)` 实际是 `_exit(0)` ；
-   `0x1AAA0 bl 0x80F0` 是 `__stack_chk_fail` ， `_exit` 不返回，不会执行到。

### 6.2 其余分支：动态 shellcode 退出

`sub_0_21B44` ：

1.  从 `0x2AABC` 取 28 字节加密模板，用 `0x2AAE8` 的密钥异或；
2.  首字加上 `0xBC0` （94 << 5）→ `mov x8, #94` ；
3.  `mmap(0, 0x1C, PROT_READ|WRITE|EXEC, MAP_PRIVATE|MAP_ANONYMOUS, -1, 0)` ；
4.  拷贝模板后 `blr` 执行 → `mov x8, #94; svc #0` = `exit_group(0)` ；
5.  `w0` 作为参数传入 shellcode（调用方都传 0）。

同库还有第二个生成器 `0x22048` （监控循环里 `0x1B448 bl 0x22048` 调用）： `0x22260` 处同样把模板首字加 `0xBC0` 得到 `mov x8, #94` ，命中后同样是 `exit_group(0)` 。

### 6.3 退出路径总表

| 命中点 | 中间路径 | 最终退出 | 退出码 |
| --- | --- | --- | --- |
| maps `0x16CE4` | `0x1AA00` → `0x1AA98` | `0x1AA9C bl 0x80C0` = `_exit(0)` | 0   |
| 线程状态 `0x1900C` | 返回 777 → `0x191F8` → `0x133D8` → `0x133F0` | `0x21B44` → `exit_group(0)` | 0   |
| 监控循环 `0x22048` | 每轮 `0x1B448 bl 0x22048` 聚合 fd / maps 结果 | `0x22048` → `exit_group(0)` | 0   |
| PrettyMethod `0x21D98` | `0x1B6D8` bit0 → 状态 `0x6DE88897` → `0x1BAD4` | `0x21B44` → `exit_group(0)` | 0   |
| fork+ptrace `0x18E74` | `0x18EFC` / `0x1887C` → `0x133D8` | `0x21B44` → `exit_group(0)` | 0   |
| 环境检查 `0x19200` | `MAGISKTMP` 命中 / `attr/prev == u:r:zygote:s0` → `0x197CC` | `0x21B44` → `exit_group(0)` | 0   |

只有 maps 分支走 libc 的 `_exit@plt` ，其余路径最终都落在 `0x133D8` / `0x21B44` / `0x22048` 的 shellcode `exit_group` 上。只 hook `exit` / `_exit` 拦不住，补丁要落在检测函数、线程入口或这些退出发生器上。

## 7\. 补丁方案

第 6 节把命中后的退出路径收敛成三个公共出口，所以补丁不必覆盖每一个检测函数：只要让“命中 → 退出”的每条路径都失效，检测继续运行也杀不掉进程。msa 层实际落地的是 **10 个 `Interceptor.replace`**；FairGuard 层的 5 个桩见第二部分。

### 7.1 从退出路径到补丁点

按出口重新归类第 6 节的总表：

| 出口  | 覆盖的命中路径 |
| --- | --- |
| `0x133D8 → 0x21B44 → exit_group` | task 状态、fork + ptrace、PrettyMethod、环境检查 |
| `0x22048 → exit_group` | 监控循环末尾的第二个生成器（ `0x1B448` ） |
| `0x80C0 _exit@plt` | maps ELF 特征匹配（ `0x1A7C0` 体内） |

除出口外，还要停两个监控循环： `0x1AAA4` （maps / fd，4 秒一轮）和 `0x191B0` （task / TracerPid，2 秒一轮）。 `Interceptor.replace` 只影响调用发生之后的执行：打补丁时线程可能已经在循环体内，甚至已经判定命中、正走向退出。所以除了线程入口， **循环体里会读检测结果或直接退出的函数也要替换**，否则当前这一轮拦不住。

`0x80C0` / `0x7F10` 两个 PLT 桩不在补丁清单里，也不需要处理：maps 分支的判定和退出都在 `0x1A7C0` 函数体内，替换入口后不会执行到 `0x1AA9C` 的 `_exit@plt` ；反过来，给 PLT 桩下补丁还会影响进程内其它调用方。

### 7.2 msa 层实际落地的 10 个 Hook

| 偏移  | 角色  | 分析位置 |
| --- | --- | --- |
| `0x21B44` | shellcode 退出生成器 genA（ `mov x8,#94; svc` ） | 6.2 节 |
| `0x133D8` | 共用退出包装，调用 `0x21B44` | 3.3 节 |
| `0x22048` | 监控循环里的第二个退出生成器 genC | 2.3 节、6.2 节 |
| `0x1AAA4` | maps / FD 监控线程入口 | 第 2 节 |
| `0x1A500` | fd_scan | 2.3 节 |
| `0x1A6AC` | fd_link_scan | 2.3 节 |
| `0x1A7C0` | maps_scan，命中后直接 `_exit@plt` | 2.1 节 |
| `0x191B0` | task / TracerPid 监控线程入口 | 第 3 节 |
| `0x18B78` | TracerPid 读取 | 3.2 节 |
| `0x1900C` | task 状态扫描（命中返回 777） | 3.1 节 |

替换统一写成：

```javascript
const cb = new NativeCallback(() => ptr(0), 'pointer', []);
Interceptor.replace(ptr(addr), cb);
KEEP.push(cb);   // 不保存会被 GC 回收
```

入口字节在 replace 后立即读回可能仍是原始值，判断是否生效要看之后的读回或行为，不能只看 `REPLACED` 那一行。最终补丁的关键片段见附录 B.4，首轮 12 点版本见附录 B.1。

### 7.3 未打补丁的检测函数

msa 层 10 个点覆盖之后，前面各节分析过的检测入口都还在跑，但它们的退出都落在已替换的函数上：

-   `0x16CE4` （maps ELF 匹配）在 `0x1A7C0` 函数体内， `0x1A7C0` 已被替换；
-   `0x21D98` （PrettyMethod）命中后走 `0x1BAD4 → 0x21B44` ；
-   `0x19200` （环境 / SELinux）命中后走 `0x197CC → 0x21B44` ；
-   `0x18E74` （fork + ptrace）走 `0x133D8 → 0x21B44` ；
-   `0x1B458` （PrettyMethod 同步入口）调用 `0x21D98` 并创建 `0x1AAA4` ，退出最终也要经过 `0x21B44` 。

所以 `0x16CE4` 、 `0x21D98` 、 `0x19200` 、 `0x18E74` 、 `0x1B458` 都不在替换清单里。判定继续命中没有关系，命中之后无路可退。

`0x1A500` / `0x1A6AC` / `0x1A7C0` / `0x18B78` / `0x1900C` 是循环体里的扫描/判定，替换它们是为了让线程不再走向退出分支，并兜住“补丁生效时已经进入本轮循环”的竞态，不是因为它们是公共出口。

## 2\. 特殊的 svc：exit_group 自毁桩

在修复后的镜像里搜 8 字节：

```
c8 0b 80 d2 01 00 00 d4
```

反汇编是：

```
mov x8, #0x5e
svc #0
```

arm64 上 `x8 = 0x5e` 是 `exit_group` ， `x8 = 0x5d` 是 `exit` 。这里没有走 libc 的 `exit` / `_exit` ，而是直接发 `svc` ，所以只 hook libc 的退出函数拦不住。

修复后的镜像里只有两处：

| 偏移  | 字节  | 含义  |
| --- | --- | --- |
| `0x345C00` | `c8 0b 80 d2 01 00 00 d4` | `mov x8,#0x5e; svc #0` |
| `0x417100` | `c8 0b 80 d2 01 00 00 d4` | `mov x8,#0x5e; svc #0` |

对 msa 和 libZzprotect 的这些地址都做了插桩，进程仍会退出，说明还有未覆盖的检测。于是换个思路，直接从 `svc` 字节特征出发做全量扫描，结果如下。

## 3\. 退出桩的分布

经过上面分析完，实际FairGuard 把退出桩注入到每个受保护业务库中。

`libZzprotect.so` 内部确实只有 `0x345C00` / `0x417100` ，但 FairGuard 在另外三个受保护库各放了一个相同 needle 的静态桩。把全部可执行映射扫一遍，结果如下：

| 模块  | 偏移  | 来源  |
| --- | --- | --- |
| `libcocos2djs.so` | `0x2251100` | 文件静态 |
| `libnative-lib.so` | `0xC1100` | 文件静态 |
| `libgame.so` | `0x77100` | 文件静态 |
| `libZzprotect.so` | `0x417100` | 文件静态 |
| `libZzprotect.so` | `0x345C00` | 运行时 RWX |

业务库名做了替换，偏移是原样本的实测值。

### 3.1 静态桩的定位规律

四个静态桩都不在库的普通 `.text` 起点，而是固定在运行时 `r-xp` 段起始 + `0x1C100` ：

| 模块  | 桩偏移 |
| --- | --- |
| `libcocos2djs.so` | `0x2251100` |
| `libnative-lib.so` | `0xC1100` |
| `libgame.so` | `0x77100` |
| `libZzprotect.so` | `0x417100` |

FairGuard 在每个受保护库尾部保留一段未加密的 `r-xp` ，退出桩放在段首 + `0x1C100` ，所以四个库可以按同一结构一次定位。 `libZzprotect.so+0x345C00` 是另一类：位于 `rwxp` 解密段，文件里该偏移全 0，进程跑起来后才生成，结构检查找不到，必须全量扫描。

扫描只搜一个特征 `c8 0b 80 d2 01 00 00 d4` 就够覆盖这套壳的全部退出桩。全量结果里以下命中不要打：

-   `libc.so` 内部的 `exit` / `exit_group` 包装：bionic 自带实现；
-   `anon@...` 的 RWX 命中：Frida / ART 自己的跳板或代码副本，不是加固桩。

## 4\. FairGuard 层的补丁：5 个桩

| 模块  | 偏移  | 类型  |
| --- | --- | --- |
| `libcocos2djs.so` | `0x2251100` | 静态 `exit_group` 桩 |
| `libnative-lib.so` | `0xC1100` | 静态 `exit_group` 桩 |
| `libgame.so` | `0x77100` | 静态 `exit_group` 桩 |
| `libZzprotect.so` | `0x417100` | 静态 `exit_group` 桩 |
| `libZzprotect.so` | `0x345C00` | 运行时 RWX 桩 |

写入方式和 msa 层一致，都是 `Interceptor.replace` 成 `NativeCallback(() => ptr(0))` 。区别是这 5 个地址替换前要先校验 8 字节 needle：静态桩在文件里就是 `c8 0b 80 d2 01 00 00 d4` ； `0x345C00` 在文件里是 0，只有运行时才会出现，所以必须在进程内按 maps 定位后再校验。

这一层最容易出错的是打桩时机：要等游戏 UI 就绪（主 Activity resumed）后再替换。更早落在 bundle 解密窗口里改桩，GLThread 会执行到未解密的数据，表现为 `SIGILL` / `SIGSEGV` ，与 bypass 是否生效无关。最终补丁的关键片段见附录 B.4。

## 三、代码页加固与页保护

上面解决了游戏 UI 加载界面杀死进程的检测，但游戏数据加载开始后，进程还是会崩。

游戏集成了 `libxcrash.so` ，崩溃时会在 APP 私有目录 `/data/data/<包名>/cache/` 下留下 `tombstone_*__<包名>.native.hitbug` 日志。

## 1\. 崩溃点

日志里的信号是 `SIGILL` ， `code 1 (ILL_ILLOPC)` ， `pc = 0x6e0c2af588` ，减掉基址 `0x6e0ba92000` 得到 `cocos + 0x81D588` ，落在 `libcocos2djs.so` 的 `r-xp` 段。

![图片描述](https://cdn.jsdelivr.net/gh/zhiyu-zeng/img@main/img/2026/11/4eb2f32484724c9d.webp)

日志里 `*pc=0xb9000260` ，反查 clean 镜像 `0x81D588` 的 4 字节是 `60 02 00 b9` ，也就是 `0xb9000260` ，一条合法的 32 位 store 指令。内存读回合法指令、执行时却报 `ILL_ILLOPC` ，说明 I-cache 里的字和内存里的字不一致——有线程在运行期反复改写这 4 字节，而且没有做 I-cache 维护。

## 2\. 触发线程

xcrash 会 dump 全部线程。pc 落在 Zz 段内的是 **Thread-22（tid 22964）** 和 **Thread-5（tid 22965）**：

![图片描述](https://cdn.jsdelivr.net/gh/zhiyu-zeng/img@main/img/2026/11/726a685edfdd9be6.webp)

两个线程的 pc 都是 `0x6e1f44a004` （ `Zz+0x347004` ）， `x8=0x65` （101， `nanosleep` 的系统调用号）， `x2` 都是 `Zz+0x347000` ——它们停在同一个 sleep 包装里， `blr x2` 的目标就是它。各自的返回地址是：

```python
lr  0x6e1f13e528 = Zz + 0x3b528
lr  0x6e1f382d2c = Zz + 0x27fd2c
```

顺着返回地址往前看，是两个结构相同的改写循环。第一个在 `Zz+0x3b4a8` ：

```python
Zz+0x3b4c4  cmp  x1,x2
Zz+0x3b4cc  udiv x0,x1,x19
Zz+0x3b4d0  msub x0,x0,x19,x1      ; x0 = i % 0x197
Zz+0x3b4d4  cmp  x0,x20            ; == 0x27 ?
Zz+0x3b4e8  ldr  x3,[x21,x1,lsl#3] ; 读原 qword
Zz+0x3b4ec  sub  w0,w24,w0         ; key = keybase - ctx->counter
Zz+0x3b4f0  eor  x0,x3,x0
Zz+0x3b4f4  str  x0,[x21,x1,lsl#3] ; ← 写点
...
Zz+0x3b524  blr  x2                ; 调 Zz+0x347000（nanosleep）
Zz+0x3b528  add  x21,x21,#0x10,lsl#12 ; 窗口 +0x10000，日志里的 lr
Zz+0x3b52c  b    Zz+0x3b4a8        ; ← 循环入口
```

第二个循环在 `Zz+0x27fca0` ，返回地址 `+0x27fd2c` 前一条 `+0x27fd28` 同样是 `blr x2` ，之后是窗口自增；写入点在 `+0x27fcf8` 。它的扫描上界没有放在通用寄存器里，而是用 `fmov x0,d8` 从 d8 取。

两个循环的寄存器和值对照：

| 值   | Thread-22（循环 1） | Thread-5（循环 2） | 角色  |
| --- | --- | --- | --- |
| 0x197 | x19 | x22 | `udiv` / `msub` 的模数 |
| 0x27 | x20 | x19 | 选中的余数槽位 |
| cocos+0x818800 | x21 | x21 | 当前 64KB 窗口基址 |
| 0x61e1ec08 | x24 | x25 | keybase |
| 0x6ebfff6190 | x23 | x28 | 共享 ctx（ `[ctx+0x1c]` 是 counter） |
| 0x10000 | x25 | x26 | 窗口大小 |
| 0xffff | x26 | x27 | 截断掩码 |
| cocos+0x1B98440 | x27 | d8  | 扫描终点 |
| 0x65 | x8  | x8  | `nanosleep` |

每个 64KB 窗口里，下标满足 `i % 0x197 == 0x27` 的 qword 被异或，约 20 个；睡 1 秒左右，窗口加 `0x10000` ，从 `0x818800` 一直扫到 `0x1B98440` 。key 每次用 `keybase - ctx->counter` 现算，同一个字被改两次不一定恢复原值，不能指望它自己改回来。

## 3\. 交叉验证

崩溃点 `cocos+0x81D588` 代入循环 1 的窗口和取模：

```python
0x81D588 - 0x818800 = 0x4D88    ; 落在第一个 64KB 窗口内
0x4D88 / 8          = 0x9B1     ; qword 下标
0x9B1 % 0x197       = 0x27      ; 正好等于 x20 / x19
```

余数是 0x27，和两个线程寄存器里的选中槽位一致。崩溃点可以确定由这两个循环写入造成。

## 4\. 保护范围

`llvm-readelf -l libcocos2djs.so` ：

```python
Type          Offset   VirtAddr           FileSiz   MemSiz    Flg Align
LOAD          0x000000 0x0000000000000000 0x225dae8 0x225dae8 R E 0x4000
LOAD          0x2264a20 0x0000000002264a20 0x002300 0x0027f8  RW  0x4000
GNU_RELRO     0x1fe4e60 0x0000000001fe4e60 0x0ea1a0 0x0ea1a0  R   0x1
```

运行期第一个 LOAD 被壳映射成 `rwx` ，所以 maps 里 `off=0` 的第一段起点就是 base。上界取 `GNU_RELRO` 的起始 `0x1fe4e60` ，按页对齐是 `0x1fe4000` ；再往后是 RELRO 和 RW 段，属于数据区，不锁。第 0 页是 ELF 头所在页，跳过。

GKI 内核页大小是 4KB，mprotect 的粒度就是 4KB，ELF 的 `p_align=0x4000` 不影响实际分页。锁的范围：

```python
[base + 0x1000, base + 0x1fe4000)
```

长度 `0x1fe3000` ，约 31.9MB，8163 页。与加固范围对照：

```python
x21 - base = 0x6e0c2aa800 - 0x6e0ba92000 = 0x818800    ← 扫描起点
x27 - base = 0x6e0d62a440 - 0x6e0ba92000 = 0x1B98440   ← 扫描终点
```

两段都在锁区间内。

## 5\. 页级写陷阱

### 5.1 处理流程

编写一个 so，启动后做四件事：

1.  把 `[base+0x1000, base+0x1fe4000)` 改成 RWX；
2.  用 dump 下来的 clean 镜像逐 4 字节比对，把已经被改坏的字修回来；
3.  装 SIGSEGV / SIGILL handler；
4.  把区间改回 RX，另起线程每 400ms 重锁一次。

之后壳每次往代码页写，store 都会触发 `SEGV_ACCERR` ；handler 里把 pc 加 4，丢掉这次写，进程继续跑。

必须先修一遍。注入发生在壳跑起来之后，目标页里已经有被 XOR 过的字；不先修回来就直接锁，锁住的还是坏字，游戏执行到就是 SIGILL。clean 镜像来自运行期 dump 的 `libcocos2djs.so` ，长度 `0x2235000` （35,868,672 字节），覆盖整个锁区间，放到 `/data/local/tmp/cocos_clean.bin` 。dump 时壳已经把所有页面解密完成，这份镜像就是“没有被改写”的基准。

不提前到壳启动前解决的原因：更早 attach 会落进 msa 的检测窗口，进程在 UI 之前就干净退出（见第一部分）；静态改 APK 不在本文范围。

### 5.2 异常分支

| 触发条件 | 处理  | 计数  |
| --- | --- | --- |
| `SIGSEGV` / `SEGV_ACCERR` ，地址在锁区间 | `pc += 4` ，丢弃这次 store | `denied` |
| `SIGSEGV` ， `pc-base==0x11FA778` 且 `x1==0` | `pc = lr` ， `x0 = 0` ，让 helper 返回 NULL | `v8` |
| `SIGILL` ，pc 在锁区间 | 从 clean 恢复 4 字节、刷 I-cache、重执行（同一地址 8 次后交还） | `repair` |
| 其他  | 转给原 handler（xcrash / Frida） | `foreign` |

第二行和壳无关：xcrash 在崩溃回调线程里 dump V8 栈，没有 isolate 时 `0x11FA758` 会读 `[x1+0x2c60]` ， `x1=0` 直接空指针崩溃。日志里会看到 `pc = base+0x11FA778` 、 `fault addr 0x2c60` ，看起来像保护失效，实际是 xcrash 自己的二次崩溃，跳过即可。

第三行是给 sweep 和上锁之间那几十毫秒的 RWX 窗口兜底：漏网的毒字执行时是 SIGILL。日志里第一现场的内存可能已经被写者改回干净值，但 I-cache 里仍是坏的，所以不管内存是否一致都要刷 I-cache 再重试；同一地址连续 8 次还失败才交还原 handler，避免死循环。

### 5.3 编译与加载

用 NDK r26 编译：

```python
aarch64-linux-android29-clang -shared -fPIC -O2 -Wall \
  -o libcodeguard.so sigfix_min.c -llog
```

push 到 `/data/local/tmp/libcodeguard.so` 。SELinux 下不能直接 `dlopen` 这个路径，boot2.js 用 `memfd_create` 把文件读进匿名内存，再 `android_dlopen_ext` 加载，按 `/memfd:codeguard` 在 maps 里找基址，按 `llvm-readelf --dyn-syms` 读出的偏移调导出：

```python

```

`guard_start` 的四个参数是 base、lo、hi 和 clean 镜像路径：


## 四、总结

## 1\. 15 个退出桩 Hook

| 层   | Hook | 作用  |
| --- | --- | --- |
| msa | `0x21B44` 、 `0x133D8` 、 `0x22048` | 3 个退出发生器 / 包装 |
| msa | `0x1AAA4` 、 `0x1A500` 、 `0x1A6AC` 、 `0x1A7C0` | maps / fd 监控线程及其扫描 |
| msa | `0x191B0` 、 `0x18B78` 、 `0x1900C` | task / TracerPid 监控线程及其扫描 |
| FairGuard | `libcocos2djs.so+0x2251100` 、 `libnative-lib.so+0xC1100` 、 `libgame.so+0x77100` 、 `libZzprotect.so+0x417100` | 4 个静态 `exit_group` 桩 |
| FairGuard | `libZzprotect.so+0x345C00` | 运行时 RWX 桩 |

## 2\. 三层防护的分工

-   msa：进程反调试，命中后经 shellcode 退出；
-   FairGuard 桩：业务库里的 `exit_group` ，干净退出；
-   FairGuard 加固：运行期改写 cocos 代码页，崩溃退出。

前两层的出口都是 `svc` ，用 `Interceptor.replace` 截断；第三层不经过任何退出桩，只能按页接管写权限。

## 3\. 三层缺一不可

-   只处理 libc 的 `exit` / `_exit` ：两层都直接发 `svc` ，拦不住；
-   只打 msa：FairGuard 在业务库里的桩还在，进程仍会退出；
-   只打 `libZzprotect.so` 两处：另外三个业务库各有一个桩，实测约 10s 后仍会退出；
-   只打 15 个桩：UI 之后 cocos 代码页继续被改写，仍会 SIGILL；
-   15 个全部替换 + 页保护：检测可以继续命中，退出路径被截断，代码页写入被丢弃。

## 4\. 验证与验收

前两层 600s 实战：UI 就绪后 attach，15/15 替换成功，心跳到 598s，线程 89～106， `HOOKS` 每轮 `15/15` ，没有 `exit_group` 发生；detach 后 replace 自动撤销，游戏继续运行，重新挂载需要重跑脚本。

第三层的验收指标：注入日志 `swept>0` ， `denied` 持续增长， `foreign=0` ，不再出现 SIGILL 崩溃和干净退出。

## 5\. 经验

-   先做退出路径收敛：找到所有命中最终汇聚的出口，再决定补丁点，比逐个猜检测函数有效；
-   直接搜 raw `svc` ： `c8 0b 80 d2 01 00 00 d4` 比 hook libc 退出函数可靠；
-   FairGuard 的静态桩有结构规律： `r-xp` 段起始 + `0x1C100` ；运行时桩在 `rwxp` 解密段，只能全量扫描；
-   全量扫描要去噪：bionic 自带的退出包装、Frida / ART 的 anon RWX 跳板不是加固桩；
-   运行期改写代码页的加固，只 Hook 退出函数不够，要按页接管写权限；
-   代码页改成 RX 后，所有来自其他线程的 store 都变成可定位、可丢弃的异常，比逐个找写入函数稳定。

```python

FUNC_EA = 0x1B458
END = idc.get_func_attr(FUNC_EA, idc.FUNCATTR_END)
DISPATCHER = 0x1B4E0

state_to_target = {
    0xA19837E7: 0x1BA48, 0xA60A3FD5: 0x1BD10, 0x6DE88897: 0x1BAD4,
    0x778D6158: 0x1BD4C, 0xB0D26C8F: 0x1BD70, 0xE1967EBE: 0x1BA54,
    0x249DEB8B: 0x1BA6C, 0x809816A5: 0x1BAE8, 0xB7302FA7: 0x1BB20,
    0x5CBB6F86: 0x1BBB4, 0x07563C85: 0x1BA90, 0x2F2914D2: 0x1BAB4,
    0x8B855CE1: 0x1BB08, 0xD48A41B3: 0x1BBA4, 0x652C51F5: 0x1BBD8,
    0x91FFD510: 0x1BC38, 0xA8BA6546: 0x1BC70, 0x66D9099A: 0x1BC90,
}

# 1) 建 W24 完整值表
w24_val = {}
for ea in idautils.Heads(FUNC_EA, END):
    m = idc.print_insn_mnem(ea)
    if idc.print_operand(ea, 0).strip().upper() != "W24":
        continue
    dis = idc.GetDisasm(ea)
    if m == "MOV" and "#" in dis:

    elif m == "MOVZ" and "#" in dis:

        w24_val[ea] = idc.get_operand_value(ea, 1) & 0xFFFF
    elif m == "MOVK":
        v = idc.get_operand_value(ea, 1) & 0xFFFF
        sh = 16 if ("LSL#16" in dis or "LSL #16" in dis) else 0
        base = 0
        for p in sorted(w24_val, reverse=True):
            if p < ea:
                base = w24_val[p]
                break
        w24_val[ea] = base | (v << sh)

# 2) patch
patched = 0
for ea, imm in w24_val.items():
    tgt = state_to_target.get(imm)
    if tgt is None:
        continue
    q = ea
    for _ in range(8):          # 放宽到 8 条
        q = idc.next_head(q)
        if idc.print_insn_mnem(q) == "B" and idc.get_operand_value(q, 0) == DISPATCHER:
            idc.patch_dword(q, 0x14000000 | (((tgt - q) >> 2) & 0x3FFFFFF))
            print(f"patched {q:#x}: B -> {tgt:#x} (state {imm:#010x})")
            patched += 1
            break
```

```python
           idc.print_insn_mnem(p) not in ("MOV", "MOVZ", "MOVK", "LDR"):
            break

    nxt = idc.next_head(ea)
    state_edges.append((ea, found, idc.print_insn_mnem(nxt),
                        idc.get_operand_value(nxt, 0)))

M = {imm: tgt for ea, imm, cond, tgt in state_edges
     if imm is not None and cond == "B.EQ" and tgt != DISPATCHER}
print(f"kept {len(M)} / {len(state_edges)}")
for k, v in M.items():
    print(f"  {k:#010x} -> {v:#x}")
```

输出 `kept 31 / ...`，保留的 31 条即 state → target 映射。

### A.2.2 字符串解密

密钥与第一部分 2.2 节相同，为 `[0x99, 0xA7, 0xA9]` 。脚本按明文的实际长度取数，不拼接 `0x00` 结尾；否则该字节会参与异或，在输出末尾多出一个字节。

```python
import ida_bytes, idaapi

B = idaapi.get_imagebase()
K = [0x99, 0xA7, 0xA9]

def dec(data):
    return bytes(b ^ K[i % 3] for i, b in enumerate(data)).decode()

def dec_imm64(v, n=8):
    return v.to_bytes(n, 'little')

print("filename   :", dec(ida_bytes.get_bytes(B + 0x2A8A0, 15)))
print("format     :", dec(ida_bytes.get_bytes(B + 0x2A8B0, 24)))
print("v104       :", dec(dec_imm64(0xEACDE2F4D0EEE6D4) +
                          (249).to_bytes(1, 'little')))
print("s2         :", dec(dec_imm64(0xC8FED0DDA3DB9DEC) +
                          dec_imm64(0xA9DA9DFCDD, 5)))
print("v55        :", dec(ida_bytes.get_bytes(B + 0x2A8E1, 16) +
                          (-8254 & 0xFFFF).to_bytes(2, 'little')))
```

## B.1 阶段 1：msa 首轮补丁

这一版在 msa 内替换 12 个点，并对两个 PLT 桩写 `ret` 。与最终版的差异：

-   多替换 `0x16CE4` 、 `0x21D98` 两个检测函数；收敛到退出路径后移除，理由见第一部分 7.3 节；
-   对 `0x80C0` / `0x7F10` 两个 PLT 桩写 `ret` 是多余的：maps 分支的判定和退出都在 `0x1A7C0` 体内，替换入口已经覆盖，最终版不再处理 PLT；
-   脚本里的 `jni_onload stub` 是早期标注，实际是第一部分 3.3 节的退出包装 `0x133D8` 。

每个点都是同一种替换，区别只在偏移。替换逻辑（示意）：

```javascript
const base = moduleBase('libmsaoaidsec.so');

// 退出发生器：命中后仍会走到这里，直接返回 0
Interceptor.replace(base.add(0x21B44),
    new NativeCallback(() => ptr(0), 'pointer', []));

// 监控线程入口：检测逻辑继续跑，但线程不再退出
Interceptor.replace(base.add(0x1AAA4),
    new NativeCallback(() => 0, 'int', ['pointer']));
```

## B.2 阶段 2：二层诊断

脚本不写内存：定位 `libmsaoaidsec.so` 与 `libZzprotect.so` 的基址，打印各目标地址前 16 字节，并安装 `Process.setExceptionHandler` 记录异常类型、地址和回溯。 `findModule` 直接用 `r.s - r.off` ，只用于观察，不能替代基于 `PT_LOAD` 的严格基址计算。回溯部分（示意）：

## B.3 阶段 3：exit_group 桩扫描

扫描分两层：先按 `r-xp` 段起始 + `0x1C100` 做结构位检查，再对 `r-x` / `rwx` / `--x` 全量分块扫描。 `HIT` 每地址只报一次，输出库名 + 偏移或 `anon@地址` ； `HB` 每 5 秒给出线程数和命中数。正文图 22 对应这一阶段的扫描结果。扫描主体（示意）：

```javascript
const NEEDLE = 'c80b80d2010000d4';
for (const r of ranges) {
    for (let p = r.base; p.add(0x1000) <= r.end; p = p.add(0x1000)) {
        const size = Math.min(0x1000, r.end.sub(p).toInt32());
        for (const hit of Memory.scanSync(p, size, NEEDLE))
            send1('HIT', `${r.name}+0x${hit.address.sub(r.base).toString(16)}`);
    }
}
```

## B.5 运行时补丁：quick.js

替代 B.4 的 `Interceptor.replace` ，直接用 `Memory.patchCode` 把 15 个点写成 `mov w0,#0; ret` ；FairGuard 的 5 个桩先校验 needle 再写。和 B.7 用同一条 frida 命令加载。核心部分（示意）：

```javascript

    code.writeU32(0x52800000);   // mov w0, #0
```


`guard_start` 等导出的偏移从 `llvm-readelf --dyn-syms libcodeguard.so` 读，换 NDK 或改源码后要重新确认；B.7 里的偏移是当前产物的实测值。

handler 的分支就是第三部分 5.2 节那张表。代码骨架如下，省略日志、错误处理和上锁线程：

```c
static void handler(int sig, siginfo_t *si, void *ctx) {
    ucontext_t *u = ctx;
    uintptr_t pc = (uintptr_t)u->uc_mcontext.pc;

    // 代码页写入：store 命中只读页，pc 后移 4 字节丢弃
    if (sig == SIGSEGV && si->si_code == SEGV_ACCERR &&
        (uintptr_t)si->si_addr >= g_lo && (uintptr_t)si->si_addr < g_hi) {
        g_denied++;
        u->uc_mcontext.pc += 4;
        return;
    }
    // xcrash 在 V8 上取栈且 x1==0：让 helper 返回 NULL
    if (sig == SIGSEGV && pc - g_base == 0x11FA778ull &&
        u->uc_mcontext.regs[1] == 0) {
        g_v8++;
        u->uc_mcontext.pc = u->uc_mcontext.regs[30];
        u->uc_mcontext.regs[0] = 0;
        return;
    }
    // 漏网的毒字：内存可能已干净，仍要恢复并刷 I-cache
    if (sig == SIGILL && pc >= g_lo && pc < g_hi) {
        uint32_t want;
        memcpy(&want, g_clean + (pc - g_base), 4);
        if (*(volatile uint32_t *)pc != want) {
            mprotect((void *)g_lo, g_hi - g_lo, PROT_READ | PROT_WRITE | PROT_EXEC);
            *(volatile uint32_t *)pc = want;
            mprotect((void *)g_lo, g_hi - g_lo, PROT_READ | PROT_EXEC);
        }
        flush_icache(pc);
        g_repair++;
        if (pc != g_ill_pc) { g_ill_pc = pc; g_ill_n = 0; return; }
        if (++g_ill_n < 8) return;
    }
    g_foreign++;
    chain(sig, si, ctx);
}
```
