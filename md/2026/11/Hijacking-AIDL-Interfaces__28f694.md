Two years ago, I wrote an [introduction article](https://dispatchersdotplayground.hashnode.dev/interprocess-communication-and-the-binder-interface) for how components communicate with each-other across the whole Android system. This article would assume that the reader has some knowledge about inter-process communication and the Binder interface.

Two Android services from two different package names can talk to each other via an **Android Interface Definition Language**, just like they can communicate with each other via `Intent` s. After all, both approaches use the `Binder` interface internally. With AIDL you can do much more, that's the only difference. Although techniques are different when it comes to exploiting `Intents` or AIDL interfaces, the vulnerability stays the same: Exported components are not fully protected:

```xml
<service
            android:name="com.victim.core.repository.services.VictimService"
            android:exported="true">
            <intent-filter>
                <action android:name="SOME_INTENT_ACTION"/>
            </intent-filter>
        </service>
```

The service above is declared exported, meaning other apps can contact it if they want to (after Android 11, they need to specifically \`query<>\` the victim but that should not be too big of an issue. In this case that I was exploring, there were no flying intents around, but I did notice a couple of extra things which made me curious.

```java
@Override // android.app.Service
    public IBinder onBind(Intent intent) {
        String action = intent != null ? intent.getAction() : null;
        if (action != null && action.hashCode() == XXXXXXX && action.equals("SOME_INTENT_ACTION")) {
            return new XuA();
        }
        return null;
    }
```

Apparently, this app was made with the intention that some other app in the system can read its' information. And since there is an `onBind` method, it's understandable that there is another service binding to it. Let's have a look at the Java code generated by jadx while reading smali:

```java
public final class XaU extends lpt5.AbstractBinderC0879lpt5 {
    public XaU(){}

    private final boolean lPT5(OtherOverloadParam ooP){ ... }

    @Override
    public void cOM4(victim.package.name.XaU xaU) { ... }

    @Override
    public void cOM4(OtherOverloadParam ooP) { ... } 
}
```

This is a typical pattern that indicates that the developers wrote a binder interface. After looking at their implementation it's relatively easy to try to mess with it. The technique here is to pretend like your malicious app is the legitimate app contacting this service. In this case, the malicious actor can just start coding and copying the interface in their app, preparing different payloads.

The rest is just coding. Once the AIDL is enabled in the attacker app, interfaces are crafted, the victim app is queried, the victim app, now the recipient, cannot tell if the service that is conducting such procedure call is legitimate or not - well because the service is not protected anyways. All you have to get right in the attacker is the package name of the victim *service*, which is totally possible via jadx or even apktool.

```java
// AIDL interfaces in attacker app
package com.victim.core;
parcelable OtherOverloadParam;
```

```java
package com.victim.core;
import com.victim.core.OtherOverloadParam;

interface OtherOverloadParam {
    void cOM4(in IOtherOverloadParamListener listener);
}
```

You can name the methods however it's prefered, but for simplicity of understanding, I copied the exact method name there. Exploit would then be just a matter of binding via the service and executing the procedure call.

```kotlin
private val connection = object : ServiceConnection {
        override fun onServiceConnected(name: ComponentName, service: IBinder) {
            // load the binder interface
        }

        override fun onServiceDisconnected(name: ComponentName) {         /////
        }

        override fun onNullBinding(name: ComponentName?) {
           /////
        }
    }
```

Once the service is connected, it's children's play to execute \`cOM4\` method on the victim app with the malicious payload:

```kotlin
 val success = bindService(intent, connection, BIND_AUTO_CREATE)

if(success) { 
   val api = copyCatAIDLInterface ?: null
   api?.let { it.c0M4("Payload") }
 }
```

Overall, this vulnerability is no different from intent hijacking. It's just that the pentester or the malicious hacker has to write more code to achieve some result.

Impact:

-   Data exfiltration
-   Unauthorized state changes
-   Abuse of privileged app capabilities

Mitigations:

-   Consider protecting such Services with `signature` level permission if the app communicating with your service is signed by the same signing key.
-   Consider algorithms that authenticate the other app with a Network call before executing any action locally. (Runtime whitelisting could also be an option here).
-   See if you can implement differently.

> This article is intended to illustrate common misconfigurations in Android IPC mechanisms from a defensive security perspective. The techniques discussed are widely known in mobile security testing and should only be applied in authorized environments, such as security assessments or lab setups.
