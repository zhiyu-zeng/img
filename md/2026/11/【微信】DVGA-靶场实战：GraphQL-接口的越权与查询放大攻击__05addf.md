## 01本质认知：GraphQL 为什么天然更容易被越权

先说 REST。在 REST 架构里，接口路径本身就是权限边界—— `/api/users/1001` 和 `/api/users/1002` 是两个不同的资源，鉴权通常就在这个路径上做。

GraphQL 打破了这个前提。它只有一个入口——通常是 `/graphql` ，然后由客户端在查询里 **声明自己要哪些字段**。

REST 与 GraphQL 请求模型的差异

```
# REST：一个请求 = 一个确定的资源 GET /api/users/1001        -> 返回 user 1001  # GraphQL：一个入口，字段由客户端指定 POST /graphql {   user(id: 1001) { id name email } }
```

这个差异直接导致三个结构性问题：

| 结构性问题 | 成因  | 安全后果 |
| --- | --- | --- |
| 越权难以在网关层拦截 | 入口只有 /graphql，路径不含资源标识 | 传统 WAF 路径规则几乎全部失效 |
| 字段级权限无处安放 | 字段在查询里动态指定，不是固定 URL | 只能逐字段校验，极易遗漏 |
| 请求复杂度不可控 | 客户端可用别名批量拼接上百个子查询 | 单次请求即可放大成批量操作 |

第一条尤其致命。很多企业以为 **「我已经在网关做了鉴权」**，但那套鉴权是按 URL 路径写的规则。当所有请求都打在同一个 `/graphql` 上时，规则的全部内容就只剩一句： *允许已登录用户访问 /graphql*。

**⚠️ 注意** 　这是我在甲方做评估时反复看到的一个真实缺口—— **很多系统确实接入了 API 网关、也确实做了认证，但业务级的对象级授权根本没有下沉到 GraphQL 层。** 网关解决了「你是谁」，完全没有解决「你能看谁的数据」。

## 02DVGA 是什么：定位、模式与关卡结构

DVGA（Damn Vulnerable GraphQL Application）是一个刻意设计成不安全的 GraphQL 应用，用于演示和训练。

| 项目维度 | 说明  |
| --- | --- |
| 名称  | Damn Vulnerable GraphQL Application |
| 仓库  | github.com/dolevf/Damn-Vulnerable-GraphQL-Application |
| 镜像  | dolevf/dvga |
| 默认端口 | 5013 |
| 协议许可 | MIT License |
| 模式设计 | Beginner（入门）/ Expert（进阶）双模式 |
| 题目组织 | 20+ 个漏洞场景，分为 6 大类别 |

六类漏洞的分类方式值得留意——它几乎就是 OWASP API Security Top 10 在 GraphQL 上的映射：

| 类别  | 核心问题 | 本质  |
| --- | --- | --- |
| Reconnaissance | introspection 开启、错误信息泄露 | 信息收集 |
| DoS | 查询深度/复杂度未限制、递归查询 | 资源耗尽 |
| Info Disclosure | 敏感字段未鉴权、错误堆栈外泄 | 信息泄露 |
| Code Execution | 注入进入 Resolver、命令注入 | 代码执行 |
| Injection | NoSQL 注入、查询注入 | 注入类 |
| AuthZ Bypass | 字段级越权、角色校验失效 | 授权绕过 |

其中值得特别注意的是最后一类 **AuthZ Bypass**。它对应的是前面说的那个结构性问题： **认证你是谁，但没验证你能读谁的数据。** 这是 GraphQL 场景下最高频、也是危害最直接的一类漏洞。

**💡 提示** 　作为本系列的定位补一句：第 12 篇的 crAPI 覆盖的是 REST 风格的 API 越权与业务逻辑缺陷，DVGA 补的是 **GraphQL 这种新型接口形态下的特有攻击面**。两者不重复——REST 的越权靠改 URL 参数，GraphQL 的越权靠改查询结构，防守手段完全不同。

## 03部署：Docker 一条命令与关键参数

DVGA 官方提供 Docker 镜像，部署很简单。

DVGA Docker 部署命令

```
# 启动 DVGA（默认端口 5013） docker run -t -p 5013:5013 -e WEB_HOST=0.0.0.0 dolevf/dvga  # 如果本机 5013 被占用，改用其他端口 docker run -t -p 5014:5013 -e WEB_HOST=0.0.0.0 dolevf/dvga 
```

这里必须解释一下参数，否则新手很容易踩坑：

| 参数  | 含义  | 不设置的后果 |
| --- | --- | --- |
| \-p 5013:5013 | 主机端口:容器端口映射 | 外部无法访问 |
| WEB_HOST=0.0.0.0 | 服务监听所有网卡 | 默认监听 127.0.0.1，外部无法访问 |
| WEB_PORT | 修改容器内监听端口 | 改主机端口映射即可，通常不需要 |

**💡 提示** 　这里体现了一个很值得注意的设计： **DVGA 默认只监听 127.0.0.1，这是一个刻意的安全默认值。** 它的意思是—— **即使你起了这个不安全的靶场，它也不会主动暴露到你的局域网里。** 而 `WEB_HOST=0.0.0.0` 是一次显式的、知情下的暴露动作。

这个设计其实传达了一个很好的工程态度： **不安全的东西应该在最小的暴露面上不安全。** 放到企业环境里，对应的实践是——演练环境的靶场应该绑定在管理网段，而不是默认挂在办公网甚至互联网出口。

**⚠️ 注意** 　另有两个实践提醒：

-   **模式切换**
    
    ：DVGA 支持 Beginner 与 Expert 两种模式，可在界面或配置中切换。建议先用 Beginner 摸清结构，再进 Expert。
    
-   **务必加防火墙规则**
    
    ：即使在本机运行，如果设置了 `WEB_HOST=0.0.0.0` ，同一网段的其他人也可能访问到。靶场暴露本身就是一个攻击面。
    

## 04第一类：Introspection 与信息收集

任何 GraphQL 测试的第一步，都是打开 introspection（自省）。它本质上是一个特殊的查询，返回整个 schema—— **所有类型、所有字段、所有参数，以及哪些字段需要什么权限。**

Introspection 查询结构

```
# introspection 查询（标准片段） query IntrospectionQuery {   __schema {     types { name kind fields { name type { name kind ofType { name } } } }   } }  # 生产环境标准做法：关闭 introspection # GraphQL 服务的部署配置项，如 Graphene/Django GraphQL 均有对应开关 
```

从攻击者视角，introspection 的价值在于 **它把黑盒变成了白盒**：攻击者不需要猜接口，整个 API 的结构会直接告诉他。

**⚠️ 注意** 　 **一个必须澄清的常见误区：关闭 introspection 不等于安全。** 很多团队把「关掉 introspection」当成了 GraphQL 安全方案，这是危险的——因为 attacker 仍然可以通过 **错误信息中的类型提示**、 **字段名猜测**、以及 **批量别名探测** 逐步枚举出 schema。introspection 只是提高门槛，不是消除风险。真正的防线是字段级授权校验。

## 05第二类：注入——从查询参数到 Resolver

注入类漏洞在 GraphQL 里的形态和 REST 类似，但 **注入点更容易被找到**——因为 schema 会告诉你每个字段接受什么类型的参数。

关键在于理解 GraphQL 的执行链路：

GraphQL 请求处理链路与注入点位置

```
# 请求链路 客户端查询    -> 解析 (Parse)    -> 校验 (Validate)   <-- schema 类型检查在这里    -> 执行 (Execute)         -> Resolver 函数  <-- 真正的数据库查询在这里  # 危险点：如果 Resolver 把参数直接拼接进数据库查询 # GraphQL 的类型校验通过了，但 SQL 注入依然成立 
```

这是 GraphQL 注入最容易踩的思维误区—— **「schema 里定义了 String 类型，所以它是安全的」**。不是的。GraphQL 的类型系统只约束 **数据形状**，完全不约束 **数据内容如何进入下游**。

一个典型的脆弱 Resolver 大致长这样：

Resolver 层的注入防护对比

```cpp
# 危险示例：参数直接拼接进查询 def resolve_user(root, info, username):     query = "SELECT * FROM users WHERE name = '" + username + "'"     return db.execute(query)  # 安全做法：参数化查询 def resolve_user(root, info, username):     return db.execute(         "SELECT * FROM users WHERE name = %s",         [username]     ) 
```

**⚠️ 注意** 　防守要点： **GraphQL 的类型系统给你的安全感是假的。** schema 说 `id: String` ，只代表客户端会传一个字符串，不代表这个字符串不会被拼进 SQL。所有 Resolver 到数据层的路径，都必须逐个确认是否使用了参数化查询。

## 06第三类：认证与会话处理缺陷

这一类问题在 GraphQL 里特别常见，原因是 **架构的天然倾向**：由于只有一个入口，很多团队会把 GraphQL 端点挂在现有的认证中间件之后，然后 **误以为鉴权已经完成了**。

| 缺陷形态 | 成因  | 后果  |
| --- | --- | --- |
| 整站未鉴权 | 端点部署时漏挂中间件 | 未登录即可枚举全量数据 |
| 只做了认证未做授权 | 只校验登录态，不校验字段权限 | 登录用户可读他人数据 |
| GraphiQL 界面未关闭 | 开发模式上线 | 攻击者获得交互式查询工具 |
| 错误信息外泄 | 调试模式开启 | 泄露 schema 与内部路径 |

第二行是重灾区。典型场景是——开发者给整个 `/graphql` 挂了一个 `login_required` 装饰器，然后觉得安全了。但 **字段级的权限差异完全没有处理**，普通用户依然能查到管理员字段。

**💡 提示** 　这里可以给出一个很实用的自查方法： **拿两个权限不同的真实账号，分别对同一个 GraphQL 端点执行完全相同的查询，然后逐字段 diff 响应结果。** 如果普通用户能看到本不该看到的字段，那就是确凿的字段级越权。这个方法不需要任何工具，一个浏览器加两个账号就能完成，但能发现绝大多数实际漏洞。

## 07第四类：授权绕过——批量查询放大攻击面

这一节是 GraphQL 授权问题里最值得单独讲的部分，因为它体现了一个 **REST 时代不存在的攻击模式**。

REST 里，越权需要一个个改 URL 去试。GraphQL 不同——由于 **别名机制** 的存在，一个请求里可以放同一字段的几十份副本，每个带不同的参数：

别名机制实现的批量对象枚举

```css
query {   u1: user(id: 1)  { id name email }   u2: user(id: 2)  { id name email }   u3: user(id: 3)  { id name email }   u4: user(id: 4)  { id name email }   u5: user(id: 5)  { id name email }   # ... 一个请求里塞进上百个 } 
```

这带来两个后果：

1.  **速率限制被绕过**
    
    ：限流通常按请求数计算。一个包含 100 个别名的请求，在计数器上只算 1 次。结果是 **单次请求完成百次对象读取**。
    
2.  **横向越权规模化**
    
    ：原本需要 100 次请求的 ID 遍历，压缩成 1 次。在日志上看起来还很像正常流量。
    

**⚠️ 注意** 　这一条对防守侧非常关键，因为它推翻了 **「我们有 WAF，有限流，所以越权不可行」** 这个假设。按请求计数的限流在 GraphQL 场景下几乎无效，真正需要的是 **按查询成本（cost）计数的限流**，以及 **字段级授权校验**。

工程上的解法是引入 **查询成本分析**：对每个字段声明权重，对每个字段声明它会触发的嵌套深度，在执行前计算本次查询的总成本，超过阈值直接拒绝。

基于成本与深度的请求准入控制

```
# 查询成本分析（伪代码） cost = sum(field.weight for field in query) * depth_multiplier if cost > MAX_COST: reject if depth > MAX_DEPTH: reject 
```

## 08第五类：DoS 与资源耗尽

DoS 是 GraphQL 最容易实现的一类攻击，因为 **查询结构本身可以是输入的一部分**。

| DoS 手法 | 原理  | 触发条件 |
| --- | --- | --- |
| 深度嵌套查询 | 字段可递归引用自身，形成指数级展开 | schema 存在递归字段且无深度限制 |
| 别名批量查询 | 单请求内重复上百个子查询 | 无查询成本限制 |
| 循环引用查询 | 通过字段互相引用构造死循环 | 无循环检测 |
| 大结果集查询 | 请求无分页的全表数据 | 字段无分页/数量限制 |

递归字段是重灾区。如果 schema 里存在 `user -> posts -> author -> posts ...`这样的循环引用，而服务端没有深度限制，攻击者可以用一个不太深的查询构造出 **指数级的实际执行量**。

**⚠️ 注意** 　这是 GraphQL 特有的 DoS 放大机制。举例：字段 A 引用 B，B 引用 C，各有两个子字段。一个深度为 10 的查询，实际返回的数据量是 2 的 10 次方级别。 **请求看起来很小，资源消耗极大。** 所以生产环境的 GraphQL 服务 **必须配置最大查询深度和最大成本双重限制**。

## 09排错清单：新手最常踩的五个坑

| 坑   | 症状  | 解决  |
| --- | --- | --- |
| 忘记 WEB_HOST | 本地能开，浏览器打不开 | 补 -e WEB_HOST=0.0.0.0 |
| 端口冲突 | 容器启动即退出 | 改主机端口映射，如 -p 5014:5013 |
| 只用 Postman 测 | 无法构造别名与嵌套查询 | 直接发原始 GraphQL 请求体 |
| 关掉 introspection 就收工 | 以为安全了 | 字段级授权才是防线 |
| 忽略递归字段 | 查询直接打挂服务 | 配置最大深度与成本限制 |

第三行值得展开。测 GraphQL 时用 Postman 图形化界面很方便，但它 **不擅长构造别名、片段、嵌套结构**。而这些恰恰是 GraphQL 测试的核心手法。更高效的做法是直接用 `curl` 或浏览器开发者工具，手工构造查询体。

事实上这也解释了为什么 DVGA 默认开启 GraphiQL 界面—— **它不是漏洞，它是靶场提供的测试工具。** 而放到生产环境，这个界面本身就应该关闭。

**💡 提示** 　排错之外补一个动手练习：建议你拿 DVGA 的 Beginner 模式， **把六类漏洞各找一个代表场景**，然后为每一类写下一句 **「如果没有这个漏洞，防守侧应该做什么」**。这个练习的价值不在靶场本身，而在于它逼你从防守视角重新审视每一个漏洞点。

## 10从 DVGA 到生产：GraphQL 安全的工程化清单

靶场通关只是第一步。下面这张清单是 **可以直接落到代码评审 checklist 里的内容**。

| 加固项 | 具体做法 | 对应漏洞类型 |
| --- | --- | --- |
| 关闭 introspection | 生产环境禁用 schema 自省 | Reconnaissance |
| 字段级授权 | 每个字段独立校验访问权限 | AuthZ Bypass |
| 错误信息脱敏 | 统一错误格式，不外泄 schema 与堆栈 | Info Disclosure |
| 查询成本限制 | 按字段权重 + 深度计算总成本并限流 | DoS |
| 最大深度限制 | 限制嵌套层数，阻断递归展开 | DoS |
| Resolver 参数化 | 所有数据层访问使用参数化查询 | Injection |
| 关闭 GraphiQL | 生产环境不暴露交互式查询界面 | Reconnaissance |
| 持久化查询白名单 | 仅允许预编译的已审核查询 | 全类  |

**💡 提示** 　倒数第二行那个「持久化查询白名单」，值得单独说明。它的做法是： **客户端不再能自由构造查询，只能引用服务端预先审核并注册好的查询**，通过查询哈希来引用。这是目前对 GraphQL 最彻底的防护思路，因为它把「客户端可控的查询结构」这个根本风险源直接消除了。代价是灵活性下降、前后端协作成本上升。

## 11等保与合规视角

GraphQL 的合规问题，主要集中在 **数据访问控制** 这一项。

| 等保 2.0 控制项 | 要求  | GraphQL 场景下的落地要点 |
| --- | --- | --- |
| 8.1.4.3 访问控制 | 最小权限、身份鉴别 | 字段级授权，替代仅路径级的粗粒度控制 |
| 8.1.4.11 数据保密性 | 敏感数据加密与隔离 | 字段级敏感数据最小化暴露 |
| 8.1.4.10 安全审计 | 记录用户行为和重要安全事件 | 审计日志需还原 GraphQL 查询内容 |

第三行有一个非常实际的坑。很多网关的审计日志只记录 **URL 路径和请求方法**。对 GraphQL 而言，这就意味着所有请求的日志长得一模一样—— `POST /graphql` 。

**而 GraphQL 真正的攻击语义全在查询体里。** 不记录查询体，就等于 **对 GraphQL 系统没有留下任何可用的审计记录**，这在等保测评中会直接导致安全审计项不符合。

**💡 提示** 　可落地的做法： **在网关层记录经过规范化处理的查询体摘要** （例如提取所有字段名与别名，或记录查询的 SHA-256），配合用户标识一起写入审计日志。这样既能支撑安全审计要求，又不会把敏感数据全文写进日志。

## 12总结

这一篇的核心，其实只有一个认知转变：

**GraphQL 不是「换了种写法的 REST」，它在安全模型上是一个根本不同的架构。**

因为入口统一、字段动态、查询结构由客户端控制，导致传统 API 安全的三件套——网关路径鉴权、限流计数、WAF 规则—— **全部需要重新设计**。

而落到工程实践上，最重要的一条是：

**💡 提示** 　 **永远不要把 GraphQL 的类型系统当成安全边界。** 它约束的是数据形状，不是访问权限，也不是数据安全。真正的安全边界只有一个—— **Resolver 里逐字段的授权校验。**
