> 💡 **AI 总结（key-points）**
>
> 通报的僵尸网络 DNS 连接并非内网主机失陷，而是外部伪造源 IP 的 UDP 欺骗请求所致，实验已验证该误判可能。
> 
> - **事件背景：** 公司互联网出口 IP 在两天内对僵尸网络域名 agronew.duckdns.org（185.157.163.139）发起 11612 次 DNS 解析，但通联流量为 0B，被监管单位通报为回连 C2。
> - **排查结果：** 对事件发生时在线且有外联流量的 20 台终端逐一检查病毒、可疑文件、DNS 流量、异常进程、系统与浏览器日志及持久化后门，均未发现木马痕迹，无法定位失陷主机。
> - **关键疑点：** 操作系统有 DNS 缓存（Windows 默认约 24 小时），20 台感染主机也不可能产生上万次查询，故判断并非真实感染。
> - **原因推断：** DNS 基于 UDP、无需握手，DNS 服务器无法验证请求包源 IP 真实性，仅凭源 IP 归属判定"某单位发起了请求"存在误判风险。
> - **实验验证：** 用 bind9 搭建 DNS 服务器，scapy 构造源 IP 伪造成第三方主机的 5 个 DNS 请求，抓包显示第三方主机未发请求却收到了响应；推测攻击者是在测试 DNS 反射放大攻击技术。

一. 背景概述

某公司被某监管单位通报了如下的安全事件信息：

在某连续的两天时间内，该公司的互联网出口IP地址回连了僵尸网络病毒的C2地址(域名：agronew.duckdns.org，IP地址：185.157.163.139)，其中请求恶意域名agronew.duckdns.org进行DNS解析11612次，与解析IP地址185.157.163.139通联传输0B。

恶意域名：agronew.duckdns.org(解析IP：185.157.163.139)归属于僵尸网络病毒。僵尸网络病毒主要通过异常下载、漏洞攻击等方式进行投递。若执行僵尸网络病毒，则会回连僵尸网络病毒C2服务器，接收服务器发送的攻击指令，向服务器回传主机信息，存在主机受控的风险。

二. 常规排查过程

2.1 排查思路

1、确定排查范围

确定事件发生时有哪些主机在该公司的网络中且产生了互联网流量。

2、上机排查

对当时在线的主机进行上机排查，以定位失陷主机。主要针对以下方面：

-   病毒查杀
    
-   可疑文件分析
    
-   DNS流量抓取
    
-   异常进程/服务识别
    
-   系统日志分析
    
-   浏览器访问日志分析
    
-   持久化后门识别
    

## 未定位失陷主机

2.2 排查结果

通过上网行为管理系统进行查询，确认在安全事件发生时，共有20台终端设备处于在线状态并且存在互联网流量。针对所有这些终端进行排查，均未发现木马程序存在和活动的痕迹，因此未定位到失陷主机。

三. 事件原因推断

再次对监管单位的通告进行分析：正常情况下，即使当时在线的20台终端同时运行了僵尸木马病毒，也不会产生上万次DNS查询请求。因为操作系统是有DNS缓存机制的(例如Windows系统默认DNS缓存时间为24小时)，在正常获取到DNS查询结果后，应用程序再次需要DNS解析时，会首先从本地DNS缓存获取解析结果，无需再向DNS服务器提交请求。

因此可认为这次安全事件并不是感染僵尸木马病毒导致的，而可能是有人在外部发送了修改了源IP地址的DNS请求包。由于DNS属于UDP协议，而UDP协议不需要通过握手建立连接，因此即使DNS请求包的源地址被任意篡改，DNS服务器也无法判断，会照常发送解析结果。同样，在互联网截获的DNS请求包，如果没有采用一定技术手段进行验证，也很难发现DNS包的源IP是否真实。因此，只通过DNS请求包的源IP地址来判断其来自某个单位是存在误判可能的。下面，我们可以通过实验来证明这一点。

## Scapy伪造源地址实验

实验：修改DNS请求包源地址

实验目的：

通过修改DNS请求包的源IP地址，理解UDP协议的无连接特性，演示DNS请求包被修改源IP地址后可以被正常发送到DNS服务器，且DNS服务器会正常解析并将结果发送到修改后的那个IP地址。

实验环境：

DNS服务器：Linux系统，IP地址：192.168.242.252

DNS客户端：Linux系统，IP地址：192.168.242.1

第三方主机：Linux系统，IP地址：192.168.242.79

实验过程：

1、DNS服务器操作

\# 更新本地软件列表

sudo apt update

\# 安装bind9软件

sudo apt install bind9

\# 查看named程序版本

named -v

\# 修改配置文件

sudo vim /etc/bind/named.conf.options # 修改为下面的形式

options {

directory "/var/cache/bind";

recursion yes;

allow-query { any; };

forwarders {

8.8.8.8;

};

forward only;

};

保存退出。

\# 检查主配置文件

named-checkconf

\# 重启服务

sudo systemctl restart named

sudo systemctl enable named

\# 使用本地的named服务进行dns解析

sudo vim /etc/resolv.conf # 修改为下面的形式

nameserver 127.0.0.1

保存退出。

2、DNS客户端操作

\# 测试解析域名

dig www.qianxin.com @192.168.242.252 +short

可以正常解析到IP地址，说明DNS服务器配置正常。

\# 将DNS请求的源地址改为第三方主机，直接在命令行执行下面的指令

sudo python -c "import sys; from scapy.all import \*; a=IP(dst='192.168.242.252',src='192.168.242.79'); b=UDP(dport=53); c=DNS(id=1,qr=0,opcode=0,tc=0,rd=1,qdcount=1,ancount=0,nscount=0,arcount=0); c.qd=DNSQR(qname='agronew.duckdns.org',qtype=1,qclass=1); p=a/b/c; \[send(p) for \_ in range(5)\]; print('attack finished!')"

在这个指令中，共向DNS服务器送了5个针对“agronew.duckdns.org”域名的解析请求。

\# 在DNS服务器上抓包，可以看到相应的DNS请求和回应

sudo tcpdump -i eth0 -nn udp and port 53

![图片](https://cdn.jsdelivr.net/gh/zhiyu-zeng/img@main/img/2026/11/d21858223bd8480a.png)

可以看到DNS服务器接收到的DNS包的源地址是第三方主机IP，而不是DNS客户端的IP地址。

3、第三方主机操作

在第三方主机抓包，可以看到在没有发送DNS请求的情况下，直接收到了DNS响应：

![图片](https://cdn.jsdelivr.net/gh/zhiyu-zeng/img@main/img/2026/11/f5d7fc7f8877f38a.png)

4、实验结论

## 反射攻击动机

将实验中的DNS服务器换成公网的DNS服务器，将DNS客户端换成在安全事件中发送篡改了源地址的DNS请求的那台主机，将第三方主机换成该公司的互联网出口IP地址，就会理解本次安全事件发生的过程。至于为什么有人会发送篡改了源地址的DNS请求，推断很可能是这个人在进行测试，因为篡改DNS请求源地址这项技术常被用于DNS反射放大攻击(通过消耗目标的带宽资源从而实现拒绝服务的一种攻击手段)。
