**白帽少年** *2026年11月26日 17:30*

上一篇把告警规则建起来了，平台从此具备了"发现异常"的能力。但发现异常只是起点：告警弹出来之后谁来看、怎么判断真假、判断完了做什么、做完之后怎么复盘——这一整套日常动作，就是安全运营。这一篇做一次完整的运营演练：一台"失陷主机"对 Web 防护节点发起多阶段攻击；从告警出现开始，走完分析研判、处置阻断、应急溯源的全流程。

## 一、安全运营是一个闭环

先说清楚安全运营在整个体系里的位置。SIEM 解决"看得见"，规则解决"报得准"，而运营解决的是"怎么处置"——它不是某个工具，而是一套有固定节奏的工作流程。业界参考最多的是 NIST SP 800-61 的事件响应生命周期：准备 → 检测与分析 → 遏制/根除/恢复 → 事后复盘。落到 SIEM 的日常，我把它压缩成四个动作组成的闭环：

研判（Triage）：每条告警到手先回答四个问题：真不真（是攻击行为还是噪音误报）、重不重（影响面多大、有没有得手）、是谁（攻击源和路径是否明确）、怎么办（观察、封禁还是升级）。这四问的答案决定了后面所有动作，也是运营工作中最依赖经验的部分。

处置（Respond）：分级响应，动作留痕。不是所有告警都值得封 IP。我的处置分级很简单：低置信度的事件观察留痕，高置信度且仍在进行的攻击做阻断，影响生产业务的动作走变更确认。有一条纪律比分级本身更重要——处置动作本身必须留痕进 SIEM。谁、在什么时间、封了哪个 IP、依据是什么，这些要变成可查询的记录，否则事后审计时"处置"就成了口说无凭的事。

溯源（Investigate）：回到证据链。阻断止住了血，但问题没答完：攻击者到底做到哪一步？有没有得手？留下什么？溯源就是把攻击窗口内的所有证据（主机日志、WAF 拦截记录、告警时间线）拼成完整故事，输出"影响面评估"。

复盘（Review）：用数据说话。每次处置后算两个数：MTTD（从攻击发生到发现）和 MTTR（从发现到处置完成）。这两个数是运营成熟度最诚实的度量，同时复盘要沉淀改进项——新的规则、新的流程，让闭环转一圈之后检测能力变强一点。

这套方法论里，"处置留痕"是最容易被忽略的一环，也是这篇演练里我唯一需要补的战前准备。

## 二、战前准备

处置留痕要做，得先让 SIEM 认识这类记录。思路和上一篇一致：demo-crm 的 JSON 日志已经有一条识别树（100700 父规则），我在 1008 规则集末尾追加一条 100840，凡是 event 字段为 security_action 的记录，以 9 级告警落地——封禁、解封这类动作会以"安全处置操作记录"出现在告警流里，附上操作者、原因和证据编号。

![图片](https://cdn.jsdelivr.net/gh/zhiyu-zeng/img@main/img/2026/11/dde72f70177b244b.png)

logtest 喂一条模拟的封禁记录，规则命中、等级 9、Alert to be generated——处置动作从此有了进 SIEM 的通道。

## 三、一次 55 秒的多阶段攻击

演练的攻击源是主机检测节点（192.168.202.130），目标是 Web 防护节点（192.168.202.131）——设定是"一台内网主机失陷后向外发起攻击"。攻击分五步，全程 55 秒（15:40:38 ~ 15:41:33）。

第一步，端口侦察。用 nc 对目标做端口探测，摸清 22（SSH）和 80（HTTP）对外开放，443/3306/3389 关闭——攻击者据此选定 SSH 和 Web 两条路。

![图片](https://cdn.jsdelivr.net/gh/zhiyu-zeng/img@main/img/2026/11/aac75143b2616a36.png)

第二步，SSH 账户探测。用三个常见服务账号名（oracle、postgres、testadm）尝试连接，都是 Permission denied——这一步在目标侧留下的是"伪用户探测"记录。

![图片](https://cdn.jsdelivr.net/gh/zhiyu-zeng/img@main/img/2026/11/51766392fe329acf.png)

第三步，SQL 注入。对 DVWA 的注入点提交 union 查询载荷，两次都被 WAF 以 403 拦下——Web 攻击没能穿透，但每次拦截本身就是一条高价值告警。

第四步，敏感接口高频访问。连续 10 次请求命令执行功能页，全部 302——单条日志不可疑，但频次已经构成扫描行为。

![图片](https://cdn.jsdelivr.net/gh/zhiyu-zeng/img@main/img/2026/11/2414183a60fb4313.png)

第五步，登录爆破。对登录接口连续提交 12 组错误口令，全部 302。到此攻击收尾：SSH 没进去、注入被拦下、爆破没成功——但从蓝方视角，攻击痕迹已经完整留在日志流里。

![图片](https://cdn.jsdelivr.net/gh/zhiyu-zeng/img@main/img/2026/11/3bf7f36322875f0b.png)

## 四、蓝方研判

切换到 SIEM 视角。攻击发生后的第一个动作不是看单条告警，而是把攻击源 IP 的告警按时间排序，看全貌。下面是 Discover 里按 data.srcip: "192.168.202.130" 过滤的视图，两个多小时窗口内该源 IP 共产生 167 条告警（当天两轮演练的累计），直方图上三波明显的峰值就是三轮攻击的时间分布。

![图片](https://cdn.jsdelivr.net/gh/zhiyu-zeng/img@main/img/2026/11/36ce370863ad3b25.png)

第一问，真不真。把告警按时间线展开看顺序：15:40:48 起三条 SSH 伪用户探测（5710），15:40:54 Web 攻击被 WAF 拦截（100610）并触发多源关联告警（100820）——主机层探测在前、Web 攻击在后、同一来源 IP，这不是单点噪音，是一条有递进结构的攻击链。

![图片](https://cdn.jsdelivr.net/gh/zhiyu-zeng/img@main/img/2026/11/48fa8c928cda8e80.png)

量化统计印证判断：近 40 分钟窗口内该源 IP 共 105 条告警，构成是登录请求留痕 34 条、敏感接口访问 24 条、SQLi 拦截 15 条、SSH 探测 9 条；升级类告警中，敏感接口高频（100801）6 条、多源关联（100820）6 条、登录爆破（100811）3 条。

![图片](https://cdn.jsdelivr.net/gh/zhiyu-zeng/img@main/img/2026/11/9f65454ae2918ecb.png)

高危告警单独看一眼：全部指向同一源 IP，等级 12~13，描述直接给出了行为定性——"疑似接口探测/漏洞扫描""疑似 Web 登录暴力破解""多源关联"。

![图片](https://cdn.jsdelivr.net/gh/zhiyu-zeng/img@main/img/2026/11/19e4ddd4db13d96b.png)

100820 的明细展开能看到完整字段：来源 agent 是 waf、解码器 apache-errorlog、攻击源 IP、MITRE 映射——研判所需的关键信息都在告警本体里，不需要再翻原始日志。

![图片](https://cdn.jsdelivr.net/gh/zhiyu-zeng/img@main/img/2026/11/3555c946360d4fd3.png)

第二问的另一半是排除误报。做两组对照：正常的健康检查连续访问登录页（200），和真人输错密码的单次登录失败（302）。之后查证这个时段的告警——健康检查因为规则只匹配 POST 请求而完全不产生告警，单次失败只留下一条 6 级留痕、没有触发频次升级。阈值设计的意义正在这里：噪音进不来，真实攻击才会升级。

![图片](https://cdn.jsdelivr.net/gh/zhiyu-zeng/img@main/img/2026/11/90c251cfc87ef0c1.png)

第三问，是谁——源 IP 192.168.202.130，内网主机检测节点，路径是"主机层探测 → Web 攻击 → 爆破"。第四问，怎么办——攻击仍在进行中（爆破在持续），置信度高、行为明确，按处置分级应该做阻断。研判结论成型，进入处置。

## 五、处置阻断

阻断动作在 Web 防护节点上执行：iptables 对攻击源 IP 下 DROP 规则，随后查规则表确认生效。紧接着做处置留痕——一条 JSON 记录写入 demo-crm 日志（动作 ip_block、操作者、原因、证据规则编号），它会被 agent 采集、命中 100840、以 9 级告警进入 SIEM。

![图片](https://cdn.jsdelivr.net/gh/zhiyu-zeng/img@main/img/2026/11/c0e919a00078d0a7.png)

处置不能只做不验。回到攻击源主机上验证封禁效果：HTTP 请求 3 秒超时无响应（curl 返回 000），22 端口连接超时——攻击源对目标的全部访问已被切断。

![图片](https://cdn.jsdelivr.net/gh/zhiyu-zeng/img@main/img/2026/11/02ecd42d4d661761.png)

SIEM 侧确认处置留痕已落库：按 100840 聚合，ip_block 与 ip_unblock 各自计数清晰可见——处置审计链成立。

![图片](https://cdn.jsdelivr.net/gh/zhiyu-zeng/img@main/img/2026/11/be3cb73c3dd63096.png)

Discover 里处置留痕的可视化视图更直观：每一条封禁/解封都带时间戳、动作类型、源 IP 和操作者，事后任何人问"这个 IP 为什么被封、谁封的"，答案直接可查。

![图片](https://cdn.jsdelivr.net/gh/zhiyu-zeng/img@main/img/2026/11/427df5a337c2cef5.png)

演练环境的最后一步是解封恢复（生产环境中这个动作要走变更流程）。解封后规则表回到空，同样写入一条 ip_unblock 留痕——处置链有头有尾。

![图片](https://cdn.jsdelivr.net/gh/zhiyu-zeng/img@main/img/2026/11/7fd1039ff5e073b6.png)

## 六、应急溯源

阻断之后回答"影响面"。溯源在两个层面展开，先目标主机（waf），后 SIEM 全量。

目标主机侧的五项取证一次做完：攻击源的 SSH 失败登录共 19 次（两轮演练累计）；攻击源的成功登录数为 0——攻击没有获得任何 shell；再交叉确认全部 SSH 成功登录的来源，都是运维工作站 192.168.202.1 的正常登录；/var/www 最近两小时无新增文件，没有 webshell 落盘；最后从 WAF 拦截记录里提取攻击载荷并解码——两条 UNION SELECT 注入语句，意图直取用户表口令。

![图片](https://cdn.jsdelivr.net/gh/zhiyu-zeng/img@main/img/2026/11/1f49b26959e78fd2.png)

这里有个值得单独说的坑：第一版取证命令 grep "Accepted" 命中了 1 条来自攻击源的"成功登录"，差点误判为攻击得手。追查发现是取证命令本身被 sudo 记进了 auth.log，后续的 grep 把自己上一条命令里的关键字也捞了进来。修正方法是锚定 sshd\[ 精确匹配 sshd 进程的日志行。取证命令的自我污染是个经典陷阱，实测一次印象深刻。

SIEM 侧的全量视图作为收口：近一小时该源 IP 共 111 条告警，各规则命中数和等级分布与前述研判一致，其中处置留痕（100840）6 条——检测、攻击、处置三类事件在同一视图里对得上账。

![图片](https://cdn.jsdelivr.net/gh/zhiyu-zeng/img@main/img/2026/11/9d8edb918f6157c5.png)

溯源结论：攻击未得手。SSH 零成功登录、注入全部被拦、爆破无命中、无文件落盘，影响面为零；攻击者的路径与意图完整还原（侦察 → 探测 → 注入 → 扫描 → 爆破），证据链闭合。

## 七、复盘

把当天的时间线拉直：攻击 15:40:38 开始，15:40:48 首条告警——MTTD 约 10 秒；15:40:54 多源关联告警定性，15:43:42 完成封禁——MTTR 约 3 分钟。三节点环境下这两个数字达标，但复盘的价值不在报喜，在改进项：

一是处置自动化。本次封禁是手工执行的，从关联告警定性到动手间隔了两分多钟；Wazuh 的 active-response 能在 100820 这类高置信度告警触发时自动执行 firewall-drop，下一步把它接上，MTTR 可以压到秒级——人工只做复核。

二是侦察阶段前移检测。nc 端口扫描在本次演练中没有触发任何告警（主机层 Suricata 的扫描规则未覆盖低速率探测），攻击的最早信号来自 SSH 探测。给扫描行为补频次类规则，可以把发现时间再往前推。

三是处置留痕的模板化。目前留痕靠手写 JSON，字段一致性依赖执行者自觉。做成固定脚本（输入 IP 和原因，自动补时间戳和操作者），既是效率问题，也是审计合规问题。

![图片](https://cdn.jsdelivr.net/gh/zhiyu-zeng/img@main/img/2026/11/0995bd252733364e.png)

## 八、总结

运营的难点不在工具，在闭环的纪律。告警按四问走完研判，处置动作留痕进 SIEM，溯源回到证据链，复盘产出可执行的改进项——每一步都不复杂，难的是每次都这么做。规则上一篇已经写好了"看得见报得准"的底座，运营要做的就是把每一次真实事件都变成检测能力升级的输入。
