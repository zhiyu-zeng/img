> 强网杯 ezphp 题解：借 SSRF 向 Redis 会话注入 phpggc 反序列化 payload，复刻 CVE-2024-40624 写入 webshell 拿 flag。
> 
> - **漏洞本质：** 题目是 CVE-2024-40624 的 CTF 复刻——缺陷在 `library/includes/functions.php` 的 `get_tracks()`，直接反序列化用户可控 cookie；官方 PoC 用 phpggc 的 `Guzzle/FW1` 任意路径写 PHP 再执行命令，本题把注入点换成可写的 Redis session。
> - **侦察路径：** 万能密码配合 sqlmap 注入，dirsearch 扫目录；`GET /status.php` 拿到版本号 34.0.3，`GET /ocs-provider/` 确认 webshell 落点目录存在；flag.php 展示的 `/opt/ctf/internal/flag.txt` 是诱饵。
> - **二次编码：** 报文里的空格必须写 `%2520`——PHP 解一层变 `%20`，curl 再解一层才是空格；少解一层会出现裸 CR/LF，只写 `%20` 则 curl 拿到的 selector 变形，实测返回空且不报错，极易卡住。
> - **Redis 注入：** SSRF 打本机 80，从 Redis 读出 420 字节原会话（`$420` 为 RESP 长度头），构造 `SET PHPREDIS_SESSION:<SID>` 报文追加 `test|<512字节 payload>`，`$937` = 420 + 5 + 512。
> - **同步细节：** SID 在包 06 键、包 07 键、包 08 Cookie 三处需一起替换；手改 body 后要同步 Content-Length（1669），长度写错返回 `-ERR Protocol error`，成功返回 `+OK`。

`$420` 是 RESP 长度头，后面 420 字节原样留着，包 07 要用。

这里的空格要 **两层**：报文里写 `%2520` ，PHP 解一层变 `%20` ，curl 再解一层才是空格。只写 `%20` 的话 PHP 直接把裸空格塞进 URL，curl 拿到的 selector 就变了——实测返回 **空**，不报错，很容易卡住。

## RESP会话注入

**注入**

这个 body 解开一层后就是一条 RESP 命令（下面是示意，真实字节是中间夹着 `\r\n` 的）：

代码块

```plain
*3
$3  SET
$49 PHPREDIS_SESSION:3201b05300aa9136b3719909f84ab270
$937 <420字节原会话>test|<512字节 payload>
```

`SID` 一共出现 3 处：包 06 的键、包 07 的键、包 08 的 Cookie，换的时候三处一起换。

-   `Content-Length: 1669` 就是这一行 body 的字节数，手改内容后别忘同步；
-   `$937` = 420 + 5(`test|`) + 512，写错会 `-ERR Protocol error` ；
-   成功返回 `+OK` 。

## 漏洞溯源分析

只是思路上复杂一些，代码审计方面的困难较大。这是 **CVE-2024-40624**

-   缺陷在 `library/includes/functions.php` 的 `get_tracks()` ，它直接反序列化用户可控的 cookie；
-   官方 PoC 写得很直白：用 `phpggc` 的 `Guzzle/FW1` 往任意路径写 PHP，然后执行命令。

换句话说， **这题是 CVE-2024-40624 的“CTF 复刻场景”**：同样的链，只是注入点从“cookie 反序列化”换成了“能写 Redis 的 session”。
