> 💡 **AI 总结（key-points）**
>
> 以一个 gets 溢出小程序为例，在 pwndbg 中逐条调试演示 x86 调用约定、call 相对寻址改写与 ret2libc 栈布局的完整构造过程。
> 
> - **编译准备：** 用 gcc -m32 静态编译并强制链入 system，关闭 PIE、栈保护并开 execstack，从 main 入口断点逐步跟踪栈布局；str[12] 因 SSE 16 字节对齐实际按 `sub esp,0x10` 分配 16 字节，位于 ebp-0x14。
> - **返回地址偏移：** 距离 = 分配大小(0x10) + saved ebp(4) + padding(4) = 24 字节，第 25 字节起覆盖返回地址（本例为 __libc_start_call_main 压入的 0x08049e45）；gets 会在输入末尾自动补 `\0`。
> - **执行流改写（重点公式）：** x86 直接近调用的 rel32 = 目标函数地址 − call 指令地址 − 5，如 `set *(int*)(0x80498df+1)=0x2ecc` 把 call printf 改为 call do_system；do_system 经 regparm 从 EAX 取参，与 printf 的栈传参方式完全不同。
> - **溢出难点：** 该 GCC 版本 main 收尾是 `pop ecx; lea esp,[ecx-4]; ret`，ECX 备份恰在溢出路径上，全填 A 会在 ret 前崩溃；需在 ECX 槽位精准填 0xffffcc50 使 ecx−4 指向 system 地址槽，payload 还须命令串以 `\x00` 截断、EBP 修复为合法栈地址、system 地址与参数之间插入返回地址槽位。
> - **简易模式与局限：** 加 `-mpreferred-stack-boundary=2` 强制 4 字节对齐后收尾退化为 leave/ret，栈结构简化为局部变量+Saved EBP+返回地址，20 字节垫片后即可纯净劫持 EIP；文中硬编码栈地址仅限当前调试环境，真实利用需配合信息泄露自动化完成。

#### 计算公式(重点部分)

在 32 位 x86 汇编中，直接调用函数的 `call <target>` 采用的是相对近调用

也就是这个指令是两个部分

call 指令 + 4字节的一个地址

```python
[ 0xE8 ] [ byte 0 ] [ byte 1 ] [ byte 2 ] [ byte 3 ]
  Opcode   |----------------- rel32 -----------------|
```

然后 `call` 指令本身所在的地址是 `0x80498df`

所以要修改 `call function` 的地址要在 `call` 指令 `+1` 的位置调整即可

这里要稍微标记一下 `call function` 这条指令本身不是 `call` 后面的地址本身

而是 这样的一个公式 `call call指令本身地址-目的函数的相对距离`

做个假设 比如 `call` 指令本身的地址是 `0x1234` 目标函数是 `0x1244` 那么想要调用目标函数 不是 `call 0x1244` 而是 `call 0x10(0x1244-0x1234)` 但是注意 `call 0x1234` 这个指令本身要占5个字节 也就是说如果直接 `call 0x10` 那么是从第五个字节向后算的所以 `call` 的最终公式应该如下(套用 `0x1234` 和 `0x1244`)

**`call ( 0x1244(目的函数地址)-0x1234(call指令地址)-0x5(call指令长度) )`**

最终如果想要从 `0x1234` 的 `call` 指令地址成功调用位于 `0x1244` 的函数的话这个计算结果就是

`call 0xb`

#### 注释1

在现代 x86/GCC 中，出于性能优化以及满足 SSE 指令集的 16 字节对齐要求，编译器开辟局部变量空间时，会按照 **16 字节（0x10）的倍数向上取整**。

也就是说当前的代码

```cpp
char str[12];
```

`str` 分配的空间小于 `0x10` 所以向上取证

但是当这个部分大于 `0x10` 时比如等于 `18` 那么还是会向上取证

```cpp
#include <stdio.h>
#include <stdlib.h>

char *gets(char *s);
int main(){
  char str[18];
  gets(str);
  printf("%s",str);
  return 0;
}
```

```bash
gcc -m32 -Wl,--undefined=system --static -z execstack -no-pie -g hello.c -o hello18 -fno-stack-protector
```

#### 注释2

```python
lea  eax, [ebp-0x14]   ; 取地址：计算出 str 的起始内存地址，放入 eax
push eax               ; 传参：将这个内存地址压入栈中
call gets              ; 调用：gets 拿到这个地址，才能知道把用户输入的字符往哪个内存位置写
```

注意此处的 `lea eax, [ebp-0x14]` 与 `lea -0x14(%ebp),%eax` 在机器码层面完全相同，唯一的区别是汇编代码的语法风格（Syntax Flavor）不同：前者是 Intel 语法，后者是AT&T语法。

#### 注释3

`printf` 是格式化输出函数

-   原型： `int printf(const char *format, ...);`
-   它需要在内部代码逻辑中主动去解析第一个参数 `format` 里的 `%` 符号。当扫描到 `%s` 时，它才会去读取栈上的下一个参数（即你的 `str` ）并完成拼接/替换。

`system` 是命令执行函数

-   原型： `int system(const char *command);`
-   它只有 1 个参数，根本没有格式化解析功能。
-   在 32 位 `cdecl` 调用约定下，函数进入时，只会取栈顶指向的第一个值作为它的第 1 参数：

do_system 是 `glibc` 内部核心执行函数

-   原型： `static int do_system(const char *line);`
-   它只有 1 个参数，同样没有格式化解析功能，负责真正调用底层系统接口执行 `/bin/sh -c <line>` 。
-   在 32 位 x86 内部编译优化（如 `regparm` ）下，它不从栈顶读取参数，而是默认从 `EAX` 寄存器获取命令字符串的地址作为第 1 参数：
    -   如果调用前未主动将目标字符串地址装入 `EAX` （或者 `EAX` 残留了其他数据），它就会直接将 `EAX` 所指的内容当成命令提交给 shell 执行。

### 理解溢出

理解了执行流以后来尝试溢出的部分, 溢出首先就不能手动去更改执行流, 而是需要通过输入被动修改执行流

直白的说就是: 不可能直接调试目标程序, 所以要从程序的输入当中破坏程序的预期执行流, 让程序走向我的预期执行流

在基础理解部分已经写出了分配的空间大小, 以及原因, 直接看关键部分代码

```
0x080498b4 <+15>:    sub    esp,0x10
```

这里分配了 `0x10` 空间大小, 在 `gets` 调用结束后打断点

```asm
   0x080498c9 <+36>:    call   0x8051c80 <gets>
   0x080498ce <+41>:    add    esp,0x10

b *main+41
```

一个本办法找到当前的内存空间 `esp` 和 `ebp` 是栈顶和栈底 那其实只需要查看一下 `esp` 和 `ebp` 就知道范围

```bash
pwndbg> dd $esp 1
```

大略过一下地址情况

这个地址 `ffffcc30` 很明显是 `str` 字符串的存储位置

接下来的 `ffffcc40 + 8` 的位置是 `ebp` 那么 `ffffcc40 + 12` 的位置是返回地址的位置

查看这个地方 稍微做一下注解

![图片描述](https://cdn.jsdelivr.net/gh/zhiyu-zeng/img@main/img/2026/11/5f11008cfcdd2873.webp)

在 Linux C 语言环境中，程序的第一个执行入口并不是 `main` 函数，而是编译器链接进去的 `_start` 汇编桩

1.  操作系统加载：内核加载 ELF 后，先跳转到 `_start` 。
2.  glibc 运行时初始化： `_start` 调用 glibc 的启动入口 `__libc_start_main` 。
3.  调用 main： `__libc_start_main` 内部通过子函数 `__libc_start_call_main` 来负责真正发起 `call main` 。

在 `__libc_start_call_main` 执行 `call main` 的瞬间，CPU 硬件机制自动将紧接着的下一条指令地址（即 `0x08049e45` ，也就是 `__libc_start_call_main+101` ）压入栈中作为返回地址（Return Address）。

简单来说在这种情况下 把 `main` 函数看做一个普通函数这个函数返回会向着 `__libc_start_call_main` 这里去返回

溢出攻击的终极目标是覆盖掉返回地址（Return Address），让程序在 `ret` 时跳去执行预期的代码。

内存布局如下

```python
内存地址      内容        对应含义
ffffcc34    41414141   <-- str[0..3]（输入的 4 个 A）
ffffcc38    080efd00   <-- str[4..7]
ffffcc3c    080b07c2   <-- str[8..11]
------------------------------------------------------
ffffcc40    ffffcc60   <-- 函数开头 push 保存的 ecx
ffffcc44    080ebff4   <-- 函数开头 push 保存的 ebx
ffffcc48    00000002   <-- 函数开头 push 保存的 ebp (Saved EBP)
ffffcc4c    08049e45   <-- 真正的目标：返回地址 (Return Address)
```

所以这个部分的距离计算如下

`0xffffcc4c - 0xffffcc34 = 0x18 = 24字节`

可以理解一共分配了 `0x10(16)` 字节的空间大小那么 `ebp` 在 `0x10 + 4` 的位置然后返回地址在 `ebp+4`

所以常规状态下 这个距离也可以这样算

`分配大小 + ebp(4字节) + 一个到return address的padding 一般为(4字节)`

也就是在本例当中 `0x10(16)+0x4(4)+0x4(4)=0x18(24)` 也就是从第25个字节开始覆盖到返回地址

按照这个逻辑输入到24个 `A` 看到的内存布局应该是 `A` 紧连返回地址

![图片描述](https://cdn.jsdelivr.net/gh/zhiyu-zeng/img@main/img/2026/11/ffa8c29599d066c6.webp)

来查看这个内存布局 继续向下执行一定是崩溃的

在崩溃之前有一个点需要理解

```
ffffcc40     41414141 41414141 41414141 08049e00
```

在这里 `ffffcc40+0xc` 这个位置原本的返回地址从 `08049e45` -> `08049e00` 这里并不是返回地址变了

从这个变化恰恰应证了溢出是正常覆盖了的 `00` 是因为 `gets()` 会在读取完字符串末尾自动追加一个空字节 `\0`

#### 溢出攻击

综上 尝试28个 `A` 时应该会让返回地址变成 `0x41414141` 然后由于没有这样的地址所以报错

由于我们 `gcc` 编译器版本的原因 所以导致GCC 编译器生成了一种特殊的函数收尾机制，它不是直接 `ret` ，而是：

精准修复 `ECX` （Stack Pivoting / 栈迁移变种）：

溢出时不能全填 `A` ，必须把 `0xffffcc40` 位置精准填入一个合法的栈地址（比如原始的 `0xffffcc60` ）。这样 `lea esp, [ecx-4]` 算出来的还是合法栈顶，程序就能活着执行 `ret` 。

构造标准的 ret2libc 栈结构： 在 `ret` 后面不能只填函数地址，必须按照 32 位函数调用的栈格式来排布：

```python
[填充到 ECX] + [合法的栈地址] + [填充到 RET] + [system 地址] + [system 的返回地址] + [参数字符串地址]
```

这里存在的问题有几个

**大量文字来袭**

1.栈帧布局错位

在内存中， `SYSTEM_ADDR` 之后紧接着写入了 `EAX_ADDR` （ `0xffffcc34` ）当 `ret` 跳转到 `system` 时， `system` 内部从栈顶读取数据：

-   `[ESP]` （返回地址槽位）被写入了 `0xffffcc34` （本该是参数）。
-   `[ESP + 4]` （参数槽位）被写入了 `0x080efd00` （后续的栈内存）。

`system` 接收到的参数指针不是 `"id;"` ，而是错误的垃圾地址，导致命令无法执行。

2.缺少合法的返回地址槽位

`system` 函数执行完毕后，试图从 `[ESP]` （此时是错误的值 `0xffffcc34` ）返回，导致控制流飞向非法地址或异常退出。

3.命令字符串缺少空字符截断 (`\x00`)

`b'id;A'` 没有以 `\x00` 结尾。如果想要命令执行这里需要用 `\x00` 去截断一下

4.EBP 寄存器被连续的 `C` 字符破坏

`b'C' * 8` 覆盖了 `EBP` 槽位，导致被调用函数无法建立正确的栈帧。

* * *

简单来说就是如果想要这样调用，首先要给 `system` 创建独立的栈帧, 让进入 `system` 以后能够正确的读取到参数, 并且参数的格式要正确

那么调整思路就是首先要让 `0xffffcc40` 这里精准指向 `system`, `system` 的地址是要放在 `ffffcc40 + 0xC` 的位置的也就是 `0xffffcc4c`

但是由于本例当中的二进制程序在 `main` 函数收尾时，有一句特殊的编译器内置指令： `lea esp, [ecx-4]` 并非常规的 `ret` 这里的流程如下

`pop ecx` 会把 `0xffffcc40` 这个栈格子里的值弹出来，存进 `ECX` 寄存器里。

紧接着的 `lea esp, [ecx-4]` \*会拿 `ECX` 里的这个值去减 4，算出新的栈顶 `ESP` 。

```asm
   0x080498ec <+71>:    lea    esp,[ebp-0x8]
   0x080498ef <+74>:    pop    ecx
   0x080498f0 <+75>:    pop    ebx
   0x080498f1 <+76>:    pop    ebp
   0x080498f2 <+77>:    lea    esp,[ecx-0x4]
   0x080498f5 <+80>:    ret
```

![图片描述](https://cdn.jsdelivr.net/gh/zhiyu-zeng/img@main/img/2026/11/e9ca868a7c78ad3f.webp)

所以，在 `0xffffcc40` 填什么数字， `ECX` 就会变成什么数字，最终算出来的 `ESP` 就会指向哪里。

所以这里一定要让 `0xffffcc40` 这个地址的值指向 `system` 函数的地址也就是 `0xffffcc40+0xC` 的位置

所以 `0xffffcc40` 的位置不能够填 `0xffffcc60` 因为 `0xffffcc60 - 0x4` 指向了一个莫名其妙的地址

填 `0xffffcc50` 就刚好 `0xffffcc50 - 0x4 =0xffffcc4c` 这就刚好指向了 `system` 函数的地址

这个最重要的部分推导完成以后修改 `payload` 大概会写一个这样的代码

##### system执行

由于像 `system` 这样的函数在被调用时，会执行函数前序指令（Prologue，如 `push ebp; mov ebp, esp` ），并使用 `ebp` 作为基址指针来寻址它的参数和局部变量

所以 `ebp` 不能被破坏 如果 `ebp` 被破坏成了非法的垃圾数据（如 `0x43434343` ），函数内部在读写内存时就会访问到无效地址，从而立刻触发段错误崩溃。替换成合法的可写栈地址，是为了让函数能安全地建立自己的栈帧。

最后就是传参的问题

目前 `SYSTEM_ADDR` 后面直接跟了 `EAX_ADDR` （参数地址）。

在 `system` 地址和参数地址之间，必须先插入一个返回地址（这个返回地址不需要是真实的, 可以优雅的退出, 也可以直接崩溃），否则 `system` 会把参数地址当成返回地址去执行。

所以可以调整一下 `payload`

```python
payload += SYSTEM_ADDR # system address
```

```bash
gcc -m32 -mpreferred-stack-boundary=2 -Wl,--undefined=system --static -z execstack -no-pie -g hello.c -o easy_hello -fno-stack-protector
```

`-mpreferred-stack-boundary=2` 强制 GCC 使用 4 字节（2^2）对齐，彻底剥离掉那套基于 `ECX` 的复杂平栈汇编。

也就是说原来是16字节对齐, 所以, 分配空间也会是按照16字节去分配, 现在是4字节对齐, 分配空间是按照4字节 而 `str` 刚好是12字节空间, 所以在这里就不会多分出空间

修改后， `main` 函数的收尾会变成最经典的：

```python
leave
ret
```

此时：

1.  栈结构直接简化为： `[str 局部变量] + [Saved EBP] + [Return Address]` 。
2.  不会再有 `ecx-4` 提前崩掉的问题，输入 20 字节垫片后，第 21 个字节就能百分之百纯净地劫持 `EIP` ，非常适合清晰、直观地验证你的计算与执行流。
