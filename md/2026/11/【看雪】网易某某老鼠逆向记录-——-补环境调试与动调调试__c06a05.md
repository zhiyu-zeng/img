## TOP2 ELF 环境补齐：PT_DYNAMIC /.dynsym / GOT

「补环境」最典型的一节。目标不是运行动态库，而是把 ELF 里能承载地址信息的结构手工重建出来，绕开被混淆的 Section Header。

### 2.1 ELF 结构

```python
ELF64 Header（文件偏移）
├── 0x00  e_ident[16]              7f 45 4c 46 / class / endian
├── 0x28  e_shoff      (Q)         Section Header 表偏移
├── 0x3a  e_shentsize  (H)
├── 0x3c  e_shnum      (H)
├── 0x3e  e_shstrndx   (H)
└── e_phoff                       Program Header 表偏移
    │
    ├── PT_LOAD                    段映射与权限（加载器只认这一层）
    └── PT_DYNAMIC ──→ .dynamic
        ├── DT_SYMTAB ──→ .dynsym  符号名 + st_value
        ├── DT_STRTAB ──→ .dynstr
        ├── DT_JMPREL ──→ .rela.plt
        ├── DT_PLTGOT ──→ .got
        └── DT_NEEDED ──→ 依赖库
│
└── e_shoff ──→ Section Headers     给静态工具看，可混淆 / strip / 填假
```

加载器只认 Program Header；Section Header 是给静态分析工具看的，可以混淆、strip、填假值而不影响运行。

### 2.2 elf_syms2.py：手工解析

这一步执行的是 `elf_syms2.py` 。它不调用 readelf，而是直接从 ELF Header 的定长偏移取字段、手工 `unpack` 节头：

```python
# -*- coding: utf-8 -*-
"""解析 ELF 动态符号表: 尝试多种编码解码被混淆的符号名"""
import struct, sys

LIB = sys.argv[1]

def parse_elf(path):
    data = open(path, 'rb').read()
    assert data[:4] == b'\x7fELF'
    is64 = data[4] == 2
    endian = '<' if data[5] == 1 else '>'
    if is64:
        e_shoff = struct.unpack_from(endian + 'Q', data, 0x28)[0]
        e_shentsize = struct.unpack_from(endian + 'H', data, 0x3a)[0]
        e_shnum = struct.unpack_from(endian + 'H', data, 0x3c)[0]
        e_shstrndx = struct.unpack_from(endian + 'H', data, 0x3e)[0]
    else:
        e_shoff = struct.unpack_from(endian + 'I', data, 0x20)[0]
        e_shentsize = struct.unpack_from(endian + 'H', data, 0x2e)[0]
        e_shnum = struct.unpack_from(endian + 'H', data, 0x30)[0]
        e_shstrndx = struct.unpack_from(endian + 'H', data, 0x32)[0]
    shdrs = []
    for i in range(e_shnum):
        off = e_shoff + i * e_shentsize
        if is64:
            sh = struct.unpack_from(endian + 'IIQQQQIIQQ', data, off)
            shdrs.append(dict(name=sh[0], type=sh[1], flags=sh[2], addr=sh[3],
                              offset=sh[4], size=sh[5], link=sh[6], info=sh[7],
                              addralign=sh[8], entsize=sh[9]))
    shstr = shdrs[e_shstrndx]
    shstr_data = data[shstr['offset']:shstr['offset'] + shstr['size']]
    def get_str(tab_off, off):
        tab = data[tab_off:tab_off + 0x100000]
        end = tab.find(b'\x00', off)
        return tab[off:end] if end != -1 else b''
    strtab = None
    for sh in shdrs:
        sname = get_str(shstr['offset'], sh['name']).decode('utf-8', 'replace')
        if sname in ('.dynstr', '.strtab'):
            strtab = sh
            break
    if strtab is None:
        print("no strtab"); return
    # 解码候选: raw / utf-16-le / gbk / latin1 各种变换
```

```python
elf_syms2.py 的补法
├── 不依赖静态工具（Section Header 被混淆时输出不可信）
├── ELF Header 定长偏移 → e_shoff / e_shentsize / e_shnum / e_shstrndx
├── shdr 结构 IIQQQQIIQQ 手工 unpack
├── shstrndx 取节名，定位 .dynstr / .strtab
├── 符号名尝试 raw / utf-16-le / gbk / latin1 多种解码
└── 结果：数万条符号（名字可读，st_value 另判，见 TOP3）
```

### 2.3 GOT / PLT 补出的调用关系

```python
某校验函数入口
└── 内部 PLT 桩 → GOT 项 → 指回同一函数
        │
另一处理函数
└── 某偏移处 bl <PLT 桩> → 调用后使用返回值
        │
第三处错误路径
└── 分支条件被静态改写
        │
旁证：业务侧确实配置了校验回调
├── GOT JUMP_SLOT 指向 set_keylog_callback
├── GOT JUMP_SLOT 指向 set_verify
└── 存在 TLS 密钥日志钩子函数
```

有 `set_verify` 的 GOT 项，说明业务代码主动配置了校验回调，不是默认不校验。这一条决定静态改写面是否值得做，也是「先验证符号可信、再谈地址」的落点。

### 2.4 三条 ELF 解析路径的函数级对照

同一批符号被三条互不依赖的路径各解析过一遍，目的不是重复，是互相证伪：节头表可以给静态工具填假值，PT_DYNAMIC 才是加载器真正读的那份。

`elf_dynsyms.py` 走动态段，函数拆成三段：

```python
def parse_phdrs(data):
    is64 = data[4] == 2
```

### 2.5 PLT stub 与 GOT 间接跳转的判定模板

`plt_finder.py` 、 `plt_finder2.py` 、 `plt_finder3.py` 、 `got_indirect_scan.py` 、 `xref_pin_scan.py` 是同一套模板的多次实现。判定链固定：

```python
PLT stub 识别链
├── ① readelf -r 取 GOT 地址；节头剥离时改用 PHDR 推 .plt 区间
├── ② text 段扫 adrp xN,<GOT页> / ldr xM,[xN,#off] / br xM 三件套
│   └── 变体：add x16,... 后 br x17；或 blr xN
├── ③ 每条 ldr 看紧邻下一条是不是 blr / br
├── ④ GOT 条目 → .dynsym 索引 → 名字
└── ⑤ 与字符串 xref 交叉，确认这条调用真的在用
```

`plt_finder.py` 的注释里写明了扫描区间与失败条件：只在可执行 PT_LOAD 中范围最大的那段里找 `ldr/ldur` 取 GOT 的指令，然后前向搜索紧邻的 `blr` ； `got_indirect_scan.py` 更保守，先收集全部 `ldr xM,[xN,#imm]` ，再反向找最近的 `adrp xN` 算出 got 地址，避免把普通常量加载误判成 GOT 引用； `xref_pin_scan.py` 只找两类—— `BL` 直调和 `ADRP+LDR` 数据引用。

```python
一次实证（说明模板为什么必要）
├── 现象：0x085620 处一条 bl 0x6be50 被当成普通函数调用
├── 反汇编：0x6be50 / 0x6c5d0 都是 adrp 0x266000 + ldr + br
├── 定位：0x266000 区是 GOT，0x6xxxx 段全是动态符号跳板
├── 结论：真实目标是动态符号，不是本地函数
└── 同节另一类误判：OLLVM 平坦化函数用 cmp w8,状态常量 分派
    ├── 整段无标准 prologue
    └── movk 出来的大常量是 switch case 值，不是算法常数
```

```python
"无引用"结论的修正
├── 过严扫描：只认精确 imm 匹配 → 全部报"无引用"
├── 放宽后：adrp 页基址 + imm 相加 → 命中目标 VA
│   └── 例：adrp 0x26b000 + imm 0x6c8 = 0x26b6c8
├── 附带产出：同一引用簇里连续 7 个点，间隔 8 B
└── 纪律：先反汇编确认寻址模式，再定扫描阈值
```

`"无 xref"` 是扫描参数的函数，不是事实。笔记里把这条单独记成一次修正，因为它推翻了前一版的多处结论。

## TOP3 符号表可信度判定

TOP2 解决「能不能读」，这一节解决「读到的值是不是真的」。

### 3.1 两份动态库的差别

```python
同一客户端
├── 主库（内嵌较旧版本 TLS 实现）
│   ├── Section Headers       被混淆
│   ├── PT_DYNAMIC            完好 → .dynsym 可读

│   └── 定位结果              主动放弃
```

差别不是「能不能读符号表」，是「读到的值是不是真的」。

### 3.3 证据分层

```python
证据分层
├── 可用 ──────────────────────────────────────────┐
│   版本串与构建日期串（若干固定地址）             │
│   证书错误串：                                   │

│     "self signed certificate"                    │
│     "unsupported certificate purpose"            │
│                                                  │
└── 不可用 ────────────────────────────────────────┤
    错误串 xref 只达错误串表 / PLT 桩区
```

### 3.4 判定顺序

```python
拿到符号
├── ① 反汇编看序言 / 首条指令
├── ② 与符号语义比对
├── ③ 不匹配 → 记为不可信，不硬用
└── ④ 匹配 → 用 GOT / PLT / 字符串 xref 交叉证明该栈确实在用
```

放弃理由按原始口径：混淆库的精确入口需要运行时内存扫描或反混淆工具，静态定位成本高于收益，因此主交付不基于它。TOP3 与 TOP5 是同一种操作：把搜索空间里走不通的部分标出来。区别是 TOP3 判「地址」，TOP5 判「假设」。

```python
    hdr = read_va(va, 32)
    ln = u64(hdr, 24)                         # CommonHeader 16B + hash 8B + len 8B
    if ln <= 0 or ln > 2000: return None
    return read_va(va + 32, ln).rstrip(b'\x00').decode('latin-1', 'replace')
```

### 4.6 两处自定义序列化的实证

前面 4.2 写的是标准 Lua 5.1 布局。后面又补了一次实证：真正卡住解析的不是加密，也不是截断，是这个构建改了两处序列化。

```python

├── opcode 表    标准顺序          →   整体重排
├── 解析器步进   p += n           →   p += n * 4
└── RETURN       30               →   5
```

判据是硬观测，不是猜：

```python
├── 修正解析器后，某主脚本 24,703 B 全量耗尽、0 字节残留
├── 还原 39 个原型（含嵌套）+ 全部常量池 + 指令流 + 行号
├── 反汇编文本 97 KB
└── 39/39 个原型的末指令 opcode 均为 5
    └── 标准 Lua 5.1 的 RETURN 是 30 → 末指令位置天然是 opcode 判定的锚
```

这一步执行的是 `lua51_disasm.py` 与 `lua_insn_layout.py` 。 `lua_insn_layout.py` 专门负责把 `lineinfo` 的步长从 1 改成 4 并验证剩余字节； `lua51_disasm.py` 则同时保留标准 OPS 表和自建 NAMES 表，输出时明确区分「结构标准」与「语义重排」。

```python
解析错位的两种根因（不要混为一谈）
├── 结构层：lineinfo 用 u32 存储
│   ├── 症状：debug 段之后所有偏移整体错位
│   └── 修法：改步长，重算消耗字节
└── 语义层：opcode 表重排 + B/C 交换 + 全局槽号
```

```python
rounds = 6 + 52 // n
DELTA  = 0x9E3779B9                       # 公开算法常数
sum    = rounds * DELTA                   # 解密时递减至 0
每轮:  e = (sum >> 2) & 3
       p = n-1 .. 1:
           ki = (p ^ e) & 3
           MX = ((z ^ k[ki]) + (y ^ sum))
                ^ (((y >> 3) ^ (z << 4)) + ((y << 2) ^ (z >> 5)))
           v[p] -= MX;  y = v[p]

           MX0 = (((z >> 5) ^ (y << 2)) + ((z << 4) ^ (y >> 3)))
```

`run_early_dd.py` 的 `check()` 是最小验证器：给定一份 16 B 候选 key，跑完整解密循环，只比前 16 B：

```python
def check(key16):
    k = struct.unpack('<4I', key16)
    v = list(struct.unpack('<%dI' % n, cdata))
    rounds = 6 + 52 // n
    sumv = (rounds * DELTA) & MASK
    while sumv != 0:
        e = sumv >> 2
        y = v[0]
        for p in range(n - 1, 0, -1):
            z = v[p - 1]
            ki = (p ^ e) & 3
            mx = ((((z ^ k[ki]) + (y ^ sumv)) & MASK) ^
                  ((((y >> 3) ^ ((z << 4) & MASK)) +
                    (((y << 2) & MASK) ^ (z >> 5))) & MASK)) & MASK
            v[p] = (v[p] - mx) & MASK
            y = v[p]
        z = v[n - 1]
        ki = e & 3
        mx0 = (((((z >> 5) ^ ((y << 2) & MASK)) +
                 (((z << 4) & MASK) ^ (y >> 3))) & MASK) ^
                (((y ^ sumv) + (z ^ k[ki])) & MASK)) & MASK
        v[0] = (v[0] - mx0) & MASK
        sumv = (sumv - DELTA) & MASK
    return struct.pack('<%dI' % n, *v)[:16] == ref[:16]
```

`xxtea_verify_pair.py` 把方向也参数化： `decrypt_sub(data, k)` 与 `encrypt_add(data, k)` 各有减法版和加法版，再对「所有偏移 × 两个方向」做笛卡尔遍历，判据是结果是否以字节码头开头。 `md5_candidates.py` 的 `test_key(key, name)` 把候选串统一编码后喂给同一对函数，用 84 B 小文件先做最快验证。

`crypto_xxtea_bitcrack.py` 的 `solve_k(mx, z, s)` 是位级 DP，不用求解器，按 32 位逐位推：

```python
def solve_k(mx, z, s):
    C1 = ((z >> 3) ^ ((z << 4) & MASK)) & MASK
    C2 = ((z << 2) & MASK) ^ (z >> 5)
    B  = (z ^ s) & MASK
    # 状态 (k_bits, c_a, c_b)：c_a/c_b 是加法链的两路进位
    cands = [(0, 0, 0)]
    for i in range(32):
        new = []
        for kb, ca, cb in cands:
            for ki in (0, 1):
                A  = zbits[i] ^ ki
                ai = A ^ Bbits[i] ^ ca
                ca2 = (A & Bbits[i]) | (A & ca) | (Bbits[i] & ca)
                bi  = C1b[i] ^ C2b[i] ^ cb
                cb2 = (C1b[i] & C2b[i]) | (C1b[i] & cb) | (C2b[i] & cb)
                if (ai ^ bi) == MXb[i]:
                    new.append((kb | (ki << i), ca2, cb2))
        cands = new
        if not cands: return None
    return cands[0][0]
```

主循环对 `p = n-1..1` 逐个求 `mx = (v_c[p] - v_p[p]) & MASK` ，用 `ki = (p ^ e) & 3` 把结果归入 4 个 key 字；同一 `ki` 出现两个不同值就记冲突，四个字集齐即停。

```python
四类脚本的职责
├── check()                完整循环 + 前 16 B 比对（黄金对验证）
├── decrypt_sub / encrypt_add   方向 × 偏移遍历（实现自校验）
├── test_key()             候选串批量编码后快速筛（84 B 小样本）
└── solve_k()              逐位 DP 反推单个 key 字（首轮差分）
    ├── 输入：mx / z / sum
    ├── 每轮候选数受进位一致性剪枝
    └── 输出：一个 32 位字或 None
```

```python
位级 DP 的状态树
├── 位 i 的输入   z_i, B_i, C1_i, C2_i, MX_i, ca, cb
├── 枚举 k_i ∈ {0,1}
├── A_i = z_i ^ k_i
├── a_i = A_i ^ B_i ^ ca       → ca' = majority(A_i, B_i, ca)
├── b_i = C1_i ^ C2_i ^ cb      → cb' = majority(C1_i, C2_i, cb)
├── 保留条件：a_i ^ b_i == MX_i
└── 32 位后 cands[0] 即一个候选 key 字
```

注意：这条路线最终没能产出可用于解密资产的结果；脚本里「把反推结果写成文件」的部分本文不引用，也不披露任何候选值。它能留下的只有方法：把加法进位链拆成逐位状态，用一致性剪枝代替穷举。

### 7.2 xxtea_z3v6.py：约束模型

以下是该脚本的模型部分，输入文件路径与具体样本标识已略去：

```python
# z3v6 诊断: 单字约束测模型速度与明文假设
# 结论判定: 1字 SAT(快) → 模型OK; UNSAT(快) → 明文假设错; 超时 → 实例本身难
CIPHER = '<某个密文样本>'
cipher = open(CIPHER, 'rb').read()
cdata = cipher[12:]                       # 跳过 12 B 容器头
n = len(cdata) // 4
rounds = 6 + 52 // n
v_c = list(struct.unpack('<%dI' % n, cdata))
MASK32 = 0xffffffff
DELTA = 0x9e3779b9                        # 公开算法常数
sum0 = (rounds * DELTA) & MASK32
es = [((sum0 - r * DELTA) & MASK32) >> 2 & 3 for r in range(rounds)]

def solve(known_map, tag, timeout=30000):
    k = [BitVec(f'k{i}', 32) for i in range(4)]
    def pick(ki):
        return If(ki == 0, k[0], If(ki == 1, k[1], If(ki == 2, k[2], k[3])))
    def MX(z, y, sumv, ki):
        t1 = (z ^ pick(ki)) + (y ^ sumv)
        t2 = ((y >> 3) ^ LShR(z << 4, 0)) + ((y << 2) ^ LShR(z, 5))
        return (t1 ^ t2) & 0xffffffff
    def MX0(z, y, sumv, ki):
        t1 = (LShR(z, 5) ^ (y << 2)) + ((z << 4) ^ LShR(y, 3))
        t2 = (y ^ sumv) + (z ^ pick(ki))
        return (t1 ^ t2) & 0xffffffff
    v = [BitVecVal(x, 32) for x in v_c]
    sumv = sum0
    for r in range(rounds):
        e = es[r]
        y = v[0]
        for p in range(n - 1, 0, -1):
            z = v[p - 1]
            ki = (p ^ e) & 3
            v[p] = (v[p] - MX(z, y, sumv, ki)) & 0xffffffff
            y = v[p]
        z = v[n - 1]
        ki = e & 3
        v[0] = (v[0] - MX0(z, y, sumv, ki)) & 0xffffffff
        sumv = (sumv - DELTA) & MASK32
    s = Solver()
    s.set(timeout=timeout)
    for i, val in known_map.items():
        s.add(v[i] == val)
    res = s.check()
    print(f'{tag}: {res}', flush=True)
    if res == sat:
        m = s.model()
        key = b''.join(struct.pack('<I', m.eval(k[i]).as_long() & 0xffffffff)
                       for i in range(4))
        return key
    return None

# 四组诊断假设：尾部零字 / JSON 头 / 版本字段 / 前缀联合
solve({24: 0}, '诊断1: 尾部零字')
solve({0: 0x20200a7b}, '诊断2: JSON 起始')
solve({1: 0x72657622}, '诊断3: 版本字段')
solve({0: 0x20200a7b, 1: 0x72657622, 2: 0x6e6f6973, 3: 0x20203a22},
      '诊断4: 前缀联合')
```

```python
z3 约束模型
├── 未知量  k0..k3（4 × BitVec 32）＝ 16 B key
├── 已知量  v_c = 密文载荷按 u32 小端解出的字数组
├── 常量    DELTA / MASK32 / rounds / es 轮索引
├── 展开    rounds 轮，每轮 n-1 次 MX + 一次 MX0
├── 假设    known_map：令某个明文字等于猜测值
├── 判定    sat → 取 model；unsat → 假设错；超时 → 实例难
└── 四组诊断
    ├── 尾部零字（弱方程）
    ├── JSON 起始 '{' + 换行 + 空格
    ├── 版本字段 '"ver'
    └── 前缀联合
```

`LShR` 与 `>>` 的区分是位级模型里容易出错的地方： `>>` 是算术右移， `LShR` 才是逻辑右移。脚本里 MX 与 MX0 的写法不完全对称，对应 TOP6 说的非对称变体。

注意：模型里出现的 `DELTA` 、若干立即数与明文假设都是公开算法常数或格式猜测， **不是密钥**；真实密钥候选值一律不在本文出现。

### 9.3 B/C 交换与实证

| op  | 语义  | 实证  | 与标准 Lua 的差别 |
| --- | --- | --- | --- |
| `7` MOVE | `R[A] = R[C]` | B 恒 0；f2=0 校验 B==0 | 标准用 B |
| `17` GETTABLE | `R[A] = R[C][B]` | B=键 256+k 或寄存器，C=表；f2=3 | 标准相反 |
| `33` SELF | 与 GETTABLE 同族 | —   | 同族  |
| `4` CALL | `fn=R[A]`, `nargs=B+1`, `nresults=C-1` | `[319] A=35 B=2 C=4 → 3 参数调用` ； `[39] B=0 → 1 参数` | C=0 → multret |
| `20` LOADK | `R[A] = k[Bx]` | —   | Bx 直接索引，无 -256 |
| `34` GETGLOBAL | `R[A] = global[k[Bx]]` | —   | 同上  |
| `12` SETGLOBAL | `global[k[Bx]] = R[A]` | 新确认（ABx） | 直接索引 |
| `36` SETTABLEK | `R[A][k[C-256]] <- R[B]` | C=283→'ctor'、284→'init' 方法名递增吻合 | C>=256 时是常量索引 |
| `0` LT | `R[B] < R[C]` ，A=跳转极性 | `[283] A=0 B=33 C=339 → R33 < 0.0` | B/C 常量感知 |
| `22` EQ | `R[B] == R[C]` ，A=1 → 不等跳 | —   | B/C 常量感知 |
| `16` CONCAT2 | `R[A] = R[C] .. R[B]` | `[306] R32=R32..后缀` ； `[313] R32=R32..后缀` ； `[323] 前缀..R32` | 二元拼接 |
| `14` TEST | `R[A]` 真值；B=0 常规 | —   | —   |

```python
按差别归类
├── 寄存器来源改用 C     MOVE / GETTABLE / SELF / CONCAT2
├── Bx 直接索引          LOADK / GETGLOBAL / SETGLOBAL / SETTABLEK
├── 参数编码改动         CALL 的 nargs/nresults
├── 比较极性在 A         LT / EQ / TEST
└── 未定                op10 LOADIMM 疑似 R[A]=k[Bx] 或立即数
```

```python
│   └── w3=3 按 w2 的 bit8 决定清位后比较 / 直接比较
├── 0x609270   分发到具体 handler
├── handler     统一先做寄存器边界检查
├── 0x60933c   取下一条指令
└── 0x60915c / 0x6091b8   两个统一错误出口
```

```python
从位域到校验子的映射
├── 指令字 v
│   ├── v[5:0]    → op → FMT 下标
│   ├── v[13:6]   → A  → 与寄存器上限 w11 比较
│   ├── v[22:14]  → B  → helper 的 w2 实参（ubfx #0xe,#9）
│   └── v[31:23]  → C  → lsr #0x17
└── FMT[op]
    ├── [1:0] → 三条分路
    ├── [3:2] → 第二次 helper 的 w3
    └── [5:4] → 第一次 helper 的 w3
```

把 helper 单独认出来之后，9.2 那张「f2 / f4 操作数校验子」表才从猜测变成有指令依据的结论： `f2=0` 对应「B 必须为 0」， `f2=3` 对应「B 可作常量索引 256+k」，正是 helper 里 `tbz w2,#8` 与 `and w2,#0xfffffeff` 两条路径。

### 10.4 表构造还原与三种输出形态

`vm_table_restore.py` 是针对「纯数据脚本」写的：这类脚本的顶层几乎全是 `LOADK + NEWTABLE + SETTABLEK + RETURN` ，逐行反汇编反而看不出是个表，所以直接折叠成表字面量。

```python
NAME = {4:'CALL', 5:'RETURN', 7:'MOVE', 9:'CALLSETUP', 10:'LOADIMM',
        14:'TEST', 17:'GETTABLE', 20:'LOADK', 21:'JMP', 22:'EQ',
        25:'GETTABLE2', 30:'NEWTABLE', 33:'SELF', 34:'GETGLOBAL',
        35:'ARITH', 36:'SETTABLEK', 3:'LOADBOOL', ...}

def fmt_const(c):
    if c is None: return 'nil'
    if isinstance(c, bool): return 'true' if c else 'false'
    if isinstance(c, float):
        return repr(int(c)) if c == int(c) else repr(c)
    if isinstance(c, str):
        return repr(c.rstrip('\x00'))      # 引擎字符串填充，剥尾部 \0

def fmt_code(code, consts):
    for i, v in enumerate(code):
        op = v & 0x3F; a = (v >> 6) & 0xFF
        c = (v >> 14) & 0x1FF; b = (v >> 23) & 0x1FF
        Bx = (v >> 14) & 0x3FFFF
        if op == 20:   ...  R[a] = K[Bx] 常量值
        elif op == 36: ...  R[a][K[c]] = R[b]
        elif op == 30: ...  array=c+1, hash=b+1
        elif op == 17: ...  R[a] = R[b][R[c]]
```

`gen_table` 的做法是先跟踪寄存器，再折叠连续指令：

```python
def gen_table(code, consts):
    reg_val = {}
    for v in code:
        if (v & 0x3F) == 20:                # LOADK → 记住寄存器里的常量
            a = (v >> 6) & 0xFF
            Bx = (v >> 14) & 0x3FFFF
            reg_val[a] = consts[Bx] if Bx < len(consts) else None
    def rval(b):
        if b < 256:
            return fmt_const(reg_val[b]) if b in reg_val else '<R%d>' % b
        return fmt_const(consts[b - 256])  # b>=256 时是常量索引
    # 遇到 NEWTABLE R[a]，向后收集同一寄存器的 SETTABLEK，
    # 直到遇到新的 NEWTABLE / RETURN / 非本表指令为止
```

注意这里 `b < 256` 判寄存器、 `b >= 256` 判常量索引，与 9.3 表里 `SETTABLEK` 的 `C=283 → 常量索引` 是同一套编码。 `main()` 对折不掉的指令保留 `// [i] OP... A= B= C=` 的注释行，不假装还原成功。

`luadump.py` 是标准对照组， `RD` 类把读操作封装成 `u8 / i32 / u32 / dbl / str` ， `read_func` 产出统一的 node 字典：

```python
node = {'src': src, 'line': linedef, 'lastline': lastline,
        'nups': nups, 'nparams': numparams, 'maxstack': maxstack,
        'k': [], 'insn': [], 'kids': [], 'upnames': []}
```

`vm_pseudo_gen.py` 的 `walk_proto(p, depth, out)` 在这之上按深度缩进，把常量表和指令流拼成伪代码文本。 `deep_crypto_scan.py` 的 `walk_proto` 同构，只是把输出换成「搜某类调用点」。

```python
三种输出形态
├── 逐行反汇编（vm_disasm_engine.py / luadump.py）
│   ├── 忠实、可复核
│   └── 读不出表结构与控制流意图
├── 表字面量（vm_table_restore.py）
│   ├── 只对纯数据脚本有效
│   ├── 输入：顶层 code + consts
│   └── 输出：{ [key] = value, ... } + 未折叠行的注释
└── 缩进伪代码（vm_pseudo_gen.py / 反编译器产出）
    ├── 按 Proto 深度递归
    ├── 常量池按名字排序便于对照
    └── 不是可编译源码，笔记里明确标为「伪代码」
```

```python
表构造折叠的判定链
├── 起点：op=30 NEWTABLE，目标寄存器 R[a]
├── 向后扫：op=36 SETTABLEK 且 A==a
│   ├── 键来自 K[c]
│   ├── 值来自 rval(b)：寄存器跟踪值 / 常量 / 未知占位
│   └── 累加到 entries
├── 终点：新 NEWTABLE / RETURN / 其它打断指令
└── 输出：R[a] = { ... } (NEWTABLE)，并把 i 跳到 j
```

10.3 里那些「不能横向相加」的数字，多数就是这三条管线各自跑出来的：同一个 luac 既可能产出一行反汇编，也可能产出一张表，还可能产出一段伪代码，计数口径不同。

## TOP11 静态字节改写与可复核性

这一节只讲方法：如何在不运行目标的前提下改一个动态库，以及如何让改动可复核。 **不涉及改写目标函数清单、具体地址、字节与用途**，也不提供任何验证流程。

### 11.1 改写流程

```python
静态改写流程
├── ① 判定符号表可信度（TOP3）
│   └── 不可信 → 整条线放弃，不硬写
├── ② 逐点比对函数序言前 8 B
│   ├── 一致 → 覆写
│   └── 不一致 → 跳过并打印，绝不盲写
├── ③ 输出改写后副本（原件留底）
├── ④ 计算改写前后 SHA1
└── ⑤ 写 manifest：前后哈希 + 每点偏移 + 描述
```

第 ② 步是关键。这一步执行的是 `patch_openssl.py` ，其结构（地址表与字节已略去）：

```python
# 输入/输出路径略去；PATCHES 为 (偏移, 期望序言, 描述) 三元组列表
PATCHES = [
    (<偏移1>, <期望序言1>, <描述1>),
    # ... 共 5 项，地址与字节本文不披露
]
PATCH_BYTES = bytes.fromhex('<8 字节，略去>')

def sha1(path):
    h = hashlib.sha1()
    with open(path, 'rb') as f:
        for chunk in iter(lambda: f.read(1 << 20), b''):
            h.update(chunk)
    return h.hexdigest()

def main():
    data = bytearray(open(SRC, 'rb').read())
    orig_sha = sha1(SRC)
    patched = []
    for va, expect_hex, desc in PATCHES:
        expect = bytes.fromhex(expect_hex)
        if data[va:va+8] != expect:
            print(f'[!] MISMATCH @0x{va:x}: ... (符号可能被混淆偏移, 跳过以保安全)')
            continue
        data[va:va+8] = PATCH_BYTES
        patched.append((va, desc))
    if not patched:
        print('[x] 无有效 patch 点, 终止'); sys.exit(2)
    open(DST, 'wb').write(data)
    with open(MANIFEST, 'w') as f:
        f.write(f'source_sha1: {orig_sha}\n')
        f.write(f'patched_sha1: {sha1(DST)}\n')
        f.write(f'patch_bytes: {PATCH_BYTES.hex()}\n')
        for va, desc in patched:
            f.write(f'0x{va:x}: {desc}\n')
```

```python
manifest 的作用
├── 前后 SHA1 → 能判断改动范围、发现二次改动
├── 逐点偏移 + 描述 → 能定位改了什么
└── 不是「改好了」一句话 → 后来人可自行复核
```

记录结果：5 点序言比对全部一致，无 MISMATCH。另有 `patch_libcocos2dlua.py` 与 `restore_libcocos2dlua.py` 分别负责另一侧尝试与还原，原件留底。

前面 12 节讲的都是「不运行、只解析」。同一次工作里还跑过一条字面意义上的补环境路线：用模拟器把动态库加载起来，缺什么依赖就补什么桩，看它能不能走到初始化。这部分结论全是环境层面的，不依赖设备。

### 12.5 模拟器自检与翻译层观测

加载之前先做了一次自检，确认模拟器真的在执行目标指令集的指令，而不是空转：用 keystone 现场汇编一小段，交给 Unicorn 跑，检查返回值。

```python

├── keystone 现场汇编 → 写入模拟内存
├── Unicorn 执行 → x0 = 100，expect = 100 → PASS
├── 加载 ELF：PT_LOAD = 3，base = 0x10000000
├── 执行 DT_INIT
│   ├── 宿主桩捕获到 mprotect 系统调用
│   │   └── nr=226 / addr=0x100E9000 / len=0x167000 / prot=7
│   └── 正常返回后跳到 base+0xB3D9E8
└── 结论：加载期代码确实被执行，页权限变更可被宿主侧观测
```

```python
三种地址空间的换算
├── 静态偏移        ELF 里的 st_value / 段内偏移
├── 加载基址        模拟器或系统分配（0x10000000 / 0x12000000 / 设备侧基址）
├── 运行时 VA       = 基址 + 静态偏移（同一翻译层内成立）
└── 文件偏移        = 段 p_offset + (VA - 段 p_vaddr)
```

```python
为什么静态地址会"存在但不经过"
├── 目标库为 ARM 指令集，宿主为 x86_64
├── 经二进制翻译层执行，原始地址不是最终执行地址
├── 冷启动时某静态偏移处观测到 0 CALL
└── 结论：静态地址只能作候选，必须经运行时证据确认
```

这一条同时解释了 0.2 的环境参数、TOP20 的 A1 失败案例，以及 TOP15 里「模块内过滤不可靠」的反例：翻译层会把代码搬出原本的模块区间， `base + offset` 只在同一个地址空间内有效。

### 14.2 dd_capture.py：按映射表挑段

这一步执行的是 `dd_capture.py` 。路径与设备细节已略去，核心逻辑如下：

```python
# 流程: 读 /proc/<PID>/maps → 挑候选 rw- 段 → 逐段 dd → pull → 本地扫字节码头
def sh(*a):
    r = subprocess.run([ADB] + list(a), capture_output=True, text=True, timeout=120)
    return r.stdout

# 1. maps
maps = sh('shell', 'su', '-c', f'cat /proc/{PID}/maps')
ranges = []
for line in maps.splitlines():
    m = re.match(r'([0-9a-f]+)-([0-9a-f]+)\s+(rw-\S)\s+[0-9a-f]+\s+\S+\s+\d+\s+(.*)', line)
    if not m:
        continue
    start = int(m.group(1), 16); end = int(m.group(2), 16)
    size = end - start
    path = m.group(4)
    # 字节码缓冲的宿主: 空路径匿名段 + 分配器池；其它映射是噪声
    if path == '' or path.startswith('[anon:'):
        if 1 * 1024 * 1024 <= size <= 32 * 1024 * 1024:
            ranges.append((start, end, size, path))
ranges.sort(key=lambda r: -r[2])

# 2. 逐段 dd
for i, (s, e, sz, p) in enumerate(ranges[:40]):
    skip = s // 4096
    count = (sz + 4095) // 4096
    sh('shell', 'su', '-c',
       f'dd if=/proc/{PID}/mem bs=4096 skip={skip} count={count} of=<设备临时文件> 2>/dev/null')
    sh('pull', '<设备临时文件>', '<宿主输出>')
```

```python
段筛选规则
├── 权限 rw-
├── 路径为空（匿名）或以分配器池标记开头
├── 大小 1 MB – 32 MB（整数幂附近，符合宿主特征）
├── 排除 jit / gralloc / 文件映射等噪声
├── 按大小降序，取前 40 段
└── 每页 4096 B，skip = start >> 12，count = ceil(size / 4096)
```

### 15.3 模块基址与偏移的复算公式

15.2 说要交叉比对，这里把公式写全，并给出那个反例的完整读法。

```python
三种地址
├── 静态偏移 off      ELF: st_value / 段内偏移 / 格式表偏移
├── 段起始 base       设备 maps 或模拟器分配
├── 运行时 VA         = base + off
├── 文件偏移 foff     = 段 p_offset + (VA - 段 p_vaddr)
└── 反向              off = VA - base；落在哪个 PT_LOAD 由区间比较定
```

```python
基址可信度检查
├── ① 插桩框架 enumerateModules() 给出模块基址
├── ② /proc/<pid>/maps 给出同名映射区间
├── ③ 两者一致 → 后续 base+off 可用
├── ④ 反汇编该地址看序言 → 与已知函数形状比对（TOP3）
└── ⑤ 任一环不一致 → 地址降级为「候选」，不能直接下结论
```

反例展开：某次按 `a.detail` 统计，2042 / 3541 个 r-- 段（约 2.5 GB）落在「模块外」。

```python
"模块外"意味着什么
├── 翻译层把代码搬离原模块映射区
├── 以模块名为过滤条件的扫描会漏掉大部分可执行内容
├── enumerateRanges() 与 enumerateModules() 的口径不一致
└── 结论：过滤条件本身要按环境重写，不能沿用真机习惯
```

```python
地址类失败的根因归类
├── 基址取错（不同实例 / 不同加载方式）
├── 偏移来自被污染的符号表
├── 静态地址不在真实执行路径（翻译层）
```

## TOP18 数据面 hook：memcpy → malloc

这一节是第二部的核心，也是第一部「静态走死」之后的转向。

### 18.1 问题重述

```python
原问题：密钥是什么？
  └── 静态侧已穷尽（TOP5 排除表 / TOP12 六条死路）

改问：脚本要执行，解密后的字节码缓冲必然在内存里存在过
  └── 明文在哪一瞬间、哪一个缓冲里可读？
```

```python
方案决策
├── ① 零注入读段         稳，未触发防护；抓到碎片，抓不全
├── ② memcpy hook        高频函数
│      → onLeave 时目标缓冲仍是密文；必崩 agent ── 弃
├── ③ ARM 库静态偏移 hook
│      → 冷启动 0 CALL（翻译层）── 弃
└── ④ malloc hook        低频，onLeave 得缓冲首址
       → 延时后读，解密已完成 ── 采用
```

### 18.2 Step 1：memcpy 侧密文捕获（S2）

这一步执行的是 `hook_memcpy.js` 。原始代码（无敏感内容）：

```javascript
// Hook memcpy/memmove: 抓大块内存拷贝
var memcpy = Module.findGlobalExportByName('memcpy');
var memmove = Module.findGlobalExportByName('memmove');
var c = 0;

function hookMem(fn, name) {
    if (!fn) { console.log('[mem] no ' + name); return; }
    Interceptor.attach(fn, {
        onEnter: function (args) {
            this.dst = args[0];
            this.src = args[1];
            this.n = args[2].toInt32();
            this.t = Date.now();
        },
        onLeave: function (ret) {
            if (this.n > 500 && c++ < 200) {
                console.log('[' + name + '] n=' + this.n + ' src=' + this.src +
                            ' dst=' + this.dst + ' t=' + this.t);
                try {
                    var b = this.src.readByteArray(Math.min(32, this.n));
                    if (b) {
                        var bytes = Array.prototype.slice.call(new Uint8Array(b));
                        var hex = bytes.map(function (x) {
                            return ('0' + x.toString(16)).slice(-2);
                        }).join('');
                        console.log('    src32: ' + hex);
                    }
                } catch (e) {}
            }
        }
    });
}
hookMem(memcpy, 'memcpy');
hookMem(memmove, 'memmove');
```

```python
S2  密文捕获
├── 手段    挂拷贝函数，抓源指针指向的加密块，按长度过滤落盘
├── 产物    14+ 块，644 B ~ 39,808 B
├── 判据    与分配侧同名明文按 size + 尾部 padding 规律一一对应
└── 结论    加密层为 XXTEA 类，key 长度 16 B
```

关键观察（阶段笔记原文口径）：

```python
DST 在 memcpy onLeave 时仍是容器魔数（密文搬移，解密延迟 / 独立调用）
延时若干秒后：部分缓冲已出现明文结构，部分仍是容器魔数
★ 解密非原地：密文拷贝到目标后，解密输出在别处
```

这一条直接否掉了「继续盯拷贝目标缓冲」的思路，把落点转到「谁分配了输出缓冲」。

### 18.3 Step 2：改用分配点

这一步执行的是 `hook_mallocsrc.js` （最终版）与 `hook_plain.js` 、 `hook_final_dump.js` 、 `hook_malloc2.js` 、 `hook_mallocf.js` 、 `hook_mallocfix.js` 、 `hook_malloc_pair.js` 、 `hook_alloc.js` 、 `hook_free.js` 、 `hook_capture.js` / `capture2.js` 等一长串演进版本。最终版代码（私有目录已泛化）：

```javascript
// malloc hook + 8s dump + source 路径解析 + 上限 2500
var mallocPtr = Module.findGlobalExportByName('malloc');
var n = 0;
var dir = '<应用私有目录>';
var savedCount = 0;

function getSource(buf, sz) {
    // Lua 5.1 main proto: 头12B + source string (size_t=8)
    try {
        if (sz < 20) return '';
        var arr = new Uint8Array(buf);
        if (arr[0] !== 0x1b || arr[1] !== 0x4c) return '';
        var dv = new DataView(buf, 12, 8);
        var len = Number(dv.getBigUint64(0, true));
        if (len < 1 || len > 200) return '';
        var s = '';
        for (var i = 0; i < len && 20 + i < sz; i++) {
            var c = arr[20 + i];
            s += (c > 31 && c < 127) ? String.fromCharCode(c) : '?';
        }
        return s;
    } catch (e) { return ''; }
}

Interceptor.attach(mallocPtr, {
    onEnter: function (args) {
        this.sz = args[0].toInt32();
    },
    onLeave: function (ret) {
        var sz = this.sz;
        if (sz > 500 && n < 2500) {
            var p = ret, idx = n++;
            setTimeout(function () {
                try {
                    var head = p.readByteArray(8);
                    if (head) {
                        var b = Array.prototype.slice.call(new Uint8Array(head));
                        if (b[0] === 0x1b && b[1] === 0x4c) {
                            var src = getSource(p.readByteArray(Math.min(sz, 200)),
                                                Math.min(sz, 200));
                            var full = p.readByteArray(sz);
                            if (full) {
                                var f = new File(dir + '/L_' + idx + '_' + sz + '.bin', 'w');
                                f.write(full);
                                f.close();
                                savedCount++;
                                console.log('★SAVED L_' + idx + '_' + sz + ' src=' + src);
                            }
                        }
                    }
                } catch (e) {}
            }, 8000);
        }
    }
});
```

```python
判定条件链
├── malloc 返回
├── sz > 500                 过滤小对象
├── n < 2500                 限流
├── setTimeout 8000 ms       等解密完成
├── 读前 8 B，判 1b 4c       字节码头
├── getSource 解析 source    头 12 B + u64 长度 + 字符串
└── 整块写盘 L_<id>_<size>.bin
```

```python
├── hook_memcpy.js       n>500, c<200, 只打前 32 B

├── hook_final_dump.js   n>4000, 200 ms 限流, n<300, 8 s 后二次判头

```

```python
为什么 malloc 比 memcpy 稳
├── memcpy 是高频调用，逐次 readByteArray 会拖垮 agent
├── malloc 的返回指针天然是缓冲起点，不用判 dst / src 谁变明文
├── 分配大小直接给 sz，落盘长度不用另猜
└── 代价：必须延时读，取指与写入之间存在时间窗
```
