我们直接猛攻一个支付apk。因为是用于支付的，它的防护强度跟别的 apk 不一样，常规那套强跳未必使得上。这趟我主要想试页面强跳和接口测试，上手先来最基本的，看能不能强行跳进它的页面、直接摸到它对外暴露的接口。手上两摊材料，一摊是它 native 库里那段加密逻辑，另一摊是模拟器里跑起来之后抓到的 hook 日志。

口令就藏在 SP 项里，是一串 base64。我从这串东西开始往下挖。

* * *

## TOP0 目标、材料与环境

要解的是 mobileaix 工作流数据库用的 SQLCipher 口令，我把它叫 `antsp` 。它就存在 SP（SharedPreferences）里，是一串 152 字符的 base64，解码后是 112 字节密文。按加密后的长度倒推，明文应该是 97 字节。

我拿到 apk 之后没急着往下解，先把环境理清楚，这一步踩过坑。真正能用的是几十个脚本和它们吐出来的输出。

```python
目标：解密 mobileaix 工作流数据库口令（代号 antsp）
  │
  ├── 密文载体：SP 项
  │     ├── key  : mobileaix_datacenter_db_password
  │     ├── 形态 : 152 字符 base64
  │     ├── 解码 : 112 B 密文
  │     └── 明文 : 97 B（预期，未直接读出）
  │
  └── 环境注记
        ├── 日志体积很大（654 MB / 582 MB，UTF-16LE）
        ├── PowerShell 重定向输出为 UTF-16LE，Python 读取需 decode('utf-16-le')
        └── 动手前先确认源目录已清空
```

环境上先撞见三件事。日志大得离谱，一次 654 MB、一次 582 MB。PowerShell 重定向出来是 UTF-16LE，Python 读的时候得显式 `decode('utf-16-le')` ，不然全是乱码。还有动手前得先确认源目录清空了，迁移可能还没做完。这些当时都影响了我后面怎么读输出。

## TOP1 SP 密文与口令生成器

我想知道明文长什么样，同时把它的生成规则摸清楚。SP key 和口令生成规则前面已经拿到，从这里接着往下。

```python
口令明文（预期 97 B）
  │
  ├── 字符集：62 个
  │     ├── 小写段 zxcvbnmlkjhgfdsaqwertyuiop
  │     ├── 大写段 QWERTYUIOPASDFGHJKLZXCVBNM
  │     └── 数字段 1234567890
  │
  ├── 抽样：Random.nextInt(62)
  ├── 次数：97 轮
  ├── 拼接：无前缀、无分隔符
  └── 结论：明文形态 = 97 位、字符集受限（未直接读出，属预期）
```

我看到的是一个 62 字符的字母数字表，顺序固定，代码用 `Random.nextInt(62)` 循环抽 97 次，无前缀直接拼起来，所以明文应该是一个 97 位、字符只落在这个表里的串。后面如果真解出了东西，长得不像 97 位受限字符集，那就错了。

SP key 是 `mobileaix_datacenter_db_password` ，来自 `classes15.dex` 的字符串 id `59466` 。

为了确认这个 key 是不是真被代码用到，我写了个 DEX 引用扫描脚本去跑它。结果冒出来两个数，一版输出说引用 780 处，另一版说 391 处。我一开始以为是脚本写错了，回头看才发现两版统计口径不一样，前者按虚方法字段去重前的计数，后者标的是引用 391 处这样的字样。两个数都留着。

```python
引用命中的类集中在检测与配置族
  UIDetectRoutingInspection / UIDetectServiceImpl
  UIDetectServiceImplInner / UIDetectConfig
  CompatibilityDetectConfig / QrCodeDetectConfig
  WhiteScreenDetectConfig / PbUtilInner / PerformanceUtils ...
```

命中都集中在检测和配置这一族类上，说明那个 key 串在 DEX 里被大量类常量池共享，字符串 id 命中不等于真有人读写了这个 SP 项。这 780 / 391 处引用大部分是噪音背景，不能当成这里就是读写点的证据，我后面也就没在字符串引用上白费功夫。

## TOP2 Java 调用链（读与写）

字符串引用靠不住，我就换个方向，顺着实际的读写调用往下追。读写两条链在 Java 层都是无变换的，只是把参数薄薄地透传到 JNI，没做派生或二次变换。这两条链是：

```python
读：PasswordUtils.getPassWord()
  → sp.getString(key, "")
  → SecurityEncryptor.decryptString(antsp)
  → EncryptDataUtils.decrypt
  → JNI 偏移 0x5658
  → PLT
  → sgStaticSafeEncryptData(mode = 2)
```

```python
写：PasswordUtils.a()
  → SecurityEncryptor.encrypt(明文 97 B)
  → EncryptDataUtils.encrypt
  → JNI 偏移 0x559c
  → sgStaticSafeEncryptData(mode = 1)
  → putString(key, 密文).apply()
```

追下来发现， `SecurityEncryptor.encrypt / decryptString` 只是 `EncryptDataUtils` 的一层薄封装，Java 层没有 key 变换。这就把问题整个推到了 native 侧。明文能不能还原，取决于 so 里那个 `sgStaticSafeEncryptData` 怎么实现，以及它依赖的运行时 key 和全局对象状态。

两个 JNI 偏移 `0x5658` （解密）和 `0x559c` （加密）是 Java 进 native 的落点， `mode=1/2` 是同一个 native 函数的加解密方向开关。这些数字我按原样记下，没改动。

## TOP3 薄封装与惰性初始化

追到 native 之前，我先排掉了两处看起来像 key 装载、其实无关的初始化。不排掉它们，我可能会在错误的函数上死磕。

-   `initNative @0x5238` 就是个 SetApiLevel，写 `0x3e8f0` ，没有任何 key 装载动作。
-   惰性初始化 `@0x5714` 读 bss 标志 `0x3e8f4` / `0x3e908` → `bl 0x35d10` （shadowhook_init）→ 置位，跟 key 无关。

```python
initNative @ 0x5238
  └── SetApiLevel
        └── 写 0x3e8f0            （无 key 装载，排除）

惰性初始化 @ 0x5714
  ├── 读 bss 标志 0x3e8f4
  ├── 读 bss 标志 0x3e908
  ├── bl 0x35c10 → 0x35d10        （shadowhook_init）
  └── 置位标志                    （与 key 无关，排除）
```

那轮反汇编还顺带打出了 PLT thunk 到 GOT 的映射：

```python
thunk 0x35c80 -> GOT 0x308
thunk 0x35c90 -> GOT 0x310
thunk 0x35cd0 -> GOT 0x330
thunk 0x35ce0 -> GOT 0x338
thunk 0x35cf0 -> GOT 0x340
thunk 0x35d10 -> GOT 0x350        ← shadowhook_init
```

这份输出末尾带了一条 Python 报错 `TypeError: %x format: an integer is required, not NoneType` ，那轮脚本解析到某个动态段字段时没拿到值，直接退出了。上面那个 thunk 映射只是它退出前打出来的一部分，后面的解析没跑完。我当时没修这个脚本，报错连同输出一起留着。解析未完成。

排掉干扰项之后，焦点落到 `libperf.so` （arm64-v8a）上。我想补环境跑它，就得先把这个 so 的骨架摸清楚。我写脚本把 ELF 头和节区表整个测绘了一遍：

```python
ELF 头
  ├── phoff      = 0x40

  └── shstrndx   = 26

PT_DYNAMIC: offset=0x360c8  vaddr=0x3a0c8

节区表
  ├── .dynsym    addr=0x2f8     off=0x2f8     size=0x540    type=11
  ├── .dynstr    addr=0x980     off=0x980     size=0x4c9    type=3
  ├── .rela.dyn  addr=0xe50     off=0xe50     size=0xae0    type=4
```

测绘完我又看了 `.rela.plt` 的重定向项，想弄清它对外面的什么能力有依赖。这份 GOT 导入表比预想的长得多，我按地址从头到尾打出来，光 `.rela.plt` 就有三十多项，type 一律是 1026（R_AARCH64_JUMP_SLOT）：

```python
.rela.plt 导入符号（type=1026，按 GOT 地址）
  ├── 0x3a2f8  __cxa_finalize          0x3a300  __cxa_atexit
  ├── 0x3a308  __register_atfork       0x3a310  __stack_chk_fail

  ├── 0x3a340  __android_log_write     0x3a348  pauseVerify(int)
  ├── 0x3a350  shadowhook_init         0x3a358  shadowhook_hook_sym_name

  ├── 0x3a380  memcpy                  0x3a388  memset
```

紧接着 `.rela.dyn` 是一片 type=1027（R_AARCH64_RELATIVE）的项，从 `0x39e90` 起一长串符号名为空的条目，这就是后面 IRELATIVE 表那一大堆 addend 的落点区。

`sgStaticSafeEncryptData` 自己出现在 GOT 导入项里（ `0x3a338` ），so 内部对它是通过 PLT 调用的，外部也有引用。 `shadowhook_init` / `shadowhook_hook_sym_name` / `shadowhook_unhook` 三个一组 in，跟之前惰性初始化里那个 `bl 0x35d10` 指向同一处，这是它自带的 inline hook 框架。 `toupper` 的出现也和后面看到的 62 字符集大小写处理呼应。

`to_string(int)` 、 `JNIEnv::NewObject` 、 `operator delete` 、 `__register_atfork` 、 `__stack_chk_fail` 这一组符号凑在一起，指向 C++ 运行时加 JNI 交互，符合加密引擎封装加 JNI 桥的形态，补环境时该准备的桩也就清楚了，malloc 一类、C++ 运行时一类、JNI 一类。后面的 Unicorn 实验就从这里起步。

## TOP5 IRELATIVE 表的四槽区

IRELATIVE 那块花的时间最多。我盯着那些项，想知道它们指向哪里，按理说 addend 应该是 resolver 函数的地址。我写了个解析脚本处理 `R_AARCH64_IRELATIVE` （类型 `0x403` ）表，脚本一开跑打出来的表头是：

```python
text addr=0x5110 size=0x5110 | got addr=0x3a2a8 size=0x362a8
```

addend 呈现出四种完全不同的形态，按形态分成四个区：

```python
IRELATIVE 表（R_AARCH64_IRELATIVE = 0x403）
  │
  ├── 槽区 A：0x39e90 - 0x3a028（48 项）
  │     └── addend 为混淆乱值 / 超范围地址
  │          例：0x47fcbc26 / 0x1f756258 / 0x70378774
  │              0x53688094 / 0x106492dc / 0x67f0a786
  │              0xffffffffe8ba0fa2（明显越界）
  │          → 判读：疑似加密数据，不是直接地址
  │
  ├── 槽区 B：0x3a040 - 0x3a0c0（17 项）
  │     └── addend 为 .text 内合法地址
  │          0x326f0 / 0x326f8 / 0x32700 / 0x32744 / 0x3282c
  │          0x32914 / 0x32928 / 0x32938 / 0x32948 / 0x32a38
  │          0x32a7c / 0x32a88 / 0x32a94 / 0x32ac0 / 0x32d40
  │          0x5128 / 0x5110
  │          → 判读：非 ifunc resolver，是普通 C++ 成员函数
  │
  ├── 槽区 C：JNI 方法表 0x3e410 - 0x3e520
  │     └── addend 统一为函数地址右移两位
  │          0x1d2e -> 0x74b8
  │          0x25a6 -> 0x9698
  │          0x522c -> 0x148b0
  │          0x5230 -> 0x148c0
  │          → 全部落 .text，需 <<2 还原真实地址
  │
  └── 槽区 D：0x3e898 / 0x3e8a0 / 0x3e8a8（3 个特殊槽）
        └── addend = 0x42e60 / 0x42e60 / 0x43660
              <<2 后 = 0x10b980 / 0x10d980（超文件）
              → 判读：疑似运行时 mmap 指针（全局对象 / key 池指针槽）
              → 真机 dump 此处有 diff（真机已填值）
```

我逐个看过之后，槽区 A 那些值明显不是代码地址， `0xffffffffe8ba0fa2` 这种带符号扩展的乱值，加上一半项超出文件范围，我当时归为疑似加密数据。槽区 B 的 17 个地址全落在 `.text` （ `0x5110` 起、 `size 0x30b30` ），是能真反汇编的代码。槽区 C 的 JNI 方法表有个统一特征，addend 是真实函数地址右移两位，要左移两位还原。

槽区 D 只有三个槽，指向文件外的 `0x10b980` / `0x10d980` ，这个反常。我判断这是运行时才填值的指针槽，key 池很可能就挂在这里，得单独追一下。

## TOP6 槽区 B 的 resolver 判读

槽区 B 长得最像 resolver，我不想凭形态下结论，就对那 17 个地址逐个反汇编。反汇编下来它们不是 ifunc resolver，是普通的 C++ 成员函数。

我靠两条现象判断。一是调用约定是 `x0 = this / w1 = 参数` ，这是成员函数形态，resolver 不会这么带 this。二是函数体在读写对象字段（ `0x268` / `0xf8` ）和数组，不像在做地址解析。

```python
槽区 B 的 17 个解析点（节选，file size 0x37210 = 225808 B）
  │
  ├── @ 0x326f0 / 0x326f8
  │     └── bti c ; ret            （空桩，仅 BTI 指令 + 返回）
  │
  ├── @ 0x32700
  │     ├── bti c
  │     ├── cmn w1, #3 ; b.ls 0x32714
  │     ├── mov w0, #1 ; ret
  │     ├── cmp w1, #0x5f ; b.ls 0x32724
  │     ├── mov w0, wzr ; ret        （w1>0x5f 返回 0）
  │     ├── cmp w1, #0x22 ; b.ne 0x32734
  │     └── mov w0, #1 ; ret          （字符分类：0x22 命中）
  │
  ├── @ 0x32928 / 0x32938
  │     └── double 数组访问器（对象字段偏移读取）
  │
  ├── @ 0x32a38
  │     └── 对象拷贝（this/源对象参数形态）
  │
  └── 对象字段偏移：0x268 / 0xf8
        └── 判读：JSON / 配置解析或加密引擎内部对象方法群
```

`0x32700` 那段是逐字节分类逻辑， `cmn w1, #3` 后 `b.ls` 、 `cmp w1, #0x5f` 后 `b.ls` 、 `cmp w1, #0x22` 后 `b.ne` ，像在判断字符是否落在某个 ASCII 区间（引号 `0x22` 、下划线 `0x5f` 是 JSON 和标识符里的常见字符）。 `0x32928` / `0x32938` 读 double 数组， `0x32a38` 做对象拷贝，整体指向配置解析或引擎内部对象的方法集合。

槽区 B 虽然长得像 IRELATIVE 的 resolver，但语义上跟密钥无关，我把它从可能的 key 线索里划掉了。

## TOP7 JNI 方法表与 addend 右移两位

槽区 C 那个 JNI 方法表（ `0x3e410 - 0x3e520` ）我单独核了一遍，它的地址变换很一致，addend 是真实函数地址 `>> 2` 。我拿 DEX 引用和 IRELATIVE 两路输出交叉对着看，落点是这几个：

```python
JNI 方法表 addend（<<2 还原）
  ├── 0x1d2e -> 0x74b8
  ├── 0x25a6 -> 0x9698
  ├── 0x522c -> 0x148b0
  ├── 0x5230 -> 0x148c0
  └── （更多项同规律，全部落 .text 0x5110-0x35c40）
```

`0x522c` / `0x5230` 还原后是 `0x148b0` / `0x148c0` ，紧邻的区域正是 JNI 方法实现附近。这里我没往下推断， `initNative @0x5238` 在文件偏移那一侧，跟还原出来的地址分属不同地址空间，不能混着用。所以只把变换规律和落点记下来，没做函数语义的发挥。

## TOP8 三个特殊槽与运行时指针

槽区 D 是我这条线最想追的地方。那三个槽 `0x3e898` / `0x3e8a0` / `0x3e8a8` ，addend 分别是 `0x42e60` / `0x42e60` / `0x43660` ，左移两位后是 `0x10b980` / `0x10d980` ，远超文件大小 `0x37210` ，不可能是文件内地址。

我倾向于认为这些是运行时 mmap 出来的指针槽，属于引擎全局对象或者 key 池的指针位置。支撑这个判断的是一份真机 dump，我手上有一份 `.data` 段的 dump，覆盖 `0x3e410` 起 1184 字节，在这些槽位上跟本地静态文件有差异（真机填了值，静态文件里是空的）。

```python
槽区 D
  │
  ├── 0x3e898  addend 0x42e60  <<2 = 0x10b980   超文件
  ├── 0x3e8a0  addend 0x42e60  <<2 = 0x10b980   超文件
  ├── 0x3e8a8  addend 0x43660  <<2 = 0x10d980   超文件
  │
  ├── 真机 .data dump
  │     ├── 覆盖 0x3e410 起 1184 B
  │     ├── 对应偏移：0x488 / 0x490 / 0x498
  │     └── 状态：真机此处有 diff（已填 8 B 值）
  │
  └── 待做（当时标注）
        ├── 读取 dump 偏移 0x488/0x490/0x498 的运行时 8 B 值
        ├── 若指向 .data/.bss 或 mmap 地址 -> 即 key 池位置
        └── 再反汇编确认 sgStaticSafeEncryptData@0x58a8 对这些全局槽的引用方式
```

## TOP22 RPC 签名链还原

## TOP25 静态与动态的互补关系
