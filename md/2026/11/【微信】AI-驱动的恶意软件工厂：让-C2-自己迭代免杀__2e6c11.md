## 它是什么

最近我给 emp3r0r C2 加了些 AI 功能。接上 MCP、让 C2 能配合外部 AI harness 之后，我想：何不干脆把 C2 最缺的那块补上？

C2 最缺的功能是什么？接触过 red teaming 的人心里有数。现代 C2 框架和 operator 大部分时间都花在绕过检测上。这也是它叫 “red teaming” 的原因：对面还有一群人在做 “blue teaming”，盯着你干的每一件事。

带着 evasion 目标写恶意软件是门手艺活。可再强的开发者也得从已知技术起步，而你丢到任何地方的样本，早晚会被人捡走。

每次被抓就重写一遍，肯定不是你想要的工作方式吧？

其实也不必。AI 模型现在的编码能力好得吓人。你需要的只是一条能让模型在上面干活的流水线，就像工厂工人在产线上干活那样。

## 工厂

这座工厂长这样。

![检测循环架构图](https://cdn.jsdelivr.net/gh/zhiyu-zeng/img@main/img/2026/11/c9a37cda456d7464.png)

### harness：ARTEX（norma）

没有重复造轮子。ARTEX 最近热度很高，我直接采用了它的 harness。 `norma` 是纯 Go 实现，对 emp3r0r 这种 Go 写的 C2 来说再合适不过。

ARTEX 是一整套 agent 栈。我只取它的 harness，没有要那个应用。Norma 是一个 Go 写的通用 agent harness SDK，提供 provider adapter、流式 tool loop、tool 与权限契约、hook、上下文 compaction 和 transcript 存储。

| Norma 提供什么 | 循环用到什么 |
| --- | --- |
| `llm`<br><br>\+ `agentcore` |     |
| `tool`<br><br>\+ `permission` + `hook` | 自定义 tool schema；按角色划分的 tool 集；读取配额；角色 allowlist；以及强制 planner/editor/debugger 输出 JSON 的 stop-hook 契约。 |
| `harness`<br><br>\+ `compaction` | 流式事件；预算到点结算；面向检测场景的 micro-compaction；摘要与溢出恢复。 |
| `transcript` | 检测存储目录下只追加的 JSONL 会话日志。 |

Norma 的 `coordinator` 、 `subagent` 、 `mcp` 、 `memory` 、 `skill` 、 `plan` 、 `noa` 这几个包都没用上。循环有自己的 coordinator、知识库和 loop memory，再叠一个 orchestrator 只会多一份重复状态。Norma 也不注入任何 system prompt，planner、editor、debugger 的每一段 prompt 都由 host 攥在手里。

### 原材料

跟用编码 agent 时一样，我把模型需要看、需要改的东西全摊开给它。

原材料本身并不隐蔽，检测点是要靠模型自己改掉的。

Windows 线可写的根目录是 `loader_windows` 、 `go_agent` 和 `crystal_pack` ，Linux 线是 `stager_linux` 、 `c_agent` 和 `malasada` 。manager 通过一份 source brief 把这些目录树交给工人，模型不用从 tool 描述里猜。它能列目录、搜子树、改根目录下的任意文件，也能在父目录已存在时新建文件；但碰不到 operator 的 checkout，也出不了这几个根。

这是三个不同的工种，不是一个代码库。Windows 上 `go_agent` 是 beacon， `crystal_pack` （或 `donut` ）把它包成 shellcode， `loader_windows` 再把 shellcode 带进 payload。Linux 上同样的角色对应 `c_agent` 、 `malasada` 和 `stager_linux` 。

![源码与构建流水线](https://cdn.jsdelivr.net/gh/zhiyu-zeng/img@main/img/2026/11/19f6f8d9fe12a874.png)

agent 在 Windows 上编译成 `windows_executable` 或 `windows_dll` ，在 Linux stager 里编成 `linux_so` 。三个根目录都纳入 shadow repository：每次编辑都记下旧文本、新文本、文件名、修改理由、是否新建，以及之后有没有被回滚。模型可以为验证一个假设改多少处就改多少处，host 负责让整批编辑可审、可逆。

“什么都能改”有一个刻意的例外：host 会拒绝 `memfd_create` 这条路。原因很简单，大家都知道我讨厌 `memfd` 那一档的 Linux tradecraft。

### 工人

工厂需要什么？工厂本质上是产出东西的流水线，得有工人和机器把东西做出来。

我们的恶意软件工厂也一样，吃进去的原材料是你的 beacon 源码。三个工人围着这批材料干活，目标是缩小检测面。他们怎么知道自己的产品能不能躲过检测？有 QA 实验室，检查成品，不合格就退回返工。

我给循环开了三条独立的模型会话，一个工人一条，各自有自己的 system prompt、tool 集、turn 上限和读取配额。

| 工人  | 做什么 |
| --- | --- |
| Planner | 读 dossier，选定一个机制和一条预测，然后决定 test、debug 还是 stop。 |
| Editor | 改源码或 producer 代码，重新构建，跑一轮 `DetectionCycle` 。 |
| Debugger | payload 没跑起来、或者 agent 没上线时，进 guest 里排查。 |

三个工人读的是同一批数据库：telemetry、knowledge cache 和 loop memory。源码也都能读，但只有 editor 能改。

传统 AI harness 给你一条会话，有时再带几个 sub-agent。模型领了指令就开干。放到这种无人值守的流水线里，单会话几乎必然卡死：它一旦不干活了，你没法像在 Claude Code 里那样把它掰回正轨。循环给每道工序单开会话，host 才能在正确的层级上重启决策、重启编辑、重启诊断。

产线是确定性的。工序很清楚：拿原材料，加工，送 QA 实验室，不合格就返工。模型本身不确定，围着它的流程就必须确定。

设计就是这样。把活拆开，让每个工人只有一个明确目标和一份明确产出，由 host orchestrator 校验并放行。

### 机器

机器包括 harness、各种 tool、构建管线、QA 实验室和 C2 gate，工人只负责用。

一次 tool 调用就是一次机器操作： `SourceRead` 把原材料送进来， `EditSource` 改料， `DetectionCycle` 让产线走完一遍。host orchestrator 负责排班、派发 tool 调用、轮换 agent、把住每一轮的闸门，并写账本。

### 经理

host orchestrator 就是经理。它要证明 payload 真的跑起来了，保证改动可逆，拒绝无法比对的轮次，还会掐掉光烧时间和 token 不出活的工人。模型提方案，经理把关。

#### 执行

每一轮都用全新的 agent UUID 和 shellcode。C2 对同一 UUID 沿用第一次见到的密钥（TOFU），所以复用 UUID 会被当成换密钥，C2 直接拒掉。

跑完之后 host 会拿预期 UUID 去 C2 查。 `execution=verified` 表示 agent 已上线； `execution=offline` 表示没上线； `execution=unverified` 表示循环没配 C2 校验。

离线的轮次照样烧预算。它只能说明 payload 没跑起来，对检测面一件事都说明不了。host 会恢复到上一份好状态，这一轮不算进展。

#### 回滚

loader 模块、agent 源码和 producer 源码都是被记录的根。检测存储目录下的 shadow git 仓库跟踪同一批目录树，不碰 operator 的 checkout。只要某一轮没执行成功，或者验证过的轮次出现回归，host 就把上一份好状态整个恢复：源码、shellcode、build options、producer options、agent 类型和 agent tags。

有了回滚，激进改动才敢放手做，工作区永远退得回去。

#### 对比

每一轮都存一份指纹：源码 hash、build options、producer options、producer、agent 类型和 agent tags。指纹和上一轮相同，host 就判为重复并拒绝——光轮换 shellcode 不算改设计。

planner 每轮还会写下一条下一轮能证伪的预测，host 记录下一轮是否命中。每一轮都带一个 mechanism 标签；同一个 mechanism 连吃两轮没有进展，host 就不许开第三轮。

#### 时间与工具预算

planner 给 5 分钟、12 次只读调用；editor 给 10 分钟、24 次只读调用；debugger 在配置之后有总的 tool 预算。每条会话都有 30 分钟的 tool 空闲超时和 2 小时硬上限。

时间窗一关、空闲计时一到，host 只取消当前这次调用，会话本身留着，然后给工人发一条指令：立刻交回规定的 JSON。如果预算正好卡在 turn 边界上耗尽，结算逻辑会把只读 tool 收走，只给工人两个 turn 作答。

tool 预算起的是同样的作用。planner 或 editor 的只读调用一用完， `PreToolUse` 就挡住后续读取。planner 必须交计划，editor 必须改代码、构建或跑一轮。反复读同一个文件却不动手的模型，别想烧掉剩下的大半场。

### 账本

传统 AI harness 把所有东西读进上下文再压缩。可这些东西真的都要塞进上下文吗？

循环每多跑一轮，检测反馈就多一截。原始遥测很快吃光上下文窗口，而模型一旦翻篇，这些数据基本没用。

所以我把它们挡在模型上下文之外，需要时让模型自己查 SQLite。这样它能专心对付眼前这一轮，不至于淹在噪声里。

知识库是人工整理的参考资料，模型可以查技术和 methodology。loop memory 是循环自己的记事本：哪种改法、哪种方法奏效过，附上确切的源码改动和验证结果。

外部缓存来自 notebook MCP：https://archeotech.r00ted.ch/mcp。 `emp3r0r knowledge-sync --url https://archeotech.r00ted.ch/mcp` 会把 `maldev` 、 `edrdev` 、 `redteam` 、 `amsi` 、 `staticanalysis` 、 `vulndrivers` 、 `crystalstardust` 、 `com` 、 `lsass` 、 `defender` 、 `mynotebook` 这些 notebook 的摘要拉下来，加 `--content` 连全文一起缓存。harness 的 playbook 是另一个本地 methodology notebook。循环离线读 `<store>/knowledge.db` ，缓存进来的文本一律当作不可信参考资料。

SQLite 是账本。payload、trace、event、finding、cycle、edit、worker run 和 loop memory 里的 technique 彼此关联，模型拿到的是 join、索引和一次性的 SELECT，而不是把全部数据背在上下文里。 `TelemetryQuery` 只开放一条只读的 SELECT/WITH， `attrs` 保持 JSON，用来承载传感器特有的细节。

这是 operator 侧的状态，不是 payload 代码。检测存储目录里就一个文件，不用装 Postgres、不用暴露端口、不用管认证和备份。WAL 加 busy timeout 让导入写入时读取照常；一条写连接串行化写入，另一条独立的只读连接服务模型查询，长时间分析不会堵住 ingestion。 `modernc.org/sqlite` 让 operator 侧保持 CGO-free 构建。

知识缓存是另一个带 FTS 的 SQLite 库，循环以只读方式打开。loop memory 留在 telemetry 库里，因为它要直接和 findings、edits 做 join。

SQLite 记发生了什么，git 记改了什么。

![Windows 源码历史](https://cdn.jsdelivr.net/gh/zhiyu-zeng/img@main/img/2026/11/056e69d157a52426.png)

每个可写根在检测存储目录下都有一个 shadow 仓库，由 `go-git` 管理。循环只镜像源码文件，提交基线、每一轮，以及最后一份完整或部分快照，并把每个根的 commit hash 随轮次一起存下。工人可以通过 `GitHistory` 读 log 或某个完整 commit。operator 的 checkout 永远不动。直接用 `go-git` 意味着不需要 git 二进制，也不牵扯 hook、用户配置和 shell 调用。

工厂有了工人、经理和账本，还差最后一环：给成品打分的 QA 实验室。

## 实验室能看到什么

Windows 线用 LitterBox，Linux 线用 PenguinBox。两者返回同一种 `emp3r0r.telemetry/v1` envelope。importer 把事件归一化进 SQLite，模型查的就是 telemetry 库里的行。

| 实验室 | 传感器 | 模型能查什么 |
| --- | --- | --- |
| LitterBox | 静态 PE、YARA、CheckPlz、Stringnalyzer；Defender、RedEdr、Moneta、pe-sieve、HollowsHunter、HSB、Patriot、Blender、YARA/CheckPlz、HolyGrail BYOVD 以及各类 EDR profile | PE 的熵、import、section 和 checksum；文件、注册表、进程、线程、网络、模块事件；ETW-TI 的内存写入、保护属性、映射和分配；内核回调与 ntdll hook；PEB 与已加载 DLL 查询；Defender 的行为与判定 |
| PenguinBox | Tracee、Falco、ELF、YARA | 带 LSM 参数的 `exec` 、文件变更、内存、网络、mount/namespace、BPF、kexec 和内核模块 syscall；带 rule、priority 和 `evt.type` 的 Falco 告警；ELF 与 YARA 命中 |

Tracee 是原始行为层，Falco 是命名规则层。LitterBox 也是同样的分工：ETW/ETW-TI 和 RedEdr 给行为，Defender 和各类分析器给判定或摘要。

## 早期结果

我在两条线上试了这套设计：Linux 配 PenguinBox，Windows 配 LitterBox。这不是 benchmark，问题要窄得多：循环能不能真的改源码、重建、引爆，并证明结果？

| 线   | 平台  | 轮数  | Verified | High | Total | Verdicts | 结束状态 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| Linux | PenguinBox | 17  | 17  | 10 → 0 | 14 → 4 | 2 → 0 | 预算耗尽 |
| Windows | LitterBox | 8   | 6   | 3 → 0 | 50 → 20 | 0 → 0 | producer 停滞；最后两轮离线 |

Linux 线去掉了 `/proc/self/maps` 的读取，废掉了 stager 的 YARA 特征，也拿掉了 runtime 的 maps 规则，最后记录在案的 high finding 为零。

Windows 线清空了静态面：熵、import、checksum 三类 finding 全没了。动态内存异常依然在，LitterBox 还是给 payload 打了 58/100。最后两轮离线，未予保留。

## 改了什么

| Finding | 模型看到了什么 | 改动  | 结果  |
| --- | --- | --- | --- |
| Linux maps | YARA 和 runtime 规则匹配到字面量 `/proc/self/maps` 读取 |     | 第 12 轮 runtime 的 `Process Memory Map Read` 消失 |
| Linux loader | `PenguinBox_LinuxStager_LoaderCode`<br><br>匹配到 ABI store、syscall 扫描和 trampoline | 在运行时拼出 ABI magic，编码比较，trampoline 用 NOP 填充 | 第 3 轮 YARA 消失 |
| Windows 静态 | `.rdata`<br><br>里 RC4 密文带来的 PE 熵；CRT import；checksum | 在 `.incbin` 前先给密文套一层 base64 边界；把依赖 CRT 的 loader 换成 `-nostdlib` 自加载器、PEB export walk 加 `fixpe` 后处理 | 静态 finding 30 → 1；动态内存仍打 58 |

模型先从便宜的字符串改动下手。编码 `/proc/self/maps` 、再按线程做 alias，代价都不大，runtime 规则照旧触发。去掉这次读取才是结构性改动。Windows 那边，给密文套 base64 边界改变了熵分布，freestanding loader 去掉了 import 和 checksum，可 LitterBox 还是标出了无后备文件的可执行内存，照样打 58 分。执行路径根本没有动。

exec 内存这一处也是同样的读法：规则盯的是申请可执行保护这一步，模型就把授权挪到 `pkey_mprotect` ，直接创建 RWX 映射，换了 syscall，也换了 flag。

![Windows 静态清洁度](https://cdn.jsdelivr.net/gh/zhiyu-zeng/img@main/img/2026/11/f74ca1e6eb149dab.png)

真正有用的产出，是这份规则到改动的对照记录。

## 结语

Linux 线去掉了 `/proc/self/maps` 读取和 stager 的 YARA 特征；Windows 线清掉了静态 finding，动态内存行为还在。两次运行都留下了规则到改动的对照记录，循环也在证据不再变化的时候停了下来。

这套设计远谈不上完善，不过已经能拿出说得过去的结果。

Windows 免杀路上最大的拦路虎，是 producer 连续两轮没有改善后 host 的强制退出。模型本来可以多花几轮把计划做出来，host 却先把这条 mechanism 掐了。
