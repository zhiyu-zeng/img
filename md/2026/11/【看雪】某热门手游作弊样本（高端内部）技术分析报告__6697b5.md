## 1\. 报告范围与阅读说明

本文依据项目现有原始分析、离线执行证据和内核模块专题，全程由ai（6.1 sol）进行分析编写，由于没有真实网络数据包（高端内部，开户买卡），也没有真实运行，并且样本还是高度混淆的，ai在分析上会存在一点点失真和噪声，而且一些云端数据也无法进行分析。内核深入分析对象为 `component_06.o` ，对应 6.6 / Android 15；

样本由启动器、加密资源包、游戏进程内载荷和内核模块共同组成， **所有样本全部都是高强度混淆，包括内核模块**。启动器负责资源恢复、联网授权和注入；载荷承担游戏内功能；内核模块提供凭据检查、页内容切换、可见性控制，并包含独立的远程控制逻辑。

**阅读前提：本项目未在真实设备上执行样本，也未连接样本服务器。** 真实设备仅用于只读提取游戏库及核对文件身份；动态结论来自原始机器码在隔离内存中的执行，系统接口由有限模型提供。本文按已恢复的调用关系说明设计流程；某个函数被验证，不代表整条链已经自然成功运行。证书校验、有效服务器签名、真实注入和硬件页表效果的边界在对应环节说明。

### 2.3 四条通信链分别连接谁

上述部件通过不同通道协作。先区分各条通信链的两端和职责，再看载荷通道中的 memh 记录，便能把后续的握手、授权和页修改放回各自的位置。

| 通信链 | 两端  | 入口与用途 |
| --- | --- | --- |
| 远端登录通道 | 启动器 ↔ 授权服务器 | `103.253.43.10:54360` ，TCP / TLS，其内还有自建签名握手和 AES-GCM 记录层 |
| 本地管理通道 | 启动器 ↔ 本机内核模块 | 私有 `syscall 289` 路径，处理凭据、线程绑定、状态查询等命令 |
| 载荷控制通道 | 游戏内载荷 ↔ 本机内核模块 | 借用 `getrandom` ，提交范围登记、页修改、填充及恢复请求 |
| 内核远程控制通道 | 内核模块 ↔ 远端控制端 | UDP 特征触发与内核 TCP 后台；默认 TCP 端点为 `5.75.158.192:43183` |

**“内层签名握手”发生在第一条远端登录通道中。** “内层”指 TLS 内部的应用加密层。本机内核的握手与凭据安装走 `syscall 289` 管理通道，memh 登记走 `getrandom` 载荷通道。网络授权与内核凭据共用验证信任根，但它们的报文、调用入口和状态机各自独立。

### 2.4 memh 的含义与范围登记

`memh` 是样本自定义的控制标签。它以完整 64 位值 `0x00000000686D656D` 出现在记录中，按小端存储时，前四字节对应 ASCII 字符 `memh` 。现有证据尚未确认其英文全称。

**严格来说，memh 命令负责向内核登记载荷的内存范围和控制材料。** 分析报告中的“memh 内核桥”则是对载荷经 `getrandom` 与内核模块交互这条通道的概括称呼。

载荷启动时生成一条 32 字节记录：

| 偏移  | 长度  | 字段  | 已确认用途 |
| --- | --- | --- | --- |
| `0x00` | 8 字节 | 进程 PID | 来自载荷的 `getpid` 调用，与内核目标进程绑定 |
| `0x08` | 8 字节 | memh 标签 | 完整值为 `0x00000000686D656D` |
| `0x10` | 8 字节 | 范围下界 | 来自载荷解析出的自身映射 |
| `0x18` | 8 字节 | 范围上界 | 与下界来自同一映射记录 |

这条记录通过 ARM64 `getrandom` 系统调用入口提交，调用参数为记录指针、长度 32 和标志 0。模块准备了针对 `__arm64_sys_getrandom` 的拦截回调，用它识别私有记录，检查当前进程、地址空间、调用 PC 范围及授权材料，并在通过后保存登记信息。

登记的范围还被映射显示过滤、远程取页限制和部分信号处理等消费者使用。当前离线实验中，原载荷生成的记录在签名检查处被拒绝，未建立有效控制会话。

### 2.5 getrandom 通道中的命令分工

| 完整 64 位标签 | 已恢复的作用 |
| --- | --- |
| `0x00000000686D656D` | memh：范围登记与控制材料保存 |
| `0x000000000073686B` | 96 字节修改页请求，进入修改页后端 |
| `0x00000000736E7370` | 48 字节填充页请求，建立另一种数据访问视图 |
| `0x000000007273686B` | 按目标地址所在页解除；目标为零时可进入批量解除 |
| `0x0000000000737261` | 准备批量解除 |
| `0x0000000000687772` | 恢复当前线程暂存的硬件断点地址 |

这些标签位于 getrandom 私有协议中；管理命令 23、46、69、140，以及远程 TCP 的命令选择值，属于另外的编号空间。

## 3\. 启动与资源恢复

### 3.1 解壳、初始化与卡密处理

正式包使用修改版 UPX / NRV2E 加载器，叠加滚动异或及首块扰动。分析按原加载器逻辑恢复五个压缩块、ARM64 分支过滤和程序入口，得到 63,420,304 字节的分析 ELF。

39 个静态初始化函数运行后进入 `main` ，分析地址为 `0x3518C74` 。主体仍存在大量间接调用、算术混淆和控制流平坦化，因此流程结论结合了静态数据流和原代码的离线执行。

启动器处理自身路径、工作目录、副包路径和卡密参数。显式卡密分支执行本地 UUID 格式检查，接受符合版本 1 至 5 及标准 variant 的形式。格式通过只说明输入满足本地语法要求，在线授权还在后面。

### 3.2 目标进程、缓存和本地设置

程序检查目标游戏进程，并准备工作文件。已分析的分支会尝试删除游戏缓存目录中的 `dsdk_inner.txt` 、 `h.log` 、 `dsdk_crash.seq` ，以及 `/data/adb/` 下的部分同名文件。一条目标进程检查分支还会准备 SIGKILL 请求；现有证据不足以概括为所有启动条件下均杀掉游戏。

随后读取以卡密命名的 `.ini` 文件。该文件实际是固定 200 字节二进制配置，由 16 字节头和 184 字节主体组成。184 字节设置主体进入共享上下文，再随注入参数传入游戏载荷。菜单配置和运行设置因此有一条从磁盘到目标进程的传递链。

### 3.3 验签、解密并拆出副包组件

副包恢复依次包含四层处理：

1.  **发行签名检查。** 容器以 `CIFWXPK1` 开头，包含 24 字节头、密文正文及 64 字节 Ed25519 签名；签名覆盖头和全部密文。
2.  **对称解密。** 使用 AES-128-CBC、全零 IV 和 PKCS#7。已恢复的密钥在不同卡密输入下相同，副包内容解密本身不依赖某张卡的在线授权。
3.  **自定义解包。** 188 个块分别经过 rANS、MTF、逆 BWT、异或变换及滚动校验。
4.  **组件布局检查。** 核对内部范围、滚动指纹和 ARM64 可重定位 ELF 等条件，得到载荷、元数据与七个模块。

内核组件涵盖 5.10 / Android 12、5.10 / Android 13、5.15 / Android 13、5.15 / Android 14、6.1 / Android 14、6.6 / Android 15、6.12 / Android 16。两个明确的 6.6 版本输入均选中索引 5，即 `component_06.o` ；这还不足以定义完整的版本兼容矩阵。

### 4.2 建立 TCP / TLS 并固定校验服务器公钥

客户端配置包含服务器 `103.253.43.10:54360` 、内嵌 CA、客户端证书及加密 RSA-4096 私钥材料。工作线程完成地址解析和 TCP 连接后进入 TLS。

样本除普通证书链校验外，还对服务器叶子证书的 SPKI，即公钥信息的 DER 编码，计算 SHA-256 并与内嵌固定值比较：

`1cb974875234a2468c0bbd8ee326a39eadb1cb3f2d308543d290c73dcf2b4651`

### 4.3 TLS 内部再建立应用加密层

按设计，TLS 完成后，启动器还要与同一远端服务器进行自建握手。客户端 hello 为 84 字节：4 字节长度前缀、16 字节固定头、32 字节随机数和 32 字节 X25519 临时公钥。服务端 hello 的正文为 144 字节，包含对应随机数、公钥和 64 字节签名。

客户端使用 Ed25519 验证以下 176 字节握手记录（transcript）的签名：16 字节域标记、80 字节客户端 hello 正文和服务端 hello 的前 80 字节。域标记中含 `CHANNEL` 。验签通过后才利用 X25519 共享秘密和 HKDF-SHA256 派生双向材料；每个方向各得到 32 字节 AES 密钥和 12 字节基础 nonce。

业务记录层使用 AES-256-GCM。记录包含头部、序号、密文和认证标签；头部与序号也参与认证。接收端要求下一条序号严格等于上一条加一，拒绝跳号和重放。

原算法与标准向量及独立实现进行了核对；全零服务端签名则使握手状态进入失败，清除临时私钥。只有内层状态首次转为“记录层就绪”，接收回调才选择首次卡密请求准备分支。通道就绪之后，还需要业务授权成功。

### 4.4 构造请求、封包并等待回复

首次请求包含 12 项成员，主要承载设备绑定值、会话头和随机数、系统及内核信息、卡密、QQ 号与微信偏好列表，以及无线网地址信息等扩展数据。卡密还参与配置掩码计算：先做 FNV-1a32，再作为系统信息 XXH64 的 seed。

发送方向的应用编码按以下顺序组织：

`请求对象 → Protobuf → 字段换序与混淆 → 外层 Protobuf → 外层混淆 → 表异或 → Snappy → 应用帧`

应用帧随后才进入内层 AES-GCM 记录层和 TLS。独立构造实验得到 542 字节应用封包，逆解出的 460 字节 Protobuf 正文与原对象的 12 项字段一致。

实际发送还检查连接活动标志与内层记录阶段。已测试的未就绪状态使原发送器返回，没有自然提交记录或 TLS 业务写出。请求对象、应用封包和待回复登记分别是不同环节。

接收方向按相反顺序解除记录加密和应用封装，再进入消息分派。外层六个浮点字段用于三个椭圆边界点的数学检查，另有一次性质数状态检查；这些字段当前不能解释为游戏坐标。

### 4.5 授权回复同时约束前端与内核

已恢复的主回复包含三类关键材料：

| 材料  | 消费者及意义 |
| --- | --- |
| 176 字节 CCAUTH 凭据 | 前端验证设备、端点、时间、会话及密文绑定，并核对 Ed25519 签名 |
| sealed 加密正文与 TLV 配置 | 解密、解析后进入客户端和注入上下文；部分配置继续进入载荷 |
| Base64 编码的 268 字节载体 | 通过本地操作 140 交给内核，安装或更新其凭据缓存 |

CCAUTH 的短时有效期最多 1800 秒，签发时间最多领先当前时刻 60 秒。客户端还存在另一条 480 秒单调时钟缓存窗口，两者对应不同检查。现有证据没有把这些时间直接等同于卡密的产品有效期。

内核对 268 字节载体进行 ChaCha20 处理，恢复 152 字节签名凭据，其中前 88 字节是正文，后 64 字节是 Ed25519 签名。正文包含 36 字节 UUID、32 字符标识和时间字段。网络验证与内核验证共用同一 Ed25519 信任根，分别检查各自的格式、上下文和期限。

当前没有有效服务器签名。零签名 CCAUTH 被拒绝，授权输出清零；内核凭据安装的自然成功链也未闭合。

## 5\. 本地内核服务准备与模块 Hook 框架

### 5.1 凭据提交、组件装载与本地握手

后续内核服务准备函数取得卡密、组件向量和共享凭据缓存。已恢复的局部顺序中，先有一次操作 140 提交；另一个装载后分支会解码同一份缓存，再次提交相同的 268 字节材料。模块是否已存在、装载是否成功和检查失败都会影响后继路径。

模块装载器还原选中的组件，创建临时副本，并将它交给 `init_module` 。对 6.6 组件，完整调用缓冲与原 `component_06.o` 的摘要一致，长度为 4,915,368 字节。分析停在真实系统调用前；声明装载失败的实验进入原错误清理和返回路径。

按已恢复的调用关系，凭据及装载检查后还涉及以下本地管理命令：

| 命令  | 已确认职责 |
| --- | --- |
| 140 | 接收载体，解密、校验并条件保存凭据；前端按专用结果标记判断后继 |
| 46  | 绑定调用线程的 task，并初始化相关控制状态 |
| 23  | 核对卡密对应的 UUID、复验签名；通过后的分支保存参数并重建线程集合 |
| 69  | 查询和复验缓存，构造绑定回复，并在对应后继登记线程 |
| 115 | 状态查询及逐条交付未读通知 |
| 91  | 维护一张 IPv4 整数表，参与后续网络处理 |

命令 23 中的 UUID 与前端主卡密已有数据流连接，所用绑定值来自同一卡密的 FNV-1a32。命令 69 的回复还要经过前端解码和标记比较。因此，本地“握手”包含凭据、字符串绑定、线程身份和缓存状态等检查。

这些命令不是都以数值 0 表示同一种成功。例如操作 140 的前端继续条件是专用标记 `0xFFFFFFC0107E3C98` ；管理命令、内层状态及用户页请求状态槽各有自己的语义。

凭据除了验签，还受到拥有者进程、地址空间、UUID 和时间约束。已分析的正数时间域要求两个时间上界中的较早者仍晚于当前实时时钟，且其中一个上界距离当前不超过 1860 秒；投影到启动时钟的有效期最多为 1800 秒。更新不允许该时间上界倒退，同一上界也不能借重新提交延长旧启动期限。到期会清除缓存启用位和 152 字节凭据，但保留部分身份与时间基准；回拨时钟不会自动恢复已经清除的缓存。

这些期限只描述已验证的凭据逻辑。操作 140 另有样本固定日期和元数据时间差检查，各功能也可能继续复验签名，不能把“取到缓存”概括为全部操作均获准。

### 5.2 模块初始化及内核函数拦截框架

模块自声明名称为 `xmod` 。初始化代码会从模块链表摘除自身并请求移除相关 kobject，降低模块链表和 sysfs 的可见性。符号解析链准备借助 kprobe 取得 `kallsyms_lookup_name` ；已有静态导入和动态查询去重后共 220 项依赖，当前整理到 53 对 API 与回调配对证据。

用户页机制依赖这些内核拦截点，其中包括 getrandom 控制入口和 `do_mem_abort` 异常入口。承载它们的是一套内核函数入口 Hook 框架，其已恢复流程为：

1.  保存目标入口的 16 字节，建立描述符、生成代码区和回调上下文。
2.  将被覆盖指令搬到生成代码区，并对部分 PC 相对指令和分支进行重定位。
3.  准备入口跳转，使目标先经过生成桥和回调。
4.  生成桥使用 272 字节自定义外层帧保存寄存器与状态，回调可选择继续原主体或直接返回。
5.  撤销时恢复入口字节，摘除描述符并回收运行时对象。

**这套内核入口 Hook 与后面的用户页 Hook 分属两层。** 前者让模块取得控制入口；后者处理目标进程的用户页内容和页表映射。

公开输入上的原注册、调用和撤销已有离线证据，但部分指令重定位存在差异，固定覆盖 16 字节还会影响某些短函数的相邻入口。53 对准备关系也不等于 53 个真实安装成功的拦截点；真实内核的指针认证、页权限、缓存和并发效果尚未验证。

生成代码页还有独立的权限维护：通过页遍历回调清除 PXN 等标志，并请求屏障、TLB 与缓存刷新。该动作针对生成代码页，不能据此认定目标内核文本页的全部权限限制已经解除。旧分析中还有系统调用路径与 KCFI 检查相关的修改尝试，目前只支持“准备写入或写入失败”的结论。

## 6\. 注入游戏与载荷启动

### 6.1 附加目标、远程分配与放入镜像

授权后的设计路径使用 `ptrace` 附加游戏，等待目标停下并取得寄存器。注入器解析目标 maps，以名为 `dalvik-Sentinel fault page` 的映射作锚点计算空隙，再随机选取目标地址。

随后它准备目标进程中的 `mmap` 调用，写入所需寄存器，安排目标恢复执行，并通过 `process_vm_writev` 放入长度为 `0xA95000` 的目标镜像。载荷的原重定位代码完成 62,314 笔重定位，绑定内部对象 getter、getrandom 系统调用桩和 `getpid` 等调用位置，最后准备载荷入口及参数。

副包恢复出的 `payload_image.bin` 还包含尾部元数据区， `0xA95000` 是此处写入的运行镜像长度，区别于整个资源镜像文件的大小。库名、符号及重定位记录来自尾部区段与配对掩码的恢复结果。

### 6.2 接收设置、登记 memh 并定位依赖库

载荷接收 608 字节参数记录，其中包含前述 184 字节本地设置。入口复制并转换参数，给匿名映射命名，再解析 `/proc/self/maps` ，选择包含自身锚点的映射范围，生成第 2.4 节介绍的 memh 记录。

原 memh 返回值交回用户态后，已分析的后继继续完成 600 项红黑树初始化，再选择六个键区间、申请匿名页并构造相关对象。这部分对象的全部产品用途仍有缺口。

随后，载荷轮询 maps 等待 `libUE4.so` ，再查询 `libtersafe.so` 和 `libCrashSight.so` 。已执行片段中的库定位通过字符串和映射行完成；返回的行起点不能无条件当作所有 ELF 装载场景中的正确基址。

### 6.3 CrashSight：针对原生信号处理入口的提前返回请求

当前第一个已确认的修改请求目标是：

**`libCrashSight.so` 基址 + `0x1C2E8` ，替换内容为 `C0 03 5F D6` ，即一条 ARM64 `RET` 。**

这四字节由载荷主动生成，是准备写入的替换指令。修改函数先读取目标原指令用于内部记录，再构造控制请求。

| 核对项 | 结果  |
| --- | --- |
| 目标位置 | ELF 相对虚拟地址 `0x1C2E8` ；本文件中对应偏移也是 `0x1C2E8` |
| 真实原字节 | `FF 43 05 D1` ，即 `SUB SP, SP, #0x150` ，是函数建立栈帧的首指令 |
| 函数范围 | `.eh_frame` 展开记录给出 `[0x1C2E8, 0x1D168)` ，确认目标位于入口 |
| 替换内容 | `C0 03 5F D6` ，即 `RET` ；若生效，会在建立栈帧前直接返回 |

**该函数已定位为 CrashSight 的原生信号处理入口。** 注册代码把 `0x1C2E8` 写入 `sigaction` 回调槽，再分别为 SIGSEGV、SIGABRT、SIGBUS、SIGILL、SIGFPE 等信号安装同一处理函数；另有 SIGQUIT 分支。函数内部引用 `CrashSightSignalHandler...`、 `Start to create minidump with path %s` 和 `create tombstone for native crash` 等日志，包含寄存器与原生栈记录、崩溃文件生成，以及按条件交给 Java 侧处理的路径。目标用途因此已得到注册关系与函数正文的共同支持。

## 7\. 用户页 Hook：双副本、权限异常与内容切换

### 7.1 目的与两类模式

用户页 Hook 的关键是控制“某个用户虚拟地址最终对应哪份页内容”。模块在内核维护页记录，并通过不同页表权限，让程序取指和数据访问在需要时进入异常处理。

本节中的 `mm` 指进程地址空间对象，PTE 指页表项，TLB 是 CPU 缓存地址翻译结果的结构；“取指”表示 CPU 为执行而取得指令，“数据访问”表示把地址中的内容作为数据读取或写入。

| 模式  | 执行视图 | PC 在其他页时的数据访问视图 | 主要作用 |
| --- | --- | --- | --- |
| kind=0：修改页 | 带补丁的修改副本 | 初始保留原内容的另一份副本 | 执行修改内容，并在相应读取路径提供原内容 |
| kind=1：填充页 | 真实原页 | 清零、NOP、随机或重复模式的填充页 | 保留原执行代码，为相应数据访问提供替代内容 |

CrashSight 的 96 字节请求对应第一类。第二类在后端及控制分派中已有证据，但尚未归属到某个已确认的载荷目标库。

### 7.2 接收请求并建立页记录

getrandom 回调通过公共上下文、控制状态及签名检查后，识别请求标签并复制固定结构。修改页后端 `1B0558` 按目标 `mm` 和 4 KiB 页地址查缓存；命中时取得临时引用，再检查进程归属和记录状态。

首次创建 kind=0 记录时，原代码申请一个 2360 字节对象和两份 4096 字节页：两页先复制原内容，再将替换字节写到修改副本。对象保存原 PTE、页号、两种描述符、锁、引用计数和修改记录。完成后加入全局链表与按页哈希桶。

每条修改记录保存页内偏移、长度和最多 64 字节替换内容；当前所测单次最多 16 条 ARM64 指令，每页最多 32 条修改记录。同页后续请求复用记录和页副本；失败新建路径会释放已分配的资源。

### 7.3 用权限让两种视图互相切换

kind=0 的两份页配有不同权限的描述符：修改副本用于用户态执行，限制用户数据访问；原内容副本用于用户数据访问，并设置 UXN，禁止用户态执行。

**同一个 PTE 在某一时刻只映射一份页。** 当前权限允许的访问正常进行；遇到不允许的访问时，CPU 按设计产生异常，模块再选择另一份描述符。因此，机制依赖异常驱动的映射切换，而不是一个普通 PTE 同时表达两份内容。

PTE 更新代码先清除旧槽，执行屏障和 TLB 失效序列，再写入所选描述符；修改页内容后还有缓存维护。相关指令及模型 PTE 的结果已核对，真实硬件翻译和多核缓存行为仍未验证。

### 7.4 异常入口根据访问类型分流

`do_mem_abort` 的候选回调 `3A80B0` 检查用户态、异常类型、当前地址空间、故障地址和页记录归属，再加锁处理。已分析分支接受来自较低异常级别的指令或数据异常。

```

  The "iframe" tag is not supported by your browser.
```

该图描述 kind=0。取指异常选择修改副本；当执行 PC 位于其他页时，数据异常选择原内容副本。故障地址用于定位被访问页，用户 PC 用于判断指令来自哪里，两者承担不同职责。

例如，在满足该异常路径时，执行 CrashSight 补丁位置将使用含 `RET` 的副本；另一页的代码把该位置当数据读取时，则可切回原内容副本。这解释了它同时改变行为和保留部分原字节视图的意图。

### 7.5 同页访存为何需要指令代办

如果当前指令与它要读写的数据都在受控页，直接切到禁止执行的数据页会使取指再次异常。样本在此进入 `2888B0` ，从原内容副本取得 PC 处的四字节指令，并结合用户寄存器、故障地址和读写方向，代办这一次访存。

读取结果写回用户寄存器；写入则落到原内容副本。成功后，异常回调把用户 PC 增加 4，并在写入时置脏标志；拒绝时不推进 PC，进入请求 SIGKILL 的分支。该路径保持现有修改页描述符。

这一处理并不完整。49 个公开指令对照中，34 个结果一致、8 个拒绝、7 个返回成功但语义错误。错误涉及符号扩展、后变址寄存器写回和部分 SIMD 编码，调用者仍会把错误结果当成成功并推进 PC。

kind=1 也有同页例外：已测同页读取从真实原页取值，未统一返回填充数据；同页写入样例则被拒绝。因此，两个模式都不能概括为“任何读取恒定看到同一份伪装内容”。

### 7.6 写入后重建修改页

原内容副本承担数据工作页的角色，内容可以发生变化。kind=0 的写入型异常将记录置脏；下一次选择修改副本前，内核复制最新的原内容副本，再逐条重放保存的替换记录，执行缓存维护并清除脏标志。

合成关系可以写成：

`新的执行副本 = 最新原内容副本 + 按顺序重放的全部修改记录`

这样，非补丁区域的数据变化会保留，补丁覆盖区仍由修改记录决定。没有脏标志时，已测取指分支直接复用修改副本，避免再次整页复制。

### 7.7 解除、进程退出与最终释放

恢复命令按目标地址查找其所在页，再进入原解除函数：恢复保存的原 PTE，从全局链表及哈希桶摘除记录，然后归还所有权引用。按地址解除的粒度是整页，并非只撤销该地址的一条补丁。

目标为零时可进入按地址空间和进程筛选的批量解除； `exit_mmap` 相关回调也连接到按地址空间清理。若其他路径仍持有引用，解除会先恢复映射并摘链，等最后一个引用归零后才释放页副本、对象及其持有的 `mm` 引用。

已测生命周期包含分配失败回滚、同页追加、解除及外部引用延迟释放。串行模型中的计数平衡尚不能替代真实并发、退出及卸载正确性。

### 7.8 硬件断点地址的暂存与恢复

用户页机制之外，模块还包含硬件断点状态处理。候选回调 `8212C` 根据用户 PC、断点槽的 BAS 字节选择信息和输入状态判断匹配项，将对应 BVR 地址值暂存后清除该槽，并设置任务的 `thread.debug.bps_disabled` 。每条记录保存槽号、原值和线程 PID。

载荷控制标签 `0x0000000000687772` 可进入恢复函数 `342D4` ：倒序处理属于当前线程的记录，将地址写回相应 BVR 槽，移除已消费记录并清任务标志，其他线程记录保留。这是特定地址寄存器的暂存与恢复，不能概括为关闭全部硬件调试机制。

原候选回调已通过明确指定的 Hook 生成桥完成离线交付，记录生产与恢复也有连续证据。但 `8212C` 在自然初始化中的安装来源仍未找到；调试寄存器读写使用模型表，真实硬件断点效果尚未验证。

## 8\. 游戏进程内的功能

载荷在游戏进程内部读取对象并组织功能，现有分析确认了修改控制器朝向、散布系数和后坐力相关字段的代码路径。朝向计算使用目标位置、速度、重力及角度换算，末端准备交给控制器相关调用。子弹追踪的完整“选中目标到游戏消费”专用链仍有缺口。

图形部分使用 ImGui / Vulkan，恢复出 82 个控件，其中 78 个与持久配置绑定，覆盖玩家信息、物品、瞄准、界面和颜色等设置。菜单项与配置绑定可以证明功能入口存在，全部功能的最终效果仍需逐项核对。

对目标库，目前已确认向 CrashSight 准备修改请求。对 tersafe，已确认查询和保存基址，但在已观察路径中没有形成写入证据；后续尚未执行完，也不能据此认定永远不会修改。

## 9\. 内核模块的并行功能与远程控制

除第 5 章的管理和拦截框架、第 7 章的页与断点处理外，模块还有选择性隐藏、访问限制、文件服务及远程主动操作。本章对照 [原执行流程报告](https://bbs.kanxue.com/%E6%A0%B7%E6%9C%AC%E5%AE%8C%E6%95%B4%E5%88%86%E6%9E%90%E6%8A%A5%E5%91%8A.md) 和 [内核完整功能报告](https://bbs.kanxue.com/business/reports/%E5%86%85%E6%A0%B8%E6%A8%A1%E5%9D%97%E5%AE%8C%E6%95%B4%E5%8A%9F%E8%83%BD%E5%88%86%E6%9E%90%E6%96%87%E6%A1%A3.md) 补齐功能范围，按职责说明触发入口、处理内容及当前边界。原报告与后续专题有差异时，采用后续核对结果。

以下管理命令、getrandom 标签和 TCP 选择值仍属于三套独立编号。内核网络后台与前端卡密登录也有各自的状态和检查，不能把前端登录成功视为远程控制会话已经建立。

### 9.1 进程枚举、内存访问与信号保护

模块分别判断“当前调用者是否豁免”和“目标任务是否命中规则”。判断材料包括指定 PID、线程及 PID 集合、UID、名称匹配和缓存，不能把所有集合统一称为隐藏名单。

| 入口或功能 | 已恢复的行为 |
| --- | --- |
| proc 根目录枚举 | 保留原 proc、hidepid 和权限框架；所测 TGID 小于 300 的条目直接略过，其余再按目标规则筛选；保留 self、thread-self 和续读位置处理 |
| `process_vm_readv/writev` | 调用者未豁免且目标命中时，准备返回 `-ESRCH` |
| `pidfd_open` | 在特定低 32 位标志条件下检查目标，命中准备返回 `-ESRCH` |
| 用户态信号请求 | kill、tkill、tgkill 及排队信号按调用者、目标和 TGID／TID 组合条件拒绝 |
| 内核信号投递 | 目标线程正在登记范围执行时，所测 SIGTERM／SIGCONT 可被跳过；SIGKILL、SIGSEGV、SIGSTOP 对照仍通过 |
| maps／smaps 显示 | 对主范围及附加范围选择性跳过条目；实际边界比普通半开区间交叠规则更宽 |
| 远程取页 | `get_user_pages_remote` 、 `pin_user_pages_remote` 在 mm、线程组和范围条件满足时准备返回 0 |
| `mmap` 、 `munmap` 、 `mincore` | 所测目标线程组的请求起点落在登记范围时，分别准备返回请求起点、0、0；mincore 不生成真实驻留位图 |
| `mprotect` 、 `msync` | 前者在命中且含读权限时去掉 `PROT_READ` 并准备错误；后者在所测目标线程组中的拒绝范围更宽 |

这些回调可以使某些观察或操作看不到真实结果，但现有证据没有覆盖所有内存访问入口。尤其不能把部分信号保护理解为无条件防杀，也不能把过滤器放行等同于原系统调用已经成功执行。

### 9.2 路径隐藏、目录过滤与文件内容替代

**路径规则按完整分量匹配。** 例如规则 `local` 可命中 `/data/local/item` ，不会因为 `/data/locality/item` 含有同样子串就命中。TCP 167 将规则写入非活动缓冲，再发布活动索引；已测 1 至 63 字节普通分量可用，空规则清除，点、双点、斜杠、NUL 和超长输入在消息层被拒绝，旧规则保留。另有受状态约束的生成名规则，来源尚未全部闭合。

调用者未豁免且路径命中时，filename_lookup、do_filp_open 及 unlink、mkdir、mknod、rename、link、symlink 相关回调可准备 `-ENOENT` 。重命名和链接类双路径操作检查两端，第一端复制失败也不一定阻止第二端检查。特殊路径还涉及 proc 目标、binder 日志、cgroup／acct、KGSL、dev/pts 和精确包目录；部分分支返回 `-EACCES` ，包目录特例还可能先调用原查找再拒绝，不能统一简化为一次字符串包含判断。

**目录结果过滤发生在另一层。** getdents64 取得原目录批次后，将结果复制到临时缓冲，按路径分量及 `uid_…` 、 `pid_…` 等规则筛选、压缩并回写。整批被过滤时可继续读取下一批；所测分配或复制失败则保留原结果。该入口对纯数字名称的规则与 proc 根枚举不同。

**文件内容替代直接影响读取字节。** TCP 244 可新增或替换、删除、清空路径与内容对象，最多 8 槽。vfs_read 在启用、普通可读文件和路径命中时使用缓存内容，维护偏移、EOF 和对象引用；二进制、空内容、部分复制及 `deleted` 后缀已有离线核对。它不要求把替代内容写入原磁盘文件，不能与文件隐藏或真实文件写入混为一项功能。

### 9.4 网络观察过滤与目标进程连接处理

网络处理包含两项不同用途：降低某些连接在观察接口中的可见性，以及识别目标进程自身的连接和写入。

| 路径  | 处理内容 |
| --- | --- |
| TCP／UDP IPv4 列表及 socket diag | 比较远端 IPv4 与两个解码配置地址；命中时跳过显示或填充。所测仅本地地址命中不触发相同规则 |
| 接收与发送抓包观察 | 检查 IPv4 TCP／UDP 的源或目的地址，命中时跳过 packet_rcv、tpacket_rcv 或发送观察消费者；解析／复制失败时保留原路径 |
| 目标进程 connect | 在 TGID 和控制材料条件满足时，读取 IPv4 地址并按 fd 登记；地址已在命令 91 的表内时准备拒绝，同 fd 新连接会重置材料和就绪位 |

抓包路径已测公开报文字节保持，跳过观察消费者不能等同于丢弃实际传输。16 字节识别对应的产品协议身份和连接删除生命周期尚未完全确认；这条目标进程 connect／write／close 链也不等于内核自身的 TCP 后台连接。

### 9.5 UDP 触发配置与内核 TCP 后台

**UDP 路径负责把特征输入交给连接配置。** ip_rcv 回调检查 IPv4／UDP 头、特征字段、长度、分片和分段复制，调用原解码器后再检查标记、选择值和时间。已测非负时间域允许绝对秒差不超过 86400，超出则拒绝；它是报文时间窗口，不是下述正值配置项的单位。

解码对象的选择值 1 更新一次连接配置，2 更新持续连接配置，3 清启用位。地址、端口非零及模块就绪等条件仍由配置消费者检查。另一个正值配置项已测范围为 1 至 86400，越界归一化为 60，其产品单位尚未确定；重复更新仍增加 32 位代次。

接收回调通过 busy 原子预留、pending 对象和工作队列交付配置；worker 先取走 pending、清 busy，再应用并释放对象。分配失败、重复提交和有限交错已有核对，但 busy 不是持久去重，也未证明完整 SMP／卸载竞争。完整有效 UDP 消息到自然配置应用的链尚未闭合，当前解析路径也未见独立签名或 MAC 调用，不能把流密码解码本身当作认证完成。

**TCP 路径负责建立后台会话、解帧和分派。** 已恢复的默认端点是 `5.75.158.192:43183` 。后台准备 IPv4 TCP socket 和三个约 32 KiB 缓冲；一次模式连接失败后停用并进入 100 ms 等待，持续模式保留启用并进入 4000 ms 重试等待。

声明连接成功的独立实验可观察到 48 字节首包、短写补发、12 字节前置读取、四字节大端正文长度和 ChaCha20 处理；正文长度接受 1 至 32768。明文进入分派器 `9FC1C` ，应答经对应发送辅助交回。错误或 EOF 路径准备关闭 socket 并释放缓冲。完整自然会话及其端到端认证仍未验证。

### 9.7 远程进程和 socket 清单

172 输出 TGID 与 comm 名称。所测大于 65535 的 TGID 被跳过并置状态，某些低 TGID、无 mm 和内核线程仍可列出，因此它与 proc 根目录过滤不是同一规则。

94 则面向另一套筛选：排除内核线程、缺少 mm／signal 或组内最大 exec_start 为零的对象，按 UID 域和 67 项区分大小写的名称前缀表筛选。名称优先命令行首段，失败回退 comm；排序依据组内最大 exec_start，并输出相对首个实际条目的毫秒差。 **该时间不是 CPU 占用率。**

106 从 TCP／UDP 表收集 IPv4、远端地址非零的 socket，以“协议、本地 IPv4、远端 IPv4”去重，端口不进入记录；每页最多 32 项，带继续标志和下一索引。已有有限单桶、多对象模型，全部桶、命名空间和并发退出未穷尽。

232 对有效 PID 查找任务后准备信号 9，不要求目标一定有 mm；141 则保存目标所属 TGID，失败保持旧选择值。实际信号投递均未执行。

### 9.8 SurfaceFlinger 库查询与修改控制

TCP 27 在就绪条件满足后精确查找 surfaceflinger 任务，遍历 VMA，匹配 `libsurfaceflinger.so` ，收集同路径最多 24 段映射及文件偏移，再打开库文件解析 ELF 动态符号。

第一项目标可解码为 `android::Layer::isInternalDisplayOverlay() const` 。第二项原字符串试图描述 `getPrimaryDisplayOnly` ，但名称长度编码与实际字符串长度不符，真实系统中是否有相应导出仍有疑点。

在公开合成符号和可执行映射条件下，原分支准备将查询结果固定为 false 的页修改请求，交既有后端。第一笔失败直接返回，第二笔失败会请求恢复第一笔；两笔声明成功后保存目标及 TGID。禁用时逐项请求恢复，错误时保留记录，便于后续处理。

这些证据说明模块有针对系统显示服务的控制设计，尚不能认定真实截屏、投屏或显示效果已经改变。

选中的临时凭据可覆盖相应读取、写入或目录操作的生命周期，收尾后恢复调用者 cred，real_cred 不变，也不调用 commit_creds。这与 194 对目标线程组的持续凭据发布不同。真实 SELinux 策略、挂载、命名空间和设备文件效果尚未验证。

### 9.10 Shell 命令请求、输出与超时收尾

TCP 61 准备 `/system/bin/sh` 、 `-c` 和输入命令文本，附带临时输出文件、标准错误重定向及完成标记。参数中的 argv 首项写为 dumpsys，但实际解释器路径仍是 shell。

原流程还包含备用子线程：在接口槽可用的模型中，辅助程序返回 0 或 `-ENOENT` 都会进入该路径。子线程准备 kernel_execve，并尝试取得 UID／GID 2000、 `u:r:shell:s0` 的凭据；部分凭据准备失败路径仍可走到 exec 调用前，不能认为每次均完成身份切换。

父路径从共享状态读取 exec 错误、PID 和引用计数，等待完成标记后收集输出。单次读取最多 4096 字节，累计上限 32765 字节，达到上限即置截断；空输出和二进制 NUL 均有对应处理。子线程声明的 exec 错误优先于已存在的输出或标记。

超时逻辑已离线跑完：主等待为 1200 次、每次请求 50 ms，随后准备 SIGKILL；任务仍存活时最多再等待 40 次，最终返回 `-ETIMEDOUT` ，不采集已有输出。62 秒是这些等待请求的名义总和，前置辅助程序及调度耗时另计，不是端到端硬超时。清理会请求关闭句柄、删除临时文件，但失败可能留存文件或在途共享状态。

当前确认的是原参数、子线程函数和输出／超时消费者，真实解释器、线程调度、命令与信号均未执行。

### 9.11 线程组凭据改写与设备复位

**TCP 194 按 PID 处理线程组凭据。** 原代码先为符合条件的线程分别准备新对象，将八个 UID／GID 字段清零，从模板复制五组 capability；全部准备完成后，再在目标锁下发布 real_cred 和 cred。准备阶段失败会释放临时对象并保留原目标凭据；发布后按引用计数释放旧对象，外部引用存在时延迟释放。所测退出或内核线程成员被跳过，独立子进程不随之修改。

这是具有提权含义的操作，但所测 securebits、SELinux 安全字段、seccomp 和 no_new_privs 保持，不能描述为解除全部安全限制，也未证明真实多线程发布具有整体原子性。

**TCP 178 准备设备复位。** 原代码生成并缓存含 PSCI SYSTEM_RESET 功能号 `0x84000009` 的 ARM64 代码，包含 SMC／HVC 及回跳。网络调用者在应答发送后可沿保存入口走到该生成区；所测发送返回 0 时先请求等待 200 ms，其他已测返回值也可能进入跳转。

分配或指令写入失败有错误和释放路径。正式正例均停在跳入生成代码之前，没有执行固件指令，短应答或缓存建立都不能证明设备已复位。

### 9.12 开机自动加载配置及撤销

TCP 56 的第二字节是子操作。安装分支根据 ksud／ksu、Magisk、apd／ap 等环境标志选择 modules 目录或 `/data/adb` 回退目录，使用标识 `q7n4w2m8k1p6` ，复制输入模块并准备一个 816 字节 ARM64 run 辅助程序。

modules 分支还生成 `module.prop` 、 `service.sh` 、 `skip_mount` ，并为存在的 service.d／post-fs-data.d 目录准备入口。辅助程序的静态逻辑为检查绝对路径、打开模块、调用 finit_module、关闭及退出；启动文本先请求该程序，失败再走 insmod 回退。代码还尝试迁移文件安全上下文，但部分上下文错误不阻断所测配置完成路径。

清理子操作删除对应模块目录、回退目录及外部启动入口；一处失败仍可继续清理其他入口，并返回错误。因此它能够安装或撤销开机加载配置，配置完成不等于真实开机加载成功，删除启动文件也不等于卸载已运行的模块。

### 9.13 故障监测、后台终止与卸载生命周期

**故障监测读取日志内容，不负责删除这些日志。** vprintk_emit 回调格式化有限文本，搜索 `TTBR0` 、 `kgsl_iopgtbl_map_zero_page_to_range` 、 `GPU PAGE FAULT` 。所测第六次匹配设置一次性标志并提交工作项，后续匹配不重复提交。

后台工作函数按样本内名称查找 `com.xxx.xxx.dfxxx` ，并准备 SIGKILL；另有兼容名称分支。它与前述条件信号保护是两种行为。现有证据支持“故障触发后主动终止目标进程”，没有直接证明其动机一定是防崩溃、规避检测或掩盖痕迹。

**模块卸载有恢复顺序，也有失败边界。** 已恢复的主要步骤为：恢复 SurfaceFlinger 保存目标，置页缓存停止状态并解除缓存，撤销回调、停止或清理后台及工作项，清凭据与容器，归还 PID／mm 等引用，清进程分类及 UID 缓存，最后更新末段状态。部分清理入口目前只有 RET。

Hook 恢复写入失败会保留节点，页对象仍被引用时延迟释放；部分顶层等待后的分析来自明确的独立片段，没有证明真实 RCU、后台线程和在途回调都已排空。因此能够确认模块设计了清理流程，尚不能保证卸载后全部环境必然恢复。

## 10\. 当前证据能支持的结论

样本采用“启动器授权和注入、游戏内载荷执行功能、内核模块提供保护和页视图”的分工。远端登录、内核凭据和载荷控制各有独立门槛；共享信任根把它们联系起来，memh 则把游戏内载荷的地址范围交给本机内核。

用户页机制的核心是两类内容视图与权限异常：kind=0 让执行使用修改副本、部分数据访问使用原内容副本；kind=1 保留真实执行页、为部分数据访问提供填充页。脏页重建、同页指令代办、按页解除和退出清理构成其完整生命周期。同页指令语义和内核入口重定位均有已确认的反例。

内核功能还超出载荷保护：它包含独立网络后台、进程及文件观察、内容替代、Shell 命令请求、线程组凭据发布、系统显示服务修改请求、设备复位及开机加载配置。这组设计涉及设备级控制，不能仅按游戏内功能理解；当前仍需把请求构造、离线消费者和真实设备效果分别判断。
