>
> DIVD 的 Zammad 被两个零日漏洞组成的攻击链攻破，攻击者借助自动化框架在约 26 小时内完成提权、ARP 投毒横向移动和大规模数据外泄。
> 
> - **时间线：** 9 月 21 日 07:40 开始侦察；19:27 通过会话劫持触发模板执行；19:46 写入 setuid root shell；次日 23:24 完成隔离，入侵持续约 26 小时，但攻击者始终未横向移动到其他系统。
> - **漏洞链：** CVE-2026-102489 通过 WebSocket 泄漏他人的 HTTP 头，包括会话 cookie；CVE-2026-102490 则叠加了 `/etc/zammad` 可写、root 单元的 `source conf.d` 以及可杀进程触发重启，最终形成任意文件以 root 执行的提权链；报告称 2017 年以来所有 DEB/RPM 包均受影响。
> - **横向移动：** 攻击者通过 ARP 投毒冒充网关，利用 Confluence 与 PostgreSQL 之间未启用 TLS 的明文流量摸清数据库，再通过 SQL 注入写入 `remembermetoken` 伪造令牌，拿下 Confluence 与 Jira 的管理权限。

> - **防线：** 内网启用 TLS 1.3/mTLS、微隔离默认拒绝、将 Zammad 容器化，使第二个零日漏洞失效；检测侧部署网络蜜罐与蜜标，并强调检测和隔离速度是关键变量。

QUOTE

这未必是记录在案的第一起 agentic 攻击。真正罕见的是，有人 把它的现场原样摊开 ，让所有人逐行核对。

2026 年 9 月 21 日，荷兰非营利组织 DIVD 的安全运营中心收到一串告警，来源是它对外提供服务的 Zammad 工单系统 。两天后，DIVD 委托 Merlon Security 进场取证。11 月 24 日，这份 209 页的最终报告以 TLP:CLEAR 级别公开。

报告的结论很直接：DIVD 确实被入侵了。攻击者用 两个零日漏洞链式打通 了 Zammad 服务器，拿到 root 权限，随后靠 ARP 投毒进入内网，拿下 Confluence 与 Jira 的管理权限，并在约 26 小时里留下 990 个自写脚本、3259 个输出文件。

更值得注意的是报告里的一句话：种种迹象指向攻击者使用了 开源 agentic 攻击框架 ARTEX 。

THE TIMELINE

### 26 小时：一条可以逐秒核对的时间线

先看时间轴。这份报告的时间精度到了秒，几乎每个关键动作都能对应到日志行。

2026 年 9 月 21 日 07:40:38 UTC，攻击者从 98\[.\]98\[.\]124\[.\]175 开始 探测 DIVD 的外部边界 。

18:53:50，一名在 Zammad 中拥有管理员权限的 DIVD 成员登录系统。 1.3 秒后 ，攻击者利用漏洞拿到了这个会话的 cookie。19:01:00，同一个 cookie 被复用，攻击者已经以管理员身份在系统里活动。

19:06:31，第一个文件被写入磁盘。19:27:53，一个恶意邮件模板被上传到 /opt/zammad/app/views/mailer/admin_password_auth/nl.html.erb.custom 。五秒后，一次「邮件登录」请求触发了模板渲染，代码在服务器上执行，权限是低权限的 zammad 用户。

19:45 起，攻击者用第二个漏洞把权限推到 root：先写 payload，再把 stager 放进 /etc/zammad/conf.d/，然后杀掉 zammad 进程触发重启。19:46:58， /var/tmp/i95/i95rootsh 落盘 ，一个带 setuid 位的 bash 副本。

「从拿到会话到隔离完成，攻击者在网络里待了大约 26 小时。」

报告同时确认了一件对 DIVD 而言算是好消息的事：尽管攻击者反复尝试， 始终没能成功横向移动到其他系统 。

19:27:58　边界失守

ARP 投毒建立中间人位置，明文数据库流量被完整读取，伪造的会话令牌写进 remembermetoken 表，Confluence 与 Jira 相继失守。

22 日 23:24　隔离完成

从第一条告警到全网断网，前后约 26 小时，攻击者始终没有走出这一段。

02

THE CHAIN

### 两个零日：从匿名到 root 的一条链

这条链由两个漏洞串起来，编号分别是 CVE-2026-102489 与 CVE-2026-102490。

第一个是 「类心脏滴血」 的缺陷：触发 Zammad 的 WebSocket 端点，可以把其他用户的 HTTP 头泄漏出来，其中就包括会话 cookie。攻击者不需要任何凭据， 只需要等一个管理员登录 。上面那 1.3 秒，说的就是这件事。

第二个是本地提权，成因是三个配置问题叠加。Debian 包安装的 Zammad， /etc/zammad 目录的属主是 zammad 用户而不是 root ，所以该进程可以往这个目录写文件；而 usr/bin/zammad 这个 systemd 单元以 root 启动，会先 source /etc/zammad/conf.d/ 下的文件来加载环境变量，之后才降权到 zammad；再加上 zammad 进程能杀掉自己的 web worker 来触发服务重启。

三者拼在一起，就变成了「任意文件以 root 执行」。报告在脚注里补了一句让人不太舒服的观察：2017 年 9 月 11 日发布 1.5.0 版以来，Zammad 发布过的 每一个 DEB 与 RPM 包，看起来都受这个漏洞影响 。

拿到 root 之后，攻击者把 Zammad 自己的 GET /api/v1/text_modules 接口改造成了命令通道。 用业务接口做 C2 ，流量天然混在正常请求里。

03

PERSISTENCE

### 后门、凭据，和一个没抓到鱼的陷阱

持久化分两层。应用层，攻击者用被劫持的管理员账号建了一个 API token artex-i13033 ，又建了一个带管理员权限的账号 artex.ops@divd.nl。这两个名字后来成了整份报告里最强的线索。

系统层则是三件套：一个 systemd 单元 zzr.service，两个 crontab 文件 zz9cron 与 zz17cron。它们做的事几乎一样——循环扫描 /opt/zammad/public/ 下的.txt 文件，用那个 setuid 的 bash 副本以 root 执行。 攻击者只要往公开目录丢一个文本文件 ，就等于在目标机上执行了一条 root 命令。

它装进去的那个 systemd 单元长这样，五行就够用了：

.../etc/systemd/system/zzr.service 节选

\[Service\]

Type=simple

ExecStart=/bin/bash /opt/zammad/public/zzrloop.sh

Restart=always

RestartSec=2

最值得单独说一笔的，是对 Google OAuth 的改造。

9 月 22 日 11:43:05，攻击者改写了 Zammad 的 omniauth.rb，把 Google 登录的 access_type 从 online 改成 offline ，并追加了 https://mail.google.com/ 这个 scope。改动本身只有几个字符，但 Zammad 会把 OAuth token 存进数据库的 authorizations 表。 这意味着此后任何一个用户登录，其离线 token 都会落到攻击者能读到的地方 。凭这些 token，攻击者可以发起密码重置，再用 Gmail API 读走重置链接。

32 秒后服务重载，后门进入内存。12:25:14，配套的收割脚本 i13814poll.py 上传完毕。

结果是空的。脚本日志只有三行启动记录，HTTP 日志也没显示后门生效期内有成功登录。 这段时间里没人登录 Zammad，陷阱一个都没夹到 。

04

MAN IN THE MIDDLE

### ARP 投毒六小时，读懂一个数据库

如果说前面是应用层的事，这一段就是纯粹的网络层。

9 月 21 日 21:19:53 起，攻击者开始 被动嗅探 ，用的是一段一次性的 Python 脚本。真正转向主动投毒是第二天凌晨：01:15:50 上传的第一版 ARP 投毒脚本失败了，日志里连输出文件都没生成。01:37:36 的第二版才跑通。

01:37:48，攻击者开始投毒。02:27:43，Confluence 服务器询问网关 10.10.249.1 的 MAC 地址，攻击者的脚本抢先应答。 中间人位置就此成立 。

接下来是最关键的一点：Confluence 与后端 PostgreSQL 之间 没有启用 SSL 。攻击者把这段明文流量完整抓了下来，又通过 HTTP 代理把 MITM 日志一点点下载出去，花了大约六小时，把数据库结构摸清。

05

ARTEX

### 为什么报告说「很可能用了 ARTEX」

这是全文最需要谨慎处理的部分。报告的措辞始终是「指向」「很可能」，没有下定论。

判断依据不是某个恶意软件签名，而是行为特征。第一条就是体量：26 小时内，990 个 Python、Ruby 和 Bash 脚本被投放到 /tmp 与 /opt/zammad/public/，产出 3259 个输出文件和 228 个输出目录。报告直言， 人类攻击者在同样时间窗口内几乎不可能完成 。

990

自写脚本

3259

输出文件

第二条更微妙：这些脚本的注释 写得太完整了 。人类攻击者很少这么干，而这些注释反而暴露了模型自己的思路。比如 9 月 22 日 02:06 上传的 i13245sched.sh，开头就写明它只在荷兰的工作时间投毒——脚本里写的是 NL 05:00-16:00 UTC——每个窗口结束还会把真实 MAC 地址恢复回去。

...bash 节选

\# i13245sched.sh START_EPOCH WINDOWS DUR GAP

\# Working-hours (NL 05:00-16:00 UTC) L2 MITM harvest scheduler on 10.10.249.12 (root).

\# Poisons BOTH pairs:.1/.2 <->.15/.16 (JIRA/Confluence via ingress.248.5) AND.1/.2 <->.11

\# Each window is reversible: python poisons + transparent-forwards + restores real MACs at end.

第三条是命名。ARTEX 用「intent」来管理任务，每个 intent 是一个数字作业号，会出现在所有输入输出里，前缀是字母 i。前面提到的 i13245、i13814、i95， 全都符合这个规则 。

第四条是直接的字符串。Zammad 数据库里那个 artex.ops@divd.nl 账号，在 Google Workspace 里根本不存在。顺着这条线做公开情报检索，找到了 Autumn-2731 在 GitHub 上发布的开源 agentic 渗透测试框架 ARTEX。

调查进行到一半，这个仓库被 GitHub 下架了，原因是 ARTEX 卷入了针对韩国金融机构的攻击。Merlon 在此之前已经保全了多个副本，包括 ARTEX_86162d7.zip 和它的一个分支 scopeweaver_main.zip，并在内部比对后认为 框架的工作方式与本次攻击的行为高度吻合 。

最后一条来自邮件。9 月 22 日 06:54，攻击者用窃得的 csirt@divd.nl token 往 divd@bit.nl 发了一封测试信，主题是 ARTEX-i13515 recvtest 23961b ，随后被退回。把框架名字直接写进邮件主题，基本等于自报家门。

报告附录把 divd-p-zammad104 上所有含 artex 字样的位置列成了 IOC 表。摘几条代表性的：

三个字段放在一起看，脉络就清楚了：先是攻击者留下的日志痕迹，接着是自己建的账号，然后是用这个账号跑出来的任务产物。工具链的名字从头到尾没有被刻意隐藏。

NVISO 独立报告

几分钟内产生约 6 万行日志，这种体量与速度指向自动化、AI 辅助的工具链；ARTEX 是一个「以机器速度执行端到端渗透测试与攻击操作的 自主式多智能体 AI 框架 」。

需要说清楚的是边界。Merlon 没有做归因，报告明确把归因留给执法机构，自己只研究攻击者留下的证据。所以「很可能使用 ARTEX」指向的是工具链，不是具体的人。

报告认为，这次攻击本身「相对并不复杂」：噪声很大的 ARP 投毒，公开仓库里的零日利用，没有什么精巧的隐身技巧。真正新的东西是速度和规模，以及一个不会疲倦、会自己写脚本、还会在注释里解释自己想法的执行者。

06

IMPACT

### 损失盘点：2806 个文件与 4.1 万条工单标题

外泄通道有个特点值得一提。DIVD 的网络不允许直接对外连接，攻击者只能借道：用 Zammad 自己的 text_modules API，或者把文件丢进 web 根目录再直接请求，流量统一走 divd-p-proxy101 这个出向 HTTP 代理。也正因如此， DIVD 反而拿到了攻击窗口内每一个被外泄文件的完整清单 。

总计 2806 个文件经反向代理外泄，另有约 4.1 万条工单标题经 Zammad API 被拉走。个人数据方面，报告统计了全部被窃 PII，不只限于 DIVD 成员：

| 数据类型 | 数量  |
| --- | --- |
| 电子邮箱地址 | 4121 |
| 电话号码 | 34  |
| 家庭住址 | 3   |
| BSN 号码 | 0   |

其中 207 个邮箱对应 DIVD 成员，含 7 张可辨识的个人头像照片，以及 2 名成员的电话号码。DIVD 目前约有 150 名活跃成员。

Confluence 与 Jira 被整站抓取，包括 3 个 TLP:RED 页面和 33 个 TLP:AMBER 或 TLP:AMBER+STRICT 页面。

CNA 数据是 DIVD 最敏感的一块。NVISO 检查了 Google Workspace 中三处 CNA 相关位置， 没有发现被访问的迹象 ；Merlon 在 Zammad 侧发现两份含旧邮件链的文件被带走，内容均已远超 90 天披露期。

没被拿下的部分同样值得记录：GitLab 因网络分段和防火墙配置而不可达；Slack 的 bot token 只有发送权限，读不到任何消息；个人 Google 账号与整个 Workspace 环境未被访问，只有两个共享邮箱的 OAuth token 被用来发测试邮件。

07

DEFENSE

### 报告给出的防线，与它承认的盲区

建议部分写得相当具体，挑几条最硬的。

**补丁。** 两个 Zammad 实例跑的是 6.5.2-1772600293，发布于 2025 年 9 月 10 日。对一个直接对外的服务来说，这个版本已经旧了。

**内网加密。** 这是本次事件里因果关系最清楚的一条： 如果 Confluence 到 PostgreSQL 之间启用了 TLS ，攻击者就无法读到那段明文，也就没有后来伪造会话令牌这一步。报告建议内网全面上 TLS 1.3，必要时上 mTLS。

**微隔离。** DIVD 的分段做得不算差，但一个工单系统本来不需要直连 Confluence、Jira 及其数据库，也不需要连遗留域控。 默认拒绝、按需放行 ，能把攻击面压缩到只剩 Zammad 本身。

**容器化。** 报告指出，如果 Zammad 跑在容器里，第二个零日直接失效——提权依赖「杀掉 zammad 进程触发 systemd 重启」，而在容器里杀掉 init 进程等于杀掉容器。

检测侧，报告推荐在每个子网放一个网络蜜罐，并在应用里埋蜜标，比如每天自动生成一张带假密码重置链接的工单。对会翻数据库的攻击者和 LLM 来说， 这种诱饵的吸引力很实在 。

报告也承认了几处盲区。攻击期间没有流量留存设施，网络层证据只能靠重建；Slack 没有提供有意义的日志，那条只有写权限的 token 到底做了什么，始终无法证实；Velociraptor 是事发后才临时部署的，逐台手工安装耽误了时间。报告建议提前备好 Acquire 的离线包，并定期做危机演练。

还有一个细节值得单独提。Merlon 在取证时也用了生成式 AI——私有部署的 GLM-5.3，跑在隔离沙箱里，用来解析攻击者留下的大量非结构化数据，复杂任务以外的摘要交给 GLM-5.3-Flash。报告同时写下了他们的教训： 所有模型都会幻觉、会混淆数据来源 ，甚至会把其他 agent 编造的结论当成事实引用，因此每一条结论都经过人工复核。

攻防两侧同时在使用 LLM，这大概是这份报告里最平静、也最说明问题的一句话。

∞

EPILOGUE

### 结语

报告最后一段由 Merlon 的 CEO Earth Grob 署名。他写道，被入侵的新闻几乎每天都在发生，但很少有机会站在一个新技术时代的门口；这次事件之所以特殊，是因为研究过程对所有人开放，可以被审视、被学习。他还专门肯定了 DIVD 的处置：检测与响应的中位时间都很出色，两个团队从第一小时起就配合顺畅。

我读完的感受是另一件事。这份报告真正的价值不在结论，而在颗粒度——它把每个动作都钉在了秒级时间戳上，把攻击者的脚本注释、失败重试、恢复 MAC 地址这些小动作都留了下来。 这种颗粒度才让「agentic 攻击」从一个概念变成可以复盘的对象 。

而对防守方来说，26 小时里最贵的两个变量依然是检测速度和隔离速度。攻击者留下的痕迹足够多， 多到任何一个环节早一点被发现，后面的六小时 MITM 都不会发生 。
