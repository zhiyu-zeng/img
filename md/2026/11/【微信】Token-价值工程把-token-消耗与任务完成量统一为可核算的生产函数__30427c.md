**AI安全推进计划** *2026年11月8日 09:01*

## 摘要

2025 年，企业界第一次集体意识到：AI 的账单不再只是一条技术成本线，而是一条与人力成本并列的经营成本线。但这条线的读数方式，至今没有被认真设计过。

三组数据可以说明这种失序。其一，仅有 14% 的 CFO 表示能够看到 AI 投资清晰可衡量的回报。其二，一项覆盖 2,444 家公司的研究发现，企业每在 token 上花 1 美元，就有 0.44 美元用于修复 AI 生成的缺陷、0.27 美元用于重写其产出、0.11 美元消耗在审查与合并延迟上——真实成本比账单高出约 80%。其三，token 单价正以每年约 10 倍的速度坍塌，而企业的推理预算却在同步上涨：Agent 类任务的 token 消耗是同等工作量聊天交互的 5–30 倍，高盛分析师给出的数字是 50 倍。

单价在跌，账单在涨，产出说不清。这三件事同时为真，指向同一个被回避的事实：企业从未建立"token 消耗"与"工作完成量"之间的换算关系。

现有的成本治理沿用了云计算的 FinOps 语言——按部门分账、按调用计费、按服务打标签。这套方法在云上有效，因为云资源是同质的、可替代的、边际成本递减的。token 不是。token 是异质的、与认知难度强耦合的、边际效用先升后降的。把云账本直接套在 token 上，得到的是一份精确但无意义的账单：每一分钱都记得清楚，但没有一分钱能对应到"完成了什么"。

本报告提出一套替代框架：Token 价值工程（Token Value Engineering，TVE）。

它的三个基本主张是：

1\. Token 是产能，不是成本。 与工时一样，它度量的是"投入了多少认知劳动"，而不是"产出了多少价值"。因此它必须与"任务当量"和"验收通过率"配对出现，单独出现时具有系统性误导性。

2\. token 与产出之间不存在单调关系。 存在欠思考区、有效收益区、过思考区三段；越过拐点后，更多 token 买到的是更差的答案。因此预算的正确形态不是"上限"，而是"每类任务各自的最优点 τ\*"。

3\. 可比单位不是 token，而是"通过验收的任务"。 token 在跨模型、跨供应商、跨缓存策略时不可比；只有把计量锚定在交付物上，才能跨部门、跨厂商、跨年度地比较。

围绕这三个主张，报告给出四件可落地的东西：一套标准化计量方法（nToken 与任务当量）、一组三层九项指标（TVE 指标体系）、一套 Token 会计科目（三张表）、一套机制设计（预算—定价—结算—熔断）。最后，报告给出五个前瞻判断和一个诚实的反向判断：在什么条件下，这套体系本身会失效。

## 一、问题的定义：三张账单，三个错配

## 1.1 现象：单价在坍塌，账单在膨胀

先把两条曲线放在一起看。

第一条是价格曲线。a16z 把推理成本每年下降约 10 倍的现象命名为"LLMflation"；Epoch AI 用更大样本测得，在固定能力水平下，token 价格的年降幅在 9 倍到 900 倍之间，中位数约 50 倍（2020 年至 2025 年初）。一个具体的锚点：2024 年 3 月，GPT-4 级推理的输入价格约为每百万 token 30 美元；到 2025 年 3 月，同等能力在多家供应商处已降至 3 美元。

第二条是消耗曲线。同一时期，单个任务消耗的 token 数量以更快的速度上升。原因有三，且相互叠加：

▪　推理 token。推理模型在给出答案前生成大量中间思维链，这些 token 对用户不可见，但按最贵的输出单价计费，且用量随题目难度剧烈波动。

▪　Agent 循环。工具调用型智能体每一步都要重发累积的上下文——系统提示、对话历史、工具定义、此前所有工具结果。上下文随任务推进而增长，所以越靠后的步骤越贵，任务的总输入 token 大致随步数的平方增长。

▪　上下文膨胀。为了"让模型知道得更多"，团队倾向于把整个代码库、整份合同、整段历史塞进窗口。窗口越大，塞得越多。

有行业分析给出的区间是：Agent 类任务的 token 消耗是同等工作量聊天交互的 5–30 倍。高盛高级分析师 Jim Schneider 给出的数字是 50 倍。个别极端案例更夸张：有开发者用 100 个 Codex 智能体连续运行 30 天，账单达到 130 万美元。

于是形成了一个悖论：单位价格每年降一个数量级，总账单却每年涨一个数量级。答案是算术，不是谜题——账单等于单价乘以数量，第一个因子在暴跌，第二个因子在暴涨。

这个悖论本身不新鲜。新鲜的是它带来的管理后果：当单价的信号失效时，组织失去了判断"这次调用贵不贵"的锚点。 在云时代，你看到一台 32 核虚机跑了两周，你知道它贵。在 token 时代，你看到一次调用花了 38 万 token，你没有直觉。

## 1.2 错配一：计价单位——你在按敲键盘次数发工资

设想一家公司这样给程序员发工资：不看交付了什么功能，只看他敲了多少次键盘、看了多少行代码、开了多少次会。所有人都会认为这荒谬。但今天绝大多数企业给 AI 付费的方式，正是这个逻辑：按 token 付费，等于按模型"敲键盘的次数"付费。

这个类比不是修辞，它有严格的对应关系：

| 维度  | 工时制（人力） | Token 制（AI） | 差异后果 |
| --- | --- | --- | --- |
| 计量对象 | 投入的时间 | 投入的 token | 都不度量产出 |
| 与产出的关系 | 弱相关，可被熟练度改善 | 弱相关甚至负相关（过思考） | token 更危险：可能反向 |
| 可比性 | 同一岗位内可比 | 跨模型不可比（分词器不同） | token 连"同质"都不满足 |
| 计价弹性 | 加班 1.5 倍 | 输出 token 是输入的 5 倍 | 结构比总量更重要 |
| 质量信号 | 无   | 无   | 都需要外部验收门 |

人力管理花了一百年才从"工时"进化到"绩效 + 职级 + 交付物"，中间付出了泰勒制、目标管理、OKR 三次迭代。AI 成本管理目前还停在"工时"阶段，而且连工时都不如——工时至少是同一把尺子，token 在不同分词器下长度不同，同一段中文在两家厂商的模型里可能相差 20%–40%。

结论：token 可以作为"投入侧"的计量单位，但绝不能作为"产出侧"的计量单位。把两者混为一谈，是所有 AI 成本治理失效的起点。

## 1.3 错配二：时间尺度——秒级计费，季度级价值

第二个错配更隐蔽：计量的时间粒度和价值实现的时间粒度不匹配。

一次 API 调用在 800 毫秒内完成计费，一个 token 的账单当天就能出。但一次调用的价值实现周期可能是：代码合并（天）、上线（周）、产生业务效果（季度）、被审计确认（年）。

这带来两个后果。

其一，成本可见，价值不可见，于是管理只发生在成本侧。 这是组织行为的必然：能被测量的东西会被优化，不能被测量的东西会被牺牲。当 token 账单是日报、而业务价值是年报时，所有优化动作都会指向"少花 token"，而不是"多创造价值"。这就是为什么大量企业的 AI 治理最终退化为"限流 + 审批 + 降级模型"三件套。

其二，投资性支出被当作费用性支出处理。 建评测集、建知识库、写 Skills、做提示词工程，这些投入当期消耗大量 token，但其收益在未来多个周期释放。如果全部按当期费用核算，这些"资产性投入"会在预算压力下第一个被砍掉——而它们恰恰是降低长期 token 消耗的主要手段。这是典型的"省了小钱、废了本金"。

## 1.4 错配三：责任主体——花钱的人不承担结果

第三个错配是组织性的：消耗 token 的人、批准预算的人、承担结果的人，往往是三个不同的人。

一线员工用 AI 写周报、生成代码、整理会议纪要，他不看账单。部门负责人批预算，他看不到单任务成本。CFO 看总账，他看不到任何一个具体任务的交付质量。三方各自掌握了信息的一部分，没有任何一方掌握完整链路。

微软前首席 AI 官 Sophia Velastegui 有一句评价很尖锐：大多数人默认自动化他们不喜欢的任务，而不是对公司最有价值的任务。这句话的管理学含义是：当消耗决策由"厌恶程度"驱动，而核算由"总量"驱动时，资源配置必然错位。 员工自动化了写周报，公司营收没有任何变化；工程师用 AI 生成代码速度翻倍，但代码废弃率上升了 800%。

三个错配合起来，构成了本报告要解决的问题：不是"如何降低 token 成本"，而是"如何建立 token 与工作完成量之间可核算、可归因、可比较的换算关系"。 前者是一个优化问题，后者是一个计量问题。计量问题不解决，优化问题只会不断产出"降本 30%、返工翻倍"的假胜利。

## 1.5 一个被忽略的事实：token 的会计不可比性

在进入框架之前，必须处理一个技术前提：token 本身不是一把合格的尺子。

第一，分词器不同。 同一段文本在不同模型下的 token 数不同。中文差异尤其大：有的分词器对中文按字切分，有的按词切分，同一段 1,000 字的文档可能被计为 700 token，也可能被计为 1,400 token。跨厂商比较原始 token 数，等于用两种刻度的尺子量同一块布。

第二，缓存改变计价结构但不改变占用。 提示词缓存的命中部分通常按标准输入价的 10% 计费，这极大降低了重复上下文的成本。但它带来一个会计陷阱：账单下降不等于消耗下降。缓存命中的 token 依然占据上下文窗口，依然参与注意力计算，依然导致性能衰减。缓存优化的是钱，不是能力。

第三，推理 token 是隐性的。 推理模型的思维链 token 不出现在响应里，但按输出价计费。用户看到的输出是 300 token，账单上可能是 3,000 token。这让"按输出长度估算成本"的经验法则彻底失效。

第四，供应商的计价口径不统一。 有的厂商把缓存写入单列并加价（5 分钟 TTL 加 25%，1 小时 TTL 加 100%），有的把批量折扣做到五折，有的按时段峰谷定价。同一份工作负载在不同供应商之间的可比性，远低于云主机的可比性。

这四点合起来说明：原始 token 数是一个"供应商内部"的计量单位，不是一个"企业级"的计量单位。 要建立企业级核算，第一步必须做标准化换算。这是第三章的任务。

## 二、实证基础：token 与产出的四种非线性

这一章是整份报告的证据基础。如果 token 与产出是线性关系，那么"多用多干、少用少干"就是对的；正因为不是线性，才需要一套新框架。

四种非线性，分别对应四种失效模式。

## 2.1 第一种：倒 U——推理预算的边际效用会转负

这是最硬的一份证据。

ACL 2026 Findings 收录的研究《When More Thinking Hurts》给出了 R1-32B 在 AIME 数学竞赛题上的完整预算—准确率轨迹：

| 推理预算（token） | 500 | 2K  | 4K  | 6K  | 8K  | 10K | 12K | 16K |
| --- | --- | --- | --- | --- | --- | --- | --- | --- |
| 准确率（%） | 28.2 | 41.4 | 48.2 | 52.5 | 54.8 | 55.6 | 54.9 | 53.1 |

三个特征值得注意。

第一，前段陡峭。 从 500 到 4,000 token，准确率提升 20 个百分点。这一段是"欠思考区"——模型还没组装出完整的推理链，多给预算是唯一解法。

第二，中段平缓。 从 8,000 到 10,000，只提升 0.8 个百分点。这是典型的边际递减。

第三，后段转负。 超过 10,000 token 后准确率开始下降，16,000 时回落到 53.1%，低于 8,000 的水平。研究进一步统计了"翻转事件"（flip）：模型先得出正确答案，继续推理后又推翻它。在 7,000 token 以上，负向翻转开始多于正向翻转，翻转比超过 1；到 16,000 token 时，这个比值达到 7.55。

研究对 80 个随机样本做了人工复核，其中 67.5% 确认为"真实的过度思考"——模型明确地重新考虑并否决了原本正确的答案。

这不是"浪费"，是"自伤"。多花的 token 不仅没有买到准确率，还摧毁了已经买到的准确率。

同类证据不止一份。南京大学团队用受控预算（500 至 16,000 token）测得：生成 8,000 token 的成本约为 500 token 的 16 倍，而在简单问题上，大部分支出买不到任何东西；难度调节效应明显——简单题在约 1,500 token 处达到峰值，最难的题可以受益到约 8,000 token。Anthropic 构造的一组任务上，延长推理长度使准确率从约 70% 单调下降到 30%。一项覆盖 53 个模型的基准测试发现，推理模型平均比非推理模型多生成约 18 倍 token，在某些任务上得分反而更低。

管理含义非常直接： 一个全局的"推理强度"设置，是对每一个请求做预算决策却不知道它在曲线上的位置。对简单的多数请求，你在为平坦的右尾付费；对困难的少数请求，你可能在拐点之后自毁。

## 2.2 第二种：衰减——上下文越长，可靠性越低

第二个非线性发生在输入端：上下文不是免费的信息容器，它有毒性。

Chroma 在 2025 年 7 月发布的技术报告《Context Rot》测试了 18 款模型（含 GPT-4.1、Claude 4、Gemini 2.5、Qwen3），共 194,480 次调用，在保持任务难度不变的前提下只改变输入长度。结论是：模型对上下文的处理不是均匀的，第 10,000 个 token 的可靠性远低于第 100 个；即便在"重复一个词"这类极简任务上，性能也随长度下降。

更关键的是三个调制因素：

▪　语义相似度越低，衰减越快。 当问题与答案之间不是字面匹配、而需要语义推断时，性能下滑更早、更陡。

▪　干扰项会放大衰减。 一段"看起来相关但其实不对"的内容，会显著降低准确率；四个干扰项会叠加。不同模型被不同干扰项主导，产生不同的幻觉路径。

▪　模型家族的失败方式不同。 Claude 系在不确定时倾向于弃答，GPT 系给出"自信的错误答案"的比例最高。

最具实践价值的是 LongMemEval 那组对照实验：同一批 306 个问题，分别用约 300 token 的聚焦提示和约 113,000 token 的完整历史去回答。每一个模型家族在聚焦版本上的得分都显著更高，开启思考模式能缩小差距但无法消除。

一句话总结：把检索到的 50 个片段全部塞进百万窗口，比只给最相关的 5 个片段效果更差——因为另外 45 个按构造就是干扰项。

还有一个反直觉的技术细节：提示词缓存不解决这个问题。 缓存改变的是"你为这些 token 付多少钱"，不是"这些 token 是否占据窗口"。缓存命中的前缀依然参与注意力计算，依然稀释关键信息。这意味着"缓存命中率 90%"是一个财务指标，不是一个质量指标——把它当质量指标用，是当前 AI 治理中最常见的自欺。

## 2.3 第三种：方差——同一个任务，消耗可以差 30 倍

第三个非线性是统计性的：token 消耗的方差极大，而且与质量不相关。

Bai 等人在同一批 SWE-bench Verified 任务上，用 8 个模型重复运行，观察到总 token 消耗最多相差 30 倍。更关键的后半句：更高的 token 使用量并不意味着更高的准确率。

这条发现摧毁了三种常见做法：

▪　用 token 消耗做工作量估算。 既然方差是 30 倍，任何基于单次运行的估算都不可信。可行的方法只能是"重复多次、报告分布"，而不是"跑一次、给一个数"。

▪　用 token 消耗做绩效信号。 如果一个员工用 30 万 token 完成任务，另一个用 1 万 token 完成同样任务，前者不是"更努力"，很可能是"提示词更差、上下文管理更糟、重试更多"。

▪　用平均单价做预算。 长尾任务的消耗可能是中位数的十几倍，预算必须按分位数（P90/P95）而非均值编制。

## 2.4 第四种：返工——账单之外还有 80%

第四种非线性不在 token 账单里，而在账单之外。

前述 2,444 家公司的研究给出了一个分解：每 1 美元的 token 支出，对应 0.44 美元的缺陷修复、0.27 美元的代码重写、0.11 美元的审查与合并延迟。隐性成本约为显性成本的 80%。

这个数字需要谨慎对待——它来自特定样本（以软件工程为主），不一定可外推到法务、营销、客服。但它揭示的结构是普适的：AI 产出的边际成本不是零，因为验收成本不为零。 生成一份 20 页的报告只要 0.3 美元，但审核它需要一个人 40 分钟。当生成成本趋近于零时，瓶颈从"生产"转移到"验收"，而验收成本是人力成本，不随 token 价格下降。

推论：token 价格下降 10 倍，不会让 AI 的总成本下降 10 倍，只会让成本结构从"生成主导"转向"验收主导"。 这是一个非常重要的判断，它意味着未来三年企业 AI 成本治理的主战场，将从"压低单价"转向"降低验收负担"——也就是提高一次通过率。

## 2.5 归纳：Token 是有阈值的催化剂，不是线性燃料

把四种非线性放在一起，可以得到一个统一的图景：

| 失效模式 | 触发条件 | 表现  | 治理杠杆 |
| --- | --- | --- | --- |
| 倒 U | 推理预算超过任务最优点 | 准确率回落、负向翻转 | 按任务类型设定 τ\*，动态预算 |
| 上下文腐烂 | 输入长度超过有效区 | 检索失败、指令遗忘 | 上下文工程：检索、重排、压缩 |
| 方差爆炸 | 长链路 Agent、多工具 | 成本不可预测、质量不可复现 | 重复采样、分布报告、轨迹约束 |
| 验收返工 | 一次通过率低 | 隐性成本 80% | 验收门前置、评测集、Skills 沉淀 |

四种模式共同说明一件事：token 更像催化剂而不是燃料。 在阈值以下，它决定反应能否发生；在阈值以上，它不再提高转化率，只增加副产物。管理的任务不是"少加催化剂"，而是"找到每种反应的最佳投加量"。

这也解释了为什么"降本 30%"类项目经常失败：它们在线性假设下做全局压缩，压到阈值以下，反应直接停止——表现为质量崩塌、员工弃用、返工上升。而真正的机会在于：大多数企业当前位于曲线的右侧平坦区甚至下行区，把预算从"过量"重新分配到"不足"的任务上，可以在总支出不变的情况下显著提升总产出。

这是本报告最重要的一个可操作判断。第三章给出如何度量它。

## 三、度量：从 token 到任务当量

## 3.1 为什么必须换单位

第二章的结论是：token 与产出非线性、高方差、不可跨厂商比较。既然如此，为什么企业还在用 token 做度量？

因为便宜。token 是唯一一个"自动产生、无需额外工作"的计量单位。要度量"任务当量"，你必须先定义什么是任务、什么算完成、谁来判断完成——这三件事都需要人。

但正因为需要人，它才有管理价值。一个不需要任何判断的指标，通常也不承载任何信息。

换单位不是抛弃 token，而是把 token 放回它该在的位置：投入侧。产出侧需要另一个单位。

## 3.2 nToken：把 token 标准化

第一个技术动作是定义标准化 token（normalized token，nToken），用于跨模型、跨供应商的投入侧比较。

nToken = （原始输入 token × k_tok ＋ 原始输出 token × k_out × ρ）÷ 基准模型分词密度

其中：

▪　$k\_{tok}$：分词器归一系数。以某一基准模型（建议选企业主力模型）的中文分词密度为 1，其他模型按"同一语料下的 token 数之比"折算。实测方法很简单：取 20 份企业真实文档（合同、代码、会议纪要各若干），分别在两个模型上计数，取比值的中位数。

▪　$k\_{out}$：输出权重。默认取 5（多数厂商的输出单价约为输入的 5 倍），用于把输出 token 折算成"等效输入成本"。

▪　$\\rho$：缓存折扣系数。命中缓存的部分乘以 0.1（或厂商实际折扣率），未命中部分乘以 1。

▪　分母：把结果归一到"基准模型下这段文本会消耗多少 token"，使不同模型的数字可比。

nToken 的意义不是精确，而是可比。 它承认自己是一个近似，但保证同一个任务在不同模型、不同月份、不同部门之间的数字是同一把尺子量的。没有这一步，跨部门比较就是在比较苹果和橘子。

需要强调的是：nToken 解决"投入侧可比"，不解决"产出侧有价值"。后者需要第二个单位。

## 3.3 任务当量：把工作变成可计数的单元

第二个单位是任务当量（Task Equivalent，TE）。

定义：1 TE = 一个中等复杂度、由一名具备该领域基本能力的人类在 1 小时内可完成、且经一次验收通过的知识工作单元。

这个定义有三个刻意的选择：

第一，锚定在人身上。 用"人类 1 小时"而不是"多少 token"，是为了让这个单位在 token 价格波动、模型代际更替时保持稳定。十年后 token 可能便宜一千倍，但"一份合同的风险条款比对"仍然大致是一个人一小时的工作量。

第二，强调"一次验收通过"。 这是与"任务数"的关键区别。生成了 10 份报告但 6 份被打回，有效任务当量是 4 而不是 10。这把质量内建到了计量单位里，避免了"产量虚高"。

第三，用"中等复杂度"消除长尾。 极简单的任务（分类一条工单）和极复杂的任务（重构一个模块）不适合用 TE 直接计量，前者用"批次"、后者用"项目"单独核算。TE 只覆盖中间那 80% 的常规工作。

有了 TE，两个基础指标立刻成立：

TCT（单任务成本）＝ nToken × 单价 ÷ 任务数　　　CPTA（验收单位成本）＝ 全成本 ÷ 验收通过任务数

注意 CPTA 的分子是"全成本"，不只是 token 账单，还包括人工审核时间、返工成本、基础设施分摊。这是它与 TCT 的本质区别：TCT 是供应商视角，CPTA 是雇主视角。

## 3.4 TVE 三层九指标

单个指标必然被博弈，所以需要一组相互制约的指标。本报告提出三层结构：计量层回答"花了多少"，转化层回答"浪费在哪"，价值层回答"值不值"。

![图片](https://cdn.jsdelivr.net/gh/zhiyu-zeng/img@main/img/2026/11/7fbd278a81e4aaf1.png)

图 5　TVE 三层九指标体系：从账单到价值的抽象阶梯

本报告设计

三层的关系是严格递进的，不可跨级替代：

L1 计量层——解决"数不准"的问题。三个指标：

▪　nToken 标准化量：消除分词器与计价口径差异后的可比消耗量。这是所有后续计算的分母。

▪　缓存命中率：缓存读 token / 全部输入 token。注意它是财务指标，不是质量指标（见 2.2 节）。

▪　上下文复用率：被多个任务复用的上下文 token / 输入 token 总量。这个指标衡量"知识资产化"程度——高复用率意味着企业在积累可复用的上下文（规范、模板、领域知识），而不是每次都从零构建。

L2 转化层——解决"浪费在哪"的问题。三个指标：

▪　Token 有效利用率 TER：进入验收交付物且被采纳的 token / 计费 token。这是本报告最核心的效率指标。根据 2.4 节的漏斗建模（图 4），多数企业的 TER 在 5%–15% 之间。

▪　重试放大系数 RAF：总计费 token / 首轮尝试 token。RAF 为 3 意味着每 1 个有效尝试背后有 2 个失败尝试。软件工程类任务的 RAF 通常显著高于文档类。

▪　上下文税 CTX%：重复发送的上下文 token / 总账单。行业数据显示这个比例可达 62%。它是"记忆税"的度量。

L3 价值层——解决"值不值"的问题。三个指标：

▪　单任务成本 TCT：供应商视角的单位成本。

▪　Token 价值密度 TVD：交付物价值 / 千 nToken。用于横向比较不同任务类型的"性价比"，是预算再分配的依据。

▪　验收单位成本 CPTA：雇主视角的真实单位成本。这是唯一可以直接和人力成本对比的指标——如果 CPTA 低于同等任务的外包单价，AI 就是划算的；如果高于，无论 token 多便宜都不划算。

一个常见的错误是只看 L1。L1 指标漂亮但 L3 恶化的情况非常普遍：缓存命中率 90%、nToken 环比下降 20%，而 CPTA 上升 30%——因为省下的钱被返工吃掉了。只看一层的治理，必然产生局部最优、全局次优。

## 3.5 核心公式与一个算例

把三层合成一个可比较的综合指标：

TVE ＝（V × Q × A）÷（nToken × P）

其中 V 为交付物的业务价值（可用人力替代成本或收入贡献折算），Q 为质量系数（一次通过为 1，返工一次为 0.6，返工两次为 0.3），A 为验收通过率，P 为单位 nToken 价格。

这个公式的管理含义是：TVE 的分子是价值侧三个因子的乘积，分母是成本侧两个因子的乘积。任何单因子的改善，如果以其他因子为代价，TVE 不会提升。

一个算例可以让它具体起来。

某企业 500 名知识工作者，月度 AI 相关支出 180 万元（含 token、网关、可观测性工具分摊），月完成任务 42,000 个，验收通过率 78%，实测 TER 为 7%。

▪　单任务成本 TCT = 1,800,000 ÷ 42,000 ≈ 42.9 元

▪　验收单位成本 CPTA = 1,800,000 ÷ (42,000 × 78%) ≈ 54.9 元

▪　若同类任务的外包单价为 120 元/件，则 AI 的相对优势为 2.2 倍——这是"AI 值得投"的真实依据，而不是"token 便宜"。

现在做一个不增加预算的改善推演：通过上下文工程（检索替代全量塞入）与按任务类型设定推理预算，把 TER 从 7% 提升到 12%。在总支出不变的前提下，有效产能提升 71%，月完成任务数从 42,000 增至约 72,000，CPTA 降至约 32 元。

注意这个推演的性质：它不是"降本"，是"提产"。 在 token 单价每年跌一个数量级的环境下，降本的空间会自然消失（因为成本本身在消失），而提产的空间不会——它取决于组织如何组织上下文、如何设定预算、如何设计验收。这是未来三年真正的竞争维度。

## 3.6 指标的不可能三角

必须诚实指出：这三个目标无法同时最优。

低成本、高质量、可审计——任取其二，第三个必然受损。

▪　追求低成本 + 高质量：必须依赖大量人工验收与抽检，审计成本高，且难以规模化复制。

▪　追求低成本 + 可审计：只能用规则化、模板化的方式，质量天花板低，遇到长尾任务即失效。

▪　追求高质量 + 可审计：需要多模型交叉验证、多次采样、完整轨迹留痕，成本最高。

这个三角不是缺陷，是设计约束。它的正确用法是：按任务类型选择三角形的一条边，而不是试图同时优化三个角。 合规审查类任务选"高质量 + 可审计"，客服分类类任务选"低成本 + 可审计"，创意生成类任务选"低成本 + 高质量（靠人来兜底）"。

任何声称"三个都要"的方案，通常意味着三个都没做到，只是把成本转移到了看不见的地方。

## 四、Token 会计学：三张表

## 4.1 为什么需要会计，而不只是指标

指标回答"现在怎么样"，会计回答"钱从哪来、资产是什么、什么时候该停"。

这三问在 AI 场景里格外重要，因为 AI 支出同时具有三种性质：它像费用（每月消耗）、像资产（知识库、评测集、Skills 会持续产生收益）、也像投资（模型选型、架构改造）。用一张利润表去装三种性质的东西，必然失真。

所以本报告借用会计学的三张表结构，做一次平移。这不是为了财务合规，而是为了强迫组织回答三个平时被跳过的问题。

## 4.2 损益表：这一个周期，赚了还是亏了

Token 损益表的结构如下：

| 科目  | 内容  | 计量口径 |
| --- | --- | --- |
| 营业收入 | 验收通过的任务当量折算价值 | TE × 单位价值 |
| 营业成本 | 输入、输出、缓存写入 | nToken × 单价 |
| 期间费用 | 重试、废稿、返工消化 | RAF 超出 1 的部分折算 |
| 营业外支出 | 越权调用、提示词注入导致的损失 | 安全事件工单归集 |
| 毛利润 | 收入 − 成本 − 费用 − 营业外 | —   |

三个设计要点：

第一，营业收入用"验收通过"确认，而不是"生成完成"。 这与会计的收入确认原则一致：风险与报酬转移时才确认收入。AI 生成了但没人用，不算收入。这一条会立刻暴露大量"产量虚高"的项目。

第二，期间费用必须单列重试与返工。 这是最容易藏污纳垢的地方。把 RAF 从 3 降到 1.8，损益表上体现为期间费用大幅下降，而这通常不需要换模型，只需要改上下文管理和提示词。

第三，营业外支出要单列安全损失。 这在 AI 场景里不是小概率事件：一次提示词注入导致的越权数据访问，其损失可能超过全年 token 预算。把它放在"营业外"，是为了让它在报表上显眼，而不是混在"其他"里。

## 4.3 资产负债表：你积累了什么，欠了什么

这张表最有创新性，也最容易被忽略。

资产侧：

▪　可复用上下文：领域知识库、代码规范、模板库、术语表。它们的价值体现在"降低单任务 token 消耗"，可以按"复用次数 × 单次节省的 nToken × 单价"折算。

▪　评测集：企业自有的、覆盖真实流量的评测样本。这是最重要的 AI 资产，因为它是唯一能证明"换模型不掉质量"的东西。公开榜单因污染问题已不可信（详见 5.3 节）。

▪　Skills 与工具定义：把重复的提示词逻辑封装成可复用单元，本质是把"每次重新描述"变成"一次定义、多次调用"，直接降低上下文税。

▪　缓存前缀：稳定的系统提示与知识前缀。注意它是资产也是负债（见下）。

负债侧：

▪　注意力债务：超长上下文带来的性能衰减。账面上看不出来，但它以"验收不通过率"的形式在损益表上体现。这是典型的"表外负债"。

▪　技术债与幻觉风险：未经验证的 AI 产出被直接使用，形成潜在的错误累积。

▪　供应商锁定：深度绑定某一家分词器、某一套工具链，导致迁移成本上升。

权益侧：

▪　Token 效率基线：组织沉淀下来的"这类任务应该花多少 token"的历史基准。它是一项真正的组织能力，可传承、可复用、可审计。

这张表最重要的作用，是把"省钱"和"攒资产"区分开。 一个季度省下 30% token 但砍掉了评测集建设，资产负债表上是资产减值，损益表上却是利润改善——这种"报表好看、能力退化"的情况，在只做成本治理的企业里非常普遍。

## 4.4 现金流量表：什么时候会断流

第三张表管理的是"节奏"，不是"水平"。

▪　预算流入：部门额度、项目专项、年度结转。

▪　经营流出：日常任务消耗，按日/周粒度。

▪　投资流出：评测、微调、知识库建设。这类支出应当单独设额度，不占用经营预算，否则一定被砍。

▪　筹资流入：跨部门调剂、应急追加。

▪　净流量：额度余额。当净流量接近零时触发熔断（见 5.4 节）。

现金流量表解决的是一个非常具体的问题：预算超支通常不是因为总量不够，而是因为节奏错配。 一个团队可能在 3 月就用完全年额度（Uber 的案例是 4 个月烧完全年 AI 预算），然后在剩下的 9 个月里被迫降级模型、限制使用，最终全年产出反而低于匀速使用。

把三张表压缩成可执行的科目，建议不超过 24 个，否则没人会填。

这张表的关键设计是"损耗"单独成一级科目。大多数企业的账上只有"消耗"，没有"损耗"，于是损耗被误认为消耗，优化动作也就无从下手。

## 五、机制设计：预算、定价、结算、熔断

机制不是流程，是激励结构。下面五个部件构成一个闭环：预算决定额度，定价决定流向，结算决定谁被奖励，熔断决定谁被阻止，反哺决定下一轮怎么改。

## 5.1 预算的形态：从"上限"到"最优点"

当前绝大多数企业的 token 预算是一个数字：这个月给你 500 万 token，超了告警，再超熔断。

这个设计隐含了一个线性假设：越多越好，只是不能太多。第二章已经证明这个假设不成立。正确的预算形态不是一个上限，而是一个区间，且区间的中心因任务类型而异。

对每一类任务，定义三个参数：

▪　τ\_min（最低可行预算）：低于此值，任务必然失败。这是"欠思考"边界。

▪　τ\*（最优预算）：边际收益等于边际成本的点。

▪　τ\_max（熔断预算）：超过此值，质量开始下降或成本不可接受，强制截断并转人工。

| 任务类型 | τ\_min | τ\* | τ\_max | 路由策略 | 验收门 |
| --- | --- | --- | --- | --- | --- |
| 工单分类、标签抽取 | 200 | 600 | 1,200 | 小模型 + 批量 | 抽样 5% |
| 单元测试生成 | 2,000 | 6,000 | 15,000 | 中模型 + 缓存 | 测试通过率 |
| 中等功能开发 | 15,000 | 40,000 | 90,000 | 中模型 + 工具 | 代码评审 |
| 复杂缺陷定位 | 30,000 | 90,000 | 200,000 | 强模型 + 高推理 | 复现验证 |
| 架构方案评审 | 60,000 | 150,000 | 300,000 | 强模型 + 多轮 | 专家会签 |
| 合规文档比对 | 20,000 | 60,000 | 120,000 | 强模型 + 检索 | 双人复核 |

这张表的数值是示例，企业必须用自己的数据校准。校准方法不复杂：对每类任务，取 50–200 个真实样本，在 5–6 个预算档位上各跑 3 次，记录准确率与成本，拟合出曲线，取拐点。

关键洞察：τ\* 不是由任务"看起来多难"决定的，而是由"模型当前能力下是否可解"决定的。 一个看起来很吓人的问题，对训练充分的模型可能很轻松；一个读起来很简单的问题，可能正好落在模型能力边界之外，给多少 token 都解不了。所以预算分配的依据应该是"可解性估计"，而不是"难度估计"。这也是 2026 年一批研究（如 USTC 的 Bet 系统）的核心思路：按"继续推理的期望回报"决定是否继续，实测在七个基准上平均减少约 55% 的推理 token，同时提升准确率。

把这条落到管理上：预算不应该由"任务重要性"审批，而应该由"任务可解性"路由。 重要性决定"要不要做"，可解性决定"给多少 token"。把两者混在一个人工审批流里，是当前预算制度最大的设计错误。

## 5.2 定价：三种内部转移定价模式

一旦有了预算，就必然出现"跨部门调剂"。调剂需要价格。内部转移定价有三种模式，各有适用条件。

| 模式  | 定价依据 | 适用场景 | 优点  | 缺点  | 操纵风险 |
| --- | --- | --- | --- | --- | --- |
| 成本加成法 | 实际账单 + 管理费 | 集中采购 | 简单、可审计 | 不反映稀缺性 | 低   |
| 市场参照法 | 外部公开价 × 折扣 | 多供应商 | 有外部锚点 | 长期合约难对标 | 中   |
| 影子价格法 | 内部出清价 | 额度紧张 | 引导资源流向高价值任务 | 计算复杂 | 高   |

建议的演进路径是：第一年用成本加成法（先能算清），第二年引入市场参照法（能对标），第三年试点影子价格（能优化）。 直接上影子价格，通常因为缺乏历史数据而退化为"拍脑袋定价 + 事后合理化"。

影子价格的算法不复杂：对每类任务，计算其 TVD（价值密度），按 TVD 从高到低排序分配稀缺额度，最后一单位额度所对应的 TVD 就是影子价格。额度价格高于此值的任务获得资源，低于的让出。

一个常见的错误是把预算按部门平均分配。部门是组织单位，不是价值单位。同样 100 万 token，给客服团队做分类，和给法务团队做合同比对，产生的价值可能差 20 倍。 按部门分配预算，等于放弃了这种套利机会。

## 5.3 结算：按验收通过结算，而不是按调用结算

这是整套机制里最有争议、也最关键的一条。

传统结算：\`应付 = 调用次数 × 单价\`。这本质上是"按工时付费"，供应商乐见其成，因为多调用多收钱。

建议结算：\`应付 = 验收通过的任务数 × 单任务价格\`。这把风险从买方转移到卖方，倒逼供应商优化 token 效率。

对内部团队，同样适用：部门预算的核销，应按"验收通过的任务当量"折算，而不是按"消耗的 token 数"核销。

具体做法：

1\. 任务登记。每个任务在发起时登记类型、预期交付物、验收标准。这一步的成本必须极低（一个表单、一次点击），否则会被绕过。

2\. 自动验收优先。能用程序判断的绝不让人判断：测试是否通过、格式是否符合 schema、数字是否与源文档一致、引用是否可溯源。

3\. 人工抽检兜底。按任务类型设定抽检比例（低风险 5%，高风险 100%）。

4\. 争议仲裁。设立一个轻量仲裁机制，处理"AI 认为完成、人认为不合格"的争议。仲裁记录本身是最有价值的评测数据。

需要警惕：验收门本身会成为博弈对象。 如果验收标准是"测试通过"，就会出现"改测试而不是改代码"；如果是"格式合规"，就会出现"套模板、内容空洞"。所以验收门必须包含至少一项"不可自我满足"的指标——比如下游使用率、客户采纳率、三个月后的返修率。

## 5.4 熔断：四级响应，而不是一刀切

熔断机制的设计目标不是"省钱"，而是"防止单点失控"。建议四级：

| 级别  | 触发条件 | 动作  | 恢复条件 |
| --- | --- | --- | --- |
| 一级（提示） | 额度使用达 70% | 通知责任人，显示剩余任务容量 | 自动  |
| 二级（限流） | 达 90% | 非关键任务降档到小模型，关键任务不受影响 | 额度补充或月末重置 |
| 三级（降档） | 达 100% | 全部任务降档，高推理任务转人工 | 追加预算审批 |
| 四级（停止） | 出现异常消耗（单任务超 τ\_max 的 3 倍） | 立即阻断该会话，保留轨迹待查 | 安全团队复核 |

第四级最容易被忽略，但它是唯一能防住"失控 Agent"的机制。一个陷入循环的智能体可能在几小时内烧掉一个部门的月度预算，而传统的"月度告警"根本来不及反应。

降档必须评估质量影响，尤其是安全影响。 见 9.4 节。

## 5.5 反 Goodhart：让指标无法被单独讨好

Goodhart 定律：当一个指标成为目标，它就不再是好指标。

对抗方法不是"更复杂的指标"，而是"成对指标 + 随机性 + 滞后指标"。三条设计原则：

第一，效率指标必须与质量指标成对出现。 单独考核"单任务成本"，必然导致降档降质；单独考核"验收通过率"，必然导致只做简单任务。必须成对：\`TCT ↓ 且 CPTA ↓ 且 返修率 ≤ 基线\`。

第二，保留随机抽检，且抽检比例不公开。 完全自动验收的系统会被针对性优化；完全人工验收的系统无法规模化。混合 + 随机，是唯一可行的平衡。

第三，引入滞后指标。 当期指标都可以被操纵，但"三个月后的返修率""六个月后的客户留存"很难。把滞后指标纳入考核，权重不低于 30%。

一个实用的检验方法：任何一套指标，如果一线员工能在不改变实际工作质量的前提下把它做漂亮，这套指标就失败了。 上线前让一线员工"攻击"一遍自己的指标，是最有效的设计评审。

## 六、技术实现：一条可审计的度量流水线

## 6.1 五段式架构

度量体系不是一张报表，是一条流水线。五个环节，缺一不可。

第一段：采集。 在模型网关层采集，而不是在应用层。应用层采集的问题是"每个应用各记各的账"，口径不一、遗漏多、易篡改。网关层是唯一能拿到完整调用链的位置：请求、响应、token 数、缓存命中、模型版本、耗时、错误码、调用方身份。

第二段：归一。 把不同厂商的 token 折算成 nToken，把不同计价口径（缓存写、批量折扣、峰谷价）折算成标准单价。这一步的产出是"可比"。

第三段：归因。 把一次调用挂到"任务—项目—客户—成本中心"四维上。这是全流程最难的一步，见 6.2。

第四段：定价。 按 5.2 的模式计算内部价格，生成部门账单、项目账单、客户账单。

第五段：结算与反哺。 输出三张表，同时把"哪类任务超预算、哪类任务 TER 低"回流到路由策略和提示词优化。

## 6.2 三个归因难点

难点一：共享缓存。 多个任务共用同一段系统提示或知识前缀，缓存命中带来的成本节约如何分摊？简单按调用次数均分不公平（大任务受益更多）。建议按"如果没有缓存，该任务本应消耗的 token 数"比例分摊，即用"反事实成本"分摊。

难点二：重试链。 一次失败的重试，成本应该记给原任务，还是记给"损耗"科目？建议记给损耗，但同时保留原任务 ID 的关联。这样既能在损益表上看到真实损耗，又能在任务维度追溯"这个任务总共花了多少"。

难点三：多租户与共享 Agent。 一个 Agent 同时服务多个客户时，单次调用的 token 消耗无法直接拆分。可行的方法是"按输出归属拆分"：如果输出中 60% 的内容服务于客户 A，则 60% 成本归 A。这需要输出级的结构化标记，实现成本较高，通常只在客单价足够高的场景才值得做。

## 6.3 最小数据模型

不需要大数据平台，一张宽表就能起步。

| 字段  | 类型  | 说明  |
| --- | --- | --- |
| trace_id | string | 全链路唯一标识 |
| task_id | string | 任务标识，允许为空（无任务上下文的调用） |
| task_type | enum | 任务类型，用于匹配 τ\* |
| tenant / project / cost_center | string | 归因三维 |
| model | string | 模型标识与版本 |
| input_tokens / output_tokens | int | 原始计数 |
| cache_read / cache_write | int | 缓存分项 |
| reasoning_tokens | int | 推理 token（若可获取） |
| unit_price_in / out / cache | decimal | 计价快照 |
| ntoken | decimal | 归一后的标准量 |
| attempt_no | int | 第几次尝试，用于算 RAF |
| accepted | bool | 是否通过验收（异步回填） |
| latency_ms / error_code | int / string | 性能与异常 |

这张表的两个关键字段是 \`task\_id\` 和 \`accepted\`。没有前者，无法归因；没有后者，无法算 CPTA。大多数企业的可观测性体系有前者的一半（有 trace 没有 task），完全没有后者。

## 6.4 与现有体系对接

不需要另建一套。三个对接点：

▪　APM / 可观测性：复用 trace 体系，把 token 作为 span 的一个属性，而不是新建一套追踪。

▪　FinOps / 云成本：把 AI 成本作为云成本的一个新科目，复用标签体系与分摊规则。

▪　安全审计 / SIEM：把"异常 token 消耗"作为一类安全事件接入。这不仅是为了成本，更是为了检测数据外泄（大量 token 输出往往意味着数据被批量导出）。

第三个对接点值得展开：token 消耗曲线是一个被低估的安全信号。 一个账号的日均消耗突然从 5 万涨到 500 万，可能是业务增长，也可能是提示词注入导致的批量数据抽取。把成本异常和安全告警放在同一个平台上关联分析，能发现单看任何一方都发现不了的问题。

## 6.5 自建还是采购

一个务实的判断：

▪　网关与采集层：优先采购或使用开源方案。这部分是标准化的，自建性价比低。

▪　归因与科目层：必须自建。因为这层承载的是企业自己的组织结构和任务分类，没有通用产品能覆盖。

▪　定价与结算层：先用 Excel + 脚本，跑通三个周期再考虑系统化。过早系统化会把错误的口径固化下来。

常见的失败模式是"先买平台，再想口径"。平台会给你 200 个指标，但你不知道自己该看哪 9 个。先用手工方式跑通一个部门、一个季度，再决定买什么。

## 七、组织与治理：谁对 token 负责

## 7.1 一个缺失的角色

云时代有 FinOps 工程师，AI 时代需要一个对应的角色：Token 控制官（Token Control Officer，TCO）。

这个角色不做三件事：不审批每一次调用、不决定用什么模型、不承担业务指标。他做三件事：

▪　定义口径：nToken 怎么折算、任务怎么分类、验收怎么判定。

▪　维护基线：每类任务的 τ\*、TER 基线、CPTA 基线。

▪　主持复盘：月度看"哪类任务偏离基线"，季度看"预算配置是否要调整"。

这个角色应该放在平台团队或财务 BP 团队，而不是业务团队——因为他需要跨部门的视角，且必须有一定独立性，否则会被业务方的"我们任务特殊"说服。

## 7.2 三个节奏

| 节奏  | 内容  | 参与者 | 产出  |
| --- | --- | --- | --- |
| 日   | 异常消耗告警、熔断事件 | 平台值班 | 事件工单 |
| 周   | TER、RAF、CPTA 环比 | TCO + 应用负责人 | 优化清单（不超过 5 条） |
| 月   | 三张表、预算执行率、任务结构变化 | TCO + 财务 + 业务负责人 | 预算调整建议 |
| 季   | 基线重校准、模型选型复盘、路线图修订 | AI 治理委员会 | 决议  |

关键设计：周会产出不超过 5 条优化项。 一份 40 条的优化清单等于没有清单。每周只改 5 件事，一个月能改 20 件，效果远好于一次改 40 件然后全部反弹。

## 7.3 看板：少而准

| 指标  | 健康区间 | 预警阈值 | 触发动作 |
| --- | --- | --- | --- |
| TER（有效利用率） | 10%–20% | < 8% | 检查上下文策略与重试 |
| CTX%（上下文税） | < 45% | \> 60% | 强制上下文压缩与检索改造 |
| RAF（重试放大） | < 1.8 | \> 2.5 | 检查提示词与工具定义 |
| CPTA 环比 | 下降或持平 | 上升 > 10% | 分析返工来源 |
| 预算执行偏差 | ±10% | \> 20% | 调整额度或节奏 |
| 单任务超 τ\_max 比例 | < 2% | \> 5% | 复核预算参数与任务分类 |

六个指标，一张屏。任何需要滚动的看板都不会被看。

## 7.4 文化：从"省 token"到"买结果"

最后一点是软性的，但它决定硬性机制能否存活。

如果组织的潜台词是"用 AI 越省越好"，员工会隐藏使用、转用个人账号（影子 AI），治理彻底失效。这在安全上是重大风险——数据流出企业边界，且完全不可审计。

正确的导向是：鼓励在关键任务上"贵得有理"，惩罚在低价值任务上"便宜但无用"。

具体做法：不公开个人 token 消耗排名（这会直接催生 tokenmaxxing 的反向版本——藏量），只公开任务级的 TVD 分档；对高 TVD 的任务给予更多预算，而不是更少。

## 八、前瞻：五个判断与一个反向判断

图 9　三阶段演进：从可见、可算到可交易

本报告判断

## 8.1 判断一：Token 将完成"科目化"（2026—2027）

今天企业的 AI 支出大多记在"IT 费用"或"研发费用"下，是一个混杂的池子。未来 18 个月内，它会像"云服务费"一样被拆成独立科目，并进入管理报表。

驱动力不是管理觉醒，而是审计要求。当 AI 支出占到运营支出的 5% 以上时，外部审计会问："这笔支出的受益对象是谁？"如果企业答不出来，就会被迫建立科目。

可验证的信号：主流 ERP 与财务系统开始内置"AI 用量"科目模板；四大开始提供 AI 成本归因的鉴证服务。

## 8.2 判断二：出现 Token 影子价格与内部市场（2028）

当多个部门争夺同一笔 AI 预算时，行政分配会让位于价格分配。企业会像管理外汇一样管理 token：设定内部汇率（不同模型的折算率）、建立额度交易机制、对稀缺额度竞价。

这个判断的依据是云的发展史：2015 年前后，企业开始建"云资源内部计费"；2020 年前后，出现"云资源内部市场"（预留实例的跨部门转让）。AI 会走同一条路，但速度快 2–3 倍。

可验证的信号：出现"AI 额度交易"的内部流程或第三方工具；CFO 开始用"token 单位成本"作为对外沟通的指标。

## 8.3 判断三：结果计费取代 token 计费（2029—2030）

这是最大胆的一个判断。

当买方市场形成、模型能力趋同时，定价权会从卖方转向买方。届时主流的企业采购合同将不再按 token 计价，而按"验收通过的任务"或"业务结果"计价（如"每处理一张合规工单 X 元"）。

这不意味着 token 消失，而是它从"计费单位"退化为"生产成本"——就像今天没人按"CPU 周期"买软件，但 CPU 周期仍是软件公司的成本项。

对企业的直接影响：采购策略要从"比单价"转向"比 CPTA 与验收标准"。 一个单价高 3 倍但一次通过率高 20 个百分点的供应商，CPTA 可能低 40%。

## 8.4 判断四：Token 与碳账户合并（2028—2030）

推理有真实的能耗。当监管要求披露 AI 相关碳排放时，"每千 token 碳排放"会成为与成本并列的第二个计量维度。

两个账户合并后，会出现一个新的优化目标：不是"最低成本"，也不是"最低碳"，而是"单位价值下的成本—碳双约束最优"。这会改变模型路由策略——某些场景下，本地小模型虽然单位成本略高，但碳排更低、数据不出域，综合更优。

## 8.5 判断五："Token 效率审计"成为合规项（2030 前后）

当 AI 支出足够大、且出现过多起"AI 项目烂尾"事件后，监管或行业自律组织会要求企业对 AI 投入产出做第三方审计。

审计内容不会是"你花了多少钱"，而是三件事：任务定义是否清晰、验收标准是否可复核、成本归因是否可追溯。 这三件事恰好对应本报告的三张表。

对安全行业而言，这是一个明确的产品机会：把"AI 成本与效能审计"作为 AI 治理平台的一个模块，与现有的 AI-SCAN、模型评测、审计回源能力结合。

## 8.6 反向判断：什么情况下这套体系会失效

必须诚实。以下四种情况下，TVE 体系不仅无效，还会产生负作用：

第一，任务无法被清晰定义时。 探索性研究、创意生成、开放式咨询——这些工作的"完成"没有客观标准。强行定义任务当量，会产生"为了可计量而做低价值任务"的扭曲。

第二，模型能力发生代际跃迁时。 如果出现一个模型，简单任务和复杂任务都能一次做对，那么 τ\* 的差异会消失，整套预算分层失去意义。这在 3–5 年内是可能的。

第三，组织规模太小时。 50 人以下的团队，月度 AI 支出可能不到 1 万元，建立完整核算体系的成本高于收益。此时"看总账 + 抽查"就够了。

第四，当计量的目的不是改善而是考核时。 如果 TVE 被直接用于绩效考核、与薪酬挂钩，它会立刻退化为一个被博弈的数字。度量用于改进，还是用于评判，决定了它是工具还是武器。

## 九、风险与反模式

## 9.1 反模式一：tokenmaxxing

现象：把 token 消耗量当作"AI 采用度"的代理指标，公开排名、内部竞赛。

后果：员工故意使用更贵的模型、更长的提示、更多的重试，以显示"深度使用"。有投资人用了一个精准的比喻：这就像靠"把所有灯都打开"来衡量生产力。

识别信号：token 总量上升，但验收通过任务数不变；平均单任务 token 上升，但 CPTA 不变或恶化。

## 9.2 反模式二：度量暴政

现象：指标层层加码，一线为了达标而扭曲行为。

典型表现：只做容易验收的任务；把复杂任务拆成多个小任务刷数量；在验收前手动修改产出以"通过"。

对策：5.5 节的成对指标 + 随机抽检 + 滞后指标。此外，必须保留一条"例外通道"：允许一线申请"不计入考核的高价值探索任务"。没有例外通道的系统，一定会被绕过。

## 9.3 反模式三：归因谬误

现象：把成本归到错误的维度，导致错误决策。

最常见的一种：把所有 AI 成本按人头平摊到部门。结果是"用得少的部门被罚，用得多的部门被补贴"，完全反向激励。

第二种：把共享基础设施成本（网关、评测、知识库）全部计入"平台费用"，业务方看不到，于是无限索取。

第三种：把重试成本计入原任务，导致"越是难任务越显得贵"，最终没人愿意接难任务。

## 9.4 安全侧效应：降档的隐性代价

这一条与本报告的其他部分不同，它关乎风险而非效率，但在 AI 安全语境下必须单列。

当预算压力导致模型降档（从强模型切到小模型）时，被削弱的往往不只是"回答质量"，还有安全能力：

▪　对提示词注入的抵抗力下降。小模型更难区分"指令"与"数据"，更容易被文档内容劫持。

▪　对敏感信息的识别能力下降。DLP 类判断依赖模型的语义理解，降档后漏判率上升。

▪　对工具调用的边界控制变弱。Agent 场景下，模型对"该不该调用这个工具"的判断直接决定越权风险。

因此，降档策略必须做安全回归测试，且安全相关任务不得纳入降档范围。 一个可操作的规则：把任务分为"可降档""不可降档"两类，后者包括所有涉及数据出域、权限变更、对外发布的场景。

这条规则的本质是：成本优化的边界，是安全基线。 越过这条线的"降本"，是把确定性成本换成了期望损失——而期望损失在财务报表上要等到事件发生才显现。

## 9.5 合规与留痕

三个必须留的东西：

▪　计价快照：每次调用时的单价、折扣、汇率（nToken 折算率）。否则三个月后无法解释账单。

▪　验收记录：谁在什么时候、依据什么标准判定通过。这是争议仲裁的唯一依据。

▪　模型版本：同一任务在不同模型版本下的表现差异，是"质量波动"归因的关键。

这三样东西的保存期限，建议与财务凭证一致（通常 10 年）。

## 十、落地路线图

## 10.1 前 30 天：让它可见

目标：能回答"钱花在哪、谁花的、花在什么任务上"。

▪　在网关层接入 token 遥测，落一张宽表（6.3 节）。

▪　选定 3 个高频任务类型，定义验收标准，开始回填 \`accepted\` 字段。

▪　出一张日报：总消耗、Top 10 消耗任务、异常告警。

▪　不要做：不要建指标体系，不要定预算，不要买平台。

验收标准：能手工算出一个部门的 CPTA，误差在 ±15% 以内。

## 10.2 前 90 天：让它可算

目标：能回答"这类任务该花多少、现在浪费在哪"。

▪　完成 nToken 折算（取 20 份真实文档做分词比对）。

▪　对 3 个任务类型做预算校准（5 个档位 × 3 次重复），得出 τ\*。

▪　上线 TER、RAF、CTX% 三个指标，建立基线。

▪　选一个部门试点预算制，跑一个完整月度周期。

验收标准：试点部门的 TER 提升 3 个百分点以上，且 CPTA 不上升。

## 10.3 前 180 天：让它可管

目标：能回答"预算该怎么分、要不要换供应商"。

▪　扩展到全部任务类型，建立 TVD 分档。

▪　上线内部转移定价（成本加成法起步）。

▪　建立月度三张表，进入管理报表。

▪　用 CPTA 做一次模型选型复盘，验证"贵模型是否真的更贵"。

验收标准：预算配置调整有数据依据；至少一次因 CPTA 而非单价更换了供应商或模型。

## 结语

这份报告试图回答一个问题：当 AI 的单价趋近于零，成本管理还有意义吗？

答案是：意义不在"省钱"，在"换算"。

当 token 便宜到可以忽略时，企业面临的将不是"花不起"，而是"算不清"——算不清哪个团队真的产出了价值，算不清哪个供应商真的更划算，算不清一次架构改造到底该投多少推理预算。价格信号消失之后，唯一能指导决策的，是价值信号。

Token 价值工程要建的，就是这个价值信号。它的核心不是那九个指标、三张表、四级熔断，而是一个姿态：拒绝把"投入"当成"产出"，拒绝把"便宜"当成"值得"，拒绝把"能量化"当成"已理解"。

三年前，我们把云资源管成了财务报表。今天，我们需要把认知劳动管成生产函数。

## 附录 C　一页纸总结

如果只能记住五句话：

1\. token 是产能指标，不是产出指标。 单独看它，一定得出错误结论。

2\. token 与产出的关系是倒 U 形。 存在一个最优点，超过它会自伤；预算的形态应该是区间，不是上限。

3\. 账单的 62% 花在"让模型重新想起"，只有约 4% 变成用户读到的答案。 真正的成本中心是上下文，不是模型选型。

4\. 可比单位是"通过验收的任务"。 只有把计量锚定在交付物上，才能跨部门、跨厂商、跨年度比较。

5\. 度量用于改进，还是用于评判，决定它是工具还是武器。 一旦直接挂钩绩效，数据必然失真。

三张表、九个指标、四级熔断，都是这五句话的工程化。反过来，如果不接受这五句话，那些工具只会让错误的判断显得更精确。
