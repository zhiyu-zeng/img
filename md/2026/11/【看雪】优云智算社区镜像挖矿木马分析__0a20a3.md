## 一、事件摘要

今天早打开我的租赁GPU上部署的MiniMax H3（社区镜像） ComfyUI 启动失败后查看日志寻找蛛丝马迹有了这篇文章。根因是恶意自定义节点 `zzkit` 在导入阶段冻结了 aiohttp 路由表，导致框架无法注册静态路由而退出。

排查该故障时发现主机已被入侵，至少两名攻击者同时在机器上运作：

-   三条挖矿线，对应三个不同矿池、三个不同钱包；
    
-   一个 ComfyUI 进程内 HTTP 后门（ `/zzxe` 、 `/zzsh` 、 `/zzp` ）；
    
-   三把未授权 SSH 公钥；
    
-   两个互相 `pkill` 的看护进程；
    
-   取证期间（03:46-03:52）攻击者仍在活动，现场完成了新一轮部署：新增 `argmask` 预加载库、迁移到 `/var/.cache<随机>` 目录、启动自称 `FreeForGemPear 1.6.3` 的矿工并已提交有效 share。
    

关键结论：入侵不是 ComfyUI 的问题，也不是镜像文件被植入。恶意文件全部产生在容器启动后的运行期，最早一条为 2026-11-17 09:19 UTC（开机后 20 分钟）。

### 1.1 结论速览

三条异常特征，按发现概率排序：

1.  `/proc/<pid>/environ` 读出来是一串 `0x00` ， `cmdline` 末尾带一大片空格；
    
2.  进程持有 `/dev/nvidia*` 句柄，但进程名对不上任何已知框架；
    
3.  `/tmp` 、 `/dev/shm` 、 `/var/.cache*` 下有超过 1MB 的可执行文件，且 ELF 节头数量远少于正常值。
    

三条检测命令：

```bash
# 1) environ 全零的进程for p in /proc/[0-9]*; do [ -s $p/environ ] && [ "$(tr -d '\0' < $p/environ | wc -c)" = 0 ] && echo $p; done# 2) 持有 nvidia 句柄的进程及其命令行for p in /proc/[0-9]*; do ls -l $p/fd 2>/dev/null | grep -q nvidia0 && echo "$p $(tr -d '\0' < $p/cmdline)"; done# 3) 隐藏目录里的可执行文件find /tmp /dev/shm /var -maxdepth 3 -type f -size +1M -perm -u+x 2>/dev/null
```

六项清除动作：杀掉矿工与看护循环、删除隐藏目录、清空 `authorized_keys` 、还原 `/etc/hosts` 、 移除 `custom_nodes` 下的恶意节点、重启业务进程。

## 六、内存取证

### 6.1 为什么读内存而不是脱壳执行

样本的加壳目标是隐藏字符串、符号与导入表。这类壳对静态分析有效，对运行中的进程无效——明文必然以解密形态存在于内存。样本从 09:19 起已运行 18 小时，直接读取即可，无需承担再次回连与算力消耗的风险。

### 11.3 关于三把公钥的正确读法

公钥数量不能用来数人头。三把钥匙里只有两条能追到写入者：

| 公钥  | 写入者 | 证据  |
| --- | --- | --- |
| root@vm-c8353138 | `custom_nodes/zzboot/__init__.py` 里的 rw11.sh | 脚本第 15-20 行直接把该钥追加进 authorized_keys |
| tunnel@g2 | `/tmp/.pkx.sh` | 脚本用 `grep -qF "njNpI2YoT/fAUep+D4Cm"` 判重后追加 |
| zzpod | 未观测到 | 无写入脚本留痕，仅与 zz 前缀工具集同名 |

所以公钥只能推出"至少存在两套投递脚本"，推不出人数。单个操作者放多把钥匙是常规做法，目的有四层：

1.  冗余。双方都在删对方的钥匙——A 的清理循环每 3 秒执行 `rm -f /root/.ssh/tk` ——多留一把就多一条后路，一把被清还有备份。
    
2.  分渠道。 `tunnel@g2` 的命名本身就指向反向隧道，而 `root@vm-c8353138` 是 `ssh-keygen` 的默认主机名格式，通常用于交互登录。两者在工具链上分属不同用途。
    
3.  分工具集。每套 kit 自带一把钥，哪套上线成功、哪套被清理可以分开统计，吊销时互不影响。
    
4.  降关联。不同注释、不同生成机器，避免从 authorized_keys 一眼看出属于同一批作业。
    

判定"两名攻击者"的依据在行为层，不在钥匙层，三点：

-   两个互斥的看护循环：A 每 3 秒 `pkill` 掉 `/tmp/.`、 `/dev/shm/.` 下的进程并删 `/root/.ssh/tk` ；B 反向杀掉所有 `while true; do for p in` 形态的脚本。任何单个操作者都不需要自己杀自己。
    
-   三套互不重叠的矿池与钱包：herominers、pearlhash/kryptex、192.255.247.182:80，抽水比例与 worker 命名规则都不同。
    
-   A 的清理规则明确拉黑三个 IP，其中之一 192.255.247.182 正是 B 的矿池地址与 SSH 来源。
    

这三条属于行为证据与资产证据，权重高于"文件有几把钥匙"。

### 13.1 进程侧

```bash
# 1) cmdline 尾部大量填充空格
for p in /proc/[0-9]*; do
  c=$(tr '\0' ' ' < $p/cmdline); n=${#c}
  [ $n -gt 60 ] && [ "$(echo "$c" | tr -d ' ')" != "" ] && \
    [ $((n - $(echo "$c" | sed 's/ *$//' | wc -c) + 1)) -gt 20 ] && echo "masked: $p"
done

# 2) environ 全零
for p in /proc/[0-9]*; do
  [ -s $p/environ ] && [ "$(tr -d '\0' < $p/environ | wc -c)" = "0" ] && echo "env-zero: $p"
done

# 3) exe 指向 /tmp 或 /var/.cache*，但进程名是系统进程名
for p in /proc/[0-9]*; do
  e=$(readlink $p/exe 2>/dev/null)
  case "$e" in /tmp/*|/var/.cache*) echo "$p $e";; esac
done

# 4) 持有 nvidia 句柄但不是已知框架
for p in /proc/[0-9]*; do
  ls -l $p/fd 2>/dev/null | grep -q nvidia0 && echo "$p $(tr -d '\0' < $p/cmdline)"
done
```

### 16.4 一点观察

这台机器能被发现，是因为恶意节点为了独占后门路由冻结了框架的路由表，把宿主程序搞挂了。如果 `zzkit` 只改 `_frozen` 而不调用 `freeze()` ，ComfyUI 会正常运行，三条矿工线大概会安静挖到租期结束。

反过来，第二轮部署暴露了对手的作业方式：发现被查之后，换目录、换名、加 `LD_PRELOAD` 、加 30 秒自愈，仍然使用同一个 IP 与同一套钱包前缀。这种"改外壳不改基建"的做法，配合矿池地址与钱包地址，比进程名和文件路径可靠得多。
