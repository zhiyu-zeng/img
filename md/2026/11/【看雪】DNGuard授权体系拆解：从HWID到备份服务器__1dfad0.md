代码保护解决的是"别人看不看得懂你的代码"，授权管理解决的是"别人能不能用你的软件"。这两件事经常被混为一谈：花大力气加了壳，授权却只是一句 `if (expireDate > DateTime.Now)` ——dnSpy 一开，把判断改掉，壳还在，钱已经收不到了。

DNGuard HVM 在加密之外，其实提供了一整套授权管理能力。把它的 Change Log 按"授权"这一条线重新排列，会发现这不是几个零散功能，而是一条从设备识别、序列号发放、试用期控制到服务器容灾的完整链路。本文就把这条链路拆开讲。

## 一、先搞懂挂载点：授权校验发生在业务代码之前

官网对 Licensing Management Support 的描述里有一句非常关键的话：DNGuard HVM 提供一个 **预定义的安全回调函数**，允许把自定义授权代码集成进被保护的代码；这个函数会在 **任何应用代码执行之前** 被调用；校验失败时，代码依然处于受保护状态，应用代码根本无法执行。

这句话决定了授权体系的强度：

-   **传统做法**：在 `Main` 或某个初始化方法里判断授权。判断逻辑本身是 IL，反编译后直接 patch 一个跳转就能绕过。
-   **DNGuard 做法**：校验挂在保护层的回调上，先于业务代码执行；即使失败，代码也不解密、不落地 IL。破解者要绕过，面对的是保护引擎本身，而不是一行可改的 if。

再叠加 HVM 的内存保护（IL 转为 HVM 伪代码，运行时以伪代码交给 JIT，内存中不出现完整 IL），内存 dump 也拿不到可重放的原始程序集。

**结论：授权逻辑要放在"代码执行前"，而不是"代码执行中"。** 这是选型时最该先问的一句话。

## 二、SDK 的两组积木：变量读取与操作写入

官网只说"安全回调 + 自定义授权代码"，真正把能力落地的是 License SDK。从 Change Log 能还原出它的两组积木： **变量（Variable）读取** 和 **操作（Operation）写入**。

| 能力  | 类型  | 引入版本 | 解决什么问题 |
| --- | --- | --- | --- |
| `[DNGTrialDate]` | Trial SDK 变量 | 4.9.1（2024-12-08） | 读取试用日期，做试用期控制 |
| `[LicenseValidThru]` | License SDK 变量 | 4.9.1 | 读取授权有效期截止日 |
| `[LicenseHWID]` | License SDK 变量 | 4.9.5（2026-01-31） | 读取设备硬件标识，做设备绑定 |
| `[LicenseSN]` | License SDK 变量 | 4.9.5 | 读取序列号 |
| `[SaveLicenseSN]` | License SDK 操作 | 4.9.5 | 保存序列号，免得用户每次重新输入 |

（来源：DNGuard 官方 Change Log。具体 API 签名与调用方式以随附 SDK 文档、WindowsApplication1 示例工程为准——4.9.5 同步更新了该示例。）

这组能力其实回答了三个问题：

1.  **知道"谁在用"**： `LicenseHWID` 把授权和设备绑起来， `LicenseSN` 标识授权本身。
2.  **知道"用到什么时候"**： `LicenseValidThru` / `DNGTrialDate` 让有效期和试用期不再是自己手搓的字符串比较。
3.  **知道"怎么留住授权"**： `SaveLicenseSN` 把序列号落盘，注册一次，后续启动自动校验。

顺带一提，4.9.1 同时引入了 `[SP]` 路径分隔符支持和 OutputPage 拆分——这些看起来是打包流程的改动，实际上也在为授权文件的存放与输出让路。

## 三、按"授权"重排 Change Log，看到的是一条演进线

| 版本  | 时间  | 授权相关变化 |
| --- | --- | --- |
| 4.1.0 | 2022-06-30 | 新增命令行生成序列号功能 |
| 4.3.1 | 2023-05-19 | 新增备份授权服务器 |
| 4.4.0 | 2023-05-22 | 新增备份授权服务器；改进 License Management 的 HWID 生成 |
| 4.7.1 | 2024-01-14 | 授权服务器更新 |
| 4.9.1 | 2024-12-08 | 新增 `[DNGTrialDate]` 、 `[LicenseValidThru]` |
| 4.9.2 | 2025-01-12 | 新增命令行参数 `--show-register-dlg` ，可在用户端重新打开注册对话框 |
| 4.9.5 | 2026-01-31 | 新增 `[LicenseHWID]` 、 `[LicenseSN]` 、 `[SaveLicenseSN]` |
| 4.9.7 | 2026-09-15 | 修复 uKey 授权问题 |
| 4.9.7.1 | 2026-10-31 | 紧急安全更新（过渡版本） |

这条线的方向很清楚： **从"能授权"走向"授权可控、可恢复、可运维"。**

早期解决的是"能不能发序列号"；中期补上 HWID 生成和备份服务器，解决"授权服务挂了怎么办"；近两年则把设备、序列号、有效期、试用期这些字段直接做成 SDK 变量，让开发者在自己的授权代码里随手可用。4.9.7 修 uKey 授权问题，说明硬件介质这条线也仍在维护。

## 四、三个典型落地场景

### 场景 1：HWID 绑定 + 序列号注册

最常见的商业软件模式。流程大致是：

1.  首次启动，回调里读取 `[LicenseHWID]` ；
2.  用户凭 HWID 获取授权（自助下单或人工发放）；
3.  输入序列号，通过 `[SaveLicenseSN]` 落盘；
4.  后续启动读取 `[LicenseSN]` 与 `[LicenseValidThru]` 完成校验；
5.  换机或重装时，用 `--show-register-dlg` （4.9.2 引入）在用户端重新打开注册对话框。

两个容易被忽略的运营细节： **HWID 绑定要留"换机/重装"的出口**，否则客服会被折腾死； **授权服务器要配备份** （4.3.1 / 4.4.0 已支持），避免单点故障影响已授权用户。

### 场景 2：试用期控制

用 `[DNGTrialDate]` 记录试用起点， `[LicenseValidThru]` 判断授权是否到期。宣传"免费试用 N 天"时，不必再自己维护一套注册表或配置文件。

需要注意的是，本地时钟可以被修改。如果业务对时间敏感，建议结合授权服务器做校验——官方从 4.3.1 起就提供备份授权服务器，并在 4.4.0、4.7.1 持续维护，这个能力不该被当作可选项。

### 场景 3：uKey 授权 + 服务器容灾

4.9.7 修复了 uKey 授权问题，说明 uKey 是官方支持的授权载体之一。对离线部署、内网环境，或者对授权介质有强要求的客户，uKey 加备份授权服务器是更稳的组合。如果正在使用 uKey，鉴于 4.9.7.1 被标记为"紧急安全更新 / 过渡版本"，建议把升级优先级调高。

## 五、几个容易踩的坑

1.  **别把加壳当授权。** 壳防逆向，授权防"没付费也能用"，两条线都要做。
2.  **升级 SDK 变量要回归测试。** 4.9.1 和 4.9.5 两次新增变量/操作，升级后注册、续费、过期、换机四条流程都要跑一遍。
3.  **序列号落盘位置要先想清楚。** `[SaveLicenseSN]` 写在哪、权限如何、重装系统后是否保留，直接影响客服成本。
4.  **授权服务器别只部署一台。** 备份服务器被官方反复维护，说明它在实际部署中确实重要。
5.  **试用期别只依赖本地时钟。** 关键时刻让服务端参与判断。

## 结语

加密保护的是代码，授权保护的是收入。很多软件不是被破解的，是被"授权逻辑写在业务代码里"这件事本身打败的——判断语句一改，壳就成了摆设。

DNGuard 这套授权体系的价值，不在于多了几个变量，而在于它把校验放到了 **业务代码执行之前的保护层**，并且把设备、序列号、有效期这些字段标准化，让开发者不必从零搭建授权基建。工具选对了，剩下的就是把自己的授权流程设计清楚。
