## 概述

数据库访问控制通常被建模为一道硬性安全边界：应用或租户若以低权限角色连接，就只应能读取或修改明确授予它的模式与表。然而从攻击性安全 (offensive security) 的视角看，SQL 授权约束的只是逻辑对象。这条边界的实际强度，仍然取决于每条被允许的 SQL 语句所能触达的每个 C 与 C++ 子系统的内存安全与逻辑正确性。即便权限被严格收紧的账号，也依然可以驱动查询优化器、有状态的聚合求值器 (aggregate evaluator)、预备语句解析器 (prepared-statement resolver) 与二进制线协议解析器 (wire-protocol parser)。这些路径中任意一处出现内存破坏缺陷，都会让 SQL 权限模型塌缩为以数据库的 OS 服务账号执行任意命令。

Oracle 的 11 月安全更新 修复了 CVE-2026-114819（CVSS 9.9），这是我们在 Oracle AI Database 中报告的一个漏洞。它与 CVE-2026-91609 直接串联，后者是我们在 10 月披露的 Oracle GraphQL 接口中的一处缺陷。两者合起来，使一个只能访问对外暴露的 HTTP 端点的未认证攻击者可以把构造好的文档夹带进数据库，并以数据库的 OS 服务账号身份执行任意命令。

> 图示（database-flow）：Oracle AI Database：预认证阶段。PostgreSQL：连接，临时权限。MySQL：创建临时表。ClickHouse：创建临时表。

每条路径都可导致以数据库服务账号身份执行远程代码，

并拥有对主机、文件、数据、密钥、云与网络的访问。

为了判断这种暴露是否为 Oracle 独有，我们审计了 PostgreSQL 与 MySQL 中最小权限账号仍可触达的原生引擎代码，并在两者中都找到了完整的 RCE 链路。Oracle、MySQL 与 PostgreSQL 合计占据 2026 年 11 月 DB-Engines 排名 前四名中的三席，它们所定义的角色模型支撑着主要的多租户与生产环境。PostgreSQL 位于包括 Amazon RDS、Neon 与 Supabase 在内的托管产品底层，MySQL 则为 GitHub 与 Shopify 等组织的核心生产负载提供支撑。

把我们在 Oracle AI Database、PostgreSQL 与 MySQL 中发现的缺陷，与其他人近期报告的漏洞放在一起看，其底层机制是一致的。限制性的 SQL 授权之下，一片出人意料的宽广原生攻击面依然完好无损，而向无特权角色开放的会话级特性（例如临时模式、临时表与绑定参数）同时充当堆布局整理 (heap grooming)、ASLR 绕过与控制流劫持的可靠构件（在 Oracle 的情形中，这条链路甚至在登录发生之前就已触达存在缺陷的引擎代码）。由于 Oracle AI Database 是闭源的，本文借助我们的 PostgreSQL 与 MySQL 链路，以及在 ClickHouse 中复现的漏洞，逐一说明根因、利用原语 (exploit primitive) 与权限要求。

## PostgreSQL：从默认登录角色到 RCE

### 根因：SORTOP 优化跳过 FINALFUNC

PostgreSQL 允许用户仿照 `SUM` 、 `MAX` 这类内建函数定义自定义聚合函数 (aggregate function)。每个聚合都指定一个 **转移函数 (transition function)** （ `SFUNC` ），负责把到来的行值逐一折叠进一个运行中的状态（ `STYPE` ），并可选地指定一个 **终值函数 (final function)** （ `FINALFUNC` ），负责把最终状态转换为该聚合声明的输出类型。例如，某个聚合可以接受整数，在状态中记录迄今见过的最大值，并在结束时把这个整数转换为 `text` ：给定输入 `3` 、 `8` 与 `5` ，转移状态最终停在 `8` ，终值函数返回 `"8"` 。

如果一个聚合在带索引的列上表现得像 `MIN` 或 `MAX` ，那么经由 `SFUNC` 扫描整张表就是浪费。为了让用户自定义聚合也能走上同一条规划器快速路径，PostgreSQL 在 CREATE AGGREGATE 上支持 `SORTOP` 参数，用于声明该聚合的输出对应此运算符排序下的极值输入。当查询形态符合条件且存在兼容的 B-tree 索引时，规划器会把该聚合改写为一次索引查找，直接取出极值元组 (tuple)。 `SORTOP` 属于纯粹的机会性优化：一旦没有合适的索引，或该查询不符合改写条件，执行就会回退为对输入行运行 `SFUNC` ，随后运行 `FINALFUNC` 。

> 图示（aggregate-paths）：常规路径把 3、8 与 5 作为转移函数的输入，产生整数 8，再由终值函数把它转换为 text。索引捷径从 B-tree 取回整数 8，跳过终值函数，调用方则把该整数的比特位解释为一个 text 指针。

CVE-2026-116331 中的缺陷在于，这条规划器捷径 没有考虑 `FINALFUNC` 会改变结果的返回类型。在上面的整数转 text 示例中，正常执行路径会调用 `FINALFUNC` ，并交给调用方一个 `text` 数据值 (datum)（ `"8"` ）。 `SORTOP` 索引路径完全跳过 `FINALFUNC` ，返回索引中的原始整数 `8` ，而外层表达式求值器仍然期待 `text` 。在 64 位构建上，PostgreSQL 把定宽的 `int8` 值按值直接放在 8 字节的 `Datum` 内传递， `text` 、 `bytea` 这类变长类型则按引用以指针传递。跳过 `FINALFUNC` 会让 PostgreSQL 把索引中的原始整数比特位解释为指向 `text` 的指针，干净地形成一处按值传递 / 按引用传递类型混淆 (type confusion)。

### 利用：在 pg_temp 中构造信息泄露与伪造对象原语

乍看之下，从无特权会话出发把这个规划器缺陷变成可用利用似乎很困难。触发这条快速路径需要一张带索引、并已写入攻击者选定值的表，还需要创建自定义函数与聚合的权限。默认角色（此处指新建、没有任何额外授权的 PostgreSQL 登录角色）对现有应用表没有写权限，在加固过的部署中也无法在 public 中创建对象。

填补这一差距的是 PostgreSQL 的会话级临时模式 (temporary schema)。开箱即用时，默认登录角色在数据库上继承 TEMPORARY 权限。在 pg_temp 内，该角色可以创建临时表、向其中写入任意值、在其上建立 B-tree 索引，并定义辅助函数与自定义聚合，全程无需触碰任何应用模式。下面的设置完全在 pg_temp 内触发该类型混淆（函数体与载荷常量已省略）：

SQL

\-- Every object lives in the role's temporary schema.

CREATE TEMP TABLE t (v int8);

CREATE INDEX ON t (v);

INSERT INTO t VALUES (...); -- attacker-chosen value

CREATE FUNCTION pg_temp.keep_max(int8, int8) RETURNS int8...;

CREATE FUNCTION pg_temp.as_text(int8) RETURNS text...;

CREATE AGGREGATE pg_temp.confused(int8) (

SFUNC = pg_temp.keep_max,

STYPE = int8,

FINALFUNC = pg_temp.as_text, -- declares a text result

SORTOP = '>' -- enables the index shortcut

);

SELECT pg_temp.confused(v) FROM t; -- index path returns int8; caller reads text

由于该角色可以在 64 位 PostgreSQL 上针对任意类型对反复实例化这一模式，单个缺陷就足以提供可靠的多阶段利用所需的每一种原语：

**1.** **堆指针泄露（ `bytea` 被混淆为 `int8` ）：** 对一列 `bytea` （其 `Datum` 持有一个 64 位堆指针）建立索引，并在其上使用一个 `FINALFUNC` 声明为 `int8` 的聚合，索引捷径就会把原始 `bytea` 指针以 64 位整数的形式直接返回给 SQL 客户端。这立刻给出一次 `addrof` 式的泄露，暴露攻击者控制的堆数据。

**2.** **有界内存读取与 ASLR 绕过（ `int8` 被混淆为指针）：** 反转类型错配的方向，会让 PostgreSQL 把攻击者选定的 `int8` 值当作指针解引用，从而在任意地址附近提供有界读取。在泄露的堆缓冲区附近探测，可以发现一个指向 `postgres` 二进制的代码指针，从而击破 PIE/ASLR。再次执行 `bytea` → `int8` 的泄露，即可精确确定最终伪造对象载荷所在的堆地址。

**3.** **经由扩展对象的控制流劫持（ `int8` 被混淆为 `text` ）：** 在最后阶段，攻击者把构造好的载荷字节的 64 位地址存入一个带索引的 `int8` 列，并把输出混淆为 `text` 。PostgreSQL 的变长表示支持内存中的扩展对象 (expanded object)，其头部是一个包含方法表指针（ `eoh_methods` ）的 `ExpandedObjectHeader` 。把伪造的 `text` 数据值传给 `length()` ，会触发一次经由 `eohptr->eoh_methods->get_flat_size(eohptr)` 的间接调用。由于 `eohptr` 与 `eoh_methods` 都位于攻击者控制的内存中，该调用会转入一段简短的指令序列，进而调用 `system()` 。

这条链路说明，可达子系统的广度与初始缺陷本身同样重要。 `TEMPORARY` 访问权限让默认角色得以触达存在缺陷的 `SORTOP` 规划器路径，还为攻击者提供了按需创建的表、B-tree 索引、用于击破 ASLR 的多态 `Datum` 转换，以及 `length()` 这类内建表达式汇聚点 (expression sink)，而全程对应用数据零访问。

## MySQL：越界的位计数器递增

### 根因：预备阶段的大小计算与执行阶段的实际长度

CVE-2026-101786 是 MySQL 窗口化 `BIT_OR` 聚合中的一处越界写 (out-of-bounds write)。与标准 `GROUP BY` 的按位聚合不同，滑动窗口必须在一行离开帧 (frame) 时减去该行的比特位。MySQL 的做法是在会话内存区域 (memory arena) 上维护一个 64 位计数器数组，为每个输入比特分配一个计数器。

当 `SELECT BIT_OR(?) OVER (...)` 这样的预备语句使用一个在预备阶段具体类型尚不明确的参数时，Item_sum_bit::resolve_type() 会假定它是 511 字节的二进制 `VARCHAR` ，并分配 4,088 个计数器（32,704 字节）。然而在执行阶段，客户端可以绑定一个更长的 `BLOB` 值。 `Item_sum_bit::add_bits()` 按实际运行时长度执行循环，没有重新检查 511 字节上限；它唯一的数组边界检查是一条调试用 `assert` ，在发布构建中被编译去除。

上游补丁 在更新计数器之前于运行时拒绝超长值：

CPP

buff_length = s1->length();

if (m_is_window_function &&!m_is_xor &&

buff_length > m_digit_cnt_card / 8) {

my_error(ER_INVALID_BITWISE_AGGREGATE_OPERANDS_SIZE,

MYF(0), func_name());

return true;

}

### 利用：塑造内存区域并微调清理指针

缺少该检查时，绑定一个 512 字节的参数会使最后一个字节索引到第 4,088 至 4,095 号计数器，即越过分配末尾的八个 64 位槽位（64 字节）。该第 512 字节中每一个置位的比特，都会在窗口内每求值一行时给对应的槽位加 `1` 。与一次任意的 64 字节覆写相比，这个缺陷提供的是一处选择性、可重复的 64 位递增原语，其总偏移量等于处理的行数。

普通的会话特性即可把这受限的递增变为在官方 MySQL 26.7.0 镜像上的可靠代码执行：

**1.** **内存区域布局控制：** 为会话设置 `query_alloc_block_size = 65536` ，会把计数器数组放置在某个内部表达式节点（ `Item_ref` ）的正前方，使八个越界槽位之一与它的 `next_free` 清理指针对齐。

**2.** **借助临时表实现精确的指针递增：** 该会话使用 `CREATE TEMPORARY TABLES ON *.*` 权限创建一张临时表，通过递归 CTE 填入 184 行，并在其上运行预备好的窗口查询。处理 184 行会把 `next_free` 前进 184 字节，使它转而指向绑定的参数对象。

**3.** **清理阶段劫持：** 语句结束并清理其表达式列表时，MySQL 会沿着被偏移的 `next_free` 指针进入那 512 字节的参数缓冲区，把攻击者控制的字节当作 C++ 对象处理，并派发一次虚调用。把栈切换至该缓冲区后，一段简短的 ROP 链即可从 GOT 中解析出 `system()` ，以 `mysql` 服务账号执行命令。

受测用户仅持有 `CREATE TEMPORARY TABLES ON *.*` ，对任何现有应用表都没有 `SELECT` 权限。

## ClickHouse：RowBinary 中的长度回绕

### 根因：未加检查的长度相加且缺少大小上限

在 ClickHouse 的 RowBinary 格式中，一个 `String` 值以一个变长整数加上其原始字节的形式发送。随着行陆续到达，字符串反序列化器 把每个字符串追加进一个扁平字节向量，并通过把声明的字符串长度加上向量现有大小来计算新的缓冲区大小：

CPP

UInt64 size = 0;

readVarUInt(size, istr);

if (settings.binary.max_binary_string_size &&

size > settings.binary.max_binary_string_size)

throw Exception(...);

size_t old_chars_size = data.size();

size_t offset = old_chars_size + size;

offsets.push_back(offset);

try {

data.resize(offset);

istr.readStrict(reinterpret_cast<char \*>(&data\[offset - size\]), size);

} catch (...) {

offsets.pop_back();

data.resize_assume_reserved(old_chars_size);

throw;

}

正常情况下， `format_binary_max_string_size` 设置会在前置阶段拒绝荒谬的超大长度。然而在默认配置下，无特权的 HTTP 调用方可以在查询字符串中传入 `format_binary_max_string_size=0` ，关闭该策略检查，从而暴露出未加检查的 `old_chars_size + size` 相加。

如果第一行写入 64 字节（ `old_chars_size == 64` ），第二行声明长度为 `UINT64_MAX` ，则 64 位无符号相加会把 `offset = 64 + UINT64_MAX` 回绕为 `63` ，同时 `offset - size` 回绕回 `64` 。调用 `data.resize(63)` 会把向量的逻辑长度缩短一字节，却不会释放或重新分配其底层堆缓冲区。随后的读取于是从偏移 64 开始写入，把 HTTP 请求体中剩余的每一个字节（在我们的 PoC 中为 6,144 个受控字节）越过缓冲区复制进相邻的堆内存，直至到达流末尾并抛出短读异常 (short-read exception)。等到 `catch` 块恢复向量的元数据时，周边的堆已经被覆写。

### 利用：Memory 表堆布局整理与虚调用劫持

为在 ClickHouse 26.7.5.10 上利用该溢出，我们的 PoC 先创建一张临时的 `Memory` 表并插入构造好的行以整理堆布局，然后借助 `INSERT INTO FUNCTION null('a String') FORMAT RowBinary` 并设置 `format_binary_max_string_size=0` 触发这次回绕写。这次 6,144 字节的溢出把伪造的 vtable 指针与命令字符串植入相邻的 C++ 对象，使后续的一次虚调用重定向至 `system()` ，运行于 `clickhouse` 服务账号之下。仅使用一个被授予 `CREATE TEMPORARY TABLE ON *.*` 的账号，我们的利用就获得了以 `clickhouse` 服务账号运行的交互式 shell。

## 要点：SQL 授权与可触达的引擎代码

纵观 Oracle、PostgreSQL、MySQL 与 ClickHouse，SQL `GRANT` 做到了它被设计要做的事——控制对持久化模式与表的访问，同时几乎不缩减一个会话可以动用多少底层 C 与 C++ 引擎。操作系统的系统调用过滤器能够封隔整个内核子系统；一个被允许执行查询的数据库会话则仍然直接驱动规划器捷径、滑动窗口状态机与二进制线协议反序列化器。

对利用开发同样重要的是，那些从数据访问角度看似乎无害的临时权限（PostgreSQL 中默认授予 `PUBLIC` 的 `TEMPORARY` ，或 MySQL 与 ClickHouse 中的 `CREATE TEMPORARY TABLES` ），为攻击者提供了把细微的内存破坏缺陷转化为代码执行所需的一切，且无需触碰生产表。在 PostgreSQL 中撤销默认的 `TEMPORARY` 权限，或在应用不需要时避免宽泛的 `CREATE TEMPORARY TABLES ON *.*` 授权，会抬高认证后利用的门槛；不过像我们的 Oracle 链路这样的登录前路径会完全绕过 SQL 角色检查。最小权限角色在正常运行下对隔离数据仍然不可或缺，但 `SHOW GRANTS` 的简短输出并不意味着原生攻击面就小。
