首先，我们必须知道与英雄相关的内容被存放在哪里（例如英雄位置），
通过观察dump.cs可以推测应该是被存放在了ActorManager类中，接下来进一步观察，发现它是全局静态单例，
游戏想要引用它里面的各种内容，必然得先知道这个单例存放在哪里了，猜一猜程序如何知道的呢？他一定被存放在了某个全局class图纸中，这里一共就两个class图纸（IActorManager是接口），既然
ActorManager没有，那就进父类图纸看看，然后就找到了s_instance，现在我们只需要找到Singleton<ActorManager>的图纸，就能直接拿到里面存放的ActorManager的指针（注意Singleton是泛型类，他的每一种特定型号都有一个单独的图纸，例如Singleton<A>,Singleton<B>以及我们的Singleton<ActorManager>）

补充要点：诸如Singleton`1中所携带的[`1]代表这是一个泛型类，并且泛型参数数量为1，如果是A`2，则代表泛型参数数量为2

我意识到程序似乎总是喜欢把这个ActorManager的指针存放进某个class图纸里，例如此处存放进了Singleton<ActorManager>的class图纸里。为什么程序要这么做，程序难道能直接找到这个class图纸的内存地址吗？
是的，程序不仅能直接找到这张“图纸”的内存地址，而且在编译链接阶段就已经把去往这张图纸的“路线”写死在代码里了。这是由编译器完成的

额外要点：继承是把图纸的产物合在一起，但不把图纸合在一起，例如 public class A : B, 则是把AB两个图纸生成的实例合在一起（A实例里直接包含了B实例），因此静态字段这种位于图纸的东西，即便A继承了B，也依旧需要我们跑到B的图纸里去找。（这里提醒一下：实例只包含字段，它是不会包含方法的，方法位于class图纸）


现在我们需要找到Singleton<ActorManager>的图纸位置，前面提到过编译器在编译时会把寻找图纸的路径直接写死在程序里，那它具体写到哪里了呢？
此处需要先明确，C++规定：任何非静态成员方法在执行时，必须由调用者通过第一个参数（ARM64 架构下的 `X0` 寄存器）传入 `this` 指针（即 `ActorManager` 实例的位置）
所以我们直接找一个ActorManager的成员方法被调用的地方，调用它的地方在调用之前必然找到了Singleton<ActorManager>的图纸位置（并借此调用内部的Singleton<ActorManager>.Instance 获取了ActorManager实例位置）
我们试图寻找GetActor处的交叉引用，但没有搜到结果，这说明有一个地方存着GetActor的内存地址（代称为 间调处），程序其它地方全部引用的见调出
这属于GOT 函数指针表，应该位于内存的.data段，我们直接在ida搜索GetActor的内存地址字节码即可搜到，然后查看间调处的交叉引用
然后随便进入一个调用它的地方（这里最好找在ida中跳转过去之后往上翻一小段就直接到了调用处的整个函数的开头的地方）
直接查看调用处的伪代码
类似于（不同地方代码会有差异）

```c
v105 = qword_E58D7F8;                 // 1. 加载全局泛型方法上下文指针
v113 = (_QWORD *)off_DFBFFA0(v105);   // 2. 调用泛型单例 GetInstance() 获取实例
off_DC98B80(v113, 0, ...);            // 3. 将实例作为 this 传入 GetActorTotalCount[cite: 7, 8]
```
qword_E58D7F8 是 Singleton<ActorManager>.Instance的泛型方法的小票，Singleton<>的public static T Instance { get; } 属于泛型方法
编译器不会单独为每个特定类型的泛型方法都单独生成一个方法，它只会生成一个模板，该模板会接受一个参数（特定泛型方法小票），内部依据该参数进行运算，不同小票返回的结果不同

补充点:针对泛型类，编译器会为每个泛型类的特定泛型都生成一张图纸，但针对其内的泛型方法却只有一个泛型方法模板，并不会为每个特定类型的泛型方法都单独生成一个方法

off_DFBFFA0则是指向Singleton<>的public static T Instance { get; }，我们直接跳转过去，看看它是如何依据小票计算出对应的特定泛型实例的位置的（Singleton<ActorManager>的位置）

f5伪代码类似于
```c
v1 = *(_QWORD *)(a1 + 32);              // +0x20 : 关联类元数据
v3 = *(_QWORD *)(v1 + 192);             // +0xC0 : Il2CppClass->rgctx_data (运行时泛型上下文表)
v4 = *(_QWORD *)(v3 + 16);              // +0x10 : 取出真正的 Singleton<ActorManager> 图纸 (Il2CppClass*)
v11 = **(_QWORD **)(v4 + 184);          // +0xB8 -> +0x0 : 静态字段表(static_fields) -> s_instance

```
可以清楚的看到，通过小票_QWORD计算出了Singleton<ActorManager>的位置

注意:在 dump.cs 里，静态字段（static）和普通实例字段的计算基准点（Base Address）是完全不同的两套规则
普通非静态字段（如 HeroActors // 0x18）：
基准点是实例对象（Instance）的首地址。
静态字段：
基准点不是“图纸（Il2CppClass）”本身，而是图纸的static_fields（静态字段表指针）区域的首地址（通常此处距离图纸首地址偏移+0xB8）
这也就解释了为什么dump.cs里s_instance偏移为0，但此处伪代码却说s_instance位于图纸（v4）偏移0xB8的位置

额外补充：
泛型定义模板是没有固定内存布局的（具体内存布局取决于它具体被填入了什么类型）
dump.cs解析字段变量偏移时是依据图纸的实例产物的，而泛型模板本身没有实例产物（有实例产物的是特定类型泛型的class图纸，而不是那个最初的未指定特定类型的泛型模板class图纸）
因此dump解析不出泛型模板的字段偏移，如AbstractBaseTinyList<T>中的字段变量的偏移全部都被dump记作0x0了
但是，因为dump解析方法偏移时依据图纸本身，而非图纸的实例化产物，因此泛型模板class图纸虽然无实例化产物，但其内的方法依旧可以被dump正确的解析出偏移（例如AbstractBaseTinyList<T>的方法都被解析出了偏移）

接下来，依据dump.cs（内部已经标注好了ActorManager内部的个字段的偏移）
我们直接可以通过ActorManager的位置偏移出HeroActors的指针的位置（public TinyValueList`1 HeroActors 这里存的是指向TinyValueList<>实例的指针），取出里面的指针，这个指针直接指向TinyValueList<>实例


得到了指向TinyValueList<>实例的指针之后，我们接下来就得确定，人物位置究竟是存放在TinyValueList<>实例的哪里了？
这里再次注意：实例包含自身及所有父类中所包含的字段变量，因此TinyValueList<>实例包含TinyValueList和AbstractBaseTinyList二者中的所有字段变量
然后你会发现TinyValueList的所有固定类型的字段变量都没有包含人物位置
那么唯一可能的地方就是TinyValueList的会变化类型的字段变量了（因为类型会变，所以里面存的东西也会变，如果变为了一个包含人物信息的类型，那么这个字段变量就包含人物信息了）
而TinyValueList只有一个泛型变量（类型不固定），那就是【protected internal T[] Item_Backends】变量
接下来问题来了，这个被HeroActors所指向的特定的TinyValueList<>实例的里面的Item_Backends变量的类型究竟是什么？

注意观察dump.cs里的ActorManager，有一个字段叫做【public static PoolObjHandle`1 EMPTY_ACTOR_LINKER】
中文译名：空ACTOR句柄
从名字不难看出，它指向一个空的ACTOR，那么他的类型肯定就是这个空的ACTOR的类型，因此ACTOR类型为PoolObjHandle，再结合dump.cs里的PoolObjHandle的内容，可以确定该游戏通过对象池句柄（PoolObjHandle）来对Actor进行管理，整个ActorManager在存储和传递Actor时统一采用PoolObjHandle进行托管（这是为了更安全的对Actor进行各种操作）
猜测一下它的作用：1.游戏里有些地方需要查询并返回一个ACTOR实例，例如ActorManager的GetHeroByCfgID()方法，当没有查到任何ACTOR时，要么返回null，但这容易引起空指针异常，因此游戏选择返回一个空的ACTOR
2.游戏里有索敌，这个你记得吧？当你释放索敌时，游戏将索敌目标定义为这个空的ACTOR，以确保你不会索敌场上任何一个真实的ACTOR
你可能会问，那为什么不直接在需要空ACTOR的时候现场创建一个空的ACTOR呢？因为太耗性能，重复引用同一个，就不需要反复重创了，既省内存又节约开销

既然游戏把Actor托管给了PoolObjHandle，那么【protected internal T[] Item_Backends】就应当是对PoolObjHandle进行的包联
故此TinyValueList<>的泛型被确定为是PoolObjHandle<>

我们在dump.cs中直接搜到了这个接口的实现类ActorLinker
这个实现类中包含了大量的与对局中Actor自身可能包含的字段变量相关的字段变量，例如Position、Visible等
由此可见这个实现类的确就是Actor本身的类的类型

现在实例的类型变成了TinyValueList<PoolObjHandle<ActorLinker>>

我们之前就已经拿到过实例的首地址了，也就是HeroActors里面存放的指针
这个实例里包含了一个【protected internal T[] Item_Backends;】（通过继承AbstractBaseTinyList获取的该字段变量）
还记得它里面存放了什么吗？是一对的PoolObjHandle（托管版的ActorLinker）
我们如果想取出里面的托管版ActorLinker，就必须获取到Item_Backends基于TinyValueList<PoolObjHandle<ActorLinker>>实例首地址的偏移量

这里需要注意：泛型定义模板是没有固定内存布局的（具体内存布局取决于它具体被填入了什么类型）
       dump.cs解析字段变量偏移时是依据图纸的实例产物的，而泛型模板本身没有实例产物（有实例产物的是特定类型泛型的class图纸，而不是那个最初的未指定特定类型的泛型模板class图纸）
       因此dump解析不出泛型模板的字段偏移，如AbstractBaseTinyList<T>中的字段变量的偏移全部都被dump记作0x0了
       但是，因为dump解析方法偏移时依据图纸本身，而非图纸的实例化产物，因此泛型模板class图纸虽然无实例化产物，但其内的方法依旧可以被dump正确的解析出偏移（例如AbstractBaseTinyList<T>的方法都被解析出了偏移）
而TinyValueList<>恰巧就是一个泛型模板，因此dump.cs并没有标注出其内Item_Backends的偏移量
因此我们必须得手动解析出当TinyValueList<>的泛型为PoolObjHandle时的实例的内部的Item_Backends基于该实例的首地址的偏移量

要想计算偏移量，我们首先要知道C语言中实例的标准结构长什么样
但是实例的标准长相有很多种，我们具体需要知道哪一种呢？
王者是基于IL2CPP的，因此我们需要知道IL2CPP实例的标准C语言实例结构

此处补充：在Unity IL2CPP游戏中，所有的类(class)和结构体(struct)在编译后都会被翻译为C语言结构体(struct)

在C#中，但凡是用class定义的类（如 class ActorManager 、class TinyValueList等），在底层都继承自Il2CppObject的C结构体（不需要开发者手动写这个继承，它是默认自动继承的，查看dump.cs也可确认这一点，没有任何类手动写了继承Il2CppObject，但对照游戏运行时的具体内存可以确认所有类实际都进行了这种继承。前面我们已经求出了一些类的内存偏移链，你可在游戏中跳转到对应的内存位置进行查看和确认）
那么Il2CppObject长什么样呢？很简单，直接查阅官方文档即可得知，大致长相如下

// 所有 C# class 的最顶层基类头部
struct Il2CppObject {
    Il2CppClass *klass;   // +0x00 (8字节)：指向“类图纸”的指针（存着方法表、静态字段等）
    MonitorData *monitor; // +0x08 (8字节)：多线程同步锁指针
};
这里说明一下两个参数的作用：1.【Il2CppClass *klass】用来标记本实例基于哪个class生成
2.【MonitorData *monitor】是一个多线程同步锁指针，意味着任何继承自该Il2CppObject的类都可以被当做互斥锁来使用，以防止多线程同时执行某一串代码造成各种异常，一旦出现抢锁，IL2CPP就会生成一个MonitorData结构包（包含抢锁的具体情况），并把该包的指针赋值给【MonitorData *monitor】，具体实例如下
lock (someObj)
{
    // 同一时间只允许一个线程进入这里
}


如果你现在直接去王者的对应内存位置（前面我们已经求出了一些类的内存偏移链，你可在游戏中直接跳转过去），就会发现对应区域的内存存储的内容似乎与这个标准模板有所不同
没错，王者对这个Il2CppObject进行了底层优化，那王者如何进行的优化呢？
查看对应内存区域可以发现，原来是删掉了【MonitorData *monitor】，那王者为什么要删掉【MonitorData *monitor】呢？
原因很简单，因为游戏的核心逻辑大多是单线程，极少直接将对象作为互斥锁使用，既如此，若每个对象都有这么一个互斥锁的功能，但实际却压根用不上，岂不是很浪费性能，故此，王者将它删掉了

故此，因为Item_Backends到TinyValueList<PoolObjHandle<ActorLinker>>实例首地址之间只间隔了一个【Il2CppClass *klass】，而【Il2CppClass *klass】的大小是8字节
因此Item_Backends基于TinyValueList<PoolObjHandle<ActorLinker>>实例首地址的偏移量应当是8字节

Item_Backends数组中存放的是所有Actor的托管版本身（即PoolObjHandle<ActorLinker>实例本身）
你可能会疑惑于为什么这里存放的是Actor的托管版本身，而不是一个指向Actor的托管版本身的指针？
这是因为PoolObjHandle是struct（结构体），是值类型，因此它的实例属于值类型实例，故而存放它的地方存放的是它本身
这一点与class（类）有所不同，class是引用类型，因此它的实例属于引用类型实例，故而存放它的地方存放的是一个指向它的指针

我们此处要提取出Item_Backends数组中存放的所有的Actor托管版本身，要想取出Item_Backends数组中存放的所有的Actor托管版本身，我们首先得先知道C语言中数组的底层结构长什么样，它内部到底是怎么存放数据的？
原生的C语言数组底层结构非常简单，里面只存放了元素（注意：如果是引用类型，存放的就是指针；如果是值类型，存放的就是值本身，例如前面提到的struct PoolObjHandle的PoolObjHandle<ActorLinker>值类型实例本身），并且一个连一个，中间没有任何间隔
但是IL2CPP中所使用的数组，实际上是一个引用类型实例（【class Il2CppArray】实例），并且该实例内部并没有存储数组的元素，元素是位于该实例内存区域的紧后边的，并且正如前文所提到的在IL2CPP中所有用class定义的类都会继承Il2CppObject一样，此处的Il2CppArray也同样会继承Il2CppObject（不过因为王者修改了Il2CppObject，所以此处Il2CppArray实际继承的是王者修改后的Il2CppObject）
该Il2CppArray的大致代码如下（采用C++，注意在C++中并没有引用类型和值类型的区别，任何内容都可以被当做‘值’直接存储和复制，也可以通过指针（*）或引用（&）被当做‘引用’来操作。不过在C#中是有明确的值类型和引用类型的划分的）
typedef struct Il2CppArray : public Il2CppObject
{
    /* bounds is NULL for szarrays (此处是数组的维度信息。若为一维零基数组则此字段恒为 NULL) */
    Il2CppArrayBounds *bounds;    // +0x10 (8字节)
    /* total number of elements of the array (数组分配的总容量，也就是元素数量) */
    il2cpp_array_size_t max_length; // +0x18 (8字节)
} Il2CppArray;
正如前面所提到的Il2CppArray内部并没有任何字段变量用于存储元素，真正的元素位置该Il2CppArray实例的内存结束位置的紧后边
举个例子，假设A元素大小16字节，你要创建一个能装下10个A元素的数组，IL2CPP并不是只申请32字节(sizeof(Il2CppArray)),而是直接申请一整块连续的192字节大小的内存区域(32字节+10 * 16=192字节)，该内存区域前部分是Il2CppArray，其余部分直接平铺那10个A元素

基于此我们可以初步推断出Item_Backends数组的第一个元素基于Item_Backends内存的首地址偏移为24字节（【Il2CppClass *klass】+【Il2CppArrayBounds *bounds】+【il2cpp_array_size_t max_length】）
我们可以到游戏对应内存区域验证一下（按照前面的教程，一步一步推，你就知道应该跳到游戏的哪个内存地址了）
然后我们就发现，我们的推测和游戏的实际内存内容对不上，我们查了8字节（Item_Backends数组的第一个元素基于Item_Backends内存的首地址偏移为32字节）

那么Raw4究竟是什么呢？
还记得PoolObjHandle里面的内容吗？它包含一个_handleSeq字段变量，依据变量名，我们不难推断出它是用于记录它所属的PoolObjHandle实例被分配的句柄编号
再回看前面四个Elem（即四个PoolObjHandle）的Seq，你会发现它们的大小全都位于Raw4的值（0x329F）附近，由此可以推断出Raw4存储的就是数组被分配的句柄编号，因为编号是在对象被创建时分配的，而数组和其内PoolObjHandle实例被创建的时间非常接近，故而它们的句柄编号也非常接近
而这个句柄编号刚好8字节，这就是我们前面缺失的那8字节

如果你忘记了，可以重新查看前文，或者跟着我一起往下走，后面会重新一步一步带着你做的

故此，我们最终确认Item_Backends数组的第一个元素基于Item_Backends内存的首地址偏移为32字节（【Il2CppClass *klass】+【Il2CppArrayBounds *bounds】+【il2cpp_array_size_t max_length】+【8字节大小的当前Il2CppArray被分配的句柄编号】）


接下来我们需要依次取出Il2CppArray后边存放的所有元素，要想正确依次取出里面的所有元素，我们需要知道每个元素的大小，也就是PoolObjHandle实例的大小
PoolObjHandle实例内部包含两个字段变量：1.【private UInt32 _handleSeq】 2.【private T _handleObj】
首先_handleSeq的类型为UInt32，此类型固定为4字节，然后是_handleObj，当它的泛型被指定为ActorLinker时，因为ActorLinker是引用数据类型，故此_handleObj存放的就是指针，固定为8字节
故此PoolObjHandle实例的实际占用大小为12字节，但是注意：数据在内存中虽然是以1字节为单位进行存储，但是ARM64处理器在读取内存时是以8字节为单位进行读取的，若此处真的以12字节的方式存入内存中，那么读取和存储就对不上了（读取出来的8KB中有4KB可能存储的是别项内容）
故此，C/C++在编译时会自动进行内存对齐，填入4字节的空白，让PoolObjHandle实例占用16字节大小（刚好是8的倍数）

如果此时你去到游戏对应的内存区域，就会发现PoolObjHandle实例的确占用了16字节大小，但里面的内容结构似乎和dump.cs不太一样
这是C#在编译时对结构体（注意PoolObjHandle不是class实例，而是struct实例）内部字段变量进行了自动重新排序
在C#中普通的struct内部的字段变量默认采用LayoutKind.Auto（自动排序布局），而非强制按开发者编写的代码中的原顺序进行排序，dump.cs体现的是王者荣耀的开发人员编写的源代码中的原本的字段变量顺序，而游戏运行内存中体现的则是C#结构体内部字段变量在编译时被自动重排后的顺序
你可能会为此处C#为什么要进行重排，或者说它为什么要把_handleObj放到_handleSeq前面？
原因很简单，还记得刚才提到过的自动内存对齐吗？
如果_handleSeq放在前面，二者中间就必须塞入4字节的空白填充，而如果_handleSeq放在后面，那么这4字节的空白填充就位于二者后面（_handleSeq后面），而非二者中间
想一想，在各种场景下，综合来看，编译器是按照开发人员编写的源代码中的原本的字段变量顺序进行排序并安放对应4字节空白（此时4字节空白可能位于结构体内存区域的中间）更好一些，还是尽可能将需要塞入4字节空白的字段变量尽可能放到结构体内存区域的后面更好一些？
答案很简单，举个按照开发人员编写的源代码中的原本的字段变量顺序进行排序的例子，如下：
--------------------------------------
+0x00 : [  A (4字节)  ]
+0x04 : [  空白 Padding (4字节)  ]  <-- 强行插在中间的废字节，被浪费掉了！
+0x08 : [        B (8字节指针)        ]  <-- 为了满足8字节对齐，被迫跳过0x04
+0x10 : [  C (4字节)  ]
+0x14 : [  空白 Padding (4字节)  ]  <-- 末尾补齐到8的倍数
--------------------------------------
总大小：24 字节（浪费了 8 字节）
你可以很清楚的看到如果我们尽可能将需要塞入4字节空白的字段变量尽可能放到结构体内存区域的后面，那么实际上我们完全不用填入任何4字节空白，可以直接省掉8KB的内存空间，效果如下：
--------------------------------------
+0x00 : [        B (8字节指针)        ]  <-- 直接从0x00开始，天然8字节对齐
+0x08 : [  A (4字节)  ]                  <-- 紧跟在0x08，天然满足4字节对齐
+0x0C : [  C (4字节)  ]                  <-- 紧跟在0x0C，天然满足4字节对齐
--------------------------------------
总大小：16 字节（0 字节浪费！）

故而C#此处进行了重排，将_handleObj放到了_handleSeq前面

到此，我们已经可以依次取出Il2CppArray后边存放的所有PoolObjHandle实例了
依据刚才分析出的PoolObjHandle实例内部的字段变量结构布局以及我们解析出的各字段变量的大小，我们从各PoolObjHandle实例的首地址进行偏移，就可以得到各存放ActorLinker实例指针的内存地址了，取出该内存地址里存放的ActorLinker实例指针，它就是ActorLinker实例的首地址

因为ActorLinker是非泛型模板，它可以被实例化，故而dump能直接解析出ActorLinker实例内部各字段变量基于ActorLinker的首地址的偏移量（此处不需要我们在手动计算偏移量了）
以ActorLinker实例内部的【public Vector3 position】字段变量为例子，dump解析出的它的基于ActorLinker实例首地址的偏移量为0x4c4（注意：不同游戏版本或运行环境中偏移量不同），那么我们直接用ActorLinker实例首地址加上0x4c4就得出了position字段变量的地址，前往此地址即可取出Actor的position的Vector3结构体（注意：因为Vector3是struct，所以position字段变量存储的不是指向Vector3实例的指针，而是存储的Vector3实例本身），依据前面所学结合dump.cs中显示的Vector3结构体的内部构造，你可以很轻易的分别取出Actor的xyz
按照前面所学，你还可以取出Actor实例中存储的其它内容，并且你还可以尝试找一找其它类型实例（王者是一款大型游戏，其内实例多的数不过来，或许你可以在此教程的基础上进一步探究它？）

-------------------------------------------------------------------------------
local OFFSET_GET_ACTOR   = 0x6F9D47C
local OFFSET_METHOD_INFO = 0xDED2C18

local function readPtr(addr)
    if not addr or addr == 0 then return 0 end
    local res = gg.getValues({{address = addr, flags = gg.TYPE_QWORD}})
    return res[1].value & 0x0000FFFFFFFFFFFF
end

local function readDword(addr)
    if not addr or addr == 0 then return 0 end
    local res = gg.getValues({{address = addr, flags = gg.TYPE_DWORD}})
    return res[1].value & 0xFFFFFFFF
end

local function readInt(addr)
    if not addr or addr == 0 then return 0 end
    local res = gg.getValues({{address = addr, flags = gg.TYPE_DWORD}})
    return res[1].value
end

local function readUInt(addr)
    if not addr or addr == 0 then return 0 end
    local res = gg.getValues({{address = addr, flags = gg.TYPE_DWORD}})
    return res[1].value & 0xFFFFFFFF
end

local function readFloat(addr)
    if not addr or addr == 0 then return 0.0 end
    local res = gg.getValues({{address = addr, flags = gg.TYPE_FLOAT}})
    return res[1].value
end

local function getRealIl2CppBase()
    local allRanges = gg.getRangesList()
    for _, r in ipairs(allRanges) do
        local name = r.internalName or r.name or ""
        if r.state == "Xa" and name:find("libil2cpp%.so") then
            if readDword(r.start + OFFSET_GET_ACTOR) == 0xD10103FF then
                return r.start
            end
        end
    end
    return 0
end

local function verifyOffsets()
    local log = {}
    local function addLog(str) table.insert(log, str) end

    local base = getRealIl2CppBase()
    if base == 0 then
        local err = "未找到有效 Base"
        gg.copyText(err, false)
        gg.alert(err)
        return
    end

    local p1 = readPtr(base + OFFSET_METHOD_INFO)
    local p2 = readPtr(p1 + 0x20)
    local p3 = readPtr(p2 + 0xC0)
    local p4 = readPtr(p3 + 0x10)
    local p5 = readPtr(p4 + 0xB8)
    local actorManager = readPtr(p5 + 0x0)
    local heroActors   = readPtr(actorManager + 0x18)
    local itemBackends = readPtr(heroActors + 0x08)
    local size         = readInt(heroActors + 0x10)

    addLog(string.format("Base:          0x%X", base))
    addLog(string.format("ActorManager:  0x%X", actorManager))
    addLog(string.format("HeroActors:    0x%X", heroActors))
    addLog(string.format("Item_Backends: 0x%X | 英雄总数: %d\n", itemBackends, size))

    local saveList = {}

    for i = 0, size - 1 do
        local elemAddr    = itemBackends + 0x20 + (i * 0x10)
        local actorLinker = readPtr(elemAddr + 0x0)
        local handleSeq   = readUInt(elemAddr + 0x8)

        if actorLinker ~= 0 then
            local objId   = readUInt(actorLinker + 0x4AC)
            local posX    = readFloat(actorLinker + 0x4C4)
            local posY    = readFloat(actorLinker + 0x4C8)
            local posZ    = readFloat(actorLinker + 0x4CC)
            local valComp = readPtr(actorLinker + 0x3B8)

            addLog(string.format(
                "[%d] Linker: 0x%X | Seq: 0x%X | ObjID: %d | Pos: (%.2f, %.2f, %.2f) | ValComp: 0x%X",
                i, actorLinker, handleSeq, objId, posX, posY, posZ, valComp
            ))

            table.insert(saveList, {
                address = actorLinker + 0x4C4,
                flags = gg.TYPE_FLOAT,
                name = string.format("Hero[%d]_X (ID:%d)", i, objId)
            })
        else
            addLog(string.format("[%d] 空指针 (0x0)", i))
        end
    end

    if #saveList > 0 then
        gg.addListItems(saveList)
        addLog("\n验证完成！所有英雄 X 坐标已加入 GG 保存列表（完整结果已复制到剪贴板）。")
    end

    local out = table.concat(log, "\n")
    gg.copyText(out, false)
    gg.alert(out)
end

verifyOffsets()

首先，你认为什么是基址？或者说互联网上的那些教程告诉你的基址是什么？
你可能会说：基址就是整个游戏的基础地址，一个在每次游戏重启后其具体所在的绝对内存地址都会发生变动的地址，所有游戏里的内容（如实例、字段变量等）都基于它来进行加载并与它保持一个固定的偏移量
如果你这么认为，那就大错特错了
首先最明显的错误点就是‘基址是整个游戏的基础地址’，这句话代表整个游戏的所有内容（如实例、字段变量等）共用同一个基址
但这显然是错误的，实际上，基址是‘内容所属模块的模块加载基址’，如前文所有提到的内容（例如class ActorManager等）均隶属于王者荣耀的libil2cpp.so模块，因此前文所有提到的内容（例如class ActorManager等）的基址均是libil2cpp.so模块的模块加载基址

必须注意：模块加载基址指的并不是模块本身起始部分的内容被加载到的位置的内存地址，而是模块内各内容加载进内存时相对的0刻度线
        这里的'模块加载基址'的具体概念不太好用一句话表述清楚，为了方便你理解，这里我举两个例子：
        1.商业游戏在运行时模块本身起始部分的内容（如libil2cpp.so的ELF头）可能被单独扔到A处（如0x7800000000），而它的代码段可能被加载到B处（如0x7100000000），此时模块本身起始部分的内容根本不位于B处（如0x7100000000），但模块里的各种内容（如实例、字段变量等）可能都把B处视作为模块加载基址（也就是0刻度线），并依据B处（如0x7100000000）的绝对内存地址进行计算得到各种内容的绝对内存地址
        2.你可以想象一张图纸，图纸的开头就是0刻度线（模块加载基址），开发者完全可以将模块本身起始部分的内容放在0刻度线后方并且距离0刻度线有一段距离的地方，例如图纸的 0x10000 处(也就是相对于图纸首地址偏移0x10000处)，此时模块本身起始部分的内容被加载到的位置的内存地址是图纸的 0x10000 处(也就是相对于图纸首地址偏移0x10000处)的绝对内存地址，但模块里的各种内容（如实例、字段变量等）都把0刻度线处（也就是相对于图纸首地址偏移0x0处）的绝对内存地址视作为模块加载基址，并依据0刻度线处（也就是相对于图纸首地址偏移0x0处）的绝对内存地址来进行计算得到各种内容的绝对内存地址

这里不得不提一下，互联网上的很多教程将‘基址’和‘由基址通过固定偏移量计算出来的静态全局指针(指向诸如ActorManager全局静态单例之类的全局静态内容的指针，这里需要注意class图纸和struct图纸一样属于全局静态内容)的绝对内存地址’混为一谈，将‘由基址通过固定偏移量计算出来的静态全局指针’视作基址。但这显然是错误的，就像依据高二(1)班的位置能推导出高二(2)班的位置，但你不能将高二(2)班的位置视作为高二(1)班的位置，一个是基址，一个是依据基址推出来的静态全局指针的内存地址，二者完全不是一个东西

既然已经知晓了基址的具体概念，那么我们具体要怎么做才能得到基址呢？
由刚才所讲的内容进行分析，我们不难发现单纯的寻找模块所属区域的首地址是不行的（模块所属区域的首地址和模块本身起始部分的内容被加载到的位置的内存地址和模块加载基址是三个完全不同的概念）
聪明的你结合前面的【必须注意】里的两个例子一定已经想到了正确的寻找模块加载基址的方法了
那就是：先通过特征码定位某一已知相对于基址的偏移量的内容的绝对内存地址，然后用该绝对内存地址减去该内容相对于基址的偏移量就能直接得出模块加载基址
注意:最好选择逆向偏移一次后直接就是基址的内容来进行特征码定位，最好不要选择具备多级偏移链的内容来进行特征码定位，因为多级偏移链中很可能包含指针，而指针具备单向不可溯源性，你无法单纯从逻辑分析上计算出究竟是哪个内存区域里存储了指向‘此处’的指针，因此无法逆推出‘此处’的上一级位置的内存地址
